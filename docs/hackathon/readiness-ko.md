# 해커톤 데모 준비 상태

이 문서는 [AKS Store Demo](https://github.com/Azure-Samples/aks-store-demo)를 사용하는 FDAI
해커톤 데모를 정리합니다. 주문 서비스의 복제본 수가 0개로 줄어들어 상품은 볼 수 있지만
주문은 접수되지 않는 상황입니다. FDAI가 고객 영향을 탐지하고, 범위가 제한된 복구를 제안한
뒤, 사람 승인을 거쳐 결과를 검증하는 흐름을 보여 줍니다.

> **준비 상태:** 선택한 시나리오와 준비 목록이며, 실제 환경에서 완료한 데모가 아닙니다.
> 아래 저장소 근거만으로 배포 또는 전체 복구 흐름이 검증되었다고 볼 수 없습니다.
>
> **범위:** 격리된 Azure Kubernetes Service(AKS) 실습 환경과 합성 주문만 사용합니다. 이
> 문서는 테넌트, 구독, 클러스터 인스턴스 또는 배포 계획을 선택하지 않으며, 배포, 장애 주입,
> 모델 호출 또는 복구 작업을 승인하지 않습니다.

## 시나리오 요약

유지보수가 끝났지만 주문 서비스를 다시 켜지 않은 상황입니다. 검토된 운영 기준은 서비스
시간에 최소 1개가 실행되어야 한다는 것이지만, 복제본 수는 0개로 남아 있습니다. 유지보수
후 복원이 누락되었다는 설명은 보관된 변경 기록이 뒷받침할 때만 사용합니다.

| 항목 | 데모 목표 |
|------|-----------|
| 애플리케이션 | 공개 AKS Store Demo와 합성 상품 및 주문 |
| 정상 기준 | 상품 조회와 주문 접수 성공, `order-service`의 준비된 복제본 1개 |
| 주입할 장애 | `order-service` Deployment의 복제본 수만 1개에서 0개로 변경 |
| 고객 영향 | 상품은 계속 보이지만 주문 접수 실패 |
| 탐지 | 테스트 주문의 반복 실패와 검토된 최소 복제본 수 기준 위반 |
| 복구 제안 | `ops.scale-out`으로 같은 Deployment를 `replica_count: 1`로 복원 |
| 완료 조건 | 독립적인 리소스 관찰과 테스트 주문 접수 성공 |
| 발표 길이 | 3-5분을 목표로 하되, 시간을 주장하기 전에 연습하고 측정 |

이 데모는 주문 접수를 보여 줍니다. 결제, 주문 처리 완료 또는 배송을 검증하지 않습니다.
주문 접수 성공만으로 후속 작업자가 주문 처리를 끝냈다고 볼 수 없습니다.

## 이 장애를 선택한 이유

Kubernetes는 설정된 복제본 수에 맞춰 워크로드를 유지합니다. 따라서 복제본 0개는
Kubernetes 입장에서는 유효한 상태이지만, 사업 운영 기준에는 어긋날 수 있습니다. Pod
상태만 감시해서는 이 시나리오를 탐지하기 어렵습니다.

- **Pod 삭제:** 컨트롤러가 관리하는 Pod를 삭제하면 Kubernetes가 보통 직접 대체합니다.
	이를 FDAI의 복구 근거로 제시하지 않습니다.
- **잘못된 이미지:** 순차 배포가 실패해도 기존 정상 Pod가 계속 요청을 처리할 수 있습니다.
	이미지 다운로드 실패가 반드시 고객에게 보이는 장애로 이어지지는 않습니다.
- **부하 급증:** 리소스 압박과 자동 확장 때문에 진행 시간을 예측하기 어렵습니다. 단일
	서비스 복구가 안정적으로 동작한 뒤 추가할 시나리오로 남깁니다.

## 준비 범위와 제한

상위 저장소 빠른 시작 구성의 `store-front`, `product-service`, `order-service`, RabbitMQ를
최소 애플리케이션 후보로 사용합니다. 연습에 사용할 검토된 매니페스트 리비전과 이미지
다이제스트를 고정합니다. 선택 기능인 AI 서비스와 전체 주문 처리 구성은 첫 데모에서 제외합니다.

- **격리:** 전용 시나리오 실습 클러스터 경계를 따르고 데모 전용 네임스페이스를 사용합니다.
	FDAI 서비스, 공유 워크로드, 노드 또는 시스템 네임스페이스에는 장애를 주입하지 않습니다.
- **노출:** 쇼핑몰 화면만 HTTPS로 노출합니다. API, 관리 화면, RabbitMQ는 비공개로 유지하며,
	외부에 노출되는 서비스에 공개 샘플 자격 증명을 재사용하지 않습니다.
- **운영 의도:** 실행 전에 서비스와 Deployment의 연결, 최소 복제본 수 1개, 적용 서비스
	시간, 유지보수 종료 근거를 기록합니다. 승인된 유지보수가 진행 중이라면 서비스를 임의로
	다시 켜지 않습니다.
- **단일 변경 주체:** Horizontal Pod Autoscaler(HPA)와 Git의 목표 구성을 동기화하는
	GitOps 조정을 검토합니다. 승인된 작업과 같은 복제본 수를 동시에 변경하지 않도록 합니다.
	데모를 위해 안전 통제를 해제하지 않습니다.
- **합성 트래픽:** 테스트 주문은 애플리케이션 상태를 변경합니다. 별도로 승인된 합성 작업자에
	실행 주기, 요청 수 상한, 시간 제한, 정리 계획을 지정합니다. 이 작업자는 클라우드 관리
	신원을 갖지 않습니다. 읽기 전용 브라우저 캡처 권한으로 주문을 접수할 수는 없습니다.
- **탐지 조건:** 관찰 구간, 실패 임계값, 복구 임계값, 근거의 최신성 기준을 연습 전에
	확정합니다. 페이지 가용성이나 HTTP 상태만 보지 말고 실패한 주문 단계를 기록합니다.
	관찰이 없으면 성공으로 간주하지 않고 알 수 없음으로 유지합니다.
- **시간 제한:** 실행 전에 전체 및 단계별 기한을 정합니다. 기한 초과, 권한 부재, 상태
	충돌 또는 예상하지 못한 대상 변경이 발생하면 중지하고, 근거를 남겨 검토를 요청합니다.

## 1. 정상 쇼핑몰 확인

상품을 조회하고 장바구니에 담은 뒤 합성 주문을 접수합니다. 기준 관찰 구간의 주문 접수 성공,
주문 서비스의 준비된 복제본 1개, 요청을 받을 수 있는 서비스 엔드포인트, 정확한 대상 식별
정보를 보관합니다. 고객 또는 주문 본문은 저장소에 보관하지 않습니다.

## 2. 구성 장애 한 개 주입

권한이 있는 운영자가 데모 주문 Deployment의 복제본 수를 1개에서 0개로 변경합니다. 작업자,
시각, 정확한 대상, 이전 값과 변경 값을 근거로 기록합니다. 장애 주입은 FDAI의 진단과 별개이며
복구 권한을 부여하지 않습니다.

쇼핑몰 화면과 상품 서비스는 계속 실행합니다. 상품 조회는 성공하지만 테스트 주문은 실패하는
모습을 보여 줍니다. RabbitMQ 데이터를 손상시키거나 Deployment를 삭제하지 않습니다.

### kubectl 장애 주입 명령

실습 대상과 장애 주입이 승인된 뒤에만 다음 Bash 예제를 실행합니다. 이미 인증된 `kubectl`
context를 사용하고 두 자리 표시자를 바꾼 뒤, 이어지는 명령도 같은 터미널에서 실행합니다.
모든 API 요청은 대상을 명시하고 10초 제한을 사용합니다. 전역 현재 context는 변경하지 않습니다.

```bash
DEMO_CONTEXT='<approved-demo-context>'
DEMO_NAMESPACE='<approved-demo-namespace>'
demo_kubectl=(kubectl --context="$DEMO_CONTEXT" --namespace="$DEMO_NAMESPACE" --request-timeout=10s)
"${demo_kubectl[@]}" get deployment store-front product-service order-service
"${demo_kubectl[@]}" get hpa
"${demo_kubectl[@]}" get deployment order-service -o jsonpath='{.metadata.uid}{"\n"}'
```

승인된 클러스터와 네임스페이스를 확인하고 Deployment UID를 보관하며, 각 데모 Deployment에
예상한 수의 준비된 복제본이 있는지 확인합니다. `order-service`의 설정된 복제본과 준비된
복제본이 각각 1개이고, 정상 기준 주문이 성공하며, 같은 값을 변경하는 HPA나 GitOps가 없을
때만 진행합니다. 하나라도 확인에 실패하면 중지합니다. context 이름이나 비어 있는 HPA
목록만으로 격리된 환경이라고 판단하지 않습니다.

먼저 변경을 저장하지 않는 모의 실행으로 검증합니다.

```bash
"${demo_kubectl[@]}" scale deployment/order-service \
	--current-replicas=1 --replicas=0 --dry-run=server --timeout=10s
```

모의 실행이 성공하고 현재 권한이 유지되는 것을 확인한 뒤 장애를 주입합니다.

```bash
"${demo_kubectl[@]}" scale deployment/order-service \
	--current-replicas=1 --replicas=0 --timeout=10s
"${demo_kubectl[@]}" get deployment order-service
"${demo_kubectl[@]}" get pods -l app=order-service
"${demo_kubectl[@]}" get endpointslices -l kubernetes.io/service-name=order-service
```

`--current-replicas=1` 사전조건은 설정된 복제본 수가 예상과 다르면 변경을 차단하지만, 대상
잠금을 대신하지는 않습니다. 오류나 대상 변경이 발생하면 사전조건을 제거하지 말고 중지합니다.
Pod 종료와 엔드포인트 제거는 비동기로 진행됩니다. 요청을 받을 수 있는 준비된 엔드포인트가
없고 테스트 주문이 실패하는지 확인한 뒤 장애로 설명합니다. 실제 변경 시각은 승인된 감사
경로로 기록합니다. 이 터미널 명령만으로 FDAI 인시던트가 생성되지는 않습니다.

### 데모 중단 시 수동 복원

정상 진행에서는 FDAI의 승인된 복구 흐름에 복원을 맡깁니다. 다음 명령은 해당 흐름이 중지되고
대상 잠금이 해제된 뒤, 별도의 현재 수동 복원 권한이 있을 때만 사용합니다. 대상 UID가
보관한 정상 기준과 일치하고 현재 복제본 수가 0개인지 다시 확인합니다. 모의 실행이 성공한
경우에만 실제 변경을 실행합니다.

```bash
"${demo_kubectl[@]}" get deployment order-service -o jsonpath='{.metadata.uid}{"\n"}'
"${demo_kubectl[@]}" scale deployment/order-service \
	--current-replicas=0 --replicas=1 --dry-run=server --timeout=10s &&
"${demo_kubectl[@]}" scale deployment/order-service \
	--current-replicas=0 --replicas=1 --timeout=10s
"${demo_kubectl[@]}" get deployment store-front product-service order-service
```

이후 준비 상태, 서비스 엔드포인트, 상품 조회 및 새 테스트 주문의 접수 성공을 검증합니다.
FDAI 복구가 아니라 운영자의 복구로 기록합니다. 복제본 수가 이미 1개라면 다시 확장하지 말고
결과를 확인합니다. 확인에 실패하거나 결과가 불완전하면 인시던트를 해결되지 않은 상태로 유지합니다.

## 3. FDAI가 고객 영향 발견

운영자의 질문으로 진단을 시작하지 않고 합성 작업자가 계속 관찰합니다. FDAI는 주문 실패
관찰을 현재 Deployment 및 서비스 엔드포인트 상태와 함께 확인하고, 검토된 운영 기준과
비교해야 합니다.

| 대시보드 항목 | 근거에 기반해 보여 줄 내용 |
|---------------|---------------------------|
| 제목 | 상품은 보이지만 주문을 접수할 수 없음 |
| 영향받는 서비스 | 주문 접수 |
| 리소스 상태 | `order-service`: 설정된 복제본 0개, 준비된 복제본 0개 |
| 운영 기준 | 적용 서비스 시간에 최소 1개 실행 |
| 영향 | 테스트 주문 접수 실패, 상품 조회는 계속 성공 |
| 최근 변경 | 수집된 경우 정확한 복제본 수 변경 기록 |
| 최신성 | 실제 관찰 시각과 출처 참조 |
| 다음 단계 | 같은 인시던트를 열거나 이유 질문 |

반복 가능한 이 조건은 결정적 규칙으로 판단합니다. 유지보수 기록이 없으면 설명을 만들어
내지 말고 누락된 근거로 표시합니다. 대시보드, 인시던트, 승인, 실행, 감사 기록은 실제 실행의
상관관계 식별자로 연결합니다.

## 4. 주문 실패 이유 질문

운영자가 질문합니다.

> 상품은 보이는데 왜 주문이 안 되나요?

필요한 관찰이 갖춰진 경우 다음처럼 설명합니다.

> 상품 조회는 성공하지만 테스트 주문은 실패하고 있습니다. 주문 서비스의 복제본 수가 0개로
> 설정되어 있고 요청을 받을 수 있는 엔드포인트가 없습니다. 검토된 운영 기준은 최소 1개
> 실행입니다. 변경 기록에는 복제본 수가 1개에서 0개로 줄어든 사실이 남아 있습니다. 현재
> 승인과 안전성 검토를 거쳐 복제본 1개를 복원하는 작업을 제안합니다.

대상, 시각, 의존성 경로, 근거 출처를 함께 표시합니다. 유지보수는 근거가 있을 때만 관련
변경으로 설명하며, 발생 시점이 가깝다는 사실만으로 근본 원인을 확정하지 않습니다.

## 5. 범위가 제한된 복구 검토

승인에는 `ops.scale-out`, 정확한 Deployment 식별 정보와 관찰된 버전, 현재 복제본 수 0개,
요청 복제본 수 1개를 표시합니다. 요청자와 다른 사람이 승인하고 실행기 신원도 분리합니다.
새 기능은 관찰 모드에서 시작하며, 실행을 활성화하기 전에 공식 승격 절차를 거칩니다.

실제 작업 전에 기존의 일곱 가지 안전장치를 모두 확인합니다.

| 안전장치 | 데모 요구 사항 |
|----------|----------------|
| 중지 조건 | 오래된 근거, 대상이나 구성 변경, 권한 상실 또는 기한 초과 시 중지 |
| 검증된 롤백 | 현재 복구 권한에 따라 작업 전 복제본 수로 되돌리는 절차를 보관하고 시험 |
| 영향 범위 | 데모 네임스페이스의 정확한 Deployment 한 개만 변경 |
| 성공한 모의 실행 | 실행 전에 서버에서 제안된 확장 작업 검증 |
| 논리 대상 잠금 | 같은 대상에 대한 동시 변경 차단 |
| 안정적인 멱등성 키 | 중복 전달이 반복 변경으로 이어지지 않도록 방지 |
| 두 단계 감사 | 효과 발생 전에 의도를 기록하고 최종 결과 보관 |

작업 전 값인 0개로 되돌리면 복구 시도는 취소되지만 주문 접수는 여전히 불가능합니다. 이
롤백을 서비스 복구로 표시하지 않습니다. 인시던트를 열린 상태로 유지하고, 별도의 현재
권한을 갖춘 검토된 복구 또는 수동 복원 절차를 따릅니다. 다음 연습을 위한 초기화는 별도
작업입니다.

## 6. 고객에게 보이는 복구 결과 검증

활동 화면에서 다음 단계를 구분합니다.

1. FDAI가 주문 접수 실패를 탐지하고 Deployment 한 개의 복구를 제안했습니다.
2. 다른 사람이 현재 제안을 승인했습니다.
3. Kubernetes API가 확장 요청을 접수했습니다.
4. 독립 관찰자가 작업 이후 같은 대상의 목표 복제본 수, 준비된 복제본 1개, 요청을 받을 수
	 있는 엔드포인트를 확인했습니다.
5. 독립적인 합성 관찰로 미리 정한 복구 구간 동안 주문 접수 성공과 상품 조회의 정상 상태를
	 확인했습니다.
6. FDAI가 예상 효과를 검증 완료로 표시하고 연결된 감사 근거를 보관했습니다.

API 성공, 실행 중인 Pod 또는 장애 주입자의 성공 메시지만으로 서비스가 복구되었다고 보지
않습니다. HTTP 200뿐 아니라 예상한 주문 확인 결과를 검사합니다. 검증이 실패하거나 근거가
오래되거나 불완전하면 인시던트를 해결되지 않은 상태로 유지합니다.

## 7. 검토 대기 사례 확인

별도 연습 또는 Sample임을 명확히 표시한 사례에서 오래된 Kubernetes 관찰, 서로 충돌하는
운영 기준 또는 사용할 수 없는 테스트 주문 작업자를 보여 줍니다. FDAI는 어떤 근거가
부족한지 설명하고 대상을 변경하지 않은 채 작업을 검토 대기로 유지해야 합니다.

이 사례를 완료된 실행과 섞거나 Sample 데이터를 실제 관찰로 제시하지 않습니다.

## 현재 준비 상태와 남은 작업

2026-09-17 저장소 검토에서 확인한 출발점은 다음과 같습니다. 현재 환경이나 실제 실행의
완료를 보증하는 내용은 아닙니다.

| 영역 | 기존 근거 | 촬영 전에 필요한 작업 |
|------|-----------|-----------------------|
| 애플리케이션 | 상위 AKS Store Demo 빠른 시작 구성 | 승인된 격리 배포, 고정된 입력, 정상 기준 주문 성공 |
| 상거래 근거 | 기존 상거래 확장과 더 넓은 사업 시나리오 설계 | 빠른 시작 구성의 RabbitMQ 및 주문 접수 연결 확인. 기존 설계는 Azure Service Bus와 주문 처리 완료 근거를 요구함 |
| 자동 탐지 | 결정적 평가 설계 | 운영 의도에 어긋나는 복제본 0개 상태와 주문 실패를 수동 질문 없이 탐지하는 경로 검증 |
| Kubernetes 확장 | 런타임 지원 목록에 조건부 Core 연결과 집중 테스트 근거 등록 | 실습 환경에서 선택한 런타임 연결, 권한, 승격, 안전장치 및 독립 관찰 검증 |
| Console 흐름 | 기존 인시던트, 승인 및 활동 화면 | 실제 AKS 기록, 하나의 실행 식별자, 근거 링크, 전체 흐름의 다국어 설명 확인 |
| 서비스 복구 | 리소스와 서비스 효과 검증 설계 | 범위가 제한된 작업자가 실행기와 독립적으로 주문 접수를 검증하는지 확인 |
| 기존 VM Sample | `/live?data=sample`의 이전 VM 시작 설명 흐름 | 별도 대체 자료로 명확히 표시하고 AKS 근거로 사용하지 않음 |

빠른 시작 구성은 기존 주문 처리 설계보다 범위가 좁은 후보입니다. 런타임을 변경하기 전에
담당 설계 문서에서 범위와 필수 근거를 조정합니다. 데모에 맞추려고 누락된 큐 또는 주문 처리
완료 근거를 정상으로 간주하거나, 검증되지 않은 탐지기가 이미 동작한다고 설명하지 않습니다.

## 작업 순서

1. 주문 접수 범위를 확정하고 담당 상거래 설계와 일치시킵니다.
2. 기존 배포 절차에 따라 배포 대상, 신원 경계, 정확한 계획, 합성 트래픽 권한을 검토합니다.
	 이 문서는 배포 승인이 아닙니다.
3. 정상 기준과 검토된 운영 기준을 마련합니다.
4. 현재 Kubernetes, 합성 주문 및 변경 관찰을 결정적 탐지에 연결합니다.
5. 실제 복구를 승인하기 전에 관찰 모드에서 제안과 모든 안전장치를 검증합니다.
6. 같은 인시던트를 대시보드, 대화, 승인, 활동 및 감사 화면에 연결합니다.
7. 실제 전체 흐름과 별도 검토 대기 사례를 연습하고 실제 소요 시간과 부족한 항목을 기록합니다.
8. 촬영 전에 영어, 한국어, 키보드 조작 및 1440x900, 993x641, 390x844 화면을 확인합니다.

## 촬영 전 확인 목록

- [ ] 상품 조회와 정상 기준 합성 주문 접수가 성공합니다.
- [ ] 승인된 장애 주입은 데모 주문 서비스의 복제본 수만 1개에서 0개로 변경합니다.
- [ ] 상품은 계속 보이고 테스트 주문 접수는 실패합니다.
- [ ] 운영자가 질문하기 전에 FDAI가 문제를 탐지합니다.
- [ ] 설명에서 Kubernetes의 목표 상태와 검토된 운영 기준을 구분합니다.
- [ ] 주장하는 변경과 원인마다 현재 근거가 있고, 누락된 기록은 명시합니다.
- [ ] 다른 사람이 정확한 복구를 승인하며 일곱 가지 안전장치를 모두 충족합니다.
- [ ] API 요청 접수와 독립적인 리소스 및 주문 접수 검증이 별도 단계로 보입니다.
- [ ] 불확실한 사례는 검토를 기다리며 복구 실패에 대비한 검증된 복구 절차가 있습니다.
- [ ] 실제 관찰, 합성 트래픽 및 Sample 대체 데이터를 명확히 구분합니다.
- [ ] 비공개 신원, 리소스 ID, 자격 증명, 본문 데이터 또는 인프라 엔드포인트를 노출하지 않습니다.
- [ ] 이 실행으로 결제, 주문 처리 완료, 매출 또는 정식 성과 개선을 추론하지 않습니다.
