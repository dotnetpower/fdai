# 이전 형식의 Pantheon 감사 체크포인트 복구

업그레이드 후 Saga에서 `AuditChainError`가 반복되고 저장된 체크포인트가 아직 `1.0.0`
스키마를 사용한다면 이 절차로 복구하세요. 기존 이력을 검증하며, 레코드 삭제, 체인 초기화,
조치 재실행, 실행 권한 변경은 하지 않습니다.

> **범위:** 이 절차는 명시적인 검토를 거쳐 데이터베이스를 복구합니다. 선택한 실행 위치에
> 맞는 Core 서비스 소유 데이터베이스 환경을 사용하세요. Azure 데이터베이스 연결을 로컬
> 런타임에 복사하거나 명령줄에 연결 문자열을 넣지 마세요.

## 이 문서에서 다루는 내용

일반적인 시작 절차는 전체 감사 이력이 512행 이하일 때만 이전 형식을 변환합니다.
이력이 더 많으면 빈 체인으로 간주하지 않고 검토를 위해 보류합니다. 명시적 복구 명령은
Saga 레코드 최대 50,000건과 원본 JSON 64 MiB를 지원하며, 전체 제한 시간은 30초입니다.

## 원인 확인

1. Core 프로세스, 실제 브로커 처리 진행 상태, 로컬 서비스 소유 데이터베이스를 확인하세요.
2. 실패한 에이전트, 토픽, 예외 유형을 처리 실패 큐(DLQ)의 메타데이터에서 확인하세요.
   포트가 열려 있거나 소비자가 실행 중이라는 사실만으로 Saga가 이벤트를 처리한다고
   판단할 수는 없습니다.
   일반 텍스트 형식의 로컬 로그에는 핸들러의 안전한 `agent`, `error_type`, `failure_code`
   토큰을 남기며, 원문 예외 메시지, 소비자 식별 정보, 페이로드는 제외합니다.
3. `pantheon/saga/audit-chain/verified-head`가 `1.0.0` 스키마를 사용하는지 확인하세요.
4. 활동 부족과 발견 사항 부족을 구분하세요. 관측 활동, 소스 시간 초과, 근거 검증 보류,
   평가했으나 발견 사항이 없는 대상은 서로 다른 결과입니다. 화면을 바쁘게 보이게 하려고
   가짜 Incident를 만들거나 에이전트 활동을 늘리지 마세요.

## 복구 검토 및 적용

이전 버전의 Saga 쓰기 프로세스를 모두 중지한 후 변환을 적용하세요. 현재 버전처럼 리비전을
검사하는 쓰기 프로세스는 계속 실행해도 됩니다. 복구 명령은 평소와 같은 순서로 체크포인트
행과 공통 감사 추가 잠금을 획득합니다. 감사 레코드 추가와 헤드 갱신을 별도 트랜잭션으로
처리하는 이전 버전의 쓰기 프로세스는 실행 상태로 두면 안전하지 않습니다.

선택한 Core 환경이 이미 설정된 상태에서 다음 명령을 실행하세요.

```bash
uv run python scripts/automation/migrate-pantheon-audit-chain.py
```

기본 동작은 사전 검증입니다. `source_count`, `detached_count`, `length`, `retained_count`와
반환된 다이제스트를 검토하세요. 기존 체크포인트가 체인을 선택합니다. 명령은 유일하게
이어지는 후속 레코드를 따라가 오래된 체크포인트 이후에 추가된 기록도 보존합니다.
모든 원본 항목, 페이로드 다이제스트, 선행 연결을 검증합니다. 선행 항목 누락, 레코드 손상,
선택한 체인의 분기가 있으면 복구를 차단합니다.

독립된 시작점에서 만들어진 다른 이력도 추가 전용 감사 원장에 그대로 남습니다. 검토에서
이런 이력이 확인되면 보존을 명시적으로 확인하세요. 다음 명령의 값을 검토한 `plan_digest`로
바꿔 실행하세요.

```bash
uv run python scripts/automation/migrate-pantheon-audit-chain.py \
  --apply-plan <plan-digest> \
  --legacy-writers-quiesced \
  --preserve-detached-histories
```

분리된 이력이 없으면 마지막 플래그는 필요하지 않습니다. 체크포인트나 Saga 이력이 바뀌면
계획이 무효화됩니다. 이 검사를 우회하지 말고 사전 검증을 다시 실행해 새 결과를 검토하세요.
체크포인트와 `audit.chain.migrated` 증적은 하나의 트랜잭션으로 저장됩니다. 실패하면 둘 다
롤백됩니다. 기존 감사 레코드는 수정하거나 삭제하지 않습니다.

## 효과 검증

실행 중인 리비전 검사 어댑터는 다음 Saga 이벤트에서 새 체크포인트를 읽습니다. 독립적인
데이터베이스 조회로 새 `audit.record`, `2.0.0` 스키마, 증가하는 원장 리비전을 확인하세요.
새 Saga 핸들러 실패와 DLQ 추가가 멈췄는지도 확인하세요. 복구 명령의 성공만으로 런타임에서
이 효과가 발생했다고 판단할 수는 없습니다.

체크포인트 원장은 검증된 항목을 최대 512건 보관하며, 전체 이력은 감사 로그에 남습니다.
과거 DLQ 항목은 별도 검토를 거쳐 재처리할 수 있도록 유지합니다. 복구는 승인, 실행 요청,
그 밖에 권한을 수반하는 메시지를 재처리하지 않습니다.

Incident 생성 조건은 별도로 점검하세요. 자동 생성에는 여전히 상관관계가 확인된 충분한
근거와 설정된 심각도 기준이 필요합니다. 발견 사항이 없으면 새 Incident가 없는 것이 정상일
수 있습니다. 브라우저 검증에서도 Entra 로그인 요구 사항은 유지합니다.

## 원본 입력 충돌이 남아 있는 경우

Saga 체크포인트를 복구해도 활동이 적다면 원본 입력의 DLQ도 확인하세요. 이전 형식의
Huginn 대기 요청은 생산자가 재시도하면서 묶음의 `ingested_at` 수신 시각만 바꿔도 충돌로
판단할 수 있습니다. 새 요청의 식별값에서는 덮어쓰는 최상위 시각만 제외하며, 공급자의
이벤트 시각, 중첩된 타임스탬프, 내용, 권한 필드는 그대로 검사합니다. 원본 요청이 정확히
일치한 경우에만 감사 기록과 리비전 검사를 거쳐 이전 식별값을 갱신합니다.

이전 대기 요청을 검토 후 재처리하려면 원본 소스 메시지를 보존하고 전체 이전 요청
다이제스트가 일치하는지 먼저 검증하세요. 인벤토리 전용 복구는 원본 바이트와 관측 시각,
`incident_correlation: none`, 관찰 모드를 유지합니다. 게시 성공만으로 Huginn이 처리를
마쳤다고 판단하지 말고, 저장된 요청 상태와 새 Saga 기록을 독립적으로 확인하세요.
다이제스트 초기화, 대기 요청의 게시 완료 강제 처리, 새 관측을 이용한 사라진 원본 재구성은
하지 않습니다. 원본이 없는 요청은 별도로 승인된 복구를 위해 계속 보류합니다.

이미 검증해 저장한 인벤토리 전달 대기 요청은 별도의 복구 소스입니다. 표준 Huginn
유지보수는 만료된 임대 권한을 다시 확보하고 원래 변환 결과를 적용한 뒤, 저장된 Event와
Change를 타입 이벤트로 게시한 후에 완료를 기록합니다. 한 번에 최대 8건의 인벤토리 요청을
처리하며, 다이제스트, 원본 시각, 게시 표식을 보존합니다. 원본 입력을 재구성하거나 운영자,
승인, 실행 요청을 재처리하지 않습니다. 전달 대기 요청의 완료와 후속 Saga 기록을 각각
독립적으로 확인하세요.
