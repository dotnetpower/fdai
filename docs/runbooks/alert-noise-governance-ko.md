# 알림 과다 수신 관리 런북

이 런북은 알림 품질 평가를 해석하고 비활성 제안을 준비하며, 이후 통제된 변경에 필요한
근거를 검토할 때 사용합니다. 구현은 shadow 우선이며 운영 도입에는 아직 충족해야 할 조건이
있습니다. 이 절차는 공급자 알림 테스트, Azure 변경, PR 게시, 기능 승격 또는 배포를 승인하지 않습니다.

> **완료가 아닌 기준점:** 집중 구현, 커버리지, 하드닝 및 로컬 검증 결과와 남은 소스·운영·CI
> 작업은 [구현 원장](../roadmap-implementation/operations/alert-noise-governance.md)에만 기록합니다.

## 이 런북에서 다루는 내용

등록된 네 작업은 모두 `pr_manual`, 기본 `shadow` 모드, `pr_revert` 복구를 사용합니다.
각 작업은 정확한 정방향 계획의 64자리 소문자 16진수 `plan_digest`만 받습니다.
대상, 필드, 원래 개정 번호 및 복구 기준선은 호출자가 아니라 계획에서 가져옵니다.

| ActionType | 현재 지원하는 조정 | 필요한 경계 |
|------------|--------------------|-------------|
| `ops.update-alert-routing` | 보호 대상이 아닌 메트릭 또는 예약 쿼리 규칙 하나의 관측된 Action Group 연결 교체 | 기존 그룹과 정확한 Terraform JSON 작업 목록만 사용하며 수신자 재작성이나 새 그룹 생성은 없음 |
| `ops.set-alert-notification-window` | 정확한 규칙 하나를 대상으로 기존 비활성 억제 규칙에 유한한 UTC 구간 설정 | 완전한 유효 라우팅, 영향받지 않는 독립 수집, 반영 지연 예산 및 절대 만료 시점 |
| `ops.tune-alert-evaluation` | 단순 메트릭 조건 하나의 임계값 변경 | 독립적으로 수락된 동일 측정 구간 비교가 필요하며 평가 구간/빈도 변경은 보류하고 미구현 상태로 유지 |
| `ops.restore-alert-configuration` | 같은 정방향 계획의 고정 기준선 복원 | 현재 저장소 바이트가 보존된 정방향 결과와 같고 별도로 유효한 복구 권한이 있어야 함 |

## 선행 조건

- **범위와 근거:** 서버가 구성한 허용 범위 하나를 사용합니다. 범위가 제한된 Azure 조회기만으로는
  디렉터리, 현재 담당 체계/인시던트, 전체 역방향 의존성, 과거 개정 번호 및 전달 근거를
  입증할 수 없으므로 부분 상태로 유지됩니다. 독립적으로 수락된 보강 기록은 정확한 Azure
  원본과 일치해야 합니다. 오래되거나 실패한 조회를 원장만 읽은 답변으로 대체하지 않습니다.
- **보호 경로:** Sev0/Sev1, 보안, 서비스 상태, 복구, 텔레메트리 손실, 필수 승인, 정책이 보호하는
  SLO 경보 및 미확인 분류를 보존합니다. 관련 활성 인시던트, 자동화가 섞인 경로, 백업 부재
  또는 알 수 없는 의존성이 있으면 변경을 보류합니다.
- **기존 IaC:** 기존 Terraform JSON 파일과 리소스 선택자를 연결합니다. 관측된 Action Group만
  사용할 수 있습니다. 그룹이나 처리 규칙 준비는 별도로 승인된 IaC 작업입니다. 직접 Azure
  대체 경로, 인라인 리소스 생성, 동시 변경된 전체 객체 덮어쓰기는 지원하지 않습니다.
- **기존 컨트롤 플레인:** 정본 Workflow/Process 런타임, Var 승인 공급자, 승격 레지스트리,
  안전장치 조정기, 감사, GitOps 게시기 및 독립 근거 수락 경로를 사용합니다. 팩터리나 신원
  매핑으로 승인, 작성자 배제 또는 효과 증적이 생기지 않습니다.

### 런타임 구성

배포 담당자는 기존 구성과 비밀 참조를 통해 다음 비공개 연결 정보를 제공합니다. 아래 이름은
키이며 채워 넣은 테넌트 값이 아닙니다. 식별자, 엔드포인트, 자격 증명, DSN, 공급자 수신자 정보
또는 증적 본문을 저장소 예제나 채팅에 넣지 않습니다.

| 설정 | 실제 계약과 선행 조건 |
|------|-----------------------|
| `FDAI_ALERT_NOISE_SCOPE_BINDINGS_JSON` | Core: `subscription_id`, `resource_group`, `tenant_ref`, `scope_ref`가 있는 정확한 행 1-64개입니다. principal 범위와 함께 제공하며 범위 추정이나 와일드카드를 허용하지 않습니다. |
| `FDAI_ALERT_NOISE_PRINCIPAL_SCOPES_JSON` | Core와 Operator: 현재 주체를 불투명 범위에 연결하는 비공개 매핑입니다. 주체는 최대 1000개, 주체별 정확한 범위는 최대 64개입니다. 빈 권한은 접근을 허용하지 않으며 매핑으로 역할을 부여하지 않습니다. |
| `FDAI_SOURCE_REVISION` | 0이 아닌 정확한 Git 커밋 신원입니다. 없으면 알림 Workflow/작성자 연결을 사용할 수 없으며 출처를 만들어 내지 않습니다. |
| `FDAI_ALERT_NOISE_TRANSPORT_KEY` | 최소 32바이트의 기존 비밀 주입이며 인증된 요청/결과 경계에서만 공유합니다. Operator에는 영속 저장소, 이벤트 전송 및 이벤트 토픽도 필요합니다. |
| `FDAI_ALERT_NOISE_PSEUDONYM_KEY` | 목적별 불투명 근거 참조를 위한 Core 비밀 주입이며 32-256바이트입니다. 실제 HTTP 조회기와 읽기 신원도 필요합니다. |
| `FDAI_ALERT_NOISE_WRITER_BINDINGS_JSON` | 선택적 정확한 행에 `scope_ref`, `executor_ref`, `repository_ref`, `repository_revision`, `verification_trust_anchor_id`, `principal_refs`를 넣습니다. 기존 신원과 원본을 고정하며 권한을 부여하지 않습니다. |
| `FDAI_ALERT_NOISE_IAC_BINDINGS_JSON` | 선택적 정확한 행 1-64개에 `path`, `source_digest`, `resource_type`, `resource_name`, `field`, `group_ids`, `target_ref`를 넣습니다. 경로는 기존 Terraform JSON 파일을 가리킵니다. 원본 바이트는 다이제스트와 일치해야 하며 이미 구성된 GitOps 어댑터로 읽습니다. |
| `FDAI_ALERT_NOISE_EFFECT_BINDINGS_JSON` | 선택적 정확한 행 1-64개에 `tenant_ref`, `scope_ref`, `source_ref`, `observer_ref`, `executor_ref`, `identities`, `authority_class`를 넣습니다. 참조 별칭 세 개는 대소문자 차이만으로 같아지지 않는 서로 다른 정본 신원 세 개에 연결합니다. |
| `FDAI_STATE_STORE_DSN`, `FDAI_RESOURCE_LOCK_DSN` | 명시적 효과 연결에는 기존 서비스 소유 PostgreSQL 대상이 필요합니다. 선택적 잠금 DSN은 상태 DSN과 같아야 합니다. 올바른 실행 장소의 기존 구성을 사용하며 다른 서비스나 실행 장소의 데이터베이스를 사용하지 않습니다. |

선택적 연결 정보가 없으면 해당 경로를 사용할 수 없습니다. 명시한 정보가 잘못되거나 불완전하면
실패하며 검증 자료, 무조건 허용하는 검증기, 기록 전용 게시기 또는 새 공급자를 대신 설치하지
않습니다. 효과 팩터리는 연결을 지연하는 기존 PostgreSQL 전달, 종결, 잠금 어댑터를 재사용합니다.
객체 구성만으로 데이터베이스 연결이나 재시작을 테스트한 것이 아닙니다. 기존 실제 GitOps 게시기와
운영 적격 증명 기반 잠금은 작성자 통제의 선행 조건이며 다른 작성자 배제의 근거는 아닙니다.

정본 수락 출처 조회기에는 실제로 독립 생성된 범위, 평가, 권한, 작성자 배제, 효과 및 복구
기록이 필요합니다. 목적, 범위, 출처 개정 번호, 최신성 및 검증기 분리를 정확히 확인합니다.
기존 Process가 진행하려면 효과 관측 외에 별도의 Workflow 결과 수락도 필요합니다. 팩터리는
이 기록을 생성하거나 알림 테스트를 실행하거나 공급자 관측자를 만들거나 기능을 승격하지 않습니다.

### Settings와 요청 API

모든 경로는 현재 신원과 정확한 범위를 다시 검증하며 응답에 `Cache-Control: no-store`를 사용합니다.

| 요청 | 의미 |
|------|------|
| `GET /alert-quality/scopes` | 로그인한 주체에게 구성된 불투명 범위만 조회하며 쿼리 인자를 받지 않습니다. |
| `GET /alert-quality?scope_ref=<scope-ref>` | 보존된 근거와 현재 요청 가능 여부를 읽습니다. 평가가 없다는 것은 알림 과다가 없다는 증명이 아닙니다. |
| `POST /alert-quality/assess` | 사람 Contributor, Approver 또는 Owner가 `Idempotency-Key` 하나로 제한적 평가를 요청합니다. `202`는 영속 접수만 입증합니다. |
| `POST /alert-quality/proposals` | 같은 사람 역할 기준을 적용하며 정확한 `scope_ref`, 현재 `evidence_digest`, 타입 지정 `treatment` 하나와 `Idempotency-Key` 하나를 제출합니다. 승인이나 실행 필드는 받지 않습니다. |
| `GET /alert-quality/settings?scope_ref=<scope-ref>` | 선행 조건, 선호 상태/개정 번호, `mode: shadow`, `execution_authority: false`를 읽습니다. |
| `PUT /alert-quality/settings` | 해당 범위의 사람 Owner가 개정 번호 선행 조건 하나로 `scope_ref`와 `enabled`만 갱신합니다. 작업 승인이나 승격이 아닙니다. |

PUT은 본문의 정수 `expected_revision` 또는 강한 ETag/일반 숫자 형식의 `If-Match` 하나를 받으며
둘을 함께 받지 않습니다. 개정 번호는 0 이상 `9007199254740991` 미만입니다. 선행 조건 누락은
`428`, 잘못되거나 모호한 입력은 `400`, 오래된 개정 번호는 `409`, 인증/권한 오류는 `401`/`403`을
반환합니다. 저장에 성공하면 보존된 다음 개정 번호와 따옴표로 감싼 개정 번호 ETag를 반환합니다.
충돌 시 명시적으로 새로 고치고 다시 선택합니다. 결과를 모르는 상태에서 덮어쓰거나 재시도하지 않습니다.

읽을 수 있는 선호 저장소가 연결되면 미저장 기본값은 개정 번호 0의 활성 상태이며 시각을 만들어
내지 않습니다. 저장소가 없거나 실패하면 사용 불가로 명시합니다. Operator 구성은 기존
의존성 팩터리에 `StateKvAlertQualityPreferenceStore`를 전달합니다. 로컬 PostgreSQL 검사는
개정 번호 기반 쓰기 경합과 새 연결에서의 재생을 입증하며 배포 적격성을 입증하지는 않습니다.
연결된 선호 설정이 꺼졌거나
읽을 수 없으면 새 요청만 막으며 이미 접수한 작업이나 별도로 승인된 복구는 취소하지 않습니다.

## 절차

1. **요청 전에 읽습니다.** **운영 > 알림 품질**에서 Live 모드와 조회된 허용 범위를 사용합니다.
   관측 구간, 기준 시점, 만료, 수집 범위, 알 수 없는 항목 및 출처 참조를 확인합니다. 원본
   경보 묶음, 시도, 전달 및 수신 확인은 서로 다른 측정값입니다.
2. **평가 하나를 요청합니다.** 인증된 출처, 요청 작성자, 생산자 준비 상태 및 선호 설정 검사가
   허용할 때만 타입 지정 평가 요청을 사용합니다. 상관관계 참조를 보존합니다. 결과를 모르면
   다시 제출하기 전에 보존된 요청을 대조합니다.
3. **비활성 조정안 하나를 준비합니다.** 최신의 완전한 근거와 라우팅, 유한한 구간 또는 지원되는
   임계값 변경 하나를 사용합니다. 불변 계획과 정확한 원본/정방향/복구 산출물을 보존합니다.
   양식에서 표현할 수 있더라도 지원되지 않는 평가 구간/빈도 변경은 계속 보류합니다.
4. **향후 적용 선행 조건을 검토합니다.** Var를 통해 모든 영향 서비스 담당자의 현재 결정과
   별도 Owner 수준 변경 권한자의 결정을 받습니다. 요청자와 실행자는 승인할 수 없습니다.
   고정값에는 계획, 의존성, 정책, 작업 흐름, 만료 및 복구가 포함됩니다. 카탈로그 등록과
   일반 Workflow 승인 단계만으로 이 증적이 입증되지는 않습니다.
5. **shadow 경계를 유지합니다.** shadow Process는 재생 시 원래 모드를 유지합니다. 이후 별도
   승인과 승격이 이루어진 시도만 7대 안전장치, 실제 원본 작성자 배제 및 최종 최신 근거 검사를
   통과한 뒤 기존 수동 PR 게시 경로를 사용할 수 있습니다. 이 런북은 해당 게시를 요청하지 않습니다.
   작성자 배제 없는 읽기 후 쓰기 검사로 이 경계를 충족할 수 없습니다.
6. **독립 근거로 종결합니다.** 보존된 게시나 병합은 Azure 효과가 아닙니다. Heimdall/Forseti
   중계는 정확한 전달/번들/Process 계보와 독립 수락 기록을 사용합니다. 관측이 없거나 결과가
   악화되면 보류를 유지하고 기존 복구/자동화 보류 경로로 연결합니다.

## 검증

실행기와 독립적으로 구성 재조회, 지속되는 원본 수집, 실제 전달 동작, 보호 대상 대응 기한
유지 및 선언된 전체 관측 구간을 확인합니다. 유한한 억제에는 활성화와 만료 후 근거가 모두
필요합니다. 적격 이벤트가 없으면 성공이 아니라 평가 불가입니다. 더 좋은 표본을 얻으려고
구간을 연장하지 않습니다.

로컬 처리 구조와 실제 PostgreSQL 동시성/재시작, 인증된 한영 브라우저 동작, 공급자 일치성,
정확한 최종 리비전의 CI를 구분합니다. 운영 도입을 보고하기 전에 각 필수 근거를 보존합니다.
이 기준점은 해당 운영 적격성을 입증하지 않으며 실제 운영 검증도 시작하지 않습니다.

## 복구

1. 오래된 근거, 담당 체계/의존성 변경, 보호 검사 실패, 작성자 배제 상실, 관련 활성 인시던트,
   텔레메트리 손실 또는 기한 만료가 발생하면 새 정방향 효과를 중단합니다.
2. 게시 결과가 불명확하면 다시 보내거나 복원하기 전에 대조합니다. 원래 계획과 실제 전달
   신원을 유지하며 보존된 상태를 우회하려고 관련 없는 요청을 만들지 않습니다.
3. 기존 보상/복구 경로에서 같은 정방향 계획 다이제스트와 별도로 유효한 복구 권한을 사용해
   `ops.restore-alert-configuration`을 처리합니다. 원본 바이트가 보존된 정방향 결과와 같을
   때만 복원합니다. 새 개정 번호가 있으면 덮어쓰지 말고 검토합니다.
4. 독립적으로 복원을 검증합니다. 복구가 누락, 실패 또는 평가 불가이면 `recovery_incomplete`와
   영속 자동화 보류를 유지합니다. 효과 중계는 보류를 해제하지 않습니다. 알림을 다시 켜도
   알림 없이 지난 시간을 되돌리거나 누락된 호출을 다시 만들 수 없습니다.

## 감사 이력

요청/상관관계 신원, 비공개 근거와 계획 다이제스트, 원래 Workflow/Process 연결, 정확한
파일/원본/결과/복구 다이제스트, Var 결정, 현재 수락 및 작성자 배제 참조, 안전장치 세대,
게시 증적, 독립 결과 및 복구 계보를 보존합니다. 버스와 감사 기록에는 제한된 참조를 넣으며
비공개 수신자 목록, 원본 본문, 비밀값 또는 호출자가 작성한 성공 플래그를 넣지 않습니다.
게시, 관측 효과, 복구, 승격은 별도 상태로 보고합니다. 정본 구현 이력은 이 런북이 아닌 원장에 유지합니다.
