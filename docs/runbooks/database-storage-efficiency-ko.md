# 데이터베이스 저장 공간 증가 진단

PostgreSQL 집계 지표를 사용해 보존해야 할 근거와 불필요한 저장·조회 비용을 구분합니다.
테이블 개수만으로 저장 공간 낭비를 판단하지 않습니다.

> 범위: 이 문서의 명령은 포트 5432의 루프백 개발 데이터베이스만 허용합니다.
> 데이터베이스 테스트는 포트 5433의 별도 검증 클러스터를 사용합니다.
> 이 문서는 운영 데이터 삭제, 원격 데이터베이스 접근, 감사 기록과 인벤토리 근거 삭제를 승인하지 않습니다.

## 이 문서에서 다루는 내용

저장 공간을 점검하고 승인된 임시 상태 보존 정책을 적용한 뒤 변경을 검증합니다.
논리적 삭제와 실제 디스크 공간 회수를 구분하고 관측 시각, principal 격리,
롤백 데이터, 배포별 보존 정책을 유지합니다.

## 저장 구조를 변경하기 전에 측정

기존 로컬 환경이 구성된 상태에서 다음 명령을 실행합니다.

```bash
uv run python scripts/deployment/local/report-database-growth.py --json --details --no-sample
```

보고서는 힙, 인덱스, PostgreSQL의 큰 값 외부 저장 방식인 TOAST를 구분합니다.
유효 행과 삭제된 행의 수는 추정치입니다. 인덱스 조회 횟수는 보고된 통계 초기화 시점
이후의 값입니다. 조회 횟수가 0이라는 이유만으로 고유 인덱스, 기본 키 인덱스,
그 밖의 필수 인덱스를 삭제하면 안 됩니다.

`--no-sample`을 생략하면 다음 증가량 비교에 사용할 관계별 용량 집계가 저장됩니다.
데이터베이스나 관계의 식별자가 바뀌면 새 기준으로 측정을 시작합니다.
표본에는 메타데이터만 저장하며 행의 본문이나 연결 값은 저장하지 않습니다.
관계별 증가량은 시간당 바이트로 표시합니다.

`--details`는 바이너리 본문, 만료된 캐시 행, 분리된 레거시 캐시 행, 기록된 보존 정책을
제한 시간 안에 집계합니다. 파티션 부모의 자체 용량은 전체 파티션 용량의 합이 아닙니다.
실제 용량은 말단 관계별 내역으로 확인하세요.
없는 테이블은 `not_installed`로 보고합니다. 읽기 권한이 부족하면 이를 명시하고
`details_complete`를 false로 설정하며 종료 코드 2를 반환합니다.
측정하지 못한 값을 0으로 표시하거나 보고서가 스스로 데이터베이스 권한을 추가하지 않습니다.

## 행 수와 바이트로 임시 상태 제한

기존 접두사별 최신 N개 구간은 최소 보존 세대를 유지합니다.
값의 저장 용량과 제안할 바이트 예산을 미리 확인합니다.

```bash
uv run python scripts/deployment/local/compact-local-database.py --max-prefix-bytes 67108864
```

예시 예산은 지원되는 접두사마다 64 MiB이며 제품 기본값이 아닙니다.
값의 저장 바이트는 저장된 JSONB 값만 측정합니다. 힙, 인덱스, TOAST 페이지 부가 공간,
빈 공간은 포함하지 않습니다. 총 디스크 용량은 물리적 용량 보고서로 확인하세요.

필수 최신 N개 구간이 예산을 초과하면 명령은 `blocked`를 보고하고 종료 코드 2를 반환하며
삭제하지 않습니다. 예산에 맞추려고 필수 보존 구간을 줄이지 않습니다.
로컬 유지관리를 명시적으로 승인한 후 `--apply`를 추가하면 지원되는 임시 상태 접두사만
정리합니다. 정리는 범위가 제한된 트랜잭션으로 나누어 실행하며 동시 쓰기 이후의
남은 행과 바이트 예산을 다시 확인합니다. 바이트 예산을 선택하지 않아도 남은 정리 대상
행을 명시적으로 보고합니다. 나중 배치가 실패해도 앞선 안전한 배치는 커밋된 상태일 수
있습니다. 실패 원인을 검토한 뒤에만 다시 실행하세요.

## 암묵적인 테이블 재작성 없이 vacuum 실행

`--apply --vacuum`은 일반 `VACUUM (ANALYZE)`을 실행합니다.
삭제된 공간을 재사용할 수 있게 하지만 파일 시스템의 할당 용량 감소를 보장하지는 않습니다.
스키마 마이그레이션에서 변경이 잦은 `state_kv`의 autovacuum과 TOAST 기준을 설정하므로
튜닝을 위해 수동 재작성을 실행할 필요가 없습니다.

`--apply --vacuum-full`은 테이블 재작성을 명시적으로 요청합니다.
유지관리 시간, 추가 임시 디스크 공간, 배타적 테이블 잠금이 필요합니다.
두 방식 모두 연결, 문장 실행, 잠금 대기 제한 시간을 유지합니다.

## 조회 최적화에서 기존 계약 유지

- 상태 페이지는 키를 먼저 선택하고 정렬한 뒤 JSON 본문을 읽습니다. 총건수와 페이지 행은
  하나의 SQL 스냅샷에서 얻습니다. 기존 오프셋 API와 정확한 총건수를 유지합니다.
- 대화 목록은 작은 키·시각 기록만 집계한 뒤 선택된 행에서 첫 질문과 마지막 턴을 읽습니다.
  같은 시각에는 키 순서로 일관되게 선택합니다. principal 범위, 기존 대화 기록의 우선순위,
  커서 동작은 바뀌지 않습니다.
- 같은 상태 값을 다시 써도 기존 TOAST 값을 재사용하면서 최근 갱신 시각을 바꿉니다.
  이 시각 갱신을 없애면 보존 의미가 바뀝니다. 회귀 테스트는 `1`과 `1.0` 같은
  숫자 표현의 차이도 유지합니다.

## 배포 환경의 근거가 필요한 결정

저장 구조 비평의 항목별 처리 방향은 다음과 같습니다.
로컬 구현은 운영 데이터 이행 완료나 실행 중인 데이터베이스의 용량 감소를 뜻하지 않습니다.

| # | 점검 항목 | 처리 방향 |
|---|-----------|-----------|
| 1 | 세대별 멤버십 반복 저장 | 불변 멤버·최신성 페이지를 공유하고 재생 참조 체인 없이 세대별 바인딩을 정확히 보존합니다. |
| 2 | 스냅샷 속성 반복 저장 | 준비 단계의 불변 본문을 공유하고 행별 관측 메타데이터를 보존하며 참조가 없는 준비 단계 본문만 정리합니다. |
| 3 | 무기한 기본 보존 | 배포별 승인 정책과 기존 아카이브·복구 인증이 제공될 때까지 `retain`을 유지합니다. |
| 4 | 보호된 캐시 카탈로그의 만료 행 | 활성·롤백 카탈로그 바인딩과 불변 증적을 유지하면서 범위가 제한된 만료 정리를 수행합니다. |
| 5 | 유효 캐시 키의 중복 행 | 정확한 키의 유일성을 보장하고 기존 조회의 만료·생성 시각 우선순위를 유지합니다. |
| 6 | 같은 상태 값의 재쓰기 | 무조건 쓰기를 생략하자는 제안은 철회합니다. 기존 TOAST 재사용, 갱신 시각, 숫자 표현 계약을 유지해야 합니다. |
| 7 | 행 수만 사용하는 용량 제한 | 필수 최신 N개 구간을 줄이지 않고 바이트 예산을 미리 확인하거나 초과 시 작업을 차단합니다. |
| 8 | 범용 JSON 검색 | 자주 사용하는 대화 조회에 principal·세션 선택 인덱스를 추가합니다. 임의 JSON 필드는 실측에 따른 조회별 설계가 여전히 필요합니다. |
| 9 | 정확한 총건수를 제공하는 오프셋 페이지 | 본문을 읽기 전에 키를 정렬하고 한 스냅샷에서 총건수와 페이지를 얻습니다. 기존 오프셋 API를 암묵적으로 커서로 바꾸지 않습니다. |
| 10 | 전체 발화 집계 | 발화 배열을 만들지 않고 작은 키·시각 기록에서 첫 행과 마지막 행을 선택합니다. |
| 11 | 한도가 없는 보존 삭제 | 전체 제한 시간 안에서 트랜잭션당 1,000개씩 정리하고 동시에 다시 쓴 행 버전을 보호합니다. |
| 12 | 분리된 레거시 캐시 | 보존된 데이터를 측정합니다. 폐기에는 승인된 명시적 롤백 보존 기간과 복구 근거가 여전히 필요합니다. |
| 13 | PostgreSQL 안의 바이너리 본문 | 본문 바이트를 측정합니다. 외부 이전에는 저장소 선택, 실측한 이점, 무결성·권한의 동등성, 롤백이 여전히 필요합니다. |
| 14 | 수동 작업에 의존하는 vacuum 튜닝 | 마이그레이션에서 상태·TOAST vacuum을 설정하고 일반 vacuum과 명시적 전체 재작성을 구분합니다. |
| 15 | 원인을 구분하지 않는 증가량 보고 | 힙·인덱스·TOAST, 삭제된 행의 추정 수, 관계별 증가량, 인덱스 사용량과 측정할 수 없는 상세 항목을 명시적으로 보고합니다. |

| 결정 | 적용 전에 필요한 근거 |
|------|------------------------|
| 유한한 인벤토리 보존 기간 | 정확한 데이터 종류, 목적, hot/warm/archive 기간, 보존 의무, 검증된 복구 범위, 기존 non-shadow 인증이 필요합니다. 저장소의 `retain` 기본값은 유지합니다. |
| 분리된 레거시 캐시 폐기 | 남아 있는 데이터의 실측, 승인된 롤백 보존 기간, 정확한 유지관리 범위, 복구 테스트가 필요합니다. 업그레이드를 삭제 승인으로 해석하지 않습니다. |
| 바이너리 본문을 PostgreSQL 외부로 이동 | 본문·백업·복제 비용의 실측, 독립적으로 선택한 저장 백엔드, 권한·만료 처리의 동등성, 본문·서명 검증, 원자적 조회, 롤백 테스트가 필요합니다. |

이 항목들은 데이터 이행이 완료된 상태가 아닙니다.
비용을 보고하는 것은 안전하지만 보존 기간을 임의로 정하거나, 불변성 보호를 해제하거나,
Blob 계정을 대신 선택하는 방식은 지원하지 않습니다.

## 분리된 데이터베이스에서 검증

```bash
python3 scripts/automation/with-local-test-database.py \
  uv run pytest -q --no-cov tests/integration/services/test_database_storage_efficiency.py
```

집중 검증은 여러 배치의 삭제 한도, 필터와 특수 문자가 있는 접두사, 빈 페이지와 오프셋
페이지의 정확한 총건수, principal 격리, 첫 턴과 마지막 턴의 동일 시각 처리,
대화 커서를 확인합니다. 로컬 검사 통과는 운영 비용 절감이나 배포 완료를 증명하지 않습니다.
