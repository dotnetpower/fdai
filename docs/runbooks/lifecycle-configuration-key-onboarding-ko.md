# 수명 주기 구성 키 등록

이 런북에서 수명 주기 구성 패키지에 필요한 고객 소유권, 키 보관과 공개 검증 키 연결을
준비할 수 있습니다. 이러한 선행 조건은 구현된 로컬 패키지 생성기 및 인증된 공개 키 소스
API와 구분합니다. 실제 운영 등록과 원자적 Hub 패키지 가져오기는 별도의 수락 작업입니다.

> **중단 조건:** 이 런북은 키를 등록, 생성, 교체하거나 내보내지 않으며 Hub
> 가져오기 명령을 제공하지 않습니다. [로컬 CLI](../roadmap/deployment/lifecycle-configuration-ko.md#로컬-패키지-생성과-검증-명령)는
> 명시적으로 지정한 비공개 파일에 서명하고 검증하지만 키 신뢰를 확립하거나 Release를 검증하지는 않습니다.
> 아래 소스 API는 로컬 합성 테스트로만 검증했습니다. 실제 키 등록, 검증된 Release 입력과
> Hub 가져오기를 독립적으로 검증하기 전에는 실제 구성을 게시하지 마세요.

## 이 런북의 범위

고객 구성 키는 검토된 희망 구성 개정을 인증합니다. 공급업체 Release 키, 등록된 Ed25519
설치 신원과 봉인된 식별자를 보호하는 X25519 설치 키와는 다릅니다. 어떤 키도 운영 승인,
승격 또는 실행기 권한을 부여하지 않습니다.

## 1. 비공개 저장소 준비

[자리 표시자 템플릿](../../config/lifecycle-configuration-template/README.md)을 고객 소유 비공개
저장소로 복사하세요. 합성 `release-schema.yaml`은 예제로만 유지하세요. 실제 패키지에는
독립적으로 검증된 대상 Release의 스키마가 필요합니다.

자리 표시자를 바꾸기 전에 모든 값을 검토하세요.

| 값 | 저장 위치 |
|----|-----------|
| 리전, 크기, 버전 범위와 Entity 재정의 | 구성 계층 |
| 테넌트, 구독, 리소스 이름과 엔드포인트 | 비공개 봉인 입력 |
| 연동 자격 증명 | Key Vault. 저장소에는 참조만 저장 |
| 승인 프로필, 허용 정책이나 상시 권한 | 기존 거버넌스 정책 경로. 구성에는 포함하지 않음 |

upstream FDAI에는 고객 정보를 포함하지 마세요. 실제 값을 채운 파일을 공개 이슈나 로그에
첨부하지 마세요.

## 2. 키 보관 담당 지정

고객의 정상 거버넌스 절차에서 구성의 최종 책임자와 복구 승인자를 지정하세요. 개인 키를
내보내지 않는 프로바이더 호스팅 보관 방식이나 다른 검토된 서명 경계를 선택하세요. 알고리즘과
등록 세부 사항은 검토된 패키지 계약에 따라야 하며 이 런북은 호환되는 서명기를 임의로 정하지
않습니다.

개인 키 자료를 채팅, 명령 인자, 저장소 파일, 로그나 스크린샷에 넣지 마세요. 고객의 보호된
기록에는 공개 키 참조, 지문, 대상 설치 연결과 검토 신원만 기록하세요. 신뢰되지 않은 패키지에서
복사한 공개 키로 같은 패키지의 신뢰를 확립할 수는 없습니다.

## 3. 검증 키 연결 검토

등록을 완료하려면 구현에서 다음 검사를 모두 확인해야 합니다.

- 정확한 설치가 고객 구성 검증 키를 독립적으로 신뢰합니다.
- 서명된 개정은 Git 커밋, 이전 개정 다이제스트와 내용 다이제스트를 결속합니다.
- 서명이 없거나 잘못된 키, 순서가 바뀐 개정이나 갈라진 개정 이력은 Plan 계산 전에 차단됩니다.
- 봉인할 식별자는 올바른 설치 키로 암호화합니다. Hub는 평문 입력이 아니라 암호문과
  다이제스트만 보관합니다.
- 서명 전에 비밀 값을 차단하며 Hub는 Key Vault 참조로 실제 비밀 값을 읽지 않습니다.
- 구성 변경으로 정책, 승격 상태나 실행 권한을 바꿀 수 없습니다.

이는 운영 수락 기준입니다. 로컬 패키지 서명과 검증만으로 설치의 신뢰를 확립하거나
Hub 가져오기를 구현하지는 않습니다.

### 소스 전용 인증 공개 키 절차

기존 인증 Hub는 이미 등록된 설치에 다음 경로를 제공합니다.
공개 메타데이터와 증명만 받으며 개인 키나 자격 증명은 받지 않습니다.

| `/v1/installations/{installation_id}/configuration-keys` 아래 경로 | 입력 또는 결과 |
|------------------------------------------------------------------|-----------------|
| `POST /request` | 정규화된 요청 바이트, 설치 신원 증명과 별도 구성 서명자 증명 |
| `GET /requests/{request_digest}` | 독립 검토를 위한 정확한 공개 요청과 다이제스트 |
| `POST /approve` | 정확한 `request_digest`. 인증된 운영자는 서명된 요청자와 달라야 함 |
| `POST /revoke` | 정확한 현재 `request_digest`. 이력을 삭제하지 않고 구성 신뢰를 제거 |
| `GET` | 현재 버전, 승인된 다이제스트, 승인자와 회수 상태 |

[소유 설계](../roadmap/deployment/lifecycle-configuration-ko.md#승인된-구성-키-설계와-검토)는
정규 필드, 알고리즘 분리, 5분 이내 증명, 10분 승인 기한, 바인딩 만료 범위와 이전 바인딩/버전
비교를 정의합니다. 행위자 필드나 패키지 키는 승인이 아닙니다. 인증되지 않은 loopback 호출은
이 신뢰를 등록하거나 승인할 수 없습니다. 명시적 Lifecycle Hub 개정 1에서 2로의
마이그레이션은 데이터를 보존하며, 서비스 시작은 데이터를 마이그레이션하지 않습니다.

실제 계획 저장소는 영구 저장된 승인 바인딩을 확인합니다. 서버가 제공하는 구성 후보는
명시적 조합 경계를 통해 기존 원격 재계산 API에 전달할 수 있습니다. 고객 패키지 업로드나
가져오기 명령, 영구 저장된 수락 체인의 끝은 아직 없습니다. 교체는 이전 공개 메타데이터를
보존하고 이전의 대기 Plan을 보류합니다. 이전 패키지는 교체 서명 키로 재해석하지 않습니다.
다른 키에 걸친 수락 체인 가져오기는 별도 작업으로 남깁니다.

## 4. 자리 표시자 구조 오프라인 검사

FDAI checkout에서 실행하세요.

```bash
uv run --no-sync pytest -q --no-cov \
  tests/integration/test_lifecycle_configuration_template.py
```

집중 검사는 구현된 순수 검증기와 합성 값을 사용합니다. 키, 서명, 패키지, 업로드, Azure 호출이나
운영 증적은 만들지 않습니다. 테스트 개정과 결과를 이후의 연결 환경 수락 증거와 별도로
보관하세요.

## 5. 게시 전 복구 계획

키 교체 승인자와 설치가 독립적인 신뢰 경로로 새 검증 키를 인증하는 방법을 기록하세요. 이전
개정 이력을 보존하세요. 키 교체가 갈라진 개정 이력이나 기록 초기화를 허용하지는 않습니다.
개인 키를 잃어버렸거나 보관 상태가 불확실하면 검토된 운영 교체와 독립 재확인이 성공할 때까지
새 게시를 보류하세요. 소스 전용 API와 합성 테스트는 이 절차를 실제로 수행하지 않습니다.

등록된 개발 설치의 신원 개인 키를 사용할 수 없으면 Hub 행이나 Agent 파일을 직접 바꾸지 마세요.
Lifecycle Hub 배포가 `operator_auth.development_recovery`에 정확한 설치, 범위, Owner object ID,
이전 키 ID, 대체 공개 키, 사유와 최대 14일의 승인 구간을 고정한 뒤에만 전권 개발 복구를
사용합니다.

1. 선택한 대체 개인 키는 승인된 비공개 키 디렉터리에 유지합니다. 배포 입력에는 공개 키만
   파생해 사용합니다.
2. 정규 `fdai.development-identity-recovery.v1` 바이트를 만들고 정확한 대체 키로 서명합니다.
   요청 확인문에는 설치, 이전 키 ID와 대체 키 ID를 포함합니다.
3. 정확히 구성된 Owner로
   `POST /v1/installations/{installation_id}/configuration-keys/recover-identity`에 서명 요청을
   제출합니다. 정확한 재시도는 같은 다이제스트를 반환합니다.
4. 구성 서명자 바인딩을 요청하기 전에 새 설치 키 ID와 추가 전용 복구 감사 기록을 다시
   확인합니다.
5. 보호된 승인이 명시적으로 허용할 때만 같은 Owner가 첫 바인딩을 승인할 수 있습니다. 이후
   교체와 개발 외 모든 설치에는 계속 다른 운영자가 필요합니다.
6. 첫 바인딩 뒤 복구 승인을 제거하고 Hub의 변경 없음 계획을 확인합니다.

Plan이 열려 있거나, 구성 신뢰 또는 대기 중인 키 요청이 이미 있거나, 증명이 5분보다 오래됐거나,
고정 입력이 하나라도 다르면 복구를 중단합니다. 무결성 서명 키를 다른 용도로 사용하거나 이력을
다시 쓰거나 Hub로 개인 키 바이트를 전달하지 않습니다.
