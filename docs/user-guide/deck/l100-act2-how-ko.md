# 덱 2막: 어떻게 동작하고 무엇을 얻는가

11-21번 장표는 두 가지 질문에 순서대로 답합니다. 이벤트 한 건이 실제로 어떻게
처리되는가, 그리고 잘못된 조치를 무엇이 막는가. 그다음에야 버티컬별 아웃컴을
보여주고 데모로 넘깁니다.

밀도, 시간 배분, 고객마다 채우는 슬롯은 [덱 키트](README-ko.md)를 먼저 확인하세요.

## 11번 장표. 이벤트 한 건의 여정

- **핵심 메시지**: 모든 신호는 같은 통제 경로를 지납니다.
- **밀도**: `상세`
- **본문** - 다섯 단계를 한 줄씩
  - 수집과 상관: 스키마를 검증하고, 재시도를 안전하게 만드는 키로 중복을 제거하고,
    관련 신호를 하나의 인시던트로 묶습니다.
  - 라우팅: 그 이벤트를 판단할 수 있는 가장 낮은 티어로 보냅니다.
  - 리스크 분류 전 검증: 모델이 제안한 조치는 서로 다른 모델 간 교차 확인, 근거 확인,
    스키마와 정책과 보안과 what-if 검사를 통과해야 합니다.
  - 안전성 검토 적용: 조치 리스크, 영향 범위, 시스템 상태, 정책을 종합해 자동 실행,
    사람 승인, 차단 중 하나를 반환합니다.
  - 한 번만 실행하고 모든 경로를 기록: 리소스별 락, 재시도해도 안전한 조치, 그리고
    승인, 거부, 타임아웃, 롤백, 무처리 모두에 대한 감사 기록.
- **비주얼**: 아키텍처 흐름도를 단순화한 가로 파이프라인, 마지막에 안전성 검토의 세
  가지 결과가 분기.
- **스피커 노트**: 구체적인 이벤트 하나를 끝까지 따라갑니다. 20번 장표의 데모와 같은
  시나리오를 쓰는 것이 가장 좋습니다.
- **근거 문서**: [FDAI 아키텍처](../architecture-ko.md)

## 12번 장표. 결정론 우선

- **핵심 메시지**: 추론은 기본값이 아니라 예외입니다.
- **밀도**: `상세`
- **본문**
  - T0, 결정론적 규칙: 정답이 정해진 policy-as-code 판단. 모델 호출 없음. 목표
    커버리지 70-80%.
  - T1, 경량 재사용: 패턴 매칭, 과거 해소된 인시던트와의 유사도, 소형 분류기. 목표
    15-20%.
  - T2, 근거 기반 추론: 프런티어 모델에 교차 모델 합의, 결정론적 검증기, 근거 확인을
    결합. 목표 5-10%.
  - 이 숫자는 설계 목표이며 측정된 결과가 아닙니다. FDAI는 측정된 베이스라인이 있을
    때만 커버리지를 보고합니다.
- **비주얼**: 세 티어로 이루어진 퍼널, 각 구간에 목표 비중과 "결과가 아닌 목표치"
  라벨.
- **스피커 노트**: 마지막 불릿은 반드시 소리 내어 말합니다. 주장의 한계를 먼저 밝히는
  것이 나머지 숫자의 신뢰를 만듭니다.
- **영업 포인트**: 비용과 예측 가능성이 모두 이 장표에서 나옵니다. 대부분의 이벤트는
  모델 호출까지 가지 않습니다.
- **근거 문서**: [결정론 우선](../concepts/deterministic-first-ko.md),
  [목표와 지표](../../roadmap/architecture/goals-and-metrics-ko.md)

## 13번 장표. 모든 조치는 자기 안전 계약을 지닙니다

- **핵심 메시지**: 즉흥적인 조치는 없습니다. 모든 변경은 타입이 정의된 액션의
  인스턴스입니다.
- **밀도**: `상세`
- **본문**
  - FDAI가 할 수 있는 변경은 자유 서술 지시가 아니라 코드로 관리되는 카탈로그
    항목입니다.
  - 타입이 정지 조건, 롤백 경로, 영향 범위 한도, 드라이런, 리소스별 락, 재시도를
    안전하게 만드는 키, 감사 기록을 정의하고, 실제 조치가 이를 그대로 상속합니다.
  - 그다음 안전성 검토가 리스크, 범위, 시스템 상태, 정책을 기준으로 자동 실행, 사람
    승인, 차단 중 하나로 라우팅합니다.
- **비주얼**: 액션 카드 한 장을 확대해 각 안전 필드에 라벨을 붙이고, 이 필드들이
  인시던트마다 새로 쓰이는 것이 아니라 상속된다는 설명을 추가.
- **스피커 노트**: "모델이 파괴적인 작업을 요청하면 어떻게 되느냐"에 대한 답입니다.
  타입이 없는 조치는 애초에 만들어질 수 없습니다.
- **근거 문서**: [온톨로지 기반 자동화](../concepts/ontology-driven-automation-ko.md),
  [리스크 티어](../concepts/risk-tiers-ko.md)

## 14번 장표. 관찰 모드에서 변경 적용으로

- **핵심 메시지**: 새 기능은 무엇도 건드리기 전에 먼저 지켜봅니다.
- **밀도**: `표준`
- **본문**
  - 새 규칙이나 액션은 모두 관찰 모드로 시작합니다. 판단하고 기록하되 적용하지
    않습니다.
  - 측정된 정확도가 유지되고 가드 지표가 나빠지지 않은 뒤에야 적용 모드로 승격됩니다.
  - 이후 가드 지표가 나빠지면 해당 기능은 자동으로 관찰 모드로 되돌아갑니다.
- **비주얼**: 설치에서 관찰, 승격 게이트, 변경 적용으로 이어지는 타임라인과 "자동"
  라벨이 붙은 복귀 화살표.
- **스피커 노트**: 26번 장표의 파일럿과 묶어서 설명합니다. 파일럿 1일차는 항상 관찰
  모드이므로 초기 몇 주는 변경 리스크가 없습니다.
- **영업 포인트**: "도입 첫날부터 우리 운영 환경을 바꾸느냐"에 대한 직접적인 답입니다.
  그렇게 할 수 없습니다.
- **근거 문서**: [관찰 모드](../concepts/shadow-then-enforce-ko.md)

## 15번 장표. 사람이 남는 자리

- **핵심 메시지**: 승인자와 실행 주체는 결코 같은 아이덴티티가 아닙니다.
- **밀도**: `표준`
- **본문**
  - 승인 요청은 Teams나 Slack 카드로 도착하며, 결정 내용과 근거와 롤백 경로가 함께
    담깁니다.
  - 사람의 역할과 실행자 아이덴티티는 서로 다른 주체이며, 자기 승인은 허용되지
    않습니다.
  - 승인 채널이 중단되면 고위험 작업은 승인 없이 진행되지 않고 대기합니다.
- **비주얼**: 왼쪽에 승인 카드 목업, 오른쪽에 승인자와 실행자가 분리된 아이덴티티
  경계 다이어그램.
- **근거 문서**: [승인과 채널](../concepts/approvals-and-channels-ko.md),
  [변경 승인하기](../guides/approve-change-ko.md)

## 16번 장표. 모든 경로에 증거

- **핵심 메시지**: 자동 실행, 차단, 타임아웃, 롤백, 무처리가 모두 같은 방식으로
  기록됩니다.
- **밀도**: `표준`
- **본문**
  - 감사 기록은 추가 전용이며, 조치가 일어난 결과뿐 아니라 아무것도 바꾸지 않은
    결과까지 포함합니다.
  - 각 기록은 결정을 근거, 규칙이나 모델 경로, 승인자, 롤백 참조와 연결합니다.
  - 운영자 콘솔은 읽기 전용 투영만 봅니다. 실행 권한이 없고 승인도 할 수 없습니다.
- **비주얼**: 감사 기록 한 건을 필드 단위로 펼치고, 그 옆에 읽기 전용 콘솔 화면을
  배치.
- **스피커 노트**: 컴플라이언스 중심 고객은 이 장표에서 설득되는 경우가 많습니다.
  데모에서 실제 기록 한 건을 함께 보자고 제안하세요.
- **근거 문서**: [감사 로그 읽기](../guides/read-audit-log-ko.md)

## 17번 장표. 아웃컴 - 복원력

- **핵심 메시지**: 복구는 장애 중에 확인하는 것이 아니라 정기적으로 증명합니다.
- **밀도**: `상세`
- **본문**
  - 재해 복구 예행 연습이 지정된 훈련 시간대 안에서 실행되고 결과를 기록합니다.
  - 데이터베이스 훈련은 목표 복구 시점과 복구 시간에 맞춰 복원을 수행하고, 문제가
    되기 전에 격차를 식별합니다.
  - 장애 주입 실험은 선언된 영향 범위 안에서만 수행됩니다.
  - 해소된 인시던트와 일치하는 실패는 자동으로 수정되고, 새로운 유형은 사람에게
    올라옵니다.
  - 예시: 야간 작업이 핵심 데이터베이스에서 point-in-time-restore 격차를 발견하고,
    훈련 시간대 안에 복원 훈련이 예약되고, 복원이 목표를 충족하고, 감사 기록이
    남습니다.
  - 측정 지표: 해소 시간(중앙값과 p90), 사람 개입 없이 해소된 이벤트 비율. 가드
    지표: 롤백률, 미탐률.
- **비주얼**: 훈련 캘린더 띠 아래에 베이스라인과 목표 칸이 비어 있는 아웃컴 지표 행.
- **근거 문서**: [회복탄력성](../capabilities/resilience-ko.md)

## 18번 장표. 아웃컴 - 변경 안전

- **핵심 메시지**: 모든 변경은 운영에 도달하기 전에 평가됩니다.
- **밀도**: `상세`
- **본문**
  - 제안된 변경은 무엇을 적용하기 전에 policy-as-code 기준으로 드라이런됩니다.
  - 선언된 상태에서 벗어난 설정은 탐지되어 자동으로 교정되거나 검토로 올라옵니다.
  - 저위험 변경은 자동으로 병합되고, 고위험 변경은 승인을 기다립니다.
  - 변경은 풀 리퀘스트로 전달되므로 변경 기록과 롤백 경로가 이미 git 안에 있습니다.
  - 예시: 인프라 풀 리퀘스트가 외부로 열린 네트워크 규칙을 제안하고, 안전성 검토가
    고위험으로 분류하고, 승인 카드가 채널에 도착하고, 승인자가 수락하면 수정이 감사
    기록과 함께 병합됩니다.
  - 측정 지표: 변경 리드타임(중앙값과 p90). 가드 지표: 변경 실패율은 올라가면 안 되고,
    정책 위반이 그대로 통과한 건수는 0이어야 합니다.
- **비주얼**: 안전성 검토를 분기점으로 하는 변경 파이프라인, 두 가드 지표를 레드라인
  표시로 고정.
- **근거 문서**: [변경 안전](../capabilities/change-safety-ko.md)

## 19번 장표. 아웃컴 - 비용 거버넌스

- **핵심 메시지**: 낭비는 제거가 안전한 곳에서만 자동으로 제거됩니다.
- **밀도**: `상세`
- **본문**
  - 기대 베이스라인에서 벗어난 지출은 발견된 문제로 올라옵니다. 탐지 자체는 결코
    조치하지 않습니다.
  - 과다 프로비저닝된 리소스는 되돌릴 수 있는 구체적 수정안과 함께 표시됩니다.
  - 저위험 항목인 유휴 디스크 정리, 미사용 공인 IP 회수, 고아 네트워크 인터페이스
    제거는 롤백 경로를 가진 채 자동으로 실행됩니다.
  - 실제 영향 범위가 있는 변경은 승인을 기다립니다.
  - 예시: 비용 이상 탐지가 과다 프로비저닝된 캐시 계층에서 발생하고, 결정론적 규칙이
    매칭되고, 2주간의 관찰 모드가 규칙을 검증하고, 해당 조치가 적용 모드로 승격되고,
    적정 사이징 수정이 롤백 경로와 함께 풀 리퀘스트로 전달됩니다.
  - 측정 지표: 최적화 건당 비용. 가드 지표: 롤백률은 올라가면 안 됩니다. FDAI는 짝지어
    측정하지 않은 절감 배수를 주장하지 않습니다.
- **비주얼**: "스스로 조치함"과 "사람을 기다림"으로 나눈 2열, 각 열에 해당 조치 예시.
- **근거 문서**: [비용 거버넌스](../capabilities/cost-governance-ko.md)

## 20번 장표. 데모

- **핵심 메시지**: 이벤트 한 건, 처음부터 끝까지, 5분.
- **밀도**: `표준`, 진행 지침은 상세
- **본문**
  - 동영상 슬롯: 4-6분, 소리 없이도 이해 가능, 한국어 자막 삽입.
  - 시나리오 전개: 드리프트 신호 도착, 결정론 티어가 판단, 승인 카드가 채널에 표시,
    승인자가 수락, 수정이 풀 리퀘스트로 전달, 감사 기록으로 루프 종료.
  - 재생 전 30초 셋업: 어떤 이벤트이고 무엇을 볼지 짚어 줍니다.
  - 재생 후 30초 정리: 화면에 나온 안전 필드를 13번 장표와 연결합니다.
  - 재생 실패에 대비해 다음 숨김 장표에 대체 스틸 3장을 둡니다.
- **비주얼**: 동영상 프레임을 중앙에 두고, 재생이 실패해도 스토리가 남도록 아래에
  시나리오 다섯 단계를 캡션 띠로 배치.
- **스피커 노트**: 동영상 위에 설명을 덮어씌우지 않습니다. 끝까지 재생한 뒤 해석합니다.
- **영업 포인트**: 고객 환경과 가장 가까운 시나리오를 고릅니다. 화려한 수정보다 익숙한
  리소스 타입이 더 효과적입니다.

## 21번 장표. 운영자가 보는 화면

- **핵심 메시지**: 같은 감사 기록 위에 놓인 읽기 전용 콘솔입니다.
- **밀도**: `표준`
- **본문**
  - 스크린샷 슬롯: 근거가 함께 보이는 결정 상세, 승인 대기 목록, 감사 기록, 담당 체계
    뷰.
  - 콘솔은 상태와 근거를 보여줍니다. 실행자 아이덴티티를 갖지 않으며 승인이나 변경을
    할 수 없습니다.
  - 운영자는 자기 언어로 질문할 수 있고, 답변은 감사 기록과 동일한 기록에서 구성됩니다.
- **비주얼**: 스크린샷 4장을 2x2로 배치하고 전체에 "읽기 전용" 배지.
- **스피커 노트**: 스크린샷은 데모 데이터만 사용합니다. 이 장표를 위해 고객 환경을
  캡처하지 않습니다.
