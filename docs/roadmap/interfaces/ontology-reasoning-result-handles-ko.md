# 온톨로지 추론 결과 핸들과 이어 읽기

이 문서는 답변이 보여 준 행을 턴이 끝난 뒤에도 가리킬 수 있게 하는 방법을 설계합니다. 버전이 있는
핸들, 근거, pushdown, 이어 읽기 계약과 핸들 저장 위치, 행이나 그 속성을 지목하는 후속 질문, 한 번의
답변에 다 담지 못한 조회를 끝까지 읽는 이어 읽기를 다룹니다. 이 문서는
[온톨로지 추론 컴파일러](ontology-reasoning-compiler-ko.md)와 그
[후속 질문 참조](ontology-reasoning-compiler-ko.md#후속-질문-참조)를 확장합니다.

> **상태:** 2026-10-01 제안 설계입니다. 전달 상태와 남은 작업은
> [구현 원장](../../roadmap-implementation/interfaces/ontology-reasoning-result-handles.md)에 있습니다.
> 현재 있는 shadow 바인딩 핵심은 상위 설계에서 설명합니다.

## 설계 개요

결과 핸들은 답변이 보여 준 정확한 행을 보여 준 순서대로 기록한 서버 측 레코드입니다. "두 번째 것"이나
"그 SKU" 같은 후속 질문이 단어에서 추측하지 않고 실제 행에 바인딩되게 합니다. 이어 읽기(continuation)는
한 번의 답변이 잘라 낸 조회의 나머지를 위한 서버 측 상태입니다. 덕분에 FDAI는 여러 답변에 걸쳐 모든
행을 정확한 집계와 함께 나열할 수 있습니다. 둘 다 읽기 전용이며 배포, principal, 대화, 목적,
매니페스트에 결속됩니다. 모든 행은 보안이 적용된 게이트웨이를 통해 다시 읽고, 바인딩할 수 없는 참조는
하나의 타입 지정 명확화로 반환됩니다.
H2 로컬 구현은 핸들 본문을 암호화해 Core 저장소에 보관하고 Operator는 영속 의미 턴에 불투명 참조만
보관하게 합니다. 의미 요청 및 변환 스키마는 이 참조를 추가 필드로 운반하며 읽기, 승인 또는 실행 권한을
부여하지 않습니다.

| 패키지 | 제공하는 것 | 선행 조건 |
|--------|-------------|-----------|
| H1 계약 | 롤아웃에 안전한 버전 규칙을 갖춘 핸들, 근거 매니페스트, pushdown, 이어 읽기 레코드(R1) | 없음 |
| H2 핸들 저장소 | Core가 소유하는 핸들 본문, 지속되는 Operator 턴과 함께 저장되는 불투명 참조, 요청당 최대 네 개의 참조(R8) | H1과 위협 검토 |
| H3 속성 후속 질문 | 속성 언급 도메인과 이름 붙은 리소스 하나에 대한 속성 조회 | H1 |
| H4 서수 후속 질문 | 저장된 핸들에 대한 서수와 지시어, 지목한 행의 속성 포함 | H2와 H3 |
| H5 변경 이어 읽기 | 잘린 `query.recent_resource_changes` 기간의 모든 변경을 여러 페이지에 걸쳐 제공 | H1 |
| H6 연속 관계 계획 | 의도 그래프 하나보다 큰 all-kinds 이웃을 범위가 제한된 연속 계획으로 읽기 | H1과 H5 이어 읽기 규칙 |

## 현재 상태

- shadow 실행기는 서수나 지시어를 같은 대화의 가장 최근 핸들에만 바인딩합니다. 일치하지 않으면
  타입이 지정된 `prior_result_*` 명확화 요청을 돌려줍니다.
- 잘린 변경 조회는 나열하지 않은 변경 Resource의 정확한 개수를 밝힙니다. 이 개수는 페이지와 같은
  repeatable-read 스냅숏에서 셉니다.
- 관계의 side가 의도 그래프 하나를 넘으면, 도달한 엔드포인트의 합집합 하나가 계획 하나에 들어갈
  때만 답합니다. 그렇지 않으면 목표를 거절합니다.
- 핸들이 Core 프로세스를 벗어나지 않으므로, 다음 턴의 후속 질문은 아직 핸들을 쓸 수 없습니다.

## H1 계약

각 레코드는 Core와 Operator가 공유하는 `packages/service-contracts`의 버전 있는 모델입니다.

| 레코드 | 내용 | 공개 범위 |
|--------|------|-----------|
| `ResultHandleRef` | 무작위 불투명 `handle_ref`, 키 버전, `issued_at`, `expires_at` | Operator가 턴과 함께 저장하고 요청에 다시 보냅니다 |
| `ResultHandle` | 배포 범위, principal 다이제스트, 대화, 목적, 매니페스트 다이제스트, 렌더링 순서 다이제스트, 순서 있는 타입 행 키, 정렬, 페이지, 잘림 여부, 허용 목록에 있는 스냅숏 셀 | Core 전용이며 모델이나 Operator에 보내지 않습니다 |
| `EvidenceManifest` | 답변이 인용한 근거 참조, 그 증적, 완전성, 행 다이제스트 | Core 전용 |
| `PushdownRequest` | 선택적 그룹화와 계보 루트가 있는 개수, 또는 LinkType, 방향, 깊이 한도가 있는 타입 경로 | Core에서 저장소로 보내며 정확한 증적을 돌려줍니다. 자유 형식 조회 텍스트는 없습니다 |
| `QueryContinuation` | [H5](#h5-변경-이어-읽기)와 [H6](#h6-연속-관계-계획)의 필드 | Core 전용이며 클라이언트는 불투명 참조만 갖습니다 |

저장된 레코드는 한 릴리스보다 오래 남으므로, 버전 규칙은 레코드가 저장된 전체 기간에 적용됩니다.

- 순차 배포 중에는 실행 중인 모든 reader가 지원하는 가장 높은 버전으로 씁니다. 각 reader는 자신의
  부 버전과 바로 이전 부 버전(N/N-1)을 받습니다.
- N-1보다 오래된 레코드, 더 새로운 부 버전이나 주 버전, 알 수 없는 키 버전은 타입이 지정된 오류로
  안전하게 실패하며 부분 읽기를 하지 않습니다.
- 핸들과 이어 읽기의 수명은 호환성 기간보다 짧게 유지합니다. 그 기간을 넘는 레코드는 이전하거나
  만료됩니다.
- 테스트는 코덱 왕복, 양방향 순차 업그레이드와 롤백, 지원하지 않는 모든 버전의 거부를 다룹니다.

**종료 조건:** 코덱, N/N-1, 순차 업그레이드, 롤백 테스트가 통과하고 런타임 동작은 바뀌지 않습니다.

## H2 핸들 저장소

1. 결정론적 렌더링 뒤에 Core가 `ResultHandle`을 자신의 저장소에 씁니다. 저장소는 배포 범위로
   분할되고 버전 있는 키로 저장 시 암호화됩니다. Core는 `ResultHandleRef`를 돌려줍니다.
2. Operator는 참조를 지속되는 턴과 함께 저장하고, 다음 의미 요청에 최근 참조를 최대 네 개까지
   최신순으로 보냅니다. 참조에는 범위나 행 데이터가 없으므로 Operator는 가리키는 내용을 읽거나 바꿀
   수 없습니다.
3. Core는 배포 범위, principal 다이제스트, 대화, 목적, 매니페스트 다이제스트가 요청과 모두 일치할
   때만 핸들을 읽습니다. 행 키는 현재 기준 시각에 보안이 적용된 게이트웨이로 다시 읽습니다(기본값
   `current_rehydrate`). 보여 준 내용에 대한 질문은 허용 목록에 있는 스냅숏 셀로만 답합니다
   (`snapshot_reference`).
4. 가장 최근 핸들만 바인딩합니다. 단, "그 전 목록"처럼 타입 판단이 이전 답변을 명시적으로 인용하면
   그 답변을 바인딩합니다.

H2를 출시하기 전에 위협 검토를 통과해야 합니다.

| 위협 | 통제 |
|------|------|
| 다른 대화, principal, 배포에 대한 바인딩 | Core가 읽을 때 모든 바인딩 필드를 확인하며, 일치하지 않으면 `prior_result_foreign`을 돌려줍니다 |
| 답변 이후 바뀐 권한 | 모든 재조회가 게이트웨이를 거치므로 읽을 수 없는 행은 답변에 들어가지 않습니다 |
| 추측, 변조, 재사용된 참조 | 의미를 담지 않은 무작위 참조이며, 알 수 없는 참조는 `prior_result_unavailable`을 돌려줍니다 |
| 만료된 핸들이나 삭제된 대화 | 대화를 삭제하면 그 핸들도 삭제되며, 만료되면 `prior_result_expired`를 돌려줍니다 |
| 보관된 스냅숏 값 | 이미 보여 준 셀 가운데 허용 목록 필드만 대화의 보존과 삭제 규칙에 따라 보관합니다 |
| 키 유출이나 교체 | 버전 있는 키를 쓰며, 교체 뒤에는 이전 키를 그 핸들이 만료될 때까지 복호화에만 씁니다 |

**종료 조건:** 후속 질문 홀드아웃이 shadow에서 85% 이상 통과하고, 위협 검토 테스트에서 다른 대화
바인딩이 0건이며, 렌더링 순서 다이제스트가 fixture 그래프에서 Console의 순서와 같습니다.

## H3 속성 후속 질문

"스토리지 계정 X의 SKU는 무엇인가"와 같은 질문은 지금의 형식이 담을 수 없는 속성을 묻습니다.

- **형식:** 닫힌 언급 도메인 `property`와 측정 종류 `property`를 추가합니다. 속성 언급은 주어
  ObjectType의 읽을 수 있는 속성 가운데 `rule-catalog/vocabulary/property-semantics.yaml`에 검토된
  Property 의미가 있거나 선언된 값 도메인이 있는 속성에 대해 닫힌 선택으로 근거화됩니다. 의미 ID와
  제공자 경로는 레이블일 뿐 조회 키가 아닙니다.
- **컴파일:** 측정값이 `property`인 `lookup`은 앵커를 읽고 그 속성을 투영합니다. principal이 읽을 수
  없거나 검토된 의미가 없는 속성은 타입이 지정된 지원되지 않음 이유를 돌려주며, 원시 제공자 필드를
  내보내지 않습니다.
- **검증:** V-PROV는 측정값의 바인딩에서 온 속성만 받고, V-SEM은 앵커 읽기에 그 투영을 요구합니다.
- **답변:** 값에는 출처, 관측 시각, 신선도를 함께 밝힙니다. 오래되었거나 없는 값은
  `UNKNOWN_INCOMPLETE`입니다.

**구현 메모(2026-10-01):** 매니페스트는 검토된 Property 의미마다 리소스 유형별 제공자 경로 하나를
담습니다. 매니페스트 다이제스트가 이 읽기 정보를 묶으며, principal이 Resource 제공자 속성 묶음을 읽을
수 있을 때만 제공됩니다. 한 의미에 검토된 경로가 둘 이상인 리소스 유형은 제외됩니다. 앵커 바인딩은
바인딩된 리소스의 유형을 기록하므로 조회는 그 유형의 검토된 경로만 정확히 투영하고, 구조 검증기는
읽을 수 있는 객체 속성 안쪽의 투영만 허용합니다. 인벤토리는 개별 속성을 관측한 시각을 기록하지
않으므로, 답변은 출처와 그 의미의 검토된 최신성 기준을 밝힙니다. 인벤토리 최신성 상한보다 더 새로운
근거가 필요한 의미는 `property_freshness_unestablished`로 보류됩니다. 없는 값은 알 수 없음으로
밝히며, 목표 상태 `UNKNOWN_INCOMPLETE`는 승격 프로그램의 검증된 답변 작성과 함께 부여됩니다.

**종료 조건:** 이름 붙은 리소스 하나에 대한 속성 조회가 정확한 값으로 답하고, 검토된 의미가 없는
속성은 타입이 지정된 이유와 함께 보류됩니다.

## H4 서수 후속 질문

서수나 지시어는 저장된 핸들(H2)의 행에 바인딩되고, 속성 측정값(H3)이 그 행을 읽을 수 있습니다.
"두 번째 것의 SKU는 무엇인가"는 재인가 뒤 핸들의 두 번째 행에 앵커를 둔 속성 조회가 됩니다.
로컬 H4 구현은 최신 저장 핸들에 대해 "두 번째 것의 상태는 무엇인가" 같은 상태 조회 후속 질문도
다룹니다. 최신 불투명 참조만 로드하고, 현재 기준 시점의 보안 게이트웨이 재조회로 행 키를 다시
매핑하며, 단어만 보고 바인딩하지 않습니다.

**종료 조건:** 추적된 서수 SKU 후속 질문이 정확한 속성 값으로 답합니다.

## H5 변경 이어 읽기

PostgreSQL reader는 파생 관계 안에서 각 Resource의 가장 최근 변경을 고르고(`DISTINCT ON
(subject_ref)`), 하나의 수집 기준 시각(`recorded_at <= known_at`)에 고정합니다. 그런 다음 그 관계를
`effective_at` 내림차순, `subject_ref` 오름차순으로 정렬합니다. 이어 읽기는 Resource마다 가장 최근
변경을 고른 뒤 바깥 조회에서만 탐색하므로, Resource의 이전 관측이 다시 나타나지 않습니다.

```text
WHERE effective_at < :last_effective_at
   OR (effective_at = :last_effective_at AND subject_ref > :last_subject_ref)
```

- 남은 개수는 같은 기준 시각의 같은 파생 관계에서 세며, 답변은 마지막 페이지에서만 완전하다고
  밝힙니다.
- 구현은 원시 탐색 키를 Core 소유 이어 읽기 상태에만 저장합니다. 결정 이벤트와 Operator 트래픽은
  불투명 참조와 다이제스트만 전달합니다.
- Core는 이어 읽기 상태를 저장합니다. 상태에는 배포 범위, principal 다이제스트, 대화, 목적, 수용된
  목표와 계획 다이제스트, 매니페스트 다이제스트, 조회 버전 다이제스트, 기간, 기준 시각, 정렬, 커서,
  페이지 크기, `expires_at`이 들어갑니다. 클라이언트는 불투명 참조만 갖습니다.
- 모든 페이지를 다시 인가합니다. 결속된 필드가 하나라도 다르거나 만료되면 타입이 지정된
  `continuation_invalid`를 돌려주며, 조용히 다른 집합을 읽지 않습니다.
- 실제 loopback PostgreSQL 테스트는 Resource마다 여러 관측, 같은 시각의 동점, 기준 시각 뒤에 기록된
  행, 바뀐 페이지 크기를 다룹니다.

**종료 조건:** 변경이 20개를 넘는 24시간 기간의 모든 변경을 이어 읽기에 걸쳐 정확한 집계와 함께
나열합니다.

## H6 연속 관계 계획

`all_kinds` 관계가 의도 그래프 하나의 한도인 노드 32개와 출력 8개보다 많은 side를 필요로 하면,
컴파일러는 검토된 side를 순서 있는 묶음으로 나눕니다. 첫 묶음이 앵커 식별자와 원본 세대를 고정합니다.
이후 묶음은 각각 독립적으로 검증된 계획입니다. 그 이어 읽기에는 행 개수 대신 `remaining_batches`, 다음
묶음 서술자, 이미 나열한 엔드포인트의 다이제스트를 기록합니다. 뒤의 묶음은 아직 실행되지 않았기
때문입니다. 답변은 도달한 각 엔드포인트를 LinkType과 함께 나열하고 남은 묶음 수를 밝힙니다. 세대가
바뀌면 지금의 shadow 실행기처럼 이어 읽기를 불완전으로 끝냅니다.
로컬 구현은 promotion이 실제 답변 동작을 연결할 때까지 이를 shadow 경로의 기본 비활성 상태로 유지합니다.

**종료 조건:** 추적된 연결 리소스 질문이 연속 계획에 걸쳐 도달한 모든 엔드포인트를 LinkType과 함께
나열합니다.

## 안전과 권한

- 모든 패키지는 읽기 전용입니다. 핸들이나 이어 읽기는 실행, 승인, 더 넓은 읽기 권한을 주지 않으며,
  모든 행은 다시 읽을 때 재인가됩니다.
- 결정 이벤트에는 다이제스트와 개수만 담고, 행 식별자, 이름, 스냅숏 값은 담지 않습니다.
- 바인딩할 수 없는 참조는 상위 설계가 요구하는 대로, 새 핸들로 바뀔 수 없는 확인을 모두 마친 뒤에
  타입이 지정된 명확화 요청 하나를 돌려줍니다.

## 승인이 필요한 결정

1. Core가 핸들 본문을 저장하고 Operator는 지속되는 턴과 함께 불투명 참조만 저장합니다(제안). 이는
   Operator가 핸들을 저장한다는 상위 설계의 표현을 바꿉니다. 대안은 Core가 봉인한 봉투를 Operator가
   저장하고 그대로 돌려주는 방식입니다.
2. 핸들과 스냅숏의 보존은 대화의 보존과 삭제를 따르되, 호환성 기간을 넘지 않습니다(제안).
3. 이어 읽기는 15분 뒤 만료됩니다(제안).
4. 속성 후속 질문은 읽을 수 있는 모든 속성이 아니라, 검토된 Property 의미나 선언된 값 도메인이 있는
   속성만 읽습니다(제안).

## 비평과 수정

초안에 대한 독립 비평에서 다음 문제가 나왔습니다. 이 설계는 각 수정을 반영합니다.

| 발견 사항 | 수정 |
|-----------|------|
| 핸들 소유권이 모순되었습니다. Operator가 저장한 본문을 Core가 다시 읽을 수 없었고 배포 범위도 결속하지 않았습니다 | Core가 암호화되고 범위로 분할된 본문을 소유하고 Operator는 불투명 참조를 저장하며, 결정 1에서 승인을 요청합니다 |
| 이어 읽기가 대화, 목적, 조회 의미, 버전에 결속되지 않았고, 묶음 이어 읽기가 행 개수를 재사용했습니다 | Core에 저장한 상태가 모든 필드를 결속하고 페이지마다 재인가하며, 묶음은 `remaining_batches`와 나열한 엔드포인트 다이제스트를 씁니다 |
| keyset 탐색이 불충분하게 정의되어 이전 관측이 다시 나타날 수 있었습니다 | Resource마다 가장 최근 변경을 고른 뒤에만 서로 다른 방향의 조건식으로 탐색하고 PostgreSQL 테스트를 둡니다 |
| N/N-1 코덱만으로는 저장된 레코드가 롤아웃에 안전하지 않았습니다 | 쓰기 버전 협상, 타입이 지정된 거부, 호환성 기간 안의 수명, 롤백 테스트 |
| 연결된 원장이 없었습니다 | 원장이 있으며 이 문서의 남은 작업을 담당합니다 |
