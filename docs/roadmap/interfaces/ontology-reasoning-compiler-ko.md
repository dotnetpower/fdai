# 온톨로지 추론 컴파일러

이 문서는 운영자 질문을 닫힌 타입과 원문 구간에 근거한 질문 논리 형식으로 바꾸고, 그 형식을
결정론적으로 검증된 온톨로지 조회 계획으로 컴파일하는 목표 설계를 담당합니다. 모델은 질문을
이해하고, 개념을 전체 카탈로그에서 고르고, 답변 문장을 씁니다. 코드는 그 의미를 검증하고, 앵커를
바인딩하고, 검토된 경로를 고르고, 보여 주는 모든 주장을 검증합니다.

> **상태:** 2026-09-28에 승인된 설계입니다. 일부 연산만 다루는 초기 부분 shadow 구현이 있으며, 운영
> 턴에는 연결되지 않았습니다. 구현 범위, 측정된 커버리지, 편차는
> [원장](../../roadmap-implementation/interfaces/ontology-reasoning-compiler.md)에 기록합니다. 현재 런타임은 [계층형 대화 계획](hierarchical-conversation-planning-ko.md)과
> [온톨로지 조회 커버리지 구현 계획](ontology-query-coverage-implementation-plan-ko.md)에 설명되어 있습니다.
> 커버리지 목표와 측정된 한도는 [온톨로지 추론 커버리지](ontology-reasoning-coverage-ko.md)가 담당합니다.
>
> **권한 경계:** 논리 형식, 수용 증적과 컴파일 증적, 앵커 바인딩, 결과 핸들, 계획은 모두
> `execution_authority=false`인 읽기 전용 기록입니다. 명시적인 변경 요청은 여전히 기존의 타입이
> 지정된 액션 초안만 만듭니다.

## 설계 개요

| 단계 | 책임 에이전트 | 출력 | 모델 사용 |
|------|---------------|------|-----------|
| 1. 대화 사전 판별 | Bragi | 사교, 지식, 운영 경로 선택 | T1, 변경 없음 |
| 2. 논리 형식 판단 | Bragi | 제안된 `SemanticQuestionForm` | T1, 한 번 호출과 최대 한 번의 스키마 복구 |
| 3. 수용 | Bragi | 수용된 형식, 명확화 또는 검토 요청 | 선택적 T2 검토 |
| 3a. 제약 검토 | Bragi | 수용된 형식과 비교하는 블라인드 제약 추출 | 다른 모델 계열의 T1, 판단과 나란히 호출 한 번 |
| 4. 개념 근거화 | Mimir 카탈로그를 쓰는 Bragi | 언급마다 영역 전체 카탈로그에서 고른 정규 개념 하나 | 빠짐없는 카탈로그 조각에 대한 T1 |
| 5. 앵커 바인딩 | Muninn | 하나의 스냅샷에 고정된 정확한 식별자 | 없음, 범위가 제한된 읽기 1회 |
| 6. 컴파일과 검증 | Bragi 턴, 기계적 구성 요소 | 계획, 참고용 커버리지 증명, 독립적인 커버리지 검사 | 없음 |
| 7. 실행 | Muninn과 Heimdall 읽기 구성 요소 | 증적, 테이블, 계보, 완전성 | 없음 |
| 8. 답변 작성 | Bragi | 근거에 묶인 주장, 목표별 상태, 이중 언어 답변 | T1 작성, V-CLAIM, 독립 T1 검토 |

컴파일러와 검증기는 Bragi가 소유한 의미 턴 안의 기계적인 Core 구성 요소입니다. 변경 불가능한
변환 결과를 소비하고, 에이전트를 호출하지 않으며, 아무것도 발행하지 않고, 턴 감사 기록은 Saga가
유지합니다. 지원되는 형식은 기능 이름 기반 의도와 모델이 작성한 프레임과 계획을 대체하며, 지원되지
않는 형식은 가장 가까운 기능 대신 빠진 원자와 이유를 정확히 반환합니다.

## 검증된 기준선

검토에서는 [`semantic_planning.py`](../../../services/core-control-plane/src/fdai/core/conversation/semantic_planning.py)의
`SemanticPlanningService.plan`부터 [`semantic_turn_processor.py`](../../../services/core-control-plane/src/fdai_core_service/semantic_turn_processor.py)의
렌더링까지 한 턴을 추적했습니다.

| 단계 | 현재 추론이 일어나는 곳 | 미비점 |
|------|-------------------------|--------|
| 사전 판별 | T1이 닫힌 운영 계열 9개 또는 `none` 중 하나를 고름 | 관계, 집계, 인식 축이 없어 관계 질문이 목록 또는 현재 상태 계열로 승격될 수 있음 |
| 판단 | T1이 FunctionType 이름을 `primary_intent`로 고르고, 대상 종류와 facet은 자유 토큰임 | FunctionType 이름 밖의 의미를 담을 타입이 없고, `resource_group` 같은 인스턴스 종류를 모델이 추측함 |
| 프레임 | 결정론적 빌더 22개, 없으면 T1 프레임 모델 | `SemanticProblemFrame`에 앵커, 관계, 방향, 집계, 이전 결과 필드가 없음 |
| 계획 | 형태별 컴파일러 32개, 없으면 T1 계획 모델 | 컴파일러가 정규식으로 발화에서 식별자와 구간을 다시 뽑고, 계획 모델은 레시피를 채우며 피연산자를 지어낼 수 있음 |
| 검증기 | 정확한 매니페스트, 끝점 연쇄, 한도, 형태와 노드 정렬 | 의미 보존, 피연산자 출처, 인스턴스와 스키마 구분 검사가 없음 |
| 실행 | 범위가 제한된 보안 ObjectSet, 단일 루트 탐색, 단계별 타입 경로 | 탐색 행에 루트 계보가 없고 링크 근거 속성은 가려짐 |
| 답변 | 형태별 템플릿, 불완전한 증적이 하나라도 있으면 턴 전체를 보류함 | 목표별 인식 상태가 없고, 후속 질문 맥락은 이전 턴 텍스트뿐임 |

2026-09-28에 영어와 한국어 추론 사례 36개로 두 번 실행한 범위가 제한된 실시간 계획 탐침은 관리되는
증적이 아니라 세션 안에서만 쓴 설계 입력이며, 실행마다 6개 사례만 질문대로 답했습니다. 14개에서
16개 사례는 다른 질문에 대한 검증된 계획을 만들었습니다. 이웃 대신 앵커 자신, 인스턴스 질문에 대한
스키마 관계, 뒤집힌 포함 방향, 이름 조각으로 읽힌 리전, 모두 0인 인시던트 식별자가 그 예입니다. 두
실행에서 같은 결과는 23개뿐이었습니다. 로컬 그래프에는 탐침한 앵커의 검증된 링크가 이미 있었으므로
관계 질문 실패는 대부분 컴파일러와 계약의 미비점이며, 측정된 데이터와 용량 한도는
[온톨로지 추론 커버리지](ontology-reasoning-coverage-ko.md#측정된-기준선)에 기록되어 있습니다.

## 질문 논리 형식

`SemanticQuestionForm` 버전 `1.0.0`은 `SemanticJudgmentProposal` 스키마 `1.4.0`의 추가 필드
`question_form`으로 전달됩니다. 모든 필드는 닫힌 열거형, 범위가 제한된 정수, 언급 참조, 또는 인용한
구절과 그 출현 순번 중 하나이며, Core가 인용을 정확한 원문 구간에 결속합니다. 모델은 FunctionType,
LinkType, ObjectType 피연산자, 인스턴스 값을 절대 제공하지 않습니다.

| 필드 | 닫힌 값 |
|------|---------|
| `mentions[].form` | `identifier`, `name`, `concept`, `value`, `anaphor`, `ordinal` |
| `mentions[].domain` | `instance`, `object_type`, `resource_type`, `resource_class`, `state`, `health`, `metric`, `region`, `declaration_kind` |
| `mentions[].qualifier` | 앞선 언급 식별자 하나와 관계 의미, 예를 들어 이름이 지정된 네트워크 안의 서브넷 이름 |
| `goals[].level` | `instance`, `schema` |
| `goals[].operation` | `select`, `count`, `lookup`, `traverse`, `path`, `aggregate`, `rank`, `history`, `compare_windows`, `compare_entities`, `diff_versions`, `impact`, `explain_cause`, `verify_evidence`, `describe_schema`, `diagnose`, `draft_action` |
| `goals[].subject_scope` | `anchor`, `collection`, `prior_result`, `goal_output` |
| `filters[].role` | `type`, `state`, `health`, `region`, `name_fragment`, `scope` |
| `relation.sense` | `containment`, `attachment`, `dependency`, `connectivity`, `traffic`, `classification`, `composition`, `ownership`, `authorization`, `evidence` |
| `relation.scope` | `one_sense`, `all_kinds` |
| `relation.anchor` | 관계가 시작되는 언급이며, 목표 주체가 앵커이면 생략 |
| `relation.anchor_role`, `relation.result_role` | 관계 의미의 양 끝, 예를 들어 `container`와 `member`, `dependent`와 `dependency`이며, 방향이 없으면 둘 다 `either` |
| `relation.reach` | `one_hop`, `transitive` |
| `relation.reach_cue` | 관계 단어와 떨어진 도달 범위 단어의 선택적 인용 |
| `measure.kind` | `count`, `state`, `health`, `metric`, `change`, `event`, `forecast`, `cost` |
| `measure.group_by` | `endpoint`, `type`, `container`, `none` |
| `time.kind` | `current`, `window`, `as_of`, `two_windows`, `versions`, `future`, `unspecified` |
| `want` | `fact`, `cause`, `verification`, `completeness` |
| `filters[].cue`, `measure.cue` | 제한, 측정값, 묶음 기준을 나타내는 단어의 선택적 인용 |
| `context` | 제약을 나타내지 않는 단어의 인용, 최대 32개 |
| `unsupported_constraints` | 닫힌 필드로 표현할 수 없는 제약을 나타내는 단어의 인용, 최대 8개이며 하나라도 있으면 명확화 |

판단 한 번에는 6 KiB 안에서 언급 최대 16개와 목표 최대 4개가 들어갑니다. 목표마다 신뢰도와 연산
및 관계의 단서 구간이 있고, 목표는 앞선 목표에 의존할 수 있습니다. 더 큰 질문은 모든 목표가 집계될
때까지 판단을 여러 번 이어서 합니다. 모호성은 대안 최대 세 개로 표현하며, 각 대안은 원자 차이 최대
6개로만 적고 하나로 합친 형식은 쓰지 않습니다.

예: `Which resources depend on aks-prod-01?`

```yaml
question_form:
  mentions: [{id: m1, form: name, domain: instance, span: {text: aks-prod-01, occurrence: 1}}]
  goals:
    - {id: g1, level: instance, operation: traverse, subject: m1, subject_scope: anchor,
       relation: {sense: dependency, anchor_role: dependency, result_role: dependent,
                  cue: {text: depend on, occurrence: 1}}, confidence: 0.93}
```

모델은 `aks-prod-01`이 의존 대상이고 결과가 그것에 의존하는 리소스라고만 말합니다. Core는 앵커를
바인딩하고, `dependency` 특성으로 `depends_on`을 고르고, `incoming` 방향을 읽습니다.

## 수용

Bragi는 모든 구간이 더 긴 식별자를 자르지 않고 발화와 일치하고, 모든 목표가 신뢰도 하한을 넘고, 남은
대안이 없고, 관계의 두 역할이 한 의미의 양 끝이고, 선언된 모든 언급이 쓰이고, 두 언급이 같은 단어를
나누지 않고, 어떤 그룹도 한 목표의 범위이면서 관계 앵커가 아니고(그 그룹에서 구성원으로 가는 포함 관계는
범위의 전체 구성원을 다시 말할 뿐이므로 예외이며, 그 전체 구성원으로 읽습니다), 모든 한정자가 이름이 지정된 인스턴스 하나를
이름이 지정된 다른 인스턴스 안에 두고, 수준이 모든 언급 영역과 맞을 때만 형식을 수용합니다. 조회, 이력, 원인 목표에서 이름이 지정된 자기 주어를 앵커로 삼는 관계는 aks-app 안의 작업처럼
그 주어를 다시 말할 뿐이고, 영향 목표에 밝힌 장애 상태는 그 전제를 다시 말할 뿐이므로 둘 다 읽지 않는 원자가
아닙니다. 결과의 종류,
상태, 컨테이너를 한정자로 밝힌 형식은 구조 결함이며, 이를 필터나 목표의 관계로 다시 쓰게 하는 수리를 한 번
받습니다. 다만 한정자가 목표 주어에 있고 그 목표 자체의 필터를 가리키면(예: running 필터가 있는 running VMs)
필터가 그 내용을 읽으므로, 한정자는 필터를 다시 말할 뿐 아무것도 빠뜨리지 않습니다. 그렇지 않으면 명확화 하나를 반환하거나 신뢰도가 낮은 필드를 닫힌 필드만 비교하는 독립적인 T2
검토 한 번에 보냅니다. 한정자나 밝힌 상대편처럼 검토된 빌더가 읽지 않는 수용된 원자는 타입이 지정된 미지원
사유를 반환하며, 절대 무시하지 않습니다.

**발화 구간 회계**: 발화의 모든 문자, 숫자, 수학 기호, 통화 기호는 언급, 목표·필터·관계·시간·측정값
단서, 문맥 인용, 지원되지 않는 제약 중 하나 안에 있어야 합니다. Core는 이를 유니코드 범주로만 확인하며
단어의 의미를 분류하지 않습니다. 이런 문자를 하나라도 빠뜨린 형식은 유효하지 않으며, 한 번의 복구 요청이
빠진 단어를 알려 주고 식별자는 가립니다. 인용이 일부만 담은 단어는 단어 전체와 함께 인용되지 않은 문자의
자리를, 예를 들어 마지막 문자처럼 알려 주므로, 이름의 조각만 따로 인용하는 일은 없습니다. 단어가 제약을
나타내는지는 모델이 판단하므로, 단어를 문맥으로 분류하는 것은 모델의 명시적 판단이며 블라인드 제약 검토가 이를
확인합니다. `remaining_goals`를 설정한 판단은 확인을 마지막 판단으로 미루며, 마지막 판단은 앞서
수용된 판단의 언급과 단서에는 기댈 수 있지만 문맥에는 기대지 않습니다. 마지막 판단이 수용되기 전에는 어떤
컴파일도 내보내지 않습니다. 빠진 단어를 채우는 복구는 언급, 목표, 필터, 단서 범위, 문맥, 기본값으로 남은
값을 더할 수만 있고, 이미 밝힌 값을 바꾸거나 없애지 않습니다. 그 복구 뒤에도 남은 단어는 블라인드 제약
검토에 맡깁니다. 회계는 제안 모델이 모든 단어를 살피게 할 뿐이고, 단어가 제약을 나타내는지는 검토가 판단하기
때문입니다. 그 복구가 인용을 빼고는 모든 목표를 제안과 똑같이 읽었지만 배치가 바꿀 수 없는 인용을 바꿨다면,
제안은 원래대로 남고 배치되지 않은 단어는 같은 검토에 맡깁니다. 목록을 개수로 읽는 것처럼 목표를 다르게
읽거나 파싱되지 않는 복구는 경쟁하거나 빠진 해석이므로 턴을 보류합니다. 검토 복구가 배치하지 않은 단어는 그
형식을 다시 읽는 검토에 맡깁니다. 인스턴스 이름이나 식별자에 같은 단어로 붙은 조사는 그 언급과 함께
회계하며, 어떤 복구도 그런 언급의 인용을 바꾸지 못합니다. 그 인용은 정확한 조회 키여서, 넓힌 인용은 다른
이름을 조회하기 때문입니다. 조사가 나타내는 제한은 여전히 검토가 판단합니다. 끝까지처럼 관계 단어와 떨어진
도달 범위 단어는 관계의 `reach_cue`에 인용합니다.

**블라인드 제약 검토**: 다른 모델 계열의 두 번째 T1 호출이 판단 호출과 나란히 질문만 읽고, 모든
제약을 닫힌 역할과 함께 추출합니다. Core는 두 출력을 구조적으로 비교합니다. 추출한 제약의 모든 문자와
숫자는 의미를 나타내는 구간 안에 있어야 하고 목표 단서나 문맥만으로는 안 되며, 이름이 붙은 대상은 언급과
겹쳐야 합니다. 언급 뒤에 붙은 조사는 공백으로 구분한 같은 단어 안에서 그 언급에 속합니다. 다만 추출기가
그런 조사 안에서 따로 떼어 낸 제한, 부정, 비교, 순서, 시간은, 예를 들어 만처럼, 그 언급이 나타낸
것으로 보지 않습니다. 닫힌 필드로는 not이나 만 같은 제외를 나타낼 수 없고, 순위나 비교는 순위 또는 비교
목표만 나타낼 수 있으므로, 부정, 비교, 순서는 지원되지 않는 제약이나 그 목표의 단서에 닿아야 하며, 그
복구는 모든 단서를 그대로 둔 채 지원되지 않는 제약을 더합니다. 모든이나 전부처럼 전체만 뜻하는 단어는 별도의
역할인 quantifies를 가지며, 요청 단어처럼 덮어야 할 제한을 나타내지 않습니다. 그 역할이 없을 때
추출기는 이런 단어를 제외로 분류했습니다. 그 밖의 역할은 참고로만 쓰는데, 두 판독자가 어떤 단어가 제한인지
관계인지에 대해 합리적으로 다르게 볼 수 있기 때문입니다. 다만 가정 전제는 영향 목표만 나타낼 수 있습니다.
언급 하나는 개념이나 식별자 하나에 바인딩되므로, 언급 하나가 추출된 제한과 겹치지 않는 다른 추출 제약을 함께
담으면 안 됩니다. 예를 들어 언급 하나가 `AKS ObjectTypes`를 인용하면 바인딩이 둘 중 하나만
남기고 다른 하나를 버립니다. ObjectType이나 선언 종류 언급은 닫힌 이름 하나에 바인딩되므로, 역할과
관계없이 겹치지 않는 두 번째 추출 제약을 담을 수 없습니다. 실제 실행에서 `Resource
ObjectType`은 ResourceType ObjectType에 바인딩되었고, 선언 종류로 바인딩된
`Workload ObjectType`은 모든 ObjectType을 나열했으므로, 종류 단어는 별도의 선언 종류
언급으로 둡니다. the second one의 second처럼 참조의 순서 단어는 타입이 지정된
position이므로, 참조는 합쳐진 언급이 되지 않습니다. 추출기는 각 리터럴 값도 주변 단어나 조사 없이
따로 인용합니다. 이름 조각 필터가 읽는 언급인 리터럴 피연산자는 그대로 쓰이므로, 그 인용은 추출기가 인용한
리터럴 중 하나와 같아야 합니다. 그렇지 않으면 턴을 보류하며, 리터럴이 어디서 끝나는지를 한 판독자만 정하지
않습니다. 덮이지 않은 제약은 정보를 더하기만 하는 검토 복구를 한 번 받고, 같은 추출과 다시 비교합니다. 그
위반 메시지는 제약의 일부만 인용한 언급을 알려 주며, 리터럴 피연산자의 인용은 그대로 유지해야 하므로 나머지
단어는 그 언급을 가리키는 단서에 둡니다. 같은 복구는 [검토와 보류 개선](#검토와-보류-개선)에서 설명하듯
합쳐진 언급을 추출기가 따로 인용한 부분별로 나눌 수 있으며, 일치하지 않는 리터럴은 복구로 옮길 수 없으므로 복구
없이 보류합니다. 추출이 없거나, 비어 있거나, 위치를 찾을 수 없거나, 덮이지
않은 제약이나 합쳐진 언급, 일치하지 않는 리터럴이 남으면 아무것도 내보내지 않습니다. 모든 질문은 적어도 무엇을
묻는지는 밝히고 모든 인용은 질문에서만 가져오므로, 앞선 턴과 함께 만든 추출이 비어 있으면 앞선 턴 없이 한 번 더
묻습니다. 실제 추적에서 긴 답변이 몇 번 이어진 뒤 단독 질문에 대해 추출기가 아무것도 반환하지 않은 사례가 있었습니다.

**방향 확인**: 방향이 뒤집힌 관계는 정반대 질문에 답하며, 열린 추출은 관계의 시작점을 너무 드물게 밝혀
이를 잡지 못했습니다. 충실한 검토 뒤에, 관계에 방향이 있는 각 목표는 either로 밝힌 경우가 아니면 추론
모델에 집중된 호출 한 번을 받습니다. 방향은 문법에 달려 있기 때문입니다. 일곱 개 질문을 두 번씩 물었을 때
추론 모델은 모든 방향을 맞게 읽었지만, 작은 모델들은 한국어 목적어 절을 제안 모델과 같은 방식으로 잘못
읽었습니다. 판독자는 가린 질문, 이름이 밝혀진 시작점, 의미, 그 의미의 두 역할을 선언된 순서대로 볼 뿐
제안 모델이 고른 역할은 보지 않으며, first, second, either, unclear 중 하나로
답합니다. Core는 그 답을 형식과 비교합니다. 다른 역할, unclear나 빠진 답, 상호적인
LinkType이 없는 의미에 대한 either는 턴을 보류합니다. 상호적인 LinkType이 있는 의미에 대한
either는 그 LinkType을 어차피 양쪽 모두 읽으므로 받아들입니다.

닫힌 스키마나 구조 규칙을 어긴 형식은 코드가 작성한 위반 목록과 함께 복구 호출을 최대 한 번 받습니다. 각
위반은 필터가 받아들이는 언급 영역처럼 형식이 어긴 계약 규칙을 밝히고, 회계되지 않은 구간은 인용해서 보여
주며, 어떤 위반도 질문의 단어를 해석하지 않습니다. 언급 ID는 이름표일 뿐이므로, 복구된 형식을 제안과
비교하기 전에 앞선 각 언급의 ID를 형식과 영역이 같고 인용이 앞선 인용을 담는 단 하나의 복구된 언급에
돌려주며, 모든 참조도 함께 바꿉니다. 그런 상대가 정확히 하나가 아닌 앞선 언급이 있으면 ID는 쓰인 그대로
둡니다. 복구된 형식은 같은 수용 검사를 통과해야 하고, 거부된 제안이 밝힌 인용 피연산자, 목표, 연산,
`want`, 타입 시간, 피연산자를 가진 관계, 경쟁 해석, 남은 목표 신호를 모두 유지해야 합니다. 그렇지
않으면 원래 위반이 그대로 남습니다. 다만 회계만 어긴 경우는 앞에서 설명한 대로 검토에 맡깁니다. 이 필드들은
닫힌 스키마가 정규화한 값으로 비교합니다. 파싱되지 않은 제안은 명시적인 false나 null이 아닌 남은 목표
값을 모두 대기 중으로 보고, 목표 목록 누락, 잘못된 컨테이너, 중복된 목표 ID, 읽을 수 없는 연산이나
`want`처럼 비교하는 필드가 닫힌 형태를 잃으면 복구를 거부합니다. 파싱된 제안에서 어떤 목표도 인용하지
않고 타입 시간 단서를 정확히 인용한 언급만 복구된 언급 대신 복구된 시간 단서 안에 남을 수 있습니다.
명확화는 운영자에게 하는 답이므로 복구하지 않습니다.

수용은 모델 권한을 제한할 뿐 없애지 않습니다. 틀렸지만 자기모순이 없는 형식은 단서 구간 검토, T2
검토, [보정된 수용](ontology-reasoning-coverage-ko.md#보정된-수용)의 해석 재진술과 확인 우선 칸, 평가
정답으로만 잡힙니다. 모델은 식별자, LinkType, 경로 단계, FunctionType, 답변 주장을 고르지 않습니다.

## 결정론적 컴파일

### 개념 선택

모델은 지시어가 아닌 각 언급을 선언된 영역 안에서 근거화합니다. Core는 전체 후보 카탈로그를 검토된
이름과 함께 예산에 맞는 만큼의 조각으로 나누어 제시하고, 모델은 모든 조각을 평가하며, 증적은 모든
후보가 정확히 한 번 제시되었음을 증명합니다. Core는 그 후보를 제시한 조각에서 나온 식별자만
받아들입니다. 조각마다 다른 최종 후보는 결선 호출 한 번에서 함께 비교합니다. 이름은 모델이 보는
맥락일 뿐 조회 표가 아니며, 명시적인 루트 후보가 리소스 전체를 뜻합니다. ObjectType 후보의 이름 뒤에는
검토된 설명이 붙으므로, 선택자는 Resource와 ResourceType을 이름이 아니라 의미로 구분할 수 있습니다.
FunctionType과 ActionType은 연산에서 따라 나옵니다.

- **클래스 폐포**: `resource_class` 언급은 `query.resource_class_closure`를 거쳐 정확한
  `Resource.type` 집합으로 컴파일되고 폐포 증적을 고정합니다.
- **영역 간 일치**: 스키마 수준에서 `AKS ObjectType`은 영역을 `object_type`으로
  선언하지만, 모델은 `AKS`를 `Resource.type` 후보 중
  `kubernetes-cluster`로만 찾습니다. Core는 다른 선언으로 바꾸지 않고 그 후보를 알려
  주는 명확화를 반환합니다.
- **형제 종류 근거화**: 제안 모델은 ObjectType과 리소스 유형을 양쪽 방향으로 혼동하며, 관련
  없는 프롬프트 문구에도 선택이 뒤집힙니다. 인용하는 모든 목표가 두 종류 모두 컴파일되는 인스턴스 수준
  컬렉션 주어로만 쓰는 개념은 먼저 밝힌 카탈로그에서 근거화합니다. 두 선택자가 거기서 아무것도 찾지 못하면
  둘 다 형제 종류 카탈로그에서 다시 고르고, 둘 다 고른 의미가 언급의 영역을 정합니다. 밝힌 카탈로그에서
  선택이 엇갈렸고 형제 카탈로그에서는 일치하면, 두 선택자가 엇갈린 최종 후보와 그 의미를 함께 한 번 보고,
  둘이 같은 의미를 고를 때만 바인딩합니다. 종류를 바꾼 형식은 수용 검사를 다시 거쳐 이후의 모든 단계와
  기록에서 제안을 대신합니다. 비평은 ObjectType과 리소스 루트를 같은 의미로 보는 방안을
  기각했습니다. 둘은 유형 필터, 관계 끝, 스키마 주어로서 다르게 동작하기 때문입니다. 어느 단계가 밝힌
  형식을 계속 읽게 되는 종류 변경도 기각했습니다.
- **모호성**: 한 영역 안에 후보 두 개가 남으면 둘 다 알려 주는 명확화 하나를 반환합니다.
- **블라인드 선택자 두 개**: 제안 모델과 추출 모델의 서로 다른 모델 계열 선택자 두 개가 각자
  모든 조각을 보고, 상대의 선택을 보지 않은 채 각자의 결선을 치릅니다. 두 선택자가 같은 값에
  이를 때만 바인딩이 유지되므로 그룹과 그 유형은 일치로 봅니다. 그 밖의 답은, 리소스 전체와
  정확한 유형 하나가 맞서는 경우를 포함해 `concept_disagreement`로 명확화합니다. 두 번째 모델
  계열이 없으면 아무것도 바인딩되지 않습니다. 각 선택자는 제시된 언급 ID, 후보 ID, 조각 다이제스트로
  닫힌 스키마로만 답하므로 텍스트 답이나 지어낸 식별자는 파싱되지 않습니다. 검토된 조각의 비밀·식별자
  검사는 선택자, 조각, 재시도마다가 아니라 조각 다이제스트마다 한 번만 실행하므로, 완전한 카탈로그를
  제시해도 이벤트 루프를 막지 않습니다.

### 앵커 바인딩

영역이 `instance`인 `identifier` 또는 `name` 언급은 앵커가 됩니다. 바인딩은 두 단계 프로토콜입니다.

1. 수용과 매니페스트, 목적, 범위 검사가 끝나면 Core는 단일 노드 해석 계획을 검증합니다. 조건은 정확한
   `id` 일치 또는 저장소에서 대소문자를 구분하지 않는 `name` 일치, principal 범위, 현재 그래프 기준
   시점, 행 7개 한도입니다. 대소문자만 다른 이름은 모호한 것으로 봅니다.
2. 실행기는 스냅샷 하나를 읽습니다. 바인딩 증적은 원본 세대, 객체 리비전, 기준 시점, release,
   매니페스트, 범위 다이제스트를 고정합니다.
3. 컴파일된 계획은 그 증적 다이제스트를 참조하고 정확한 `root_ids` 또는 `object_ids`를 써야 합니다.
   실행기는 활성 원본 세대가 고정된 세대와 같은지 확인합니다. 세대가 바뀌면 기록되는 재바인딩과
   재컴파일을 한 번 허용하고, 그 뒤에는 보류합니다.

| 결과 | 처리 |
|------|------|
| 객체 1개 | 정확한 식별자와 바인딩된 ObjectType, `Resource.type`으로 컴파일 |
| 객체 2개에서 6개 | 범위가 제한된 후보를 담은 명확화 하나 |
| 객체 7개 | 이름을 좁혀 달라고 요청하는 불완전 명확화 |
| 없음, 원본 완전 | 검증된 범위 안의 부재와 범위가 제한된 이름 제안 |
| 없음, 원본 불완전 | 타입이 지정된 완전성 사유와 함께 보류 |

모델은 인스턴스를 리소스 그룹이나 클러스터로 분류하지 않으며, 바인딩된 타입이 그 추측을
대신합니다. `qualifier`가 있는 언급은 한정자를 먼저 바인딩한 뒤 그 한정자의 포함 범위나 타입 범위
안에서만 찾으므로, 기본 서브넷처럼 공유되는 이름도 정확하게 유지됩니다. 재현은 같은 증적을
해석하거나, 바인딩을 재현할 수 없다고 보고합니다.

### 관계 컴파일

관계 의미는 검토된 `semantic_traits`와 바인딩된 앵커 ObjectType으로 LinkType을
고릅니다. 검토된 의미별 역할 규약이 저장된 각 끝의 역할을 정합니다. 예를 들어 포함 링크의 `from` 끝은
container입니다. 따라서 앵커 역할이 저장된 방향을 바꾸지 않고 `outgoing` 또는
`incoming`을 고릅니다. 밝힌 두 역할이 그 의미의 양 끝이 아니면 명확화를 반환합니다. 피어링처럼
상호적인 LinkType에는 방향이 없으므로, 형식이 밝힌 역할과 상관없이 저장된 양쪽을 모두 읽고,
V-SEM도 이를 다시 도출합니다. `transitive` 도달은 전이적이고 자기 합성이 가능하다고 선언된
LinkType에만 허용되며 깊이는 최대 5입니다.

| 의미 | 특성 | 현재 LinkType |
|------|------|---------------|
| `containment` | containment | `contains` |
| `attachment` | attachment | `attached_to` |
| `dependency` | dependency | `depends_on` |
| `connectivity` | connectivity | `peered_with`, `routes_to`, `kubernetes_exposes_endpoint_slice` |
| `traffic` | traffic | `routes_to`, `runtime_calls` |
| `classification` | classification | `resource_classified_as`, `resource_type_member_of_class` |
| `evidence` | evidence | `kubernetes_backed_by`, `capacity_forecast_targets_resource`, `cost_observation_targets_resource` |
| `composition`, `ownership`, `authorization` | 검토할 특성 대기 | `implemented_by`, `workload_runs_on`, `owns`, `service_owned_by` |

- **매핑되지 않은 링크**: 검토된 특성이 없는 LinkType은 제외하고 `link_sense_unmapped`로 이름을 밝힙니다.
- **경로**: `path` 목표는 `BusinessService implemented_by Workload workload_runs_on Resource` 같은
  검토되고 버전이 지정된 경로 문법만 씁니다. 매니페스트 조회 방향에 대한 오프라인 탐색은 검토할
  문법을 제안할 수 있지만, 런타임이 스스로 최단 경로를 고르지는 않습니다. 적용 가능한 문법이 둘이면
  둘 다 보여 주는 명확화를 반환합니다.
- **모든 종류**: `연결된` 같은 모호한 표현은 [계층형 대화 계획](hierarchical-conversation-planning-ko.md)이
  요구하는 대로 대안 형식과 명확화 하나를 만듭니다. 모든 관계를 명시적으로 요청할 때만
  `scope: all_kinds`를 수용하며, 이 경우 범위가 제한된 1단계 이웃을 읽고 링크를 LinkType 역할별로
  묶어 보여 줄 뿐 하나의 합친 관계로 표현하지 않습니다.
- **실현 가능성**: 컴파일된 방향이 비어 있고 반대 방향에 링크가 있으면 답변은 그 사실을 제한 사항으로
  알리며 방향을 절대 뒤집지 않습니다.

### 연산자

| 연산 | 컴파일 |
|------|--------|
| `select`, `count`, `rank` | 근거에 기반한 타입, 상태, 건강, 이름 조각, 범위 조건식을 가진 ObjectSet 뒤에 정렬과 한도 노드, 인벤토리 전체 개수는 보안 집계 pushdown 사용 |
| `lookup` | 앵커 ObjectSet과, 선언된 출력이 요청한 측정을 포함하는 FunctionType, 바인딩되면 예측과 비용 reader 포함 |
| `traverse` | `root_ids`와 탐색을 가진 ObjectSet, 또는 끝점 타입이 있는 단계에는 `typed_path` |
| `aggregate` | 탐색이나 ObjectSet 뒤에 집계 노드, `endpoint`와 `container` 그룹화에는 행별 루트 계보가 필요 |
| `history` | 앵커에 대한 `query.resource_change_activity`, `query.resource_state_transitions`, `query.resource_event_history` |
| `compare_windows`, `diff_versions` | `topology_at` 노드 두 개와 `topology_diff`, 또는 `query.ontology_release_diff` |
| `compare_entities` | 같은 ObjectType의 앵커 두 개를 하나의 고정 기준 시점에서 같은 측정으로 읽음 |
| `impact` | 앵커에서 역방향 의존과 구성 폐포, 답변은 관측된 영향이 아닌 가능한 영향으로 표시 |
| `explain_cause` | 증상 측정, 이웃의 변경, 인과 지지 또는 반박 근거 |
| `verify_evidence` | 앵커 관계에 대한 링크 근거 변환 결과, 또는 범위 완전성을 위한 `query.ontology_evidence_health` |
| `describe_schema` | `query.manifest`, `query.ontology_declaration`, `query.ontology_relationships`, `query.resource_class_closure` |
| `diagnose` | 바인딩된 `Resource.type`과 증상 개념으로 고른 검토된 레시피 |

- **계약**: FunctionType 선택은 선언된 입력, 출력, `x-fdai-measure-concepts`, 의존성 전용 인자를
  맞춥니다.
- **집계 식별**: 개수는 서로 다른 객체 식별자를 세고, 경로 사이의 중복을 없애고, 숨겨진 객체는 알리지
  않은 채 합계와 연결에서 빼며, 계보나 관계 커버리지가 불완전하면 불완전 상태를 유지합니다.
- **시간**: 모델은 수량과 단위로 된 기간이나 운영자 시간대의 달력 오프셋 같은 타입 시간 값을 원문 구간과
  함께 제안합니다. 코드는 신뢰할 수 있는 UTC 시각을 계산하고, 유효 시간, 이벤트 시간, 기록 시간을
  구분하며, `unspecified`에는 버전이 고정된 기본값을 씁니다.
- **계획 묶음**: 계획 하나의 노드 32개나 출력 8개를 넘는 목표는 턴 예산 하나 안의 순서가 있는 계획
  묶음으로 컴파일되고, 남은 묶음은 검증된 구간을 이어서 보내는 범위가 제한된 후속 실행으로 계속됩니다.
- **지원되지 않는 원자**: `region` 필터는 두 블라인드 선택자가 그 언급을 검토된 리전 어휘의 같은
  코드로 근거화할 때만 `Resource.location` 조건식으로 컴파일되고, 적용 가능한 레시피가 없는 `diagnose`
  목표는 다른 타입의 레시피를 재사용하지 않습니다. 근거화되지 않은 리전과 없는 레시피는 이름 조건식이나
  대체 기능 대신 타입이 지정된 사유를 반환합니다. 한 행의 위치는 하나이므로 여러 리전을 밝히면 하나의
  합집합으로 읽으며, V-SEM은 모든 결과 읽기에 그 조건식을 요구합니다.
- **스키마 읽기**: 스키마 관계에는 주어 ObjectType 자신의 LinkType을 양방향으로 한 단계만 읽는
  `query.ontology_relationships`로만 답하고, manifest 개수는 선언 종류별로만 묶습니다. Workload 안의
  LinkType처럼 ObjectType 하나로 범위를 좁힌 LinkType 주어는 같은 조회이므로 그 ObjectType의 관계
  조회로 컴파일하고, ObjectType으로 범위를 좁힌 다른 선언 종류는 지원하지 않습니다. 그 밖의 스키마
  관계, 방향, 상대편, 도달 범위, 앵커, 묶음 기준은 타입이 지정된 미지원 사유를 반환하며, V-SEM도 이를
  독립적으로 거부합니다.

### 후속 질문 참조

Core는 결정론적 렌더링 뒤에 `ResultSetHandle`을 발급하므로 운영자가 본 결과와 일치합니다. 불투명한
서버 측 핸들은 배포 범위, principal, 대화, 목적, 매니페스트 다이제스트, 만료, 렌더링 순서
다이제스트를 묶고, 타입 행 키, 정렬, 페이지, 잘림 메타데이터를 저장합니다. Operator는 핸들을 영속
턴과 함께 저장하고, 협상된 버전 아래에서 최근 핸들 참조를 최대 4개까지 타입이 지정된 요청 맥락으로
보냅니다. `ordinal` 또는 `anaphor` 언급은 재인가 뒤 핸들 행에 바인딩됩니다. `current_rehydrate`는
정확한 식별자를 현재 기준 시점에 다시 읽고 답변을 현재 상태로 표시하며, `snapshot_reference`는
보존된 스냅샷으로만 답합니다. 핸들이 없거나 만료되었거나, 다른 대화의 것이거나, 삭제되었거나,
범위를 벗어나면 명확화 하나를 반환합니다.

긴 대화 안에서도 독립 질문은 타입 판단이 순서 표현, 지시 표현 또는 명시적인 이전 결과 참조를 인용하지
않는 한 독립 질문으로 남습니다. multi-turn routing은 대화 길이에서 이를 추론하지 않고 참조 바인딩을
증명해야 하며, 동등성 probe는 같은 질문을 새 대화와 20턴 대화 맥락에서 비교하여 독립 답변이 조언이나
모호한 보류로 흔들리지 않게 합니다.

shadow 실행기는 바인딩의 핵심을 구현합니다. `ResultSetHandle`은 표시된 행을 표시된 순서대로 담고, 대화,
principal, 목적, `QueryManifest.manifest_digest`, 시간대가 있는 만료 시각에 묶이며, 중복 없는 행 식별자를
최대 1,000개까지 담고 잘림 여부를 표시합니다. 후속 질문은 가장 최근 핸들에만 바인딩되며, 조건이 맞지 않으면
타입이 지정된 명확화 하나를 반환합니다. 사유는 `prior_result_unavailable`, `_foreign`, `_changed`,
`_expired`, `_empty`, `_out_of_range`이고, 잘린 답변의 끝에서부터 센 순서는 `_ambiguous`입니다. 모델은 순서
표현에 부호가 있는 `position`을 줍니다. 첫 번째는 1이고 마지막은 -1입니다. 수용 단계는 position이 없거나
0인 경우, 다른 형식에 position이 있는 경우, 순서 표현의 십진수 숫자와 position이 다른 경우를 거부합니다.
정확히 한 행을 가리키는 참조, 즉 순서 표현이나 한 행짜리 답변을 가리키는 지시 표현은 자신이 시작하는
조회의 앵커가 됩니다. 관계의 앵커가, 앵커를 밝히지 않았다면 목표 주어가 그 참조 자체인 관계이거나, 조회,
이력, 영향 조회일 때입니다. 탐색 시작점 검사가 그 앵커를 확인합니다. 그 밖의 경우 참조는
컬렉션 조회의 결과나 다른 곳에 앵커가 있는 관계의 결과를, 자신의 행과 정확히 같은 `id in` 조건으로
제한합니다. 지시 표현은 핸들의 모든 행을, 순서 표현은 그 한 행을 씁니다. V-PROV는 그 행에서 온 `id in`
피연산자만 허용하고, V-SEM은 참조가 제한하는 조회가 어느 것인지 형식에서 다시 도출해 각 조회에 그 제한을
요구합니다. 여러 행에서 조회를 시작하지는 않으며, 이 경우
`prior_result_multiple_anchors_unsupported`를 반환하고, 계획 노드 하나에 담기에 너무 큰 제한은
`prior_result_too_large`를 반환합니다. 참조는 새 핸들로도 바뀌지 않는 검사를 모두 마친 뒤에만 명확화를
요청합니다. 잘린 핸들은 지시 표현에
`prior_result_truncated` 제한을 붙입니다. 행은 보안 게이트웨이를 통해 다시 읽으므로 principal이 더는 읽을
수 없는 행은 답변에 들어가지 않으며, 각 단계는 행 식별자 없이 참조 다이제스트를 기록합니다. Operator
영속화, 요청 계약, 렌더링 순서 다이제스트, `snapshot_reference`, 이전 핸들 선택은 R8 작업으로 남습니다.

## 검증과 근거 의미

컴파일러는 `SemanticCoverageProof`를 참고용 증명으로 내보냅니다. 검증기는 이를 신뢰하지 않습니다. 카탈로그의
버전이 지정된 커버리지 규칙 표와 타입이 지정된 노드 출력 계보로 기대 커버리지를 다시 구성하고,
기존 검사는 모두 유지합니다.

- **V-SEM 커버리지**: 모든 연산, 필터, 관계, 측정, 정렬, 시간, 요구 원자는 규칙이 요구하는 노드
  패턴에 대응해야 합니다. 컴파일할 수 없는 제한 원자는 그 목표와 의존 목표를 막으며, 더 넓은 결과로
  낮추지 않습니다.
- **V-SEM 관계**: 탐색의 LinkType과 방향은 바인딩된 앵커 타입과 주체 위치에 대한 규칙 집합과 같아야
  합니다.
- **V-PROV 피연산자**: 모든 식별자나 리터럴 피연산자는 구간, 바인딩 증적, 결과 핸들, 신뢰할 수 있는
  서버 맥락, 서버 기본값 중 하나를 출처로 가져야 합니다. 모두 0인 식별자에는 출처가 없습니다.
- **V-LEVEL**: 인스턴스 목표는 스키마 전용 함수로 해결될 수 없고, 스키마 목표는 인스턴스를 읽을 수
  없습니다.
- **V-WANT**: `cause` 요구는 [시간과 인과에 관한 질문](hierarchical-conversation-planning-ko.md#시간과-인과에-관한-질문)의
  인과 조건을 충족하고 이름이 붙은 대안을 유지해야 합니다. 그렇지 않으면 목표는 시간 거리로만
  제한되고 원인을 주장할 수 없습니다.

각 목표는 [`epistemic_coverage.py`](../../../services/core-control-plane/src/fdai/core/conversation/epistemic_coverage.py)의
`EpistemicStatus` 어휘로 런타임 상태를 받습니다. `VERIFIED_EMPTY`에는 닫힌 모집단 증명, 즉 완전한
원본, 잘림 없음, 컴파일된 LinkType에 대한 완전한 관계 커버리지가 필요합니다. 그 밖의 빈 결과는
`UNKNOWN_INCOMPLETE`이며 검증된 범위 안에 일치 항목이 없다고만 말합니다. 워크로드 매핑이 없으면
비어 있는 것이 아니라 사용할 수 없는 것입니다. 목표 하나가 실패해도 검증된 형제 목표를 숨기지 않고,
답변은 알 수 없는 원자를 모두 나열합니다. 링크 근거는 `verified`, `verification_method`, 권한 주체,
유효 시간, 신선도 한도, 완전성으로 이루어진 검토된 허용 목록을 쓰며, 보이는 링크가 숨겨진 끝점을
드러낼 수 없다는 규칙은 그대로 유지합니다.

## 모델의 역할

| 결정 | 현재 | 목표 |
|------|------|------|
| 질문 의미 | 기능 이름과 자유 facet 토큰 | 단서 구간과 수용 검사를 갖춘 닫힌 논리 형식 |
| 이해의 완전성 | 빠진 제약을 확인하지 않음 | 다른 모델 계열의 블라인드 제약 추출과 구조적 비교 |
| 이름이 붙은 객체의 인스턴스 종류 | 모델이 정한 대상 종류 | 앵커 바인딩 |
| 관계 방향 | 프레임 또는 계획 모델 | 수용된 위치를 검토된 방향으로 대응 |
| 경로와 LinkType 집합 | 계획 모델 또는 고정 레시피 | 검토된 특성과 경로 문법 |
| 개념, 값, 시간 | 용어 목록, 어휘 순위, 정규식 | 전체 카탈로그 조각과 타입 값에서 모델이 고르고 코드가 검증 |
| 피연산자 | 발화 정규식 또는 계획 모델 | 구간, 바인딩, 핸들, 서버 기본값 |
| 답변 문장 | 코드 안의 형태별 템플릿 | V-CLAIM과 독립 검토를 통과한 모델 작성 주장 |

판단 프롬프트는 보호된 루트를 유지하고, 읽기 목표에는 FunctionType 카탈로그 없이 닫힌 형식, 구간과
단서 규칙, 연산별 이중 언어 예시만 설명합니다. 컴파일된 형식에서는 프레임과 계획 모델 호출을 없애고,
계획 모델은 컴파일되지 않은 형식에 대해서만 shadow로 남아 V-SEM과 V-PROV를 통과해야 합니다. T2는
계획을 작성하지 않으며, 쓰이지 않는 `query.<LinkType>` 의도 경로는 제거합니다.

| 개념에 대한 임베딩 권한 | 기각 | 유사도는 후보만 제안할 수 있음 |
| 결정론적 답변 템플릿 | 기각 | 경직된 문장은 운영자 질문을 놓치고 SRE Agent 기준을 넘을 수 없으며, 검증된 모델 작성 주장이 사실을 정확하게 유지함 |
| 논리 형식과 결정론적 컴파일러 | 선택 | 모델은 닫힌 분류에 머물고, 바인딩, 경로, 주장은 코드로 옮김 |

초안에 대한 독립 검토가 찾은 결함과 반영 내용은 다음과 같으며, 모두 이 설계의 일부입니다.

| 발견 | 반영 |
|------|------|
| 과장된 모델 권한과 어휘적 개념 추론 | 수용 검사, 단서 구간, 목표별 신뢰도, 닫힌 필드 T2 검토, 영역이 제한된 근거화 |
| 합쳐진 `연결된` 답변과 최단 경로 추측 | 모호하면 명확화, 명시적 `all_kinds`, 검토된 경로 문법 |
| 스스로 인증하는 커버리지와 바인딩 경쟁 조건 | 독립적인 규칙 기반 커버리지, 막히는 제한 원자, 두 단계 스냅샷 프로토콜 |
| 안전하지 않은 핸들, 불분명한 소유권, 약한 통계 | 묶인 핸들, 책임 에이전트, 잠긴 홀드아웃, 독립 정답, 신뢰 구간 |
| 용량 검토: 중복 이름, 출력 예산, 빠진 질문 형태 | 한정 언급, 원자 차이 대안, [온톨로지 추론 커버리지](ontology-reasoning-coverage-ko.md#질문-분류-체계-완결)의 분류 추가 |
| Owner 지시: 어휘적 의미 금지, 템플릿 답변 금지, 한도로 빠지는 항목 금지 | 전체 조각에 대한 모델 근거화, V-CLAIM을 쓰는 근거 기반 작성, 연속 판단, 계획 묶음 |

## 답변 작성

Bragi의 T1 작성자는 해석 재진술을 포함한 모든 답변을 수용된 형식, 검증된 근거 표, 목표별 인식 상태,
타입이 지정된 제한 코드만으로 씁니다. 답변 문장은 코드 템플릿에서 나오지 않으며, 모델 없이 표시되는
것은 카탈로그 알림과 검증된 데이터 보기뿐이고 이들은 사실을 더하지 않습니다. 작성자는 구조화된 주장을
반환하고, 주장은 검증을 통과한 뒤에만 보입니다.

| 주장 필드 | 계약 |
|-----------|------|
| `kind` | `restatement`, `fact`, `count`, `relation`, `state`, `change`, `cause_hypothesis`, `limitation`, `next_check` |
| `refs` | 주장을 뒷받침하는 근거 칸 또는 제한 코드 |
| `proposition` | 정규 주체, 방향을 포함한 술어, 대상 또는 값, 긍정과 부정, 비교나 수량 표현, 단위, 시간 기준과 시간대, 양상, 반올림 |
| `spans` | 명제에 묶인 모든 표현과 리터럴의 정확한 문장 구간 |
| `rows` | 목록과 개수 목표에서 주장이 이름을 대거나 집계한 행 식별자 |

V-CLAIM은 이름을 부분 문자열이 아니라 정규 식별자로 비교합니다. 참조가 없는 주장, 근거와 다른 명제나
리터럴, 선언되지 않은 리터럴, 빠진 필수 제한이나 목표나 형식 원자, 권위 있는 개수와 다른 개수, 이름도
집계도 전체 표도 아닌 결과 행, 인과 근거 없는 원인 주장이 있으면 답변을 거부합니다. 이어서 독립 T1
검토자가 도출 관계를 확인합니다. 거부된 답변은 타입이 지정된 사유와 함께 한 번 다시 생성하고, 그래도
실패하면 검증된 근거 보기와 함께 보류합니다. 작성 호출 하나보다 큰 근거는 조각으로 작성한 뒤 같은 행
집계 아래에서 종합합니다. 평가와 동등성 게이트는
[온톨로지 추론 커버리지](ontology-reasoning-coverage-ko.md#보증과-sre-agent-동등성)가 담당합니다.

## 전달 라운드

| 라운드 | 범위 | 종료 근거 |
|--------|------|-----------|
| R0 | 코호트, 홀드아웃 세트, 고정 그래프, 엄격한 정답, 운영과 같은 하네스, Azure SRE Agent 기준선 | 기준선 L1, L2, 동등성 증적 |
| R1 | 버전 협상을 갖춘 형식, 수용, 개념 선택, 바인딩, 핸들, 커버리지 규칙, 근거 매니페스트, pushdown, 주장 계약 | 코덱과 N/N-1 테스트, 동작 변경 없음 |
| R2 | 기존 타입 판단 필드에 대한 임시 V-PROV와 V-LEVEL, 정확한 그룹에서 `contains`로 구하는 리소스 그룹 소속 | 지어낸 식별자 리터럴 0건, 인스턴스 대상에 대한 스키마 답변 0건, 고정 그래프에서 `contains` 폐포와 같은 소속 |
| R3 | 전체 조각에 대한 shadow 형식 판단, 수용, 개념 선택 | 홀드아웃 세트에서 유형별 원자와 개념 정확도, 안정성 90% 이상 |
| R4 | 앵커 바인딩 프로토콜과 타입 시간 값 | 고정 그래프에서 L2 바인딩과 시간 정확도 100% |
| R5 | 특성 검토, 경로 문법, 탐색 루트 계보 뒤의 관계 컴파일러 | shadow 관계와 포함 홀드아웃 세트 85% 이상, 절대 0 유지 |
| R6 | 집계, 순위, 진단 레시피, 위치 속성 출시 뒤의 리전 | shadow 집계와 진단 홀드아웃 세트가 절대 0 유지 |
| R7 | 링크 근거 허용 목록 뒤의 이력, 버전, 원인, 검증 | 이력이 없을 때 타입이 지정된 사용 불가, 인과 근거 없는 인과 주장 0건 |
| R8 | 위협 검토 뒤의 결과 핸들과 근거 기반 답변 작성 | 후속 질문 홀드아웃 세트 85% 이상, 대화 간 바인딩 0건, V-CLAIM 누락 0건 |
| R9 | 승격 레지스트리를 통한 연산 계열별 승격 | 계열별 승격과 SRE Agent 동등성 증적, 승격된 계열의 프레임과 계획 프롬프트 제거 |
| R10 | 승격된 경로에서 어휘적 재추출과 템플릿 렌더러 제거 | 재현 동등성과 안정적인 롤백 릴리스 1회 |

모든 라운드는 구현하고, 집중 테스트를 실행하고, L1을 2회 이상 반복하고 L2를 실행하고, 회귀를
고치고, 원장에 행을 추가합니다. 형식 경로는 현재 경로 옆에서 shadow로 실행되고 다이제스트와 처리
결과만 기록합니다. 한 계열은 모든 반복과 표본 shadow 턴에서 절대 0이 유지되고, 홀드아웃 세트 정확도가
절대 하한을 넘고 잡음 구간 밖에서 현재 경로보다 좋으며, 영어와 한국어의 차이가 5점 이하이고, p95
지연이 늘지 않고, SRE Agent 동등성이 유지되고, 68개 사례 코퍼스가 후퇴하지 않을 때만 승격됩니다. 롤백은 이전
레지스트리 항목을 복원하며, 현재 경로는 R10까지 그대로 유지됩니다.
[온톨로지 추론 커버리지](ontology-reasoning-coverage-ko.md#완결-프로그램)의 계열별 레인이 이 라운드들을
제한합니다.

**운영 shadow 연결**: 승격 증거는 승인된 첫 번째 결정대로 기존 판단 호출의 추가 필드로 실어 보낸 형식에서만
나옵니다. 턴 옆에서 자체 모델 호출을 하는 탭은 독립적으로 표본 추출된 다른 판독을 측정하므로, 그 기록은
승격에서 제외하는 실험입니다. 어느 연결이든 설계 비평에서 나온 다음 조건을 지켜야 합니다.

- 앵커 조회는 조회하는 순간의 게이트웨이 기준 시점을 씁니다. 게이트웨이는 자신의 기준 시점에서 몇 초
  안의 `as_of`만 받아들이고 모델 호출은 그보다 오래 걸리기 때문입니다. 거부된 조회는 일반적인 사용 불가가
  아니라 타입이 지정된 `as_of_stale`입니다.
- shadow를 취소하거나 시간이 초과되면, shadow가 시작한 모든 공급자 호출을 취소하고 정리합니다.
- shadow는 정리된 컨텍스트에서 자체 공급자 예산으로 실행하고, HTTP 429나 503에서 병렬 호출을 멈추며,
  답변의 예산을 차감하거나 취소하지 않습니다.
- 턴마다 최상위의 적격한 운영 발화 하나만 관찰합니다. 다른 경로와 비상 권한 principal은 타입이 지정된
  건너뜀을 기록하고, 용량 부족으로 건너뛴 경우와 시간 초과도 분모에 남습니다.
- 앵커 조회는 턴의 실행기와 같은 역할, 목적, principal 범위 다이제스트 구성을 씁니다.
- 기록은 발화나 principal의 솔트 없는 다이제스트 대신 키가 있는 표본 식별자를 담고, 영속 싱크로 보내며,
  기본값이 꺼짐인 타입 설정으로만 켭니다.

**현재 경로의 중간 수정(R2)**: 계열이 승격되기 전까지 현재 판단 경로는 실제 결함이 틀리거나 빈 답변을 낸 곳에
같은 원칙을 적용합니다. `resource_group` 대상은 항상 정확한 컨테이너 하나를 뜻하므로, 함께 온 수집 facet과 관계없이
구성원을 `contains`로 읽고, 그 옆의 하위 유형 필터는 구독 전체가 아니라 구성원을 좁힙니다. 판단에는 순위 조각 대신
모든 선언 식별자를 제시하며, 속성 수준 식별자는 더 작은 허용량 안의 선택적 세부 정보입니다. preflight 라우터는 더 이상
Resource 수집에서 판단을 대신하지 않고, 제품 이름을 고정한 확인 질문도 남아 있지 않습니다. 요청이 예산을 넘으면 이전
턴 컨텍스트가 오래된 것부터 물러납니다. 로컬 프로필에서는 다른 narrator 배포의 독립 두 번째 판독기가 서로 모르는 두
선택기로 결속되지 않은 하위 유형 표현을 닫힌 선택으로 근거화합니다. 또한 블라인드 제약 판독에서 명시된 모든 제한,
부정, 비교, 순서, 시간이 복사된 구간 안에 있어야 합니다. 덮이지 않은 제약은 수정 피드백으로 판단에 돌아가고, 그래도
남으면 턴을 `semantic_constraint_uncovered`로 보류합니다. "only"나 "not" 같은 부정어는 맞닿은 복사된 피연산자가
덮습니다. 복사된 모든 구간과 떨어진 이름은 빠졌을 수 있는 하위 유형으로 같은 닫힌 선택에 제시합니다. 구성원 프레임은
정확한 그룹 없이 컴파일되지 않고, 컨테이너 자신의 종류 단어는 구성원을 거르지 않으며, 두 번째 판독기가 없는 곳에서
명시된 관계의 피연산자를 빠뜨린 프레임은 목록을 넓히지 않고 보류합니다. 상태 수집은 네 번째 승인된 결정대로 명시된
상태에 검토된 상태 개념이 없을 때만 T2 검토가 필요하며, 형식화된 대상이 모두 근거화된 상태인 수집은 상태 수집으로
계획합니다. 한 구간을 두 대상으로 복사한 제안은 수정합니다. 이름이 지정된 인스턴스 하나에 대한 관계 질문은 이 경로에서 아직 표현할 수 없으며 관계 컴파일러를
기다립니다. 모호하다고 끝난 판단은 결정론적 프레임 이전 검사를 마친 뒤 그 판단의 명확화 요청으로 턴을 끝냅니다. 프레임
모델은 더 이상 판단과 제약 검토 없이 발화를 다시 해석하지 않습니다.

**로컬 컴파일 답변**: 로컬 개발 프로필에서는 실행기가 `FDAI_SEMANTIC_COMPILED_ANSWERS=1`도 설정합니다. 이 설정에는
second reader가 필요하며, 구성은 로컬 실행 위치에서만 이 설정을 따릅니다. 그러면 플래너는 문서 근거가 필요 없고
바인딩되지 않은 모든 운영 턴에서 판단과 함께 form 경로를 시작합니다. 이 경로는 자체 공급자 호출과 예산 범위, 절대
기한을 사용하며, 앵커 읽기는 턴 실행기와 같은 역할, 목적, principal 범위로 수행합니다. 플래너는 결정론적 프레임 이전
검사를 마친 뒤에만 이 경로를 확인하며, [검토와 보류 개선](#검토와-보류-개선)의 닫힌 모호성 reader가 그럴듯한
해석이 하나뿐이라고 답하지 않는 한 모호한 판단의 명확화 요청이 이 경로보다 우선합니다. 이 경로는 release되었고,
보존된 컴파일이 하나뿐이며, 그 안에 검증된 배치 하나로 컴파일된 목표가 정확히 하나 있고, 이어서 처리할 부분과 제한이
없을 때만 답합니다. 그러면 플래너는 게이트웨이의 현재 기준 시각으로 계획을 다시 표시하고 다시 검증한 뒤, 판단 경로의
프레임과 계획 단계 대신 그 컴파일된 프레임과 계획으로 답합니다. 완료된 관계 탐색의 최종 출력 테이블이 비어 있으면
`semantic_relation_empty_unconfirmed`로 보류합니다. 다른 타입 기반 가드가 비어 있지 않은 결과를 확인하지 않는 한, 빈
관계 결과는 관측된 부재가 아니라 불안정한 방향 또는 개념 근거화를 뜻할 수 있기 때문입니다. 판단이 명시된 제약을 포함하지 못해 보류될 때도 이런
컴파일은 보류 대신 답할 수 있습니다. 그 밖의 결과는 모두 현재 경로가 턴에 답하게 둡니다. 여기에는 형식화된 미지원 이유,
명확화, 보류된 검토, 이어서 처리할 부분, 기한 초과, 공급자 실패가 포함됩니다. 턴을 끝내거나 취소하면 경로가 취소되고,
소유 이벤트 루프가 공급자 호출을 정리합니다. 경로는 건너뜀, 취소, 기한 초과, 실패를 포함한 모든 결과마다 내용이 없는
판단 이벤트 하나를 남깁니다. 이 이벤트에는 패스별 처리 결과, 검토 결과, 목표별 상태, 이유, 제한이 들어 있으므로
`dev discuss`로 질문이 컴파일되었거나 되지 않은 이유를 볼 수 있습니다. form은 턴 옆에서 별도로 호출해 얻으므로 이 기록은
production shadow 연결이 승격 근거에서 제외하는 실험이며, 이 기록으로 승격되는 계열은 없습니다.
관계의 여러 측면이 여러 배치로 나뉜 목표는 모든 측면이 의도 그래프 하나에 들어갈 때만 하나의 계획으로 답합니다.
공유 앵커 읽기는 내용이 같을 때만 반복될 수 있습니다. 계획 하나는 출력을 최대 8개까지만 지정하므로, 측면이 8개를
넘으면 같은 ObjectType에 도달하는 순회는 노드로 남기고 그 합집합 하나를 출력으로 삼습니다. 그러면 모든 측면을 읽고,
도달한 끝점은 한 번씩만 유지합니다. Resource 상태 필터는 상태 인벤토리
함수가 선언한 개념과 레이블로 만든 검토된 상태 카탈로그로 바인딩되고, 수집은 그 함수로 읽습니다. V-PROV와
V-SEM은 그 함수의 상태 개념을 바인딩된 상태와 대조합니다. 다른 ObjectType의 상태 필터는 그 생애 주기를 읽는
검토된 reader가 없으므로 계속 `filter_unsupported:state`입니다.
컨테이너별로 묶은 개수는 구성원을 `contains`의 `from` 끝인 직접 상위 리소스별로 묶으며, V-SEM은 묶는 기준이
밝힌 기준과 다른 집계를 거부합니다. 라우팅 사전 판정의 문맥도 이제 더 작은 자체 한도 안에서 최신 항목부터
유지합니다. 이전에는 문맥이 그 한도를 넘으면 사전 판정을 건너뛰었으므로, 긴 답변이 몇 번 이어진 뒤에는 단독
질문이 적응형 플래너로 넘어가 일반 지식으로 답할 수 있었습니다. 문맥을 줄이면 유지한 항목 수와 제외한 항목
수를 판단 이벤트로 기록합니다.
경로가 답을 거절하면 통과하지 못한 선택 규칙 하나(`not_released`, `goal_not_compiled`, `merge_over_budget` 등)와
배치 수도 기록합니다. 검토가 무효이면 추출이 검토 역할을 할 수 없는 이유(빈 추출, 질문에 없는 인용 등)를 인용 없이
기록합니다. release된 해석에 어떤 빌더도 컴파일하지 못하는 목표가 있으면, 그 해석은 질문에 필요한 것을 밝혀 줍니다.
이때 현재 경로는 자체의 형식화된 빌더로 여전히 답할 수 있지만, 판단이 쓴 단어에서만 복구한 필터(예: 밝힌 타입)는 더 좁은
질문에 답하게 됩니다. 예를 들어 질문이 리전도 밝혔는데 모든 스토리지 계정을 답하는 경우입니다. 그래서 플래너는 그렇게
복구한 계획에 `semantic_stated_constraint_unsupported`를 반환하고 미지원 이유를 기록하며, 운영자가 묻지 않은 질문에
검증된 답을 내놓지 않습니다. 미지원 원자를 가리키는 이유만 해당하며, 불완전한 앵커 읽기 같은 데이터 결과는 질문에
대해 아무것도 말하지 않습니다. release 여부와 상관없이 어떤 패스의 파싱된 해석이든, 필터를 적용한 Resource 목록
하나로 답할 수 있는 범위를 넘으면 그런 계획을 보류합니다. 상태, 리전, 묶음, 이름이 지정된 컨테이너의 구성원이 아닌
관계, 시간, 스키마 수준, 두 번째 목표, 경쟁하는 해석이 여기에 해당합니다. form 형태의 첫 토큰이 이 판정을
기록합니다.

## 형식 전용 답변과 인과 맥락

이 절은 2026-09-30에 답변 경로의 어휘 기반 의미 판단을 감사한 결과와, 그 결과에 따라 제안하는 다음
단계를 기록합니다. 이 단계는 로컬 개발 프로필에서만 동작을 바꿉니다.

### 어휘 기반 의미 감사

현재 판단 경로의 런타임 코드 중 다섯 묶음이 아직 운영자의 단어에서 의미를 끌어냅니다.

| 묶음 | 예시 | 단어에서 끌어내는 의미 |
|------|------|------------------------|
| 키워드 신호 표 | 인벤토리 질의 언어 카탈로그에 대한 `query_signal_matches`, `query_target_cardinality`, `query_term_spans` | 목록 요청과 단일 항목 요청, 개수, 변경, 관계, 위치, 활동, 원인 진단 |
| 밝힌 값 대조 | `stated_value_filters`, `stated_value_term_spans`, `stated_subject_fragment` | 발화에 단어로 나타난 Resource 유형, 이름, 속성 값 |
| 복구 대체 경로 | 밝힌 리소스 필터, 현재 상태, 대상 후보 복구 | 판단이나 프레임이 불완전할 때 위 대조 결과로 만든 필터 목록이나 상태 조회 |
| 조사와 시간 정규화 | 느려짐, CPU, MySQL, 네트워크, 애플리케이션 가설 정규화기, 활동과 서비스 상태 정규화기 | 원인 가설, 증상, 부정, 조회 기간 |
| 명확화 빌더 | 리소스 대상 명확화와 필터 의미 명확화 | 단어 겹침으로 정한 모호성 |

운영 사실을 서술하는 답변 템플릿은 없습니다. 답변은 검증된 근거 표와 검토된 카탈로그 안내만 표시합니다.
모델이 작성하는 답변과 V-CLAIM은 여전히 R8 라운드 작업입니다.

### 형식 전용 답변

로컬 프로필에서 `FDAI_SEMANTIC_TYPED_ONLY=1`을 설정하면 운영 조회는 질문 형식 경로로만 답할 수 있습니다.
이 설정에는 컴파일된 답변과 로컬 실행 위치가 필요하며, 둘 중 하나라도 없으면 구성이 시작을 거부합니다.
플래너의 순서는 그대로입니다. 사전 판정, 판단과 그 포함 검토, 검증된 거부, 작업 초안 경계, 결정론적
명확화가 먼저 실행되고, 이어서 판단 자체의 명확화, 그다음 형식 경로가 실행됩니다. 앞선 단계 중 어느
것도 조회에 답하지 않습니다. 바뀌는 것은 형식 경로 다음에 일어나는 일뿐입니다.

1. 선택 규칙을 통과한 release된 컴파일이 턴에 답합니다.
2. 그렇지 않으면 형식 경로의 태그된 결정이 형식화된 결과로 턴을 끝냅니다. 이 턴은 기존 프레임·계획
   단계, 그 키워드 신호, 밝힌 값 대조, 복구 경로, 프레임 모델에 도달하지 않습니다.

| 결정 | 플래너 결과 | 의미 |
|------|-------------|------|
| `unsupported` | unsupported, `semantic_stated_constraint_unsupported` | release된 해석이 검토된 빌더가 읽지 않는 원자를 밝힘 |
| `clarification` | 보류, `semantic_reading_ambiguous` | 해석에 경쟁하는 해석, 쓰이지 않은 언급, 필드로 표현할 수 없는 제약이 있음 |
| `continuation` | 보류, `semantic_reading_continuation_required` | 한 번 더 패스가 필요하거나 답변 하나가 담을 수 있는 것보다 많은 계획이 필요함 |
| `limited` | 보류, `semantic_reading_limited` | 검토된 안내로 밝힐 수 없는 제한이 목표에 있음 |
| `unverified` | 보류, `semantic_reading_unverified` | 형식이 무효이거나 블라인드 검토가 충실하지 않다고 판정함 |
| `unavailable` | 보류, `semantic_reading_unavailable` | 경로가 시간 초과, 실패했거나 이 턴에서 시작하지 않았거나, 불완전한 앵커 읽기처럼 목표가 데이터를 바인딩하지 못함 |

바인딩된 리소스 조회나 문서 근거가 필요한 조회처럼 형식 경로가 시작하지 않은 턴도 기존 경로로 넘어가지
않고 `unavailable`로 끝납니다. 직접 사회적 응답, 한 번에 답하는 일반 지식, 적응형 지식 답변, 작업 초안은
기존 경로를 유지합니다. 이 경로들로 잘못 분류된 운영 질문은 R9 승격에서 측정할 알려진 공백으로 남습니다.
설정을 끄면 플래너는 이전과 정확히 같게 동작합니다. 배포 환경은 각 계열이 R9에서 승격될 때까지 현재 경로를
유지하며, R10은 롤백 release를 거친 뒤에만 승격된 계열의 어휘 기반 도우미를 삭제합니다.

첫 해석이 형식으로서만 실패하면, 즉 형식이 무효이거나, 쓰이지 않은 언급이나 경쟁하는 해석 때문에 명확화가
필요하거나, 블라인드 검토에서 충실하지 않다고 판정되거나, 언급 하나의 종류를 잘못 붙였으면 경로는 질문을 한 번
더 읽습니다. 두 번째 샘플도 같은 수용, 근거화, 검토, 선택 규칙을 통과해야 하므로 기준을 낮추지 않습니다.
지원되지 않는 원자가 있는 해석은 다시 샘플링하지 않으며, 어떤 턴도 샘플을 두 번보다 많이 쓰지 않습니다.

선택된 컴파일은 답변이 카탈로그 안내로 밝히는 검토된 제한만 가질 수 있습니다. 적용한 이력 기간, 기본
이력 기간, 모델이 판단한 이력 기간, 원인이 확정되지 않았다는 사실, 그리고 영향이 관측된 것이 아니라 가능한
것이라는 사실입니다. 컴파일러는 각 제한을
프레임 근거 요구 사항으로 기록하므로 프레임, 계획 다이제스트, 표시된 안내가 일치합니다. 그 밖의 제한이
있는 컴파일은 답하지 않습니다.

### 인과 맥락

aks-app이 왜 중지됐는지 묻는 질문은 이름이 지정된 Resource 하나에 대한 `cause` 원함입니다. 수용 단계는
이 질문을 앵커 하나에 대한 `want: cause` 형식의 `explain_cause` 목표로만 받으며, 상태 측정값과 시간 구간은
선택 사항입니다. 연산과 원함의 다른 조합은 수리를 한 번 받는 구조 결함입니다.

현재 상태 reader는 상태가 언제 바뀌었는지가 아니라 언제 관측되었는지를 보고하고, 로컬의 상태 전이 범위는
자주 비어 있습니다. 따라서 시간 순서만으로는 여기서 `association` 등급조차 뒷받침할 수 없습니다. 상태 전이
범위, 메커니즘 카탈로그, 반박 질의가 생길 때까지 컴파일러는 이런 목표를 원인 후보가 아니라 인과 맥락으로
답합니다. 계획은 `query.resource_current_state`로 앵커의 현재 상태를 읽고,
`query.resource_change_activity`로 밝힌 기간이나 기본 기간 동안 앵커에 기록된 컨트롤 플레인 작업을 각
행의 기록된 상태와 함께 읽습니다. 프레임은 컴파일러 전용 출력 형태인 `cause_context`를 쓰며, 프레임 모델의
스키마는 이 형태를 제공하지 않으므로 기존 프레임 경로는 이를 제안할 수 없습니다.

답변은 원인이 확정되지 않았다는 검토된 안내로 시작하고 조회 기간을 다시 밝힙니다. 두 검증된 표를
완전성과 함께 보여 주며, 어떤 작업도 원인으로 지목하지 않고 근거 등급도 매기지 않습니다. 행 한도에 도달한
활동 조회처럼 불완전한 조회는 불완전으로 표시된 채 남습니다. 이력 목표도 같은 방식으로 컴파일러 전용
`change_activity` 형태를 쓰므로 작업이 Resource 목록으로 표시되지 않습니다. 상태 전이 변경 시점, 고정된
이어 읽기로 기간 전체를 나눠 읽는 것, 의존 이웃 맥락, 메커니즘 적합성, 반박 검사, 근거 등급, V-CLAIM이
통제하는 모델 작성 원인 주장은 R7과 R8 작업으로 남습니다. 새 FunctionType을 추가하지 않으므로 온톨로지
release는 바뀌지 않습니다.

| 비평 발견 | 수정 |
|-----------|------|
| 상태 관측 시점보다 앞선다는 것은 연관이 아님 | 인과 맥락만 제공하며 후보와 근거 등급이 없음 |
| 활동 기록에 실패한 작업과 읽기 작업이 섞임 | 각 행이 기록된 상태를 유지하며 어떤 행도 순위를 매기지 않음 |
| `no_known_cause` 기준선이 없음 | 답변이 "원인 미확정"으로 시작함 |
| 한도가 있는 활동 조회가 행을 버림 | 불완전한 표는 불완전으로 남고, 전체 나눠 읽기는 남은 작업임 |
| 티켓이 없는 턴에서 형식 전용이 열린 상태로 실패함 | 그런 턴은 `unavailable`로 끝남 |
| 컴파일을 사전 프레임 가드 앞으로 옮기면 안전 검사를 건너뜀 | 순서는 그대로이며, 결정 뒤의 대체 경로만 바뀜 |
| 거절 코드가 너무 거침 | 각각 형식화된 결과가 있는 태그된 결정 |
| 이력 목표와 원인 목표는 항상 제한을 가짐 | 검토된 제한을 안내와 함께 프레임 근거 요구 사항으로 기록함 |
| 새 FunctionType이 전역 release를 바꿈 | 새 FunctionType 없음 |
| 원인 질문의 두 가지 인코딩 | `want: cause`인 `explain_cause` 하나만 정식 형식임 |

### 해석 신뢰성과 불완전한 수집 범위

라이브 Console 질문 28~30개로 진행한 형식 전용 점검 라운드 T4~T11에서 라운드마다 19~21개 질문에 답했습니다.
남은 보류는 세 계열에서 나왔습니다. 형식으로서만 실패한 해석, 컴파일러가 바인딩하지 않은 조회, 그리고
앵커를 쓰는 모든 조회를 불완전하게 만든 인벤토리 상태입니다. 이 단계는 각 계열을 다루며, 코드는 여전히
단어에서 의미를 읽지 않습니다.

**해석**

- **방향 다수결**: 제안자는 관계의 두 역할을 모두 밝히고, 다른 모델 계열의 블라인드 reader 하나가 이름이
  지정된 앵커가 어떤 역할인지 답합니다. 그 답이 분명하면서 제안자와 다르면 세 번째 블라인드 reader가 같은
  닫힌 질문에 답합니다. 제안자의 역할이 이미 한 표이므로 세 번째 reader는 첫 reader의 계열도 제안자의
  계열도 아닌 계열이며, 그런 계열이 없으면 불일치를 보류합니다. 구체적인 역할로 일치하는 두 답이
  결정합니다. 형식이 그대로 유지되거나, 두 역할을 reader들의 해석으로 맞바꾼 뒤 형식을 다시 수용합니다.
  세 번째 답이 상호 관계, 불분명, 무응답이면 턴을 보류합니다. 이 판정은 컴파일 전에 실행되므로 역할을
  맞바꾼 해석도 다른 해석과 똑같이 컴파일, 검토, 검증을 거칩니다.
- **인용 위치**: 밝힌 등장 위치가 다른 언급 안에 들어가는 언급은, 다른 언급이 차지하지 않은 같은 단어의
  유일한 등장 위치로 옮깁니다. 그런 위치가 없으면 수용 단계가 겹침을 거부합니다.
- **측정 단어**: 이벤트를 뜻하는 단어처럼 그룹화하지 않은 측정값의 이름만 나타내고 다른 곳에서 인용되지
  않는 개념 언급은 그 측정값의 단서가 됩니다. 이름 붙은 리소스, 리터럴, 상태·health·지표 값은 항상 언급으로
  남습니다. 코드는 형식의 두 필드 사이에서 인용을 옮길 뿐 어떤 단어도 읽지 않습니다.
- **맞춘 계약**: 형식 계약이 측정 종류마다 정의를 두고, 추출 계약이 이벤트와 작업을 측정값으로 나열하므로
  두 블라인드 reader가 같은 단어를 같은 방식으로 분류합니다. 추출기가 찾은 이름 붙은 대상에는 여전히
  언급이 필요합니다. 주체가 없는 목표의 개수 측정값은 그 목표의 유형 필터를 다시 밝힐 수 있습니다.
- **제한된 재시도**: 질문에 없는 단어를 인용한 추출처럼 쓸 수 없는 추출은 같은 추출기가 같은 검토 규칙으로
  한 번 더 읽습니다. 검토된 값과 일치하지 않는 개념 하나만이 문제인 해석은 다른 잘못 붙인 언급과 마찬가지로
  다시 샘플링합니다.
- **단어 대조 관문 없음**: 형식 전용 모드에서는 발화의 단어 중에서 카탈로그 값을 찾는 프레임 이전 관문이 더는
  조회를 보류하지 않으므로, 조회 질문이 무엇을 밝히는지는 형식화된 해석만 결정합니다. 형식 전체 규칙을 어기면
  추적에 닫힌 `form_contract_rule` 코드로 그 규칙을 기록합니다.

**조회**

- **컬렉션 이력**: 일반 Resource 전체나 주체를 밝히지 않은 "무엇이 바뀌었나" 질문은 형식화된 기간에 대해
  `query.recent_resource_changes`를 읽고, reader가 선언한 최대 행 수로 제한하며, `resource_changes`로
  표시합니다. 그 reader가 종류를 제한할 수 없으므로 종류를 밝힌 질문은 지원하지 않습니다. 바뀐 Resource가
  한도보다 많거나 변경 수집 범위를 확인하지 못한 기간은 불완전으로 남습니다. 수집 범위가 완전하면 reader는
  한도 때문에 빠진 변경 Resource를 같은 스냅숏에서 모두 세고, 표는 그 정확한 `total_rows`를 담으며, 답변은
  목록에 없는 변경 Resource의 수를 밝힙니다. 고정된 이어받기로 나머지를 나열하는 일은 남아 있습니다.
- **이벤트 이력**: `event` 측정값을 가진 앵커 이력은 reader가 선언한 최대 조회 기간 안에서 검토된 모든 이벤트
  계열에 대해 `query.resource_event_history`를 읽습니다. 더 긴 기간은 지원하지 않습니다.
- **검증**: V-SEM은 각 이력 목표에 필요한 조회 하나, 즉 컬렉션 변경, 이벤트, 활동 중 하나를 도출합니다.
  V-PROV는 컬렉션 조회의 절대 기간이 신뢰할 수 있는 컴파일 시각에 끝나고, 예상 조회 기간만큼 이어지며,
  선언된 행 한도를 쓰는지 확인합니다.
- **선언된 한도**: 빌더는 행 한도와 조회 기간 한도를 자체 사본으로 두지 않고 FunctionType 입력 스키마에서
  읽습니다.
- **합집합 입력 수**: 모든 합집합은 Console 의도 목표 하나가 보여 줄 수 있는 최대치인 의존 항목 7개까지만
  읽고, 그보다 많으면 부분 합집합으로 나눈 뒤 다시 합칩니다. 관계 개수 세기는 최대 11개 방향만 읽으므로
  합집합 트리와 집계가 의도 그래프 하나에 들어가며, Console이 의도 그래프를 보여 줄 수 없는 계획은 답하기
  전에 보류합니다.
- **답변 표**: 인과 맥락 표는 실행 상태처럼 상태 reader가 선언한 측정 필드를 영수증 필드보다 먼저 보여 줍니다.

**불완전한 수집 범위**

- **범위를 좁힌 정확한 조회**: 몇 분마다 쓰기가 일어나는 공급자 관리 부하 분산 장치처럼, 투영되지 않은
  관측이 하나라도 있으면 인벤토리는 모든 Resource 조회를 불완전으로 표시합니다. 이제 관계 없이 정확한
  식별자로 객체를 읽는 조회는 요청한 식별자의 대기 중인 관측만 셉니다. 요청한 식별자 중 하나가 대기 중인
  생성인 경우도 포함합니다. 그 밖의 공백은 모두 전역으로 유지합니다.
- **입증되지 않은 유일성**: 수집 범위가 불완전할 때 검증된 이름 일치가 하나이면 유일성이 입증되지 않은
  상태로 바인딩합니다. 답변은 부분 결과이며, 같은 이름의 다른 리소스가 아직 반영되지 않았을 수 있다는
  검토된 안내를 밝힙니다. 일치가 없다고 해서 부재가 입증되지는 않으며, 잘린 조회는 바인딩하지 않습니다. 대소문자를
  구분하는 이름 조회는 저장소로 내려보내므로, 수집 범위가 불완전해 대소문자를 구분하지 않는 스캔이 아무것도
  반환하지 않을 때도 일치 항목을 반환합니다.
- **형식화된 이유**: 바인딩되지 않은 앵커는 `candidate_limit`, `source_incomplete`, `generation_changed`,
  `extensions_unread` 중 하나를 보고합니다.

**진단**

- dev discuss는 범위 표기로 끝나는 서버 이유 코드에서 닫힌 코드 접두사를 유지하고, 로컬 프롬프트 원본
  검사는 진단을 표준 오류로 기록하므로 표준 출력의 입력 다이제스트를 계속 파싱할 수 있습니다.

이 단계의 설계 비평은 High 5개와 Medium 3개, 모두 8개의 발견을 제기했습니다.

| 비평 발견 | 수정 |
|-----------|------|
| 상호 관계나 불분명한 세 번째 방향 답을 제안자 편으로 셈 | 구체적인 역할만 한쪽 편이 되며, 그 밖의 세 번째 답은 보류 |
| 동점 판정에 제안자의 모델 계열을 다시 쓸 수 있음 | 동점 판정 계열은 첫 reader의 계열도 제안자의 계열도 아니며, 그런 계열이 없으면 불일치를 보류 |
| 측정 언급을 단서로 옮기면 이름 붙은 리소스가 사라질 수 있음 | 개념 언급만 옮기며, 측정 단서 안의 이름 붙은 대상에는 여전히 언급이 필요 |
| 값으로 쓴 범위를 이름으로 읽으면 의미가 바뀔 수 있음 | 제거함. 값으로 쓴 앵커는 잘못 붙인 언급으로 보고 다시 샘플링 |
| release된 해석이 판단이 찾은 실제 모호성을 덮어씀 | 제거함. 닫힌 모호성 reader가 생길 때까지 판단의 명확화가 우선 |
| 절대 이력 기간이 신뢰할 수 있는 시각에 묶이지 않음 | V-PROV가 기간이 컴파일 시각에 끝나는지 확인 |
| 합집합을 트리로 만든 뒤 12개 방향 개수 세기가 의도 그래프 하나를 넘음 | 최대 11개 방향으로 제한하고, 트리를 만든 뒤 노드 예산을 확인 |
| 유일성이 입증되지 않은 앵커에서 읽은 답변이 검증됨으로 표시됨 | 그런 답변은 부분 결과 |

## 검토와 보류 개선

이 절은 형식 전용 라운드가 추적한 검토, 해석, 보류의 빈틈을 메운 2026-09-30 개선을 기록합니다. 모두 로컬
프로필에서만 동작하며 어떤 권한도 주지 않습니다.

**해석**

- **이어지는 패스의 스냅숏**: 각 패스는 자신의 앵커 읽기가 본 서로 다른 스냅숏 세대를 기록합니다. 결과
  핸들의 세대는 앞선 답변의 것이므로 비교하지 않습니다. 이어지는 패스의 읽기가 첫 읽기와 다른 세대를 보았거나
  세대를 둘 보았다면 그 패스는 `continuation_generation_changed` 메모와 함께 `generation_changed`로 끝나고,
  그 컴파일은 버리며, 이어서 처리할 부분은 남은 것으로 둡니다. 남은 부분이 있는 해석은 실패한 형식이 아니라
  이어짐 결정이므로 다시 샘플링하지 않습니다.
- **합쳐진 언급 나누기**: 블라인드 추출이 제한이나 선언 이름을 겹치지 않는 다른 제약과 함께 담은 언급을
  찾으면, 한 번의 검토 복구가 그 언급과 추출기가 따로 인용한 부분을 역할과 함께 알려 주고, 제안자는 그
  언급을 부분마다 언급 하나로 바꿉니다. 확장만 허용하는 규칙과 정확한 키 규칙에서는 그 언급만 제외합니다.
  그 단어는 여전히 복구된 언급 안에 있어야 하고, 목표는 그 언급을 가리키던 자리에서 부분을 가리킬 수 있으며,
  다른 모든 언급과 목표는 밝힌 값을 그대로 유지합니다. 복구된 형식은 같은 추출과 다시 검토하므로, 여전히
  합쳐져 있으면 보류합니다.
- **답의 종류**: 추출은 질문이 묻는 답의 닫힌 종류 하나도 알려 줍니다. 목록, 개수, 상태, 값, 위치, 관계,
  이력, 원인, 스키마, 기타 중 하나입니다. 어떤 목표도 그 종류에 답할 수 없는 형식은
  `review_answer_kind:<kind>`로 보류하므로, 현재 상태 조회는 서브넷이 어디에 있는지 답하지 못하고, 그 질문에
  답하는 컨테이너 읽기는 충실한 해석으로 남습니다. 관계가 있는 선택이나 탐색은 관계에 답하고, 결과가
  컨테이너인 포함 관계는 위치에도 답합니다. null이나 기타 종류, 비교, 초안은 판단하지 않으며, 상태로 거른
  목록은 상태 질문에도 답합니다.
- **스키마 동사**: 추출에는 declared나 have처럼 온톨로지 대상이 선언되었거나 선언을 가진다는 뜻만 나타내는
  단어를 위한 닫힌 `declares` 역할이 있습니다. 그런 단어는 모든 목표가 스키마 수준일 때만 구간이 필요 없고,
  인스턴스 목표 옆에서는 관계처럼 덮어야 합니다. 판독자가 제한으로 분류한 단어는 여전히 구간이 필요하므로,
  제안자가 실제 제한을 면제할 수는 없습니다.
- **닫힌 모호성 reader**: 판단이 명확화 요청으로 끝났지만 경로가 모든 선택 규칙을 통과한 해석을
  release했다면, 세 번째 모델 계열의 reader가 두 해석 중 어느 것도 보지 않고 가린 질문만 읽어 닫힌 질문
  하나에 답합니다. 질문에 그럴듯한 해석이 하나인지, 여럿인지, 알 수 없는지입니다. 하나일 때만 release된
  해석이 답하며, 다른 답, 무응답, 시간 초과, 실패는 모두 명확화 요청을 유지합니다. 게이트웨이는 자신의
  기준 시각과 몇 초 이내의 기준 시각만 받으므로, 계획은 그 판정 뒤에야 기준 시각을 받습니다. 구성은 추론 방향
  reader가 판단과 제안자의 계열도 블라인드 검토자의 계열도 아닐 때만 이 검사를 맡기고, 그렇지 않으면 항상
  명확화 요청이 우선합니다.

**현재 경로의 계획**

- **목록만 읽는 계획**: 파싱된 형식 해석이 필터 목록 하나로 답할 수 있는 것보다 많은 것을 묻고, 계획이 그런
  목록만 읽는다면, 판단의 단어에서 복구한 계획뿐 아니라 현재 경로의 어떤 계획도 거부권으로 보류합니다.
  목록만 읽는 계획이란 종류, 이름 일부, 식별자, 컨테이너로 객체를 읽거나 컨테이너에서 구성원으로 읽고, 그
  합집합과 투영, 그룹이 없는 개수만 구하는 계획입니다.
- **블라인드 해석의 역할**: 판단의 블라인드 해석이 그룹 기준을 밝혔는데 계획에 그룹 집계가 없거나, 관계를
  밝혔는데 어떤 탐색, 경로, 함수, 컨테이너 그룹이나 필터도 관계를 읽지 않으면, 플래너는 턴을
  `semantic_plan_constraint_uncovered`로 보류합니다. 이 검사는 블라인드 해석이 도착한 뒤에만 읽습니다.
  제한은 판단의 적용 범위 검토와 형식 해석이 맡습니다.
- **인스턴스 질문에 대한 스키마 답변**: 매니페스트, 선언, 관계 읽기와 그 집계로 온톨로지 선언만 읽는 계획은
  유형이 무엇을 선언하는지에 답합니다. 블라인드 해석이 질문이 상태, 값, 위치, 이력, 원인을 묻는다고 하면,
  플래너는 R2 중간 수준 검사로서 그 답변 종류와 함께 턴을 `semantic_reading_unverified`로 보류합니다.
  스키마, 목록, 개수, 관계를 묻거나 답변 종류가 판단되지 않은 질문은 이 검사로 보류하지 않습니다.

**보류**

계획 결과는 크기가 제한된 닫힌 `hold_details`를 가집니다. 해석이 덮지 않은 제약 역할, release된 해석이 읽지
못하는 원자, 명확화의 종류, 다른 답의 종류이며, 인용 위치나 단어는 담지 않습니다. Core 변환 결과는 일반적인
근거 보류 대신 `semantic_constraint_uncovered`, `semantic_plan_constraint_uncovered`,
`semantic_reading_ambiguous`, `semantic_reading_unverified`, `semantic_stated_constraint_unsupported` 같은 타입이
지정된 이유 코드를 유지합니다. 답변은 그 역할이나 원자 범주를 밝히는 검토된 두 언어 안내이며, 검토된
레이블이 없는 코드는 보여 주지 않습니다. Console은 각 해석 보류를 원본 사용 불가 안내 대신 다시 묻기나
지원되지 않음 안내로 보여 줍니다.

**선택자 레이블**

조회 매니페스트는 읽을 수 있는 각 ObjectType의 검토된 설명도 담습니다. 설명은 매니페스트 다이제스트가
묶는 릴리스에서 정해지며 설명자 밖에 두므로, 어떤 계획 프롬프트도 커지지 않고 고정된 매니페스트
다이제스트도 바뀌지 않습니다.

**지표 조회**

지표 reader가 읽을 수 있고 바인딩된 선언이면, 매니페스트는 검토된 지표 레지스트리의 개념과 설명도 제공하며
다이제스트가 그것을 묶습니다. 측정값이 지표인 조회는 바인딩된 Resource에 대해 측정값 언급을 두 블라인드
선택자가 근거화한 개념으로 `query.resource_metric_inventory`를 읽습니다. 시간을 밝히지 않으면 검토된 기본값인
15분 기간을, 밝혔다면 reader가 선언한 범위 안의 기간을 읽고, 답변은 읽은 기간을 다시 밝힙니다. V-SEM은 그
reader를 요구하고 현재 상태 조회로는 답하지 않게 하며, V-PROV는 개념이 그 바인딩에서 왔는지 확인하고 기간을
다시 계산합니다. 근거화되지 않은 지표, 한 번에 읽을 수 있는 수보다 많은 개념, 범위를 벗어난 기간은 타입이
지정된 지원되지 않음 이유를 돌려주며, 제공자가 그 Resource에 대해 읽지 못한 지표는 불완전으로 남습니다.

**Resource Health 필터**

Resource Health reader가 읽을 수 있고 바인딩된 선언이면, 매니페스트는 검토된 Resource Health 그룹과 각
그룹이 묶는 제공자 상태도 제공하며 다이제스트가 그것을 묶습니다. 밝힌 Resource Health로 거르는 목록은
컬렉션이나 범위의 구성원을 읽은 뒤, 근거화된 개념만으로 상태 개념 없이 `query.resource_health_inventory`를
읽습니다. 이 reader는 수집 범위를 알 수 없는 행과 다른 사용 불가 상태의 행도 돌려주므로, Resource Health로
거른 개수 질문은 행을 일치 항목으로 세지 않고 타입이 지정된 지원되지 않음 이유를 돌려줍니다. 또한 reader는
받은 상태 행을 합집합으로 더하지만 밝힌 제한은 교집합이므로, 상태와 Resource Health를 함께 밝힌 목표도 타입이
지정된 지원되지 않음 이유를 돌려줍니다. V-SEM은 근거화된 개념을 읽는 Resource Health reader가 결과 읽기를
거르고 목표에 답하도록 요구하고, 그 읽기가 밝힌 다른 제한을 모두 유지하도록 요구하며, Resource Health 행을
세는 집계는 거부합니다. V-PROV는 정확히 그 개념만 있고 상태 개념은 없는지 확인합니다. Resource 상태
reader도 같은 방식으로 확인하되, 그 행은 셀 수 있습니다.

**수명 주기 상태**

검토된 값 도메인은 속성을 해당 ObjectType의 수명 주기 상태로 표시할 수 있으며, `Incident.status`는
정식 Incident 상태로 이렇게 표시됩니다. 이 값 각각은 자신의 ObjectType과 속성을 밝힌 후보로 상태
카탈로그에 들어가므로, 두 블라인드 선택자는 상태 언급을 Resource 상태와 이 값 전체에 대해 근거화합니다.
수명 주기 값은 그 ObjectType 자신의 읽기에 대한 정확한 조건으로만 컴파일되며, 그 개수도 정확합니다.
다른 주어에 밝힌 수명 주기 값, 다른 ObjectType에 밝힌 Resource 상태, 둘을 섞은 언급은 타입이 지정된
지원되지 않음 이유를 돌려줍니다. 한 행은 속성마다 값이 하나이므로, 한 수명 주기 속성의 값을 여러 개
밝히면 하나의 합집합으로 읽고, 서로 다른 수명 주기 속성은 함께 제한합니다. V-SEM은 그 ObjectType의 모든 결과 읽기에 그 조건을 요구하고, V-PROV는 그 ObjectType의 읽기에서만
근거화된 값을 받습니다.

## 승인된 결정

Owner가 2026-09-28에 다음 결정을 승인했습니다.

1. 형식을 같은 판단 호출의 추가 필드로 전달합니다.
2. 컴파일 전에 두 단계 앵커 바인딩 읽기를 허용합니다.
3. 모호한 관계에는 명확화를 유지하고, `all_kinds`는 명시적 요청에만 수용합니다.
4. 상태 구간이 카탈로그에 근거하지 않을 때만 T2 상태 검토를 요구합니다.
5. 버전이 고정된 기본 이력 구간을 설정에서 관리합니다.
6. 검토된 제공자 리전 값 영역과 함께 `Resource.location`을 선언합니다.
7. 검토된 링크 근거 허용 목록을 보안 변환 결과로 노출합니다.
8. 결과 핸들을 영속하고 의미 요청 계약에 추가합니다.
