# 사람 보고선 및 승인 라우팅

이 문서는 FDAI가 통제된 조직 문서에서 검토 가능한 사람 보고 그래프를 만들고, 선택된 고위험
작업의 적격 승인자를 찾는 데 이 그래프를 사용하는 방법을 정의합니다. 보고 관계는 검토할 사람을
추천할 수 있지만 FDAI 역할, 승인 기능 또는 실행 권한을 부여하지 않습니다.

> **범위:** 이 설계는 문서에서 추출한 사람 간 보고 관계, 관계 확인, 독립 Owner 검토,
> 승인자에게 연락하기 위한 요청자 동의 및 사람 승인(HIL) 라우팅을 다룹니다. 에이전트 담당
> 체계, RBAC, ActionType 정책 및 실행 권한은 독립적으로 유지합니다.
>
> **롤아웃:** 새 report-line 동작은 shadow 모드에서 시작합니다. 배포 환경은 실제 승인 요청
> 전달에 사용하기 전에 현재 신원, 라우팅, 응답 및 잘못된 일치에 대한 근거를 수집해야 합니다.

## 설계 개요

운영자가 조직도 가져오기를 명시적으로 선택합니다. FDAI는 근거가 있는 보고 edge 후보를
추출하고 두 사람을 정확한 디렉터리 신원으로 해석합니다. 후보를 현재 디렉터리 및 보존된 그래프
근거와 비교한 후 관련 당사자에게 각 edge가 맞는지 확인하도록 요청합니다. 독립 Owner가 확인된
edge를 검토한 후에만 현재 보고 그래프에 들어갑니다.

ActionType에 report-line 승인이 필요하면 FDAI는 요청자에게 해당 요건을 설명하고 승인 경로에
연락해도 되는지 동의를 요청합니다. 동의 후 요청자부터 가장 가까운 적격 상위자까지 현재
그래프를 탐색합니다. 기존 ActionType 및 RBAC 정책이 그 사람의 승인 가능 여부를 결정합니다.
누락되거나 오래됐거나 충돌하거나 자격이 없는 경로는 보류 또는 무작업 결과가 됩니다.

## 독립적인 권한 축

구현은 다음 레코드를 분리합니다.

| 축 | 답하는 질문 | 부여하지 않는 권한 |
|----|-------------|---------------------|
| 에이전트 담당 체계 | FDAI 에이전트의 운영 영역을 누가 책임지는가? | 사람 승인, RBAC 또는 실행 |
| 사람 report line | 현재 누가 누구에게 보고하는가? | FDAI 역할 또는 승인 기능 |
| RBAC 및 ActionType 정책 | 이 정확한 작업과 범위를 누가 승인할 수 있는가? | 보고 관계 |
| 요청자 연락 동의 | FDAI가 이 정확한 승인 요청을 확인된 경로에 보낼 수 있는가? | 작업 승인 |
| HIL 결정 | 적격한 사람이 이 정확하고 변경할 수 없는 작업을 승인했는가? | 더 넓거나 미래의 작업 승인 |

한 사람이 여러 축에 참여할 수 있지만 한 축의 근거가 다른 축을 충족할 수는 없습니다.

## 확정된 설계 결정

- **Edge별 검토:** 각 `subject -> manager` edge에는 자체 다이제스트, 상태, 근거 및 결정이
  있습니다. Console에서 일괄 제출할 수 있지만 서버는 edge별 결과를 기록합니다.
- **2단계 활성화:** 관계의 한쪽 당사자가 edge를 확인하고, 서로 다른 현재 Owner가 승인합니다.
  업로더, 확인자 및 Owner는 모두 추적 가능합니다.
- **충돌 보류:** 업로드한 edge가 디렉터리 manager 근거나 활성 그래프 리비전과 충돌하면
  보류합니다. 어떤 출처도 자동으로 우선하지 않습니다.
- **가장 가까운 적격 상위자:** 승인 라우팅은 직속 관리자부터 시작해 상위로 이동합니다.
  관리자는 현재 ActionType, 범위, 역할, quorum 및 역할 분리 정책도 충족해야 합니다.
- **실패 시 차단:** 그래프가 충분한 적격 승인자를 제공하지 못하면 작업을 실행하지 않습니다.
  구성된 거버넌스 대상에게 담당 범위 복구 알림을 보낼 수 있지만 알림은 승인이 아닙니다.
  잘못됐거나 순환하거나 깊이 한도를 넘는 경로도 제어 루프를 벗어나지 않고 같은 감사 가능한
  경로 사용 불가 결과로 처리합니다.
- **직속 관리자 범위:** 초기 구현은 주체별 현재 시점의 활성 `primary_manager` edge 하나만
  사용합니다. 참고, 점선 보고, 멘토 및 프로젝트 관계는 승인 라우팅에 참여하지 않습니다.

## 통제된 조직 문서 수집

Report-line 추출은 운영자가 명시적인 `report_line_bootstrap` 용도를 선택한 뒤에만 시작합니다.
FDAI는 파일 이름, 첨부 텍스트 또는 일반 지식 업로드에서 이 용도를 추론하지 않습니다.

기존 문서 파이프라인은 업로드 인증, 바이트 제한, 악성코드 및 보호 검사, 형식 검증,
OCR, 변경할 수 없는 버전, 접근 서술자, 보존 및 감사를 담당합니다. Report-line consumer는
반입이 허용된 `DocumentEnvelope`만 받습니다.

### 추출 순서

1. `subject`, `manager` 및 선택적 유효 기간과 같은 명시적 구조 행을 해석합니다.
2. locator를 보존하면서 범위가 제한된 표와 계층 구조 단위를 해석합니다.
3. 결정론적 추출로 관계를 해석할 수 없을 때만 주입된 근거 기반 해석기에 요청합니다.
4. 제안된 모든 edge에 원본 인용을 요구합니다.
5. 각 당사자를 하나의 정확한 활성 사람 디렉터리 신원으로 해석합니다.
6. 모호하거나 불완전하거나 신뢰도가 낮거나 근거가 없는 제안은 검토 대상으로 보류합니다.

Upstream 기본 해석기는 판단을 보류합니다. 배포 환경에서 프로바이더를 연결할 수 있지만 모델
출력은 항상 제안이며 edge를 활성화할 수 없습니다. 결정론적 추출에서 근거가 있는 edge를 하나
이상 생성한 경우 워커는 해당 해석기를 호출하지 않습니다.

현재 소스 구현은 정확한 `subject`/`employee` 및 `manager`/`reports_to` 행과 지원되는 DOCX,
PPTX, XLSX 표 셀을 인식합니다. 구조 단위에서 연결선을 복구할 수 없는 시각적 조직도는 배포
환경이 근거 기반 해석기를 제공하지 않는 한 보류합니다. 따라서 레이아웃 추측이 조직 사실로
바뀌지 않습니다.

## 보고 edge 수명 주기

각 가져오기는 변경할 수 없으며 안전하게 재시도할 수 있습니다. Edge는 독립적으로 진행합니다.

```text
extracted
  -> identity_pending
  -> pending_confirmation
  -> pending_owner_review
  -> activation_pending
  -> active
```

Edge는 `unresolved`, `conflict`, `rejected`, `expired` 또는 `superseded` 상태가 될 수도 있습니다.

`activation_pending`은 그래프를 쓰기 전에 Owner 결정을 기록합니다. 이 시점부터 당사자 결정을
추가로 변경할 수 없습니다. 중단 후 재시도로 그래프 활성화를 완료할 수 있으며 두 사람의 결정이
영속적으로 확정되기 전에는 edge를 라우팅에 사용할 수 없습니다.

활성 edge는 다음을 기록합니다.

- 정확한 주체 및 관리자 principal 참조
- 관계 종류와 선택적 범위
- 유효 시각과 기록 시각
- 원본 문서, 버전, 다이제스트 및 인용
- 추출 방식과 신뢰도
- 한쪽 당사자의 확인 증적
- 독립 Owner 검토 증적
- 변경할 수 없는 그래프 리비전과 이전 버전 참조

한쪽 당사자가 명시적으로 거부하면 다른 당사자가 이전에 확인했더라도 edge는 `conflict`로
이동합니다. 충돌을 해결할 때는 새 후보를 만들며 이전 근거를 다시 쓰지 않습니다.

## 그래프 검증 및 최신성

현재 그래프 리비전은 다음 조건을 모두 충족할 때만 수락합니다.

- 자기 참조나 방향성 순환이 없습니다.
- 한 유효 시점에 주체별 활성 직속 관리자가 최대 한 명입니다.
- 양쪽 당사자가 정확한 활성 사람 신원입니다.
- 같은 주체에 대해 대체되지 않은 edge의 기간이 겹치지 않습니다.
- 탐색 깊이가 제한됩니다.
- 확인과 Owner 검토 체인이 완전합니다.
- 원본 및 디렉터리 근거가 만료되지 않았습니다.

전체 그래프 순환 감지는 edge 수와 독립적입니다. 제한된 탐색 깊이는 조직 크기 제한이 아니라
개별 요청자의 승인 경로를 해석할 때 적용합니다.
활성화는 집계 compare-and-set 전에 과거 유효 시간 경계를 검증합니다. 승인 읽기는 저장된 case
집합 다이제스트를 검증하고 요청 시점의 현재 snapshot만 구성하며 비동기 hot path에서 이차
복잡도의 과거 검증을 반복하지 않습니다.

Edge가 변경되거나 만료되면 감사를 위한 새 전체 그래프 리비전을 만듭니다. 대기 중인 승인
요청은 탐색한 모든 edge와 적격 rung을 포함한 별도의 경로 리비전을 유지합니다. 해당 경로가
바뀌면 새 라우팅 결정을 요구하지만 조직의 다른 곳에서 바뀐 무관한 edge는 요청을 무효화하지
않습니다.

## 관계 확인

양쪽 당사자 모두 확인 요청을 받을 수 있습니다. 한 명의 확인으로 Owner 검토 단계에 들어갈 수
있지만, 어느 한쪽이 명시적으로 부인하면 edge를 충돌 상태로 보류합니다.

독립 Owner는 다음 조건을 충족합니다.

- 기록된 확인자와 다른 사람입니다.
- 현재 Owner 역할을 보유합니다.
- 정확한 edge 다이제스트와 원본 리비전을 검토합니다.
- 누락된 당사자 확인을 대신할 수 없습니다.
- 그래프 승인을 운영 작업 승인으로 사용할 수 없습니다.

일괄 명령은 개별 edge ID, 예상 리비전 및 다이제스트를 포함합니다. 한 edge가 오래됐거나
유효하지 않아도 같은 일괄 요청의 다른 edge 결과는 변경되지 않습니다.

## 승인 요청 연락 동의

Report-line 라우팅은 HIL 항목을 보내기 전에 동의 상태를 추가합니다.

```text
approval_required
  -> awaiting_contact_consent
  -> consented
  -> approval_pending
```

동의 레코드는 요청자, 정확한 Action 다이제스트, 대상 범위, 경로 리비전 및 짧은 만료 시간에
결속됩니다. 이 동의는 알림만 허용합니다. Action, 대상, 라우팅 edge 또는 적격 rung이 바뀌거나
동의가 만료되면 다시 설명하고 동의받아야 합니다.

거절, 시간 초과 또는 사용할 수 없는 경로는 감사 레코드와 함께 무작업 결과가 됩니다. 일반적인
긍정 응답으로 다른 대기 요청을 승인할 수 없습니다. 응답은 서버가 발급한 동의 ID에 결속되어야
합니다. Operator는 변경할 수 없는 동의 요청에서 명령 시간을 가져오므로 같은 멱등성 키를
사용한 HTTP 재시도는 동일한 영속 명령을 생성합니다.
승인 만료 워커와 무응답 워커는 모두 더 짧은 동의 기한에 응답하지 않은 연락 요청을 종료합니다.
늦게 도착한 응답도 영구 대기 요청을 남기지 않고 같은 시간 초과 무작업 결과를 기록합니다.

## 적격 상위자 라우팅

승인 플래너는 계속 ActionType에서 필요한 역할과 quorum을 계산합니다. Report-line resolver는
다음 순서로 처리합니다.

1. 요청자의 현재 직속 관리자부터 시작합니다.
2. 고정된 현재 그래프 리비전에서 탐색하는 모든 edge를 검증합니다.
3. 요청자, 작업 대상 사람, 실행자 및 이전 승인자를 제외합니다.
4. 활성 신원과 ActionType 및 범위 승인 정책을 다시 검사합니다.
5. Quorum이 충족될 때까지 가장 가까운 서로 다른 적격 principal을 선택합니다.
6. 경로와 적격성 근거 다이제스트를 대기 중인 승인에 기록합니다.

경로가 quorum을 충족하지 못하면 FDAI는 임의의 Owner나 그룹으로 자동 확장하지 않습니다.
명시적인 ActionType 경로 정책만 별도 fallback을 선택할 수 있습니다. 기존 채널 fallback은
전달 실패를 계속 처리하고, 무응답 감독기는 승인된 적격 경로 안에서만 진행합니다.

결정이 도착할 때와 실행 직전에 적격성, 그래프 리비전, 동의 만료, Action 무결성 및 자기 승인
금지를 다시 검사합니다.

Report-line 정책과 런타임은 quorum `1`만 허용합니다. 더 높은 quorum이 필요한 ActionType은
별도로 검토된 다중 slot report-line 계약이 구현될 때까지 기존 workflow 또는 human-access
승인 경로를 계속 사용하며 지원하지 않는 quorum 값은 구성 중 실패합니다.

## 구성

기본값은 비활성입니다. Report-line 라우팅을 사용하려면 배포 환경에서 다음 입력을 모두
구성합니다.

| 설정 | 용도 |
|------|------|
| `FDAI_GRAPH_REPORT_LINES_ENABLED` | 문서 워커의 읽기 전용 Microsoft Graph 사용자 및 관리자 조회를 활성화합니다. |
| `FDAI_REPORT_LINE_CONFIDENCE_FLOOR` | 후보 신뢰도 하한을 설정하지만 활성화 권한은 부여하지 않습니다. |
| `FDAI_REPORT_LINE_APPROVAL_ROUTES_JSON` | 현재 quorum `1`을 사용하는 정확한 ActionType을 선택합니다. 빈 값은 기존 승인 경로를 유지합니다. |
| `FDAI_PANTHEON_APPROVER_ACTIONS_JSON` | 정규화된 각 사람 principal이 승인할 수 있는 정확한 ActionType을 나열합니다. |

현재 Graph 어댑터는 기존 워커 managed identity와 `User.Read.All`을 사용합니다. 디렉터리 쓰기
권한이나 실행기 자격 증명을 추가하지 않습니다.

## API 표면

| 메서드 및 경로 | 용도 |
|----------------|------|
| `GET /ingestion/uploads/{upload_id}/report-line-draft` | 권한이 적용된 근거 기반 추출 산출물을 읽습니다. |
| `GET /handover/reporting-lines` | 현재 principal에 맞게 제한된 그래프 및 검토 상태를 읽습니다. |
| `GET/POST /handover/reporting-line-cases...` | 변경할 수 없는 edge 사례를 생성, 조회, 확인 또는 독립 검토합니다. |
| `GET /hil/report-line-contact-requests` | 인증된 요청자가 소유한 연락 동의 요청을 나열합니다. |
| `POST /hil/{approval_id}/report-line-contact` | 작업 승인 없이 연락 동의 또는 취소를 기록합니다. |

## 에이전트 및 서비스 소유권

새 에이전트를 추가하지 않습니다.

| 단계 | 소유자 |
|------|--------|
| 문서 유입 | Huginn |
| 원본 및 그래프 검증 | Forseti |
| 당사자 확인과 독립 Owner 승인 | Var |
| 변경할 수 없는 관계 및 경로 감사 | Saga |
| 현재 그래프 변환 결과 | Muninn |
| 운영 작업 실행 | Thor |
| 결과 검증과 복구 | 기존 경계를 통한 Heimdall 및 Vidar |

Operator Service는 사람을 인증하고 변환 결과를 렌더링하며 타입이 지정된 명령을 게시합니다.
그래프 edge를 활성화하거나 승인 자격을 결정하거나 작업을 실행하지 않습니다. 문서 워커는
후보를 추출하지만 승인할 수 없습니다.

## 개인정보 및 보존

조직 문서와 보고 관계는 민감한 신원 데이터입니다.

- 일반 이벤트 토픽과 로그에는 이름이나 문서 텍스트 대신 안정적인 참조와 다이제스트를
  전달합니다.
- 사람은 자신이 당사자인 edge를 읽을 수 있고 Owner는 범위가 제한된 그래프를 검토할 수
  있습니다.
- Console decoder는 승인 권한이나 실행 권한을 주장하는 report-line 또는 연락 projection을
  거부합니다.
- 원본 인용에는 문서 접근 서술자를 계속 적용합니다.
- 보존 기간과 법적 보존은 배포 정책이 소유합니다.
- 대체된 edge는 감사 근거로 남지만 라우팅에는 사용할 수 없습니다.
- upstream 코드, 예제 및 테스트는 합성 신원만 사용합니다.

## Console 환경

`Governance > Agent oversight > Reporting lines`는 다음 정보를 보여 줍니다.

- 가져오기 상태 및 원본 최신성
- 인용과 신원 해석 상태를 포함한 추출 edge
- 당사자 확인 및 Owner 검토 상태
- 디렉터리 또는 현재 그래프 근거와의 충돌
- 활성 그래프 리비전과 커버리지 공백
- 각 상위자가 선택되거나 건너뛰는 이유를 설명하는 경로 미리보기

고위험 대화 요청에서는 Action 요약, 영향 범위, 예정된 report-line 경로, 만료 및
`승인 요청 보내기` 또는 `취소` 작업을 포함한 명시적 동의 카드를 표시합니다. 동의가
기록되기 전에는 알림을 보내지 않습니다.

## 롤아웃 및 검증

롤아웃은 다음 네 단계로 진행합니다.

1. 그래프를 활성화하지 않고 후보를 추출하고 검토합니다.
2. 검토된 그래프 리비전을 활성화하지만 경로 미리보기에만 사용합니다.
3. Report-line 경로와 기존 승인 경로를 shadow 모드에서 비교합니다.
4. 측정 근거를 확보한 후 명시적으로 선택한 ActionType과 범위를 승격합니다.

권한이 없는 경로, 오래된 edge 사용, 신원 불일치, 동의 우회 또는 자기 승인이 발견되면 기능을
shadow 모드로 내리고 영향을 받는 작업을 보류합니다.
