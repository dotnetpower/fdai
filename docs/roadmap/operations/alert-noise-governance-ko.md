# 알림 과다 수신 관리

이 기능은 사용자, 팀, 역할, 채널에 전달되는 불필요한 알림을 shadow 우선으로 평가합니다.
조정 안내와 승인에 결속된 Azure 알림 변경을 분리하며, 업무 방해 감소나 대응 유지 성과를
보고하기 전에 독립적인 근거를 요구합니다.

> **구현 경계:** shadow 우선 구현이며 운영 도입에는 아직 충족해야 할 조건이 있습니다.
> 카탈로그 작업 네 개와 명시적으로 연결하는 런타임 처리 구조는 구현되어 있지만, 이 기준점은
> 공급자 알림 테스트, Azure 변경, 승격, 게시 또는 적용 완료를 입증하지 않습니다. 보고서 조회,
> 권고 수락, 선호 설정 활성화만으로 변경 권한이 생기지 않습니다.
> 아래 요구 사항은 목표 계약으로 유지합니다. 현재 한계와 구현 원장은 구현된 처리 구조와
> 아직 확보하지 못한 운영 근거를 구분합니다.
>
> **책임 경계:** 이 문서는 조직 단위 알림 과다 수신 평가와 범위가 제한된 변경 제안을
> 담당합니다. FDAI 발신 라우팅은 [채널과 알림](../interfaces/channels-and-notifications-ko.md),
> 실행 계약은 [액션 온톨로지](../decisioning/action-ontology-ko.md)가 계속 담당합니다.
> 최초 공급자는 Azure이며 공통 계약은 공급자 중립적으로 유지합니다.

## 한눈에 보는 설계

어떤 규칙이 누구에게 왜 알리는지 읽기 전용 보고서로 먼저 확인합니다. 변경하지 않는 기준선과
라우팅, 일정 또는 평가 조건 중 하나를 바꾸는 안을 비교하고, 전체 영향 범위에 권한을 가진
담당자의 승인을 받은 뒤 독립 관측자가 결과를 검증합니다. 알림 빈도가 높다는 사실만으로
잘못된 경보라고 판단하지 않습니다.

**예:** 사용자 500명과 팀 20개로 구성된 합성 조직에서 구독 역할 기반 이메일과 공용 메일링
리스트의 수신자가 겹칠 수 있습니다. FDAI는 중복 경로를 설명하고, 보호 대상이 아닌 경보에 대해
이미 설정된 서비스 당직 수신처를 제안하며, 중요 경보 경로를 유지한 채 승인을 요청합니다.
실제 전달 근거가 확보되기 전까지 수신 건수는 추정치입니다.

## 1. 범위와 경계

| 영역 | 최적화할 수 있는 항목 | 입증하거나 변경할 수 없는 항목 |
|------|------------------------|---------------------------------|
| 탐지 | 중복 조건, 반복적인 상태 전환, 임계값 및 평가 구간 후보 | 경보가 적은 탐지기가 반드시 더 좋은 탐지기는 아닙니다. |
| Azure 전달 | Alert Rule 연결, Action Group 알림 수신자, 범위가 제한된 Alert Processing Rule 일정 | FDAI 내부 중복 제거로 Azure 이메일이나 SMS가 중단되지는 않습니다. |
| FDAI 전달 | 기존 채널 경로, 인시던트 묶음 처리, A4 요약 | 채널이 요청을 접수했다는 사실은 구성원별 수신이나 열람을 입증하지 않습니다. |
| 개인 선호 설정 | 기존 브라우저 알림 선택과 공급자가 제공하는 구독 해제 안내 | 한 사람의 선호 설정으로 공용 Azure 규칙이나 필수 당직 대응 체계를 바꿀 수 없습니다. |

- **포함 범위:** 같은 테넌트의 승인된 여러 구독 평가, 팀/역할별 중복 수신, 실행 가능한 조정
  안내, 명시적 변경 승인, 제한적 적용, 검증 및 복구를 다룹니다.
- **제외 범위:** 테넌트 간 변경, 사서함 본문 수집, 메일을 줄이기 위한 Azure RBAC 또는 Entra
  구성원 변경, 탐지기 삭제, 일괄 비활성화, 학습 결과에 따른 자율 억제는 다루지 않습니다.
  새 Azure 리소스는 코드형 인프라(IaC)로 준비하며 대화나 작업 흐름의 인라인 작업으로 만들지 않습니다.
- **보호 대상 알림:** Azure Sev0/Sev1, 보안/규정 준수, 서비스 상태, 복구, 텔레메트리 손실,
  필수 승인, 정책이 지정한 서비스 수준 목표(SLO) 경보는 이 기능으로 억제, 지연, 등급 하향
  또는 요약 전환할 수 없습니다. 분류가 불명확한 알림도 보호 대상입니다.
- **인시던트 경계:** 진행 중인 인시던트가 의존하는 탐지기나 경로는 조정하지 않습니다.
  관련 없는 인시던트가 독립된 범위의 평가까지 막지는 않습니다. 폭주 대응은 기존 인시던트
  작업 흐름이 담당하며, 알림 감소를 인시던트 해결로 취급하지 않습니다.

## 2. 근거와 수신 대상 모델

[운영 온톨로지](../architecture/operating-ontology-ko.md)를 재사용합니다. 경보 규칙과 작업
그룹에는 `Resource`, 측정된 전달에는 `Observation`, 과다 수신에는 `Finding`, 운영 의도에는
`Ownership`과 `ChangeWindow`를 사용합니다. 변경 수명 주기에는 `DecisionCase`, `ActionOption`,
`ExpectedEffect`, `Change`, `Process`, `ActionRun`, `ObservedOutcome`을 사용합니다.
상관관계 키만으로 인시던트가 생성되지는 않습니다.

기존 `routes_to` 관계는 리소스 라우팅을 설명하며 사람의 권한을 뜻하지 않습니다. 구현된 수신
대상 및 평가 기록은 기존 구조에 연결되는 버전 관리 및 스키마 검증 비공개 근거입니다.
가변 권한 객체나 인벤토리의 사실이 아닙니다. 필요한 리소스, 속성 또는 관계 선언은 담당 주체와
출처를 갖춰 등록합니다. 비공개 `ProcessingRule` 기록이 이 등록을 대신하지는 않습니다.

| 근거 기록 | 필수 내용과 해석 |
|-----------|------------------|
| 구성 스냅샷 | 공급자 규칙 종류, 정확한 범위, 활성 상태, 원래 심각도와 매핑된 심각도, 조건, 평가 의미, 참조 그룹/처리 규칙, 원본 개정 번호, IaC 소유권 및 역방향 의존성 |
| 수신 대상 스냅샷 | 수신자 연결 종류, 범위가 지정된 가명 principal 또는 그룹 참조, 역할/담당 체계 개정 번호, 기본/백업 임무, 구성원 정보의 완전성 및 허용된 공개 등급 |
| 전달 관측 | 원본 경보 신원, 발생/해제 묶음, 규칙 개정 번호, 수신처, 시도/접수/전달/확인 상태, 이벤트 시각 및 증적 참조 |
| 평가 | 고정된 관측 구간, 근거 기준 시점, 쿼리/정책 버전, 수집 범위, 사용할 수 없는 출처, 무변경 기준선, 중복 수신의 상하한 및 서비스/팀별 점검 결과 |
| 변경 제안 | 단일 조정 축, 정확한 변경 전후 차이, 대상과 의존성 개정 번호, 영향받는 수신 대상, 보호 경로, 예상 효과 범위, 만료, 복구 참조 및 불변 다이제스트 |

모든 기록에는 출처 신원, 효력/이벤트/기록 시각, 최신성 정책, 완전성, 출처 다이제스트 및 합성
여부도 포함됩니다. Workflow 전달 참조는 수신 대상 참조와 달리 숫자로 시작하는 UUID와
제한된 길이의 전체 신원을 보존합니다. 늦게 도착한 근거는 새 개정 번호를 만듭니다. 공급자 속도 제한, 지원되지 않는
이력, 페이지 수집 실패, 디렉터리 권한 부족은 `unknown` 또는 `partial`로 남으며,
알림 0건이나 빈 수신 대상이 되지 않습니다.

유효 라우팅을 완전히 확인하지 못하면 개별 점검 결과뿐 아니라 보고서 전체도 부분 확인으로 표시합니다.

### 수집과 개인정보 보호

- **읽기 권한 분리:** 주입된 읽기 전용 공급자가 허용된 Azure 구성과 경보 이력을 수집합니다.
  별도 권한을 받은 디렉터리 해석기가 범위가 제한된 구성원 근거를 제공합니다. Azure 읽기 권한은
  Microsoft Graph 접근 권한을 뜻하지 않으며 평가 중 새 권한을 부여하지 않습니다.
- **수신 대상 종류:** 직접 수신자, 배포 목록, 구독 역할 기반 수신자, 팀 채널, 당직 일정을
  구분합니다. Azure 역할은 수신 메커니즘일 뿐 서비스 소유권, FDAI 역할 또는 승인 자격의
  근거가 아닙니다. 외부 대상이나 확인되지 않은 구성원 확장은 알 수 없음으로 유지합니다.
- **신원:** 같은 테넌트와 목적 안에서 검증된 신원 연결만 중복 제거합니다. 추측 가능한 이메일
  해시 대신 불투명 참조나 키를 사용하는 가명 참조를 사용합니다. 주소와 공급자 식별자는 통제된
  비공개 저장소에 보관합니다. 이 값과 메시지 본문, 비밀값이 포함된 웹훅 구성은 모델 프롬프트,
  감사 데이터, 예제 및 저장소 산출물에 포함하지 않습니다.
- **최소 공개:** 보고서는 허용된 서비스/팀별 집계 수신자 수를 보여 줍니다. 구성원 상세 조회에는
  별도 범위 권한이 필요합니다. 소규모 집단은 배포의 정보 가림 정책을 따릅니다. 유한한 보존 기간,
  법적 보존, 삭제 및 접근 감사는 기존 데이터 거버넌스를 따릅니다.
- **수신 추정 금지:** 메일링 리스트 구성원 수는 잠재 도달 범위이며 관측된 전달 건수가 아닙니다.
  채널 간 중복 제거에는 검증된 신원 연결이 필요하며, 확인할 수 없는 교집합은 상하한으로
  표시합니다. 전달 실패와 Azure 속도 제한을 성공적인 감소로 계산하지 않습니다.

### 현재 근거 구현

범위가 제한된 Azure 조회기는 메트릭, 로그, 활동 경보 구성과 Action Group, 처리 규칙,
24시간 경보 인스턴스 이력을 수집합니다. 디렉터리 구성원 확인, 현재 서비스 담당 체계,
인시던트와 전달 근거, 전체 역방향 의존성, 과거 규칙 개정 번호가 없으면 Azure 자체 근거는
부분 상태로 유지됩니다. 현재 규칙 개정 번호를 과거 경보의 버전으로 사용할 수 없습니다.
`AdmittedAlertEvidenceSource`는 독립적인 수락 검사를 거친 최신 범위/출처 결속 기록으로만
정확한 Azure 스냅샷을 보강합니다. 실패한 Azure 조회를 대체하거나 확인된 구성을 바꾸지 않습니다.
팩터리는 조회기를 제공할 뿐, 독립적으로 생성해야 할 증적을 만들어 내지 않습니다.

비공개 알림 기록은 최대 8 MiB, JSON 항목 250000개, 깊이 32단계의 전용 정규 인코더를
사용합니다. 모든 바이트를 해시에 포함하고 기존 작은 기록의 해시값을 유지하며, 온톨로지
쿼리의 64 KiB 한도는 늘리지 않습니다. 보고서와 버스 결과에는 기존의 더 작은 전송 한도를
계속 적용합니다.

## 3. 결정론적 진단과 권고

고정된 근거에는 T0(결정론적 규칙)를 먼저 적용하고 T1(경량 유사 사례 재사용)을 사용합니다.
T2(근거에 기반한 LLM 추론)는 남은 모호성에만 선택적으로 사용하며 기존의 혼합 모델 검토,
검증기, 위험 및 승인 경계를 유지합니다. Bragi는 타입이 지정된 결과를 설명합니다. 텍스트가
쓰기 대상을 선택하거나 수신자를 만들어 내거나 권한을 부여하지 않습니다. 사용자 범위가 모호하면
먼저 명확하게 확인합니다.

| 관측된 증상 | 필요한 근거 | 우선 권고 |
|-------------|-------------|-----------|
| 수신 경로 중복 | 검증된 연결/신원 교집합과 원본 경보 묶음 | 필수 대응 체계를 보존하면서 불필요한 알림 경로 하나를 제거합니다. |
| 광범위한 구독 역할 이메일 | 실제 공급자 수신 의미와 서비스 소유권 | 기존 서비스 수신 대상을 연결하며 Azure 역할을 제거하지 않습니다. |
| 잦은 발생/해제 전환 | 공급자의 상태 유지/비유지 동작과 메트릭 이력 | 반복 억제나 평가 후보를 비교하며 모든 재발을 중복으로 분류하지 않습니다. |
| 예상된 유지 관리 알림 | 승인된 구간, 정확한 리소스, 완전한 유효 라우팅 | 보호 대상과 자동화 검사를 통과한 뒤에만 유한한 알림 구간을 검토합니다. |
| 가치가 낮은 정보성 업데이트 | 검토된 분류, 전달 기한, 기존 FDAI 수집 경로 | 기존 FDAI 경로로 A4 요약을 제안하며 Azure 자체 요약 기능이라고 주장하지 않습니다. |
| 오래되거나 담당자가 없는 수신처 | 현재 담당자 및 기본/백업 전달 근거 | 담당 체계를 먼저 복구하고 대체 경로가 입증될 때까지 제거를 보류합니다. |

기존 `alert.storm`과 `alert.flapping` 규칙은 신호로 사용하며 쓰기 권한으로 사용하지 않습니다.
모든 권고에는 근거, 알 수 없는 항목, 제외한 대안, 예상 이득 범위 및 수동 조정 안내를 포함합니다.
단일 축의 기준선/조정안 비교 절차는 [경보 튜닝 지침](../../runbooks/alert-tuning-ko.md)을
따릅니다. 변경 없음과 검토 보류도 정식 결과입니다.

## 4. Azure 동작 정확성 경계

공개 Microsoft Learn 동작 설명을 2026-09-14에 검토했습니다. 쓰기 기능을 제공하려면 공급자
어댑터에 고정된 API/버전별 기능 명세와 일치성 근거가 필요합니다.

| Azure 메커니즘 | 이 설계에 미치는 영향 |
|----------------|----------------------|
| 여러 경보 규칙이 Action Group을 공유할 수 있음 | 편집하는 리소스 수뿐 아니라 역방향 참조와 수신 범위를 계산합니다. 알 수 없거나 범위 밖인 의존 대상이 있으면 변경을 차단합니다. |
| Action Group에는 알림과 자동화 작업이 함께 포함됨 | 웹훅, Event Hub, Function, Logic App, Runbook 및 인시던트 연계 동작을 보존합니다. 그룹 전체를 이메일 전용으로 취급하지 않습니다. |
| Alert Processing Rule 억제는 일치하는 발생 경보의 모든 작업 그룹을 제거함 | 개인별 알림 끄기가 아니며 자동화나 FDAI 수집을 중단할 수 있습니다. 필수 작업이나 근거 경로가 해당 호출에 의존하면 억제를 차단합니다. |
| 억제가 그룹 추가보다 우선함 | 겹치는 그룹 추가 규칙으로 중요 경보 경로를 보존할 수 없습니다. 모든 유효 규칙, 필터, 범위 및 일정을 함께 평가합니다. |
| 억제된 경보는 조회할 수 있지만 구간 종료 후 다시 발송되지 않음 | 원본 근거를 보존하고 해당 구간을 독립적으로 대조합니다. 복구로 누락된 호출이나 알림 없이 지난 시간을 되돌릴 수는 없습니다. |
| 처리 규칙 변경이 반영되기까지 최대 30분이 걸릴 수 있음 | 반영 지연과 관측 한도를 선언합니다. 즉각적인 폭주 완화를 약속하거나 API 접수를 활성화로 간주하지 않습니다. |
| 처리 규칙은 Azure Service Health 경보에 영향을 주지 않음 | 지원되지 않는 메커니즘임을 명시하며 모든 Azure 경보를 억제할 수 있다고 표현하지 않습니다. |
| ARM 역할 이메일과 채널 구성원은 공급자별 규칙을 따름 | 지원되는 구독 역할 의미와 반영 지연을 기록합니다. 상속, 자격만 있는 역할, 중첩 또는 확인되지 않은 역할을 임의의 수신자로 바꾸지 않습니다. |

출처는 [Alert processing rules](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-processing-rules)와
[Action groups](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/action-groups)입니다.
알림 테스트는 사람에게 연락하거나 작업을 호출할 수 있습니다. 따라서 명시적으로 승인된 외부
효과이며 읽기 전용 평가에 포함하거나 무해한 예행 실행 대용으로 취급하지 않습니다.

## 5. 승인과 변경 경계

| 요청 | 필요한 권한 |
|------|-------------|
| 보고서 조회 또는 시뮬레이션 | 현재 범위에 대한 읽기 권한이며 실행기 신원은 제공하지 않음 |
| 개인 선호 설정 설명 | 인증된 당사자의 기존 선호 설정 계약이며 공용 구성 쓰기는 없음 |
| 공용 변경 준비 | 권한 있는 요청자와 검증된 담당 체계이며 실행되지 않는 제안만 생성 |
| 공용 라우팅, 억제 또는 평가 조건 변경 승인 | 정확한 계획과 모든 영향 서비스에 대해 Var를 통한 독립적인 사람 승인 |
| 실행 또는 복구 | Thor의 범위 제한 실행기, 현재 위험 판정, 승격, 안전장치 및 승인에 결속된 복구 계약 |

공용 변경의 첫 제공 단계에는 권한 있는 서로 다른 두 사람의 승인을 요구합니다. 서비스 최종
책임자 승인 경로와 Owner 수준의 변경 권한 승인 경로를 분리합니다. 요청자와 실행자는 어느
승인 자리도 맡을 수 없습니다. 직함, Azure 이메일 역할, 채팅 확인 또는 그룹 구성원 자격만으로
이 권한이 생기지 않습니다. 담당자나 백업 대응 체계가 없으면 제안을 보류합니다.
영향받는 모든 서비스에는 권한 있는 담당자의 결정이 필요합니다. 한 승인자가 여러 서비스를
대표하려면 해당 범위가 검증되어야 합니다. 공용 그룹을 작은 요청으로 나눠 승인 정족수를 피할 수 없습니다.

승인은 계획 다이제스트, 정책과 작업 흐름 버전, 대상 개정 번호, 전체 의존성 및 수신 대상
스냅샷, 변경 구간, 만료 및 복구 범위를 고정합니다. 중요한 변경이나 철회가 발생하면 승인이
무효가 됩니다. 카드를 보낼 때뿐 아니라 실행 직전에 다시 검증합니다. 무응답, 승인 시간 초과,
처리 용량 부족은 변경 없음이나 상위 담당자 검토로 이어지며 동의로 해석하지 않습니다.
상시 승인 권한(`autonomy.a3_e`)은 이 기능의 첫 제공 범위에서 제외합니다.
반영 지연, 실행, 관측 및 복구의 선언된 기한이 각각의 승인 유효 구간 안에 들어와야 실행을
허용합니다. 복구는 승인된 계획에 별도로 결속합니다. 만료되거나 철회된 정방향 승인이 포괄적인
복구 권한으로 바뀌지는 않습니다.

### 등록된 작업과 현재 전달 한계

네 `ActionType` 선언은 `default_mode: shadow`, `pr_revert`, `execution_path: pr_manual`로 등록합니다.
작업 인자는 보존된 정방향 계획의 64자리 소문자 `plan_digest` 하나이며 호출자가 고른 변경 필드는 받지 않습니다.
등록은 승격이 아닙니다. 현재 Var 승인 정족수, 위험 판정, 원본 작성자 통제, 안전장치 및 독립 증명이 전달 조건입니다.
런타임 지원 매니페스트는 집중 테스트에 근거한 조건부 Core 실행, 관찰 및 복구를 기록하며 실제 운영 준비를 입증하지 않습니다.
현재 정책에 따라 T2는 `shadow_only`를 유지합니다.

| 등록된 ActionType | 구현된 제한적 변경 | 전달 경계 |
|-----------------|--------------------|----------------|
| `ops.update-alert-routing` | 보호 대상이 아닌 메트릭 또는 예약 쿼리 규칙 하나에서 기존 Action Group 연결 하나 교체 | 정확한 기존 Terraform JSON 작업 목록만 변경하며 수신자 재작성, 리소스 생성, 직접 Azure 대체 경로는 없음 |
| `ops.set-alert-notification-window` | 정확한 규칙 하나를 대상으로 기존 비활성 억제 규칙에 유한한 UTC 구간 설정 | 정확한 기존 Terraform JSON 일정만 변경하며 완전한 유효 규칙, 보호 경로 및 독립 수집 근거 필요 |
| `ops.tune-alert-evaluation` | 단순 메트릭의 임계값, 평가 구간 또는 주기 중 하나 변경 | 임계값은 같은 측정 구간을 사용하며 시간축 재생에는 균일한 표본, 사례별 재현율/지연 보호 및 정확한 Terraform 기간 필드 필요 |
| `ops.restore-alert-configuration` | 현재 바이트가 정방향 결과와 같을 때만 보존된 계획의 고정 기준선 복원 | 별도로 유효한 복구 권한에 따라 `pr_manual`을 사용하며 새 개정본은 덮어쓰지 않음 |

`AlertPlanArtifactPreparer`는 이미 연결된 GitOps 어댑터로 정확한 기존 Terraform JSON 파일을
읽고 원본/결과 다이제스트와 정방향/복구 바이트를 보존합니다. 그룹 참조는 실제로 관측된
Action Group에 연결되어야 합니다. 원본 조회는 다른 작성자 배제를 입증하지 않습니다.
권한 경계에는 저장소와 의존성을 포함하는 독립적으로 수락된 작성자 배제 증명이 여전히 필요합니다.
대체 그룹을 만들거나 직접 Azure 쓰기로 우회하는 어댑터는 제공하지 않습니다.

리소스 생성, 교체, 알림과 자동화를 함께 바꾸는 편집, 구독 전체 억제, 끝이 없는 반복 구간 및
자동 승인은 차단합니다. 새 그룹이나 처리 규칙은 별도로 승인된 IaC 선행 조건입니다.
허용된 영향 경계를 넘는 기존 공용 그룹은 다시 설계할 때까지 안내만 제공합니다.
제안을 실행하기 위해 공급자 권한을 늘리지 않습니다.

## 6. 에이전트와 영속 데이터 소유권

고정된 판테온과 [운영 계획](../decisioning/operational-planning-ko.md) 구조를 사용합니다.
알림 최적화 전용 에이전트, 대체 작업 흐름 엔진, 공유 가변 조정기 또는 Console의 직접 공급자
호출은 추가하지 않습니다.

| 책임 | 담당 에이전트와 경계 |
|------|---------------------|
| 수집과 정규화 | Huginn이 정규화된 Event를 소유하며 전달 어댑터는 기계적인 읽기만 수행 |
| 과다 수신 근거와 독립 결과 | Heimdall이 Thor와 독립적으로 관측 점검 결과와 효과 검증을 담당 |
| 맥락, 적격 제안, 최종 결정 | Forseti가 범위가 제한된 DecisionCase와 안전성 결정을 소유하며 Odin은 적격 대안만 비교 |
| 선언 검토 | Mimir가 정확한 규칙, 작업, 작업 흐름 및 온톨로지 버전을 검증 |
| 사람 승인 | Var가 작업에 결속된 승인 근거를 소유 |
| 적용과 복구 | Thor만 공급자 변경을 전달하며 Vidar의 복구 계획도 같은 경로를 사용 |
| 근거와 감사 | Muninn이 담당 읽기 모델을 구성하고 Saga가 추가 전용 의도와 최종 결과를 기록 |
| 설명과 학습 | Bragi가 범위가 지정된 조정 안내를 표현하고 Norns가 Mimir 검토용 비활성 개선안을 제안 |

평가의 결정 진행은 Forseti가 책임집니다. 기존 단일 작성자 Process 런타임은 담당 주체가
발행한 타입 지정 이벤트를 개정 번호 비교 후 갱신 방식으로 기록합니다. 새로운 결정자가 아닌
전달 역할입니다. Muninn과 Operator의 조회 결과는 Process를 진행시키지 않습니다. 권한을
전달하는 인계에는 스키마 검증 발행/구독, 발행자 소유권, 선행 단계 신원, 기한, 멱등성,
독립적인 재시도와 처리량 제어를 적용합니다. 필요한 근거가 없으면 보류로 종결합니다.

평가 단계는 정본 Process 상태를 대체하지 않고 하위 이벤트로 기록합니다.
`evidence_frozen`, `assessment_ready`, `proposal_ready`, `approval_pending`, `dispatch_recorded`,
`effect_observing`, `outcome_recorded`를 사용합니다. 거절, 만료, 충돌, 취소 또는 검증 실패가
발생하면 정방향 전달을 중단합니다. 복구에는 기존 보상 및 자동화 보류 계약을 사용하며,
중단된 시도를 관련 없는 새 계획으로 재시도할 수 없습니다.

Core는 결정, Operator는 요청 발신함과 조회 결과, Executor는 전달 상태를 소유합니다.
서비스는 서로의 테이블이 아닌 타입 지정 이벤트를 교환합니다. 서명 명령/결과/준비 상태
코덱은 정확한 모델과 한도를 보존하며 구버전 미지원은 하향 변환이나 준비 상태를 허용하지 않습니다.
양쪽 수신기를 먼저 설치하고 활성화하며 롤백 시 접수된 작업을 보존합니다. 관측 산출물은
비공개입니다. 로컬과 배포는 같은 계약과 검사를 사용하며 로컬 특권 신원이나 새 서비스/브라우저
실행기를 추가하지 않습니다. 결정론적 평가에 실제 모델 의존성도 새로 추가하지 않습니다.

명시적으로 연결하는 런타임은 기존 Workflow 조정기, Process 저장소, Var 승인 경로,
승격 레지스트리, 안전장치 수명 주기 및 GitOps 게시기를 재사용합니다. 재개 시에도 정확한
계획, 작업 흐름, 대상, 모드 및 상관관계를 유지하며 재생으로 shadow Process를 승격하지 않습니다.
`bind_alert_effect_runtime`은 Heimdall/Forseti 콜백과 보존된 게시 기록의 제한적 대조 처리를
정본 전달, 종결, 결과 저장소에 연결합니다. 독립 효과 수락과 별도의 Workflow 결과 수락이
여전히 필요하며 팩터리 구성으로 이 증적을 생성하지 않습니다.
구성 키와 선행 조건은 [운영자 런북](../../runbooks/alert-noise-governance-ko.md)을 참조하세요.

Operator는 보고서나 계획 조회 결과를 갱신하기 전에 인증된 최종 결과를 한 번만 삽입하여
확정합니다. 충돌하는 결과는 조회 결과를 바꿀 수 없습니다. 중단 후에는 정확히 같은 보존
결과를 재생해야만 멱등적인 조회 결과 저장을 마칠 수 있습니다.
PostgreSQL 작업 선점은 매개변수로 전달한 네임스페이스, 독점 행 임대와 정확한 작업자 검사를 사용합니다. 알림 기록과 Workflow 승격 결정은 출처에 결속된 실패 시 거부 검증과 함께 공유 근거 수락 목록에 등록합니다.
계획 처리기는 의존성 입출력 후와 산출물 또는 Workflow 인계 전에 요청 기한과 현재 허용 범위를
다시 확인합니다. 최종 기록에는 수락 시각이 아닌 현재 시각을 사용합니다.

## 7. 제한적 적용과 복구

[헌법의 7대 안전장치](../architecture/fdai-constitution-ko.md)는 모든 상태 변경에 적용합니다.
구현은 다음 필수 증명을 검사합니다. 이 기준점만으로 증명의 독립 생성이나 운영 검증이
이루어졌다고 볼 수는 없습니다.

| 안전장치 | 필요한 증명 |
|----------|-------------|
| 중단 조건 | 보호 경로 손실, 오래된 맥락, 새 의존성, 관련 활성 인시던트, 신원/정책 변경, 텔레메트리 손실 또는 기한 도달 시 정방향 작업 중단 |
| 검증된 복구 | 고정된 이전 필드, IaC 개정 번호, 승인된 복구 작업, 예상 복구 시간 및 독립적으로 관측한 복원 |
| 영향 한도 | 명시적 리소스/규칙/수신 대상/의존성 목록이며 실행 단위마다 리소스 그룹에 준하는 경계 하나 적용 |
| 성공한 예행 실행 | 정확한 공급자 형식 검증, IaC 변경 차이, 완전한 유효 라우팅 시뮬레이션, 양성/음성 시나리오 및 보호 경로 불변 |
| 논리 대상 잠금 | 변경 객체와 공용 라우팅 의존성의 안정적인 키, 지원되는 경우 공급자 자체 개정 번호 검사 |
| 안정적인 멱등성 | 재시도와 재시작에서도 같은 계획, 대상 개정 번호, 효과 및 구간은 하나의 전달 신원 재사용 |
| 2단계 감사 | 전달 전 Saga 의도 기록, 이후 모든 증적 참조를 포함한 권위 있는 적용/보류/실패/복구 결과 기록 |

공급자가 조건부 갱신을 강제하지 않으면 프로세스 내부 잠금과 읽기 후 쓰기 검사만으로는
충분하지 않습니다. 다른 포털, IaC 또는 자동화 작성자가 대상을 바꿀 수 없음을 통제된 독점
작성 메커니즘으로 입증하기 전까지 해당 쓰기는 사용할 수 없습니다. 작성 주체를 모르면 보류합니다.
중요 라우팅 의존성에도 변경 확정까지 같은 보호를 적용합니다. 참고용 역방향 관계 스냅샷이나
다른 작성자를 통제하지 않는 잠금은 새 경보 규칙 연결을 방어하지 못합니다.

고정된 기준선과 조정안을 먼저 비교합니다. 기존의 보호 대상이 아닌 규칙 하나와 서비스 하나로
시험 적용하고, 선행 결과가 종결된 후에만 독립적으로 승인된 다음 단위로 진행합니다.
원래 경로를 제거하기 전에 대체 경로와 기본/백업 담당자의 도달 가능성을 입증합니다. 알림
테스트에는 별도의 외부 효과 승인 범위가 필요합니다. 일시적인 이중 전달은 감소 성과가 아닌
명시적 전환 비용이며 대체 경로를 사용할 수 없으면 전환을 차단합니다.
각 임시 구간에는 공급자가 강제하는 절대 종료 시점, 명시적 표준 시간대와 일광 절약 시간 해석,
최대 기간 및 만료 후 검증이 필요합니다. 정리 작업을 만료 메커니즘으로 대신하지 않습니다.
반복적인 업무 시간 외 억제는 첫 제공 범위에서 제외합니다.

취소는 새 효과를 막지만 이미 적용한 필드를 되돌리지는 않습니다. 관련 없는 동시 편집을
보존하면서 의존성 역순으로 복구합니다. 접수 여부가 불명확하면 다시 보내거나 복원하기 전에
독립적으로 대조합니다. 검증되지 않은 복구는 `recovery_incomplete`로 기록하고 영속 자동화
보류를 유지하며 영향받지 않은 채널로 담당자를 호출합니다. 중단 스위치는 새 최적화를 막지만
이미 승인된 복구를 비활성화하지 않습니다.

## 8. 측정과 운영자 경험

원본 경보 묶음, 알림 시도, 확인된 채널 전달, 관측된 사람의 확인을 구분해 허용된 서비스/팀과
시간 구간별 중복 및 업무 방해를 보고합니다. 잠재 수신 범위와 계산된 감소량은 추정치이며
개인별 전달이 아닙니다. 비어 있거나 관측이 끊겼거나 사용할 수 없는 표본을 0으로 취급하지 않습니다.

평가 조건 변경에는 원시 텔레메트리와 독립적으로 정답을 부여한 양성, 음성 및 누락 인시던트
사례가 필요합니다. 임계값 재생은 같은 측정 구간을 사용합니다. 구간/주기 재생은 완전한 균일
메트릭 표본, 동일한 평가 주기 기준 시각, 더 큰 구간 이상의 준비 표본 및 독립적인 대응 필요
시점 정답을 요구합니다. 같은 사례 구간에서 오탐 감소, 개별 양성 사례의 탐지 누락/지연 없음,
최대 탐지 지연의 비악화를 확인합니다. 불균일하거나 누락된 표본, 정답 시점보다 이른 탐지,
호환되지 않는 공급자 값 및 지원하지 않는 규칙 종류는 보류합니다. 증적은 재생 방식과 지연
보호 지표에 결속하며 같은 측정 구간의 증적으로 구간 변경을 허용하지 않습니다. 이는 탐지기
시나리오이며 실제 공급자 전달이나 승격의 근거는 아닙니다.
독립 수락된 읽기 경로는 근거와 조정값 다이제스트에 결속된 비교 결과, 임계값 표본 또는 시간축
표본 중 정확히 하나만 받습니다. 재생은 고정된 독립 검증 시각을 사용하며 반복 조회가 유효
기간을 갱신하지 않습니다. Terraform은 공급자 스키마가 거부하는 동등해 보이는 값 대신
`PT1H`, `P1D` 등 문서에 명시된 기간 표기를 사용합니다.
발생한 경보 이력만으로 누락 인시던트를 알 수 없습니다. 트래픽/구성원 변화는 교란 요인으로
남으며 확인 응답이 없다는 이유로 경보를 불필요하게 분류하거나 인과적 개선을 입증하지 않습니다.

성공에는 독립적인 구성 재조회, 지속되는 원본 이벤트 수집, 예상 전달 동작, 보호 대상의 대응
기한 유지 및 선언된 관측 구간이 필요합니다. API 성공이나 메시지 감소만으로는 충분하지 않습니다.
적격 이벤트가 없으면 효과를 평가할 수 없습니다. 표본을 기다리기 위해 임시 억제를 계속 유지하지
않습니다. 기준선 재현율, 누락 인시던트, SLO 소진, 상위 담당자 호출 지연, 전달 실패 및 복구
완전성이 보호 지표입니다. 알림량이 줄었더라도 보호 경로가 악화되면 중단하고 복구합니다.

구현된 **운영 > 알림 품질** 화면은 Live 전용입니다. 서버가 제공한 허용 범위, 출처 기반 규칙/서비스/팀/수신 유형
필터와 비활성 라우팅, 유한한 구간, 평가 조건 제안 양식을 사용합니다. 관측 건수와 알 수 없는
값, 관측 구간과 근거 기준 시점/만료, 명시적 조정값과 보존된 기준선 참조를 구분합니다.
요청 상세는 원래 Operator 접수와 정확한 서명 결과를 사용하며 더 새로운 보고서를 완료의
증거로 사용하지 않습니다. 결과 없이 만료된 요청은 미확인 상태로 유지합니다. 정확한 원본
키 대조 후 새 요청을 명시적으로 선택할 수 있지만 자동으로 다시 보내지는 않습니다. 서명된
제안 상세는 전체 복구 기준선, 재생 지표 및 정본 Process 링크를 결속합니다. 현재 승인/결과
상태는 Process 원장이 소유합니다. 출처 기반 팀/유형 필터와 새 기간 조회는 기존 집계를 바꾸지 않으며 누락된 값은 알 수 없음입니다.
예상 이득에는 독립 근거가 필요합니다. 보고서 작업은 ARM 호출이나 승인이 아닌 타입 지정 요청을 제출합니다.
Settings API와 UI는 선행 조건, 활성화 선호 및 권한을 분리하고 해당 범위의 사람 Owner와
개정 번호를 확인합니다. 전용 Operator 요청 조립은 변환 결과, 영속 선호 설정, 이력과 감독되는 브리지 하나를 연결하며 사용할 수 없는 설정을 저장된 스위치로 표시하지 않습니다.
공통 루트는 수명 주기와 준비 상태만 소유하며 기능 정책을 판단하지 않습니다. 기능 활성화나 요청 접수로 작업이 승격되지 않습니다.

조정 안내와 최적화 알림 자체도 제한합니다. 정책, 범위, 관측 구간별 중복 제거된 사례 하나를
유지하고 중요한 갱신은 같은 사례에 기록하며 일반 요약은 A4로 전달합니다. 필수 승인과 긴급
안전 호출은 선택적 요약 선호를 적용받지 않습니다. 수백 명의 수신자마다 제안이나 승인 카드를
만들지 않습니다. 수신 대상별 업무 방해 예산은 안내의 우선순위를 정하거나 선택적 FDAI 메시지를
묶는 데 사용할 수 있지만 보호 알림을 조용히 버리는 데 사용할 수는 없습니다.

## 9. 제공 순서와 종료 근거

다음은 의존성 순서로 나눈 종료 조건이며 완료 주장이나 제공 일정을 뜻하지 않습니다.
[구현 원장](../../roadmap-implementation/operations/alert-noise-governance.md)은 구현된 처리 구조,
기준점 검증, 남은 강화 작업 및 운영 근거를 구분합니다.

| 작업 묶음 | 관측 가능한 종료 조건 |
|-----------|-----------------------|
| ANG-1: 근거와 의미 | 버전 관리되는 공급자/수신 대상 계약, 소유권, 완전/부분/거부 동작, 개인정보 검사 및 정확한 온톨로지 매핑이 쓰기 없이 집중 테스트 통과 |
| ANG-2: 평가와 안내 | 결정론적 과다/중복 수신 보고서, 무변경 대안, 수동 안내 및 범위가 적용된 한영 조회 결과가 고정된 합성 조직 사례에서 통과 |
| ANG-3: 승인 기반 라우팅 | 정확한 계획 정족수, 철회, 공용 그룹 영향, 예행 실행, 중복/재정렬/재시작, 조건부 쓰기, 독립 종결 및 복구가 기존 규칙 하나에서 통과 |
| ANG-4: 유한한 억제 | 보호 대상/자동화 제외, 유효 규칙 우선순위, 독립 수집, 반영 지연, 만료/표준 시간대 동작 및 재시작 후 복구가 통과 |
| ANG-5: 평가 조정과 승격 | 공급자 규칙 종류별 의미와 별도 검증 자료의 재현율/지연 기준이 통과하고, 별도 승인된 공급자 테스트 및 기간 제한 시험 적용이 승격 전 독립 근거를 보존 |

규모 검증 자료에는 최소 500개의 합성 principal, 20개 팀, 겹치는 직접/그룹/역할 연결 및
10000개 경보 이벤트를 포함하며 한 서비스로 부하가 치우치는 사례도 넣습니다. 버전 관리 정책은
페이지 수, 구성원 확장 깊이, 그래프 관계, 후보 수, 바이트, 동시성, 공급자 비용, 전체/단계별
시간 및 무진행 시간을 제한합니다. 한도에 도달하면 부분 근거를 보존하고 해당 변경을 보류하며
승인 범위를 조용히 잘라내지 않습니다. 공정한 범위별 큐로 과도한 테넌트나 팀의 부하를 격리합니다.

필수 거부/실패 사례에는 권한 없는 그룹 확장, 다른 테넌트 신원, 미확인 메일링 리스트 중복,
보호 경보의 정보성 오분류, 백업 부재, 범위 밖 공용 그룹 변경, FDAI 수집 제거, 억제/추가 규칙
중첩, 실제 효과 없는 API 성공, 만료된 승인, 안전하지 않은 공급자 동시성, 늦은 증적, 복구 실패 및
텔레메트리 손실을 개선으로 오인하는 경우가 포함됩니다. 실제 운영 근거와 합성 동작 검사는 분리합니다.

## 10. 설계 검토 결정

비판 검토를 통해 다음 경계를 강화했습니다. 이는 설계 판단 기록이며 사람 승인, 공급자
일치성 또는 실행 가능한 테스트의 통과를 뜻하지 않습니다.

| 채택하지 않은 지름길 | 수정한 결정 |
|----------------------|-------------|
| 경보 수를 세고 가장 많은 규칙을 끄기 | 경보 묶음, 전달, 사람을 구분하고 알림량보다 재현율과 대응 기한을 먼저 보호합니다. |
| 이메일을 억제하면서 같은 경보의 다른 그룹은 유지하기 | Azure 억제는 모든 그룹을 제거하므로 영향받지 않는 독립 수집 및 안전 경로를 보존하거나 보류합니다. |
| 수신자 한 명에게 공용 변경 승인 맡기기 | 모든 영향 서비스를 포함하고 독립 정족수를 유지하며 Azure 수신 역할에서 권한을 추론하지 않습니다. |
| 재조회나 복구를 경보 누락이 없었다는 증명으로 사용하기 | 전달과 복구를 독립적으로 검증하고 복원으로 지울 수 없는 누락 구간도 근거로 보존합니다. |
| 내부 잠금이나 나중의 정리 작업에 의존하기 | 의존성과 재시작 사례까지 포함해 실효적인 작성자 통제와 공급자가 강제하는 유한한 구간을 요구합니다. |
| 전체 재현율이나 최대 지연만 비교하기 | 사례별 대응 결과를 보존하며 한 사례의 개선으로 다른 양성 사례의 탐지 누락이나 지연을 상쇄하지 않습니다. |
