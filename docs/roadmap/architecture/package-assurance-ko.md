# 패키지 보증

이 문서는 FDAI 패키지와 배포 가능한 산출물에 실제 경계에 맞는 최소 보증 계약을
할당합니다. 내부 lockstep 코드에 릴리스 절차를 강제하지 않으면서 효과가 발생하거나
독립적으로 릴리스되는 표면에는 헌법상 안전 통제를 유지합니다.

> **권한 경계:** 패키지 가용성, 설치, 사용 설정, 사용자 접근, 작업 모드, 승인, 실행
> ID, 효과 검증은 서로 독립적입니다. 패키지 작업은 런타임 권한을 부여하지 않습니다.
>
> **구현 원장:** 제공 상태와 남은 근거는
> [패키지 보증 구현 원장](../../roadmap-implementation/architecture/package-assurance.md)에서
> 추적합니다.

## 설계 개요

FDAI는 각 패키지 또는 산출물을 경계를 넘어가는 항목에 따라 분류합니다.
[`config/package-assurance.json`](../../../config/package-assurance.json)의 기계 판독 가능
정책이 분류를 기록하고,
[`check-package-assurance.py`](../../../scripts/quality/architecture/check-package-assurance.py)는
낮은 보증 등급이 효과 발생, 게시된 계약 또는 지식 근거 경계를 약화하지 못하게 합니다.

등급은 최소 보증 묶음이며 독립적인 런타임 축을 대체하지 않습니다. 패키지는 효과 발생
분류를 바꾸지 않고 Cost Governance N-1 산출물 롤백 계약 같은 더 강한 호환성 범위를 추가할
수 있습니다.

## 수정된 설계 결정

**초기 설계:** 모든 패키지 형태의 표면에 독립 릴리스, N/N-1 호환성, 하나의 완전한
서명 키트, 하나의 라이브 수명 주기 실행, 대상별 하나의 검토 요청을 적용합니다.

**비평:** 이 설계는 저장소 구성과 프로세스, 신뢰, 근거, 권한 경계를 혼동합니다.
의존성 선언을 중복하고, 연결형 제공에 오프라인 전용 콘텐츠를 포함하며, 독립적인
검토 결정을 반복 절차로 만듭니다. 내부 라이브러리나 권한 중립 메타데이터 패키지에는
추가 작업이 안전성을 높이지 않습니다.

**수정된 설계:** 먼저 경계를 분류한 다음 해당 등급에 필요한 통제만 적용합니다.
해당되는 경우 고객 비식별 범위, 산출물 무결성, 권한 분리, 정확한 계획 승인, 롤백,
독립 효과 검증은 그대로 유지합니다.

## 보증 등급

| 등급 | 사용 대상 | 필수 보증 |
|------|-----------|-----------|
| `workspace-internal` | 하나의 배포판과 프로세스 내부에 머무는 코드 | 소유 테스트와 의존성 검사. 독립 릴리스 또는 N/N-1 의무는 없습니다. |
| `lockstep-shared` | 소비자와 함께 릴리스되는 별도 패키지 라이브러리 | 자체 매니페스트, 안정적인 가져오기 표면, lockstep 테스트. 배포 경계를 넘지 않으면 롤링 호환성 주장은 필요하지 않습니다. |
| `independent-contract` | 게시된 SDK와 프로세스 간 또는 영구 저장 wire 계약 | 변경할 수 없는 게시 스키마, N/N-1 호환성, 변환기, 생산자-소비자 근거. |
| `effect-bearing` | 영구 상태 또는 관리 리소스 효과로 이어질 수 있는 배포 도구나 선택 패키지 | 서명된 release, 연결된 수명 주기 근거, 기능별 promotion, 롤백, 승인 분리, 독립 효과 검증. |
| `knowledge-evidence` | 검토된 지식 또는 근거 패키지 | 서명된 콘텐츠, 출처, 최신성, 검토, 보존, 폐기, 독립적으로 관찰된 활성화. 실행기 권한은 상속하지 않습니다. |

파일 시스템 패키지 경계가 새 서비스를 의미하지는 않습니다.
[서비스 분리 기준](service-graduation-and-ownership-ko.md)은 패키지에 독립 프로세스,
ID, 데이터 소유자, 전송, 롤백 계획이 필요한지 계속 결정합니다.

## 의존성 소유권

각 런타임 의존성에는 하나의 소유 배포판 매니페스트가 있습니다. 설치되지 않는 저장소
루트는 루트 테스트 수집이 소유 패키지를 직접 가져오는 경우에만 의존성을 미러링할 수
있습니다.

정책은 허용된 각 미러에 다음 항목을 기록합니다.

- 의존성 이름
- 소유 매니페스트
- 루트 테스트에 필요한 이유

검사기는 루트와 소유자의 요구 버전 범위를 비교합니다. 목록에 없는 미러나 지원되지 않는
버전 불일치는 검증에 실패합니다. 정책 항목은 소유자가 더 넓은 런타임 지원 범위를 유지하는
동안 루트 테스트의 최소 버전만 더 높게 설정하도록 허용할 수 있습니다. 루트는 소유자 범위
밖으로 넓힐 수 없습니다. 작업 영역 구성원은 자체 프로젝트 이름과 버전에 맞춰 별도로
검사합니다. 이를 통해 중복 텍스트가 두 번째 기준 정보가 되지 않으면서 루트 환경을 계속
사용할 수 있습니다.

## 호환성 범위

다음 계약에는 N/N-1 및 변경할 수 없는 스키마 요구 사항을 적용합니다.

- 독립적으로 릴리스되는 소비자에게 게시됩니다.
- 배포된 프로세스 경계를 넘어 교환됩니다.
- 영구 저장되고 다른 release가 읽습니다.

릴리스된 피어나 보존 데이터가 이전 형태에 의존하지 않는 경우 내부 lockstep 레코드는
유일한 소비자와 함께 변경할 수 있습니다. 내부 레코드를 프로세스 간, 영구 저장 또는
공개 표면으로 이동하려면 먼저 보증 등급을 변경하고 버전이 지정된 호환성 계약을
설정합니다.

`fdai-service-contracts` 패키지는 계속 `independent-contract`입니다. 게시된 스키마,
호환성 매니페스트, 생성된 보기, 롤링 전환 근거는 변경하지 않습니다.

## 서명된 산출물 프로필

각 프로필에는 자체 완전한 신뢰 폐쇄 집합이 있습니다. 연결형 소스 제공은 보호된 소스 ID와
승인된 정확한 리비전 이미지 매니페스트에 바인딩되며 오프라인 키트 루트가 필요하지 않습니다.
오프라인 제공은 정확한 레거시 키트 매니페스트를 바인딩하는 서명된 배포 루트를 사용합니다.
어플라이언스는 별도로 증명된 컨테이너 안에 검증된 오프라인 폐쇄 집합을 포함합니다.

| 프로필 | 신뢰 루트 | 완전한 폐쇄 집합 |
|--------|-----------|------------------|
| `connected` | 보호된 소스 리비전과 서명된 이미지 매니페스트 | 정확한 이미지와 지원 매니페스트, 호환성, SBOM(소프트웨어 구성 명세), 출처, 변경할 수 없는 digest. 완전한 오프라인 wheelhouse 또는 공급자 미러는 필요하지 않습니다. |
| `offline` | `deployment-root.json`과 release 서명 루트 | 연결형 산출물 통제와 모든 필수 wheel, 바이너리, Terraform 공급자, 런타임 이미지, Console 산출물, 마이그레이션 입력, 공개 대체 경로 없음의 증명. |
| `appliance` | 검증된 오프라인 루트와 컨테이너 증명 | 오프라인 폐쇄 집합과 digest 고정 컨테이너, 포함된 키트 바인딩, 출처, SBOM, 공개 대체 경로가 없는 진입점. |

새 오프라인 키트에는 `deployment-root.json`과 분리된 서명이 포함됩니다. 루트에는 정렬되고
중복이 없는 키트 프로필 이름이 있으며 정확한 `offline-kit.json` 바이트에 바인딩됩니다.
키트 획득은 루트가 있으면 검증합니다. 새 레거시 형식 매니페스트도 루트를 필수로 표시하므로
두 루트 파일을 모두 제거해도 새 release를 대체 경로로 낮출 수 없습니다. 해당 표시가 없는
이전 매니페스트는 기존 매니페스트와 서명을 통해 계속 유효합니다. 이 추가형 이행은 이전
release를 보존하면서 연결형 소스 제공을 오프라인 전용 산출물 구성과 독립적으로 유지합니다.

## 연결된 수명 주기 근거

모든 증적에 다음 항목이 같으면 설치, 사용 설정, 사용 안 함, 폐기, 다시 로드, 재시작
근거를 별도의 범위가 제한된 실행에서 얻을 수 있습니다.

- 산출물 digest
- release 리비전
- 환경 ID
- 감사 상관관계 ID

근거 집합은 필요한 모든 전환을 포함하고 순서, 행위자 ID, 멱등성, 감사 계보를
보존해야 합니다. 누락되거나 충돌하는 연결은 수명 주기를 미완료 상태로 유지합니다.
하나의 통합 라이브 실행도 허용하지만 더 이상 유일한 증명 형태는 아닙니다.

## 다중 대상 검토 묶음

하나의 범위가 제한된 검토 묶음에는 Cost Governance 대상 결정을 최대 6개까지 넣을 수
있습니다. 각 항목은 하나의 패키지 활성화, `ActionType` 또는 `Workflow`와 자체 결정 및
근거를 지정합니다.

일괄 기록기는 묶음을 기존 단일 대상 레코드로 분해합니다. 안정적인 하위 요청 ID는
일괄 ID, 대상 종류, 대상 ID를 사용하므로 재시도하면 각 대상을 독립적으로 재생합니다.
각 하위 레코드는 자체 캠페인 digest, 검토자, 결정, 근거, 근거 참조, 검토 시간을
보존합니다. 부분 완료는 명시적으로 기록되며 안전하게 재시도할 수 있습니다.

검토 묶음에는 승인, 실행 또는 promotion 권한이 없습니다. 이후 활성화와 promotion은
대상별로 분리된 트랜잭션으로 유지합니다.

## 선택 패키지 준비 상태

선택 패키지 상태는 기능 범위에 한정됩니다.

- 사용할 수 없고 비활성화된 패키지는 관련 없는 기본 런타임의 준비 상태를 막지 않습니다.
- 활성화된 패키지에 필수 바인딩이 없으면 해당 기능은 안전하게 차단됩니다.
- 독립적으로 완전한 읽기, 거부, 관찰 경로는 계속 진행할 수 있습니다.
- 가용성은 패키지를 활성화하지 않습니다.
- 활성화는 작업 권한을 높이지 않습니다.

준비 상태는 누락된 선택 구성 때문에 전체 시작이 실패하도록 하는 대신 사용할 수 없는
이유를 보고합니다. 활성화되거나 효과가 발생하는 경로에 필요한 의존성은 해당 경로에서
계속 필수 실패 조건입니다.

## 확장 패키지 facade

선택 패키지는 팩터리, 리소스 로더, 준비 상태 형식, 검토된 어댑터를 위한 문서화된
권한 중립 facade를 노출할 수 있습니다. 공개 export 변경은 검색 가능성만 바꿉니다.

Core는 여전히 선택 패키지를 가져올 수 없습니다. 구성 루트가 패키지를 선택하고
바인딩하며, 기존 의존성 방향 검사가 이 경계를 적용합니다. 공급자 클라이언트, 판단,
승인, 실행 ID, promotion 권한은 facade로 이동하지 않습니다.

## 완화하지 않는 통제

패키지 보증은 다음 요구 사항을 완화하지 않습니다.

- upstream 산출물은 고객 비식별 상태를 유지하며 자격 증명과 테넌트 값을 포함하지 않습니다.
- 서명된 산출물은 정확한 digest, 출처, SBOM, 호환성, 의존성 폐쇄 집합을 보존합니다.
- 패키지 활성화는 사용자 접근, `ActionType`과 `Workflow` 모드, 승인, 실행, 롤백, 효과
  검증과 분리된 상태를 유지합니다.
- 관리 리소스 또는 외부 상태 변경은 7가지 자율 작업 안전장치를 유지합니다.
- 게시된 프로세스 간 계약과 영구 저장 계약은 버전과 호환성을 유지합니다.
- 에이전트 소유권, 이벤트 버스 통신, 단일 작성자 상태, 사람과 실행기 분리는 변경하지
  않습니다.
