# ADR-0003: Hub 관리형 수명 주기와 운영자 거버넌스

이 기록은 세 번째 설치 경로를 추가합니다. 이 경로에서는 Lifecycle Hub가 각 FDAI 설치를 구독한
release channel과 고객이 승인한 구성에 맞춰 유지합니다. 또한 대개 한 사람이 운영하는 설치에
맞게 승인, 승격, 정책 관리를 조정합니다. 이 기록은 [FDAI 헌법](../fdai-constitution-ko.md)과
[ADR-0002](0002-independent-runtime-axes-ko.md)를 개정합니다.

## 상태

**Accepted:** 2026-10-02. 이 기록은 설계 권위만 가집니다. 결정의 어떤 부분도 아직 구현되지
않았습니다. 각 소유 문서가 제공 현황을 추적하는 ledger로 연결됩니다.

## 맥락

FDAI는 각 고객의 Azure 환경에 설치됩니다. 고객마다 리전, 네트워크 격리, 모델 엔드포인트, 용량
유형, 승인 요건, 허용 정책, 연동 시스템, 받아들일 수 있는 release가 다릅니다. 이 결정 이전에
FDAI의 설치 경로는 단일 명령 소스 배포와 서명된 오프라인 패키지 두 가지였습니다. 어느 경로도
여러 설치를 최신 상태로 유지하지 못합니다. release 구독, 설치별로 기록된 원하는 구성, 보고된
수명 주기 상태, 결함 있는 release를 회수하는 방법이 모두 없었습니다.

Palantir Apollo는 hub-and-spoke 모델로 비슷한 문제를 해결합니다. Hub는 제품 카탈로그, release
channel, 환경 설정, 보고 상태를 결합하고, 오케스트레이션 엔진은 모든 제약 조건을 충족할 때만
Plan을 발행합니다. 각 spoke 환경 안의 에이전트가 그 Plan을 실행하고 상태를 다시 보고합니다
([Apollo overview](https://www.palantir.com/docs/apollo/core/overview),
[Plans and Constraints](https://www.palantir.com/docs/apollo/core/plans-and-constraints)).
Apollo에는 환경별 단일 목표 상태가 없습니다. 제품은 고정 버전이 아니라 release channel과 제약
조건으로 정의됩니다.

다음 요인이 결정을 형성했습니다.

- 헌법 제1조는 설치 경로를 두 가지로만 허용했고, 추가된 설치 관문을 결함으로 취급했습니다.
- 판테온은 15개 에이전트로 고정되어 있습니다. 수명 주기 작업 때문에 에이전트를 추가하거나 역할을
  다시 바인딩할 수 없습니다.
- ADR-0002는 런타임, 환경, 제품 표면, 수명 주기, 신원, 권한 확인, 분포를 독립 축으로
  유지합니다. 구성은 권한을 부여할 수 없습니다.
- 제품화 계획은 서로 신뢰하지 않는 테넌트를 위한 공유 게이트웨이 하나를 채택하지 않습니다.
- 규제 고객은 국내 처리, 승인된 엔드포인트만 사용, 고객 데이터에 대한 중앙 접근 금지를
  요구합니다. 인터넷에 전혀 연결되지 않은 사이트도 있습니다.
- 대부분의 설치에는 운영자가 한 명뿐입니다. 상시 권한의 2인 규칙 때문에 이런 설치에서는 비상
  완화를 쓸 수 없었습니다.
- 운영자는 release를 기다리지 않고 승인 정책과 허용 정책을 바꿔야 합니다.

## 결정

### 수명 주기

| # | 결정 | 소유 문서 |
|---|------|-----------|
| L1 | Hub 관리형 수명 주기를 세 번째 설치 경로로 추가합니다. 소스 배포와 오프라인 패키지는 그대로 유지합니다. | [Hub 관리형 수명 주기](../../deployment/hub-managed-lifecycle-ko.md) |
| L2 | Hub는 고객별로 배치합니다. 연결된 고객에게는 중앙 Hub cell, 규제 고객에게는 경계 안의 온라인 Target Hub, 서명된 번들을 가져오는 고객에게는 오프라인 Target Hub를 둡니다. 세 방식 모두 같은 Hub 소프트웨어를 실행합니다. | Hub 관리형 수명 주기 |
| L3 | Hub는 Lifecycle Plan만 계산합니다. Plan에는 목표 Release, 구성 개정, 제약 조건 결과, 범위를 좁히는 효과 경계가 들어 있습니다. 설치는 최대 효과 경계를 스스로 도출하고, 정확한 변경을 만들어 적용하며, 그 경계를 벗어난 변경은 거부합니다. Hub는 Azure 자격 증명, 비밀 값, 운영 데이터를 보관하지 않습니다. 설치는 아웃바운드 연결로 Hub를 폴링합니다. | Hub 관리형 수명 주기 |
| L4 | 두 설치 에이전트가 작업을 맡습니다. 클러스터 안의 수명 주기 에이전트는 가장 먼저 설치되고, Core와 독립적으로 실행되며, 워크로드를 적용하고 상태를 보고합니다. 실행 호스트의 인프라 에이전트는 정확한 Terraform 계획으로 Azure 인프라를 적용합니다. 둘 다 판테온 에이전트가 아닙니다. 판테온은 FDAI 소유 리소스를 관측만 합니다. | Hub 관리형 수명 주기 |
| L5 | 모든 설치는 유지 관리 구간 안에서 자기 채널의 적격한 최신 Release를 자동으로 적용합니다. 구성 변경에는 승인된 변경 요청이 필요합니다. 기존 Azure 리소스를 삭제하거나 교체하려면 운영자의 명시적 확인이 필요합니다. | [Lifecycle Release와 채널](../../deployment/lifecycle-releases-and-channels-ko.md) |
| L6 | Release는 미리 빌드된 이미지 다이제스트와 메타데이터를 서명한 집합입니다. 연결된 설치는 경계 안의 레지스트리로 이미지를 미러링합니다. 오프라인 패키지는 첫 설치용 패키지로 유지하고, 이후 Release는 새로 만든 서명된 업그레이드 번들로 전달합니다. 소스 빌드는 Trial 및 개발용 빌드로 남고, Hub에서는 검증되지 않은 빌드로 취급합니다. | Lifecycle Release와 채널 |
| L7 | release channel은 Apollo 기본 이름인 `DEV`, `RELEASE_CANDIDATE`, `RELEASE`를 사용하며 사용자 지정 채널도 허용합니다. 구현된 `development`, `beta`, `stable` 이름은 새 이름으로 옮겨 갑니다. | Lifecycle Release와 채널 |
| L8 | 구성 계층은 Apollo를 따릅니다. Release 기본값, Environment Config, Release 버전 범위별 Entity 재정의 블록 순서입니다. 일치하는 재정의 블록이 없는 Release는 배포하지 않습니다. 권한 값은 절대 구성이 아닙니다. | [수명 주기 구성](../../deployment/lifecycle-configuration-ko.md) |
| L9 | 고객 소유 Git 저장소가 원하는 구성의 원본이며, 검토된 병합이 변경 요청입니다. 병합된 각 개정은 Hub가 가져오는 서명된 구성 패키지 하나가 됩니다. 패키지는 이전 개정을 명시하므로 누락과 순서 뒤바뀜을 감지할 수 있습니다. | 수명 주기 구성 |
| L10 | 억제 구간과 권한을 낮추는 명령은 즉시 적용되며 반드시 만료됩니다. 비상 해제(break-glass) 명령은 비상 변경을 즉시 적용하고, 만료되면 승인된 Git 개정으로 조정됩니다. 권한을 높이는 재정의는 없습니다. | Hub 관리형 수명 주기 |
| L11 | Entity는 배포 단위와 Azure 플랫폼 리소스입니다. 에이전트는 Core Entity의 하위 보고 상태로 나타납니다. 기존 API Management 인스턴스, 프라이빗 DNS 영역, ITSM 엔드포인트처럼 고객이 소유한 리소스는 FDAI가 관측만 하는 비관리 Entity입니다. | Hub 관리형 수명 주기 |
| L12 | Hub 기록은 cell 또는 Target Hub마다 있는 Hub PostgreSQL 데이터베이스에 둡니다. 설치 증적은 설치의 Foundation 스토리지에 추가 전용으로 남깁니다. 운영 온톨로지는 바뀌지 않습니다. | Hub 관리형 수명 주기 |

### 운영자 거버넌스

| # | 결정 | 소유 문서 |
|---|------|-----------|
| G1 | 단독 운영자 프로덕션 프로필을 추가합니다. 승인 정책이 이 프로필을 선택하면 지정된 운영자 한 명이 그 설치의 모든 요청자, 승인자, 검토자, 정족수 요구사항을 충족할 수 있습니다. 승인자와 실행기 신원은 계속 분리됩니다. | [운영자 거버넌스 프로필](../../decisioning/operator-governance-profiles-ko.md) |
| G2 | 권한 있는 운영자는 승격 게이트를 통과하기 전에 ActionType이나 Workflow를 승격할 수 있습니다. 이 승격은 귀속된 운영자 재정의로 기록됩니다. 회귀 강등과 공급업체의 기능 회수가 우선합니다. | 운영자 거버넌스 프로필 |
| G3 | 권한 있는 운영자는 정책 관리 추가 기능을 통해 FDAI Console에서 승인 정책과 허용(OPA/Rego) 정책을 직접 편집합니다. 각 편집은 이후 결정에 적용되는 변경할 수 없고 다이제스트가 고정된 감사 대상 개정이 됩니다. | 운영자 거버넌스 프로필 |
| G4 | 규제 설치는 상주 규칙이나 엔드포인트 규칙 때문에 서로 다른 게시자의 모델 쌍을 쓸 수 없을 때 같은 게시자의 서로 다른 모델 두 개로 T2를 실행할 수 있습니다. | [모델 기능 수명 주기](../model-capability-lifecycle-ko.md) |
| G5 | 온프레미스 고객에 대해서는 버전 고정과 Azure에서 도달할 수 있는 자체 호스팅 모델만 설계합니다. 온프레미스 런타임과 로컬 모델은 별도 승인이 필요합니다. | Hub 관리형 수명 주기 |

### 별도 질문 없이 채택한 기본값

| # | 기본값 |
|---|--------|
| A1 | Release는 지원하는 데이터베이스 스키마 범위를 선언합니다. Hub는 이 범위를 제약 조건으로 검사합니다. 마이그레이션은 expand/contract 방식과 전진 전용을 유지합니다. |
| A2 | Azure 리소스를 삭제하거나 교체할 때의 기존 규칙은 Hub 경로에도 그대로 적용됩니다. 그 밖의 중단을 일으키는 업데이트는 다운타임 유지 관리 구간을 기다립니다. |
| A3 | Hub 경로는 AKS 런타임만 지원합니다. Container Apps 설치는 기존 경로를 유지합니다. |
| A4 | 기존 설치는 먼저 비관리 Entity로 등록되고 검토 후 관리 Entity가 됩니다. 첫 Hub 업그레이드가 소스 빌드 이미지를 서명된 이미지로 바꿉니다. |
| A5 | 채널 이전은 `development`를 `DEV`로, `beta`를 `RELEASE_CANDIDATE`로, `stable`을 `RELEASE`로 매핑합니다. 승격 파이프라인은 라벨, 안정화 시간, 카나리 상태, 회수를 지원합니다. |
| A6 | Console 정책 개정에는 새 인증이 필요합니다. Mimir가 개정을 검증하고, 설치 키로 서명하고, 활성화합니다. Core는 운영자 정책 뒤에 헌법의 강제 제약을 적용하므로 어떤 개정도 결과를 그 제약이나 Release 최대값 너머로 높이지 못합니다. 다중 운영자 프로필에서는 완화하는 개정에 프로필의 거버넌스 정족수가 필요합니다. |
| A7 | 회수된 기능은 이후 Release가 회수를 해제하기 전까지 다시 승격할 수 없습니다. 운영자 재정의는 다른 설치의 승격 증거로 인정되지 않습니다. |
| A8 | 같은 게시자의 T2 쌍에는 별도 배포에 있는 서로 다른 모델 계열이나 버전 두 개가 필요합니다. 모든 T2 결정은 어떤 다양성 정책이 적용되었는지 기록합니다. |
| A9 | 데이터 상주는 각 모델 바인딩의 처리 범위 제약 조건입니다. 이를 위반하는 바인딩은 거부됩니다. |
| A10 | Hub 승인자는 고객의 Microsoft Entra ID 테넌트로 인증합니다. |
| A11 | 수명 주기 에이전트는 FDAI 네임스페이스 안에서만 Kubernetes 권한을 가집니다. Azure 쓰기 신원은 실행 호스트에만 둡니다. |
| A12 | 중앙 Hub cell은 운영 루프에 들어가지 않습니다. |
| A13 | 버전 고정은 버전 범위 구독입니다. |
| A14 | 고객 식별자와 엔드포인트는 구성 패키지 안에서 설치 키로 봉인됩니다. Hub는 암호문과 다이제스트만 저장합니다. |
| A15 | Release에는 공급업체 release 서명이, 구성 패키지에는 고객 구성 서명이 있습니다. 설치 에이전트는 작업 전에 둘 다 검증합니다. |
| A16 | 설치 에이전트는 서명된 입력, 소유권 증거, 로컬 강제 정책에서 최대 효과 경계를 직접 도출합니다. Hub Plan은 그 경계를 좁힐 수만 있습니다. |
| A17 | 각 Plan은 대상 설치, Hub 키 epoch, 원본 상태 다이제스트, 순번, 펜싱 세대를 명시하며 에이전트는 재전송을 거부합니다. 설치는 등록할 때 키 보유를 증명하고, 키는 서명된 키 기록으로 교체되고 폐기됩니다. |
| A18 | 카탈로그 메타데이터는 만료되는 timestamp, 증가하는 버전, 회수 순번을 갖춘 TUF 역할을 따릅니다. 메타데이터가 만료되면 회수 roll-off만 허용하고 운영자 재정의 승격을 `shadow` 모드로 되돌립니다. |
| A19 | 로컬 수명 주기 승인 증적은 각 정확한 계획 다이제스트를 Plan, Release, 구성 개정, 구간에 결속합니다. 이 증적은 기존 정확한 계획 단계에서 운영자의 명령 실행을 대신합니다. |
| A20 | Plan은 에이전트 하나가 각각 소유하는 펜싱된 단계로 실행됩니다. 에이전트와 Target Hub는 두 개의 슬롯으로 스스로 업그레이드합니다. |
| A21 | 서명된 Foundation 증적과 Terraform 상태 식별 정보가 FDAI 소유를 증명합니다. `fdai:managed=true` 태그는 탐색 단서일 뿐입니다. |
| A22 | 비상 해제 명령은 유지 관리 구간, 억제 구간, 버전 범위만 우회할 수 있습니다. |
| A23 | 유지 관리 구간은 시간대 데이터베이스 버전을 고정한 IANA 시간대를 사용하며, Plan은 최대 소요 시간이 구간 안에 들어갈 때만 시작됩니다. |
| A24 | 중앙 cell은 대략적인 구성 요소 상태 구간만 받으며 이벤트 내용이나 리소스 식별 정보는 받지 않습니다. |
| A25 | 운영자 재정의 승격은 타입이 지정된 파이프라인을 거치는 `governance` ActionType입니다. Mimir는 정책 개정의 단일 작성자입니다. |

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|------|---------------------|
| 설치 경로를 두 가지로 유지하고 메타데이터 계층만 추가 | 여러 설치를 업그레이드, 회수, 조정할 수 없습니다. Owner가 완전한 세 번째 경로를 선택했습니다. |
| Apollo 방식의 중앙 엔진처럼 중앙 Hub가 고객 자격 증명으로 정확한 계획을 생성 | 모든 고객의 Azure 쓰기 권한이 한곳에 모이며, 규제 고객이 이를 금지합니다. |
| 모든 고객에게 Target Hub를 요구 | 공급업체가 운영하는 cell을 받아들이는 고객에게 불필요한 Hub 운영 비용이 생깁니다. |
| 판테온에 배포, 구성, 드리프트, 정책 에이전트를 추가 | 판테온은 고정되어 있으며, 자신이 실행되는 런타임을 업그레이드하는 에이전트는 순환 의존성을 만듭니다. |
| 5계층 선형 재정의(제품, 환경, 정책, Entity, 런타임) 사용 | ADR-0002의 축이 결합되고 구성이 권한을 전달하게 됩니다. |
| Hub 스토리지를 원하는 구성의 원본으로 사용 | 고객은 Git 검토와 이력을 선호합니다. Hub는 가져온 사본을 보관합니다. |
| 고객별로 이미지나 브랜치를 따로 빌드 | 제품 포크가 생기고 "한 번 빌드하고 환경별로 구성"하는 원칙이 깨집니다. |
| Release 업그레이드마다 승인 요구 | Owner가 자동 업그레이드를 선택했습니다. 채널, 버전 고정, 유지 관리 구간, 억제 구간이 통제 수단으로 남습니다. |
| 상시 권한의 2인 규칙 유지 | 단독 운영자 설치는 비상 완화를 전혀 쓸 수 없습니다. |
| 게이트 통과 후에만 승격 허용 | 운영자는 자기 설치를 직접 통제해야 합니다. |
| Git의 서명된 번들로만 정책 관리 | 일상적인 정책 변경에 너무 느리고 엄격합니다. |
| 같은 게시자의 T2 쌍을 모든 곳에서 금지 | 규제 설치가 T2를 완전히 잃을 수 있습니다. |

## 결과

**긍정적인 결과:**

- 하나의 Release가 모든 고객에게 쓰이고, 고객별 차이는 구성, 정책, 설치에 결속된 바인딩에만
  남습니다.
- 연결된 설치와 오프라인 설치 모두에서 Release를 승격, 회수, 조정할 수 있습니다.
- 규제 고객은 비밀, 자격 증명, 식별자, 운영 데이터를 자기 경계 안에 둡니다.
- 단독 운영자 설치도 비상 완화를 쓰고 자기 정책을 관리할 수 있습니다.

**부정적인 결과와 위험:**

- **자율성이 넓어집니다.** 운영자 재정의 승격, 단독 운영자 승인, Console의 정책 완화, 자동
  업그레이드가 결합되면 한 사람이 검증되지 않은 기능의 무인 실행을 켤 수 있습니다. 7개
  안전장치, A4 차단, 위험 게이트의 상한, 회귀 강등, 기능 회수, 재정의 표시, 감사 기록은
  유지됩니다. 이 장치들은 영향을 제한하지만 위험을 없애지는 못합니다.
- **침해된 Hub**는 업그레이드를 지연하거나 Plan을 보류할 수 있습니다. 하지만 효과 경계를 넓히거나,
  Release나 구성 패키지를 위조하거나, Plan을 재전송하거나, Azure 자격 증명을 얻을 수는 없습니다.
  에이전트는 공급업체가 서명한 회수가 허용하지 않는 한 이미 적용한 최신 버전보다 오래된 버전을
  거부하며, 만료된 카탈로그 메타데이터는 운영자 재정의 승격을 `shadow` 모드로 되돌립니다.
- **자동 업그레이드**는 채널, 버전 고정, 구간으로 막지 않는 한 규제 설치에도 도달합니다.
- **같은 게시자의 T2 쌍**은 모델 독립성을 낮추며 같은 실패 양상을 공유할 수 있습니다.
- **오프라인 설치**는 운영자가 다음 번들을 가져올 때만 회수를 받습니다.
- **워크로드 렌더링이** Terraform 애플리케이션 단계에서 수명 주기 에이전트로 옮겨 가므로
  마이그레이션이 필요합니다.
- 지침 파일이 바뀌었으므로 무결성 매니페스트에 키 보유자의 새 서명이 필요합니다.

**운영 및 마이그레이션:** 공급업체는 release 카탈로그와 중앙 Hub cell을 운영합니다. Target Hub를
선택한 고객은 자기 경계 안에서 Target Hub를 운영합니다. 기존 설치는
[Hub 관리형 수명 주기](../../deployment/hub-managed-lifecycle-ko.md)의 절차에 따라 등록합니다.

각 결정을 선택했습니다. 이 ADR을 반영하는 변경의 검토 기록은 정확한 diff와 집중 검증을
결속합니다.
