# Hub 관리형 수명 주기

이 문서는 FDAI의 세 번째 설치 경로를 정의합니다. Lifecycle Hub는 Palantir Apollo의
hub-and-spoke 모델을 따라 각 설치를 구독한 release channel과 고객이 승인한 구성에 맞춰
유지합니다. 이 문서는 수명 주기 아키텍처, 계획과 상태 루프, 고객 격리 경계를 소유합니다.

> **상태:** 개발 검증용으로 일부 구현되었습니다. 로컬 Hub와 플래너, 제품별 독립 배포 루트와
> 로그인/카탈로그 연결 없는 원격 기동 경로가 있으며, 전체 관리형 설치 경로는 아직 제공하지 않습니다. Azure 배포나 프로덕션
> 신뢰 루트 설정을 완료했다는 뜻은 아닙니다.
> [구현 현황 원장](../../roadmap-implementation/deployment/hub-managed-lifecycle.md)이
> 정확한 제공 범위를 추적하며, [ADR-0003](../architecture/decisions/0003-hub-managed-lifecycle-and-operator-governance-ko.md)이
> 결정을 기록합니다.
>
> **범위:** Hub 배포 엔진은 특정 애플리케이션에 종속되지 않습니다. FDAI도 하나의 배포 대상이며,
> 고정된 필수 서비스 목록이 아닙니다. 각 설치본은 독립적으로 승인된 애플리케이션, 소유권이
> 확인된 Entity와 로컬 효과 경계 안에서만 작동합니다. FDAI 운영 루프가 다른 애플리케이션에
> 대한 권한을 얻는 것은 아닙니다.
> [수명 주기 구성](lifecycle-configuration-ko.md)이 구성 계층과 비밀을, [Lifecycle Release와
> 채널](lifecycle-releases-and-channels-ko.md)이 Release, 채널, 번들, 회수를 소유합니다.

## 설계 한눈에 보기

**FDAI Lifecycle Hub**는 설치본별 배포를 관리합니다. 릴리스 발행, 서명, 채널 승격, 회수를
관리하도록 계획된 공급업체 앱인 **FDAI Release Hub**와는 별개입니다. Release Hub는
Lifecycle Hub가 사용하는 릴리스 목록, 데이터 또는 피드인 **Release Catalog**를 제공합니다.
카탈로그는 앱 이름이 아니라 기술적인 데이터 용어로 유지합니다. 초기 Release Hub는 CLI/API
작업 흐름부터 제공할 수 있으며, 이 설계가 전체 Release Hub 서비스의 구현 완료를 뜻하지는
않습니다.

| 관심사 | 결정 |
|--------|------|
| 제품과 설치 | 서명된 Release 하나가 모든 고객에게 쓰입니다. 설치마다 다른 것은 구성, 정책, 자기 환경에 대한 바인딩뿐입니다. |
| Hub 배치 | 연결된 고객마다 중앙 Hub cell을 두거나, 고객 경계 안에 온라인으로 동기화하거나 서명된 번들을 오프라인으로 가져오는 Target Hub를 둡니다. |
| 원하는 상태 | 단일 목표 상태는 없습니다. Hub는 채널 구독, 버전 범위, 구성 개정, 제약 조건에서 목표를 도출합니다. |
| 계획 계산 | Hub가 Lifecycle Plan을 계산합니다. 설치 에이전트는 최대 효과 경계를 로컬에서 도출하며, Plan은 그 경계를 좁힐 수만 있습니다. |
| 설치 에이전트 | 워크로드용 수명 주기 에이전트는 클러스터 안에, 정확한 Terraform 계획용 인프라 에이전트는 실행 호스트에 둡니다. 둘 다 판테온 에이전트가 아닙니다. |
| 업그레이드 | 유지 관리 구간 안에서 자동으로 적용합니다. 구성 변경에는 승인된 변경 요청이, Azure 리소스 삭제나 교체에는 확인이 필요합니다. |
| 데이터 경계 | Hub는 고객 워크로드의 자격 증명이나 운영 데이터를 보관하지 않습니다. Hub 자체의 제한된 서비스 ID와 서명 키는 고객 리소스를 변경할 권한을 주지 않습니다. 경계를 넘는 것은 수명 주기 메타데이터뿐입니다. |
| 기록 | cell이나 Target Hub마다 Hub PostgreSQL을 두고, 설치 증적은 Foundation 스토리지에 추가 전용으로 남깁니다. |

## 애플리케이션에 종속되지 않는 패키지 경계

선택적인 `fdai.application-release.v2` 확장은 서명된 구성 요소 이미지와 고객이 독립적으로
검토한 비공개 실행 묶음을 분리합니다.
[실행 묶음 계약](lifecycle-runtime-bundles-ko.md)이 지원 객체 종류, 서명된 설정의 정확한
고정 해시, 보안 한도와 주기 작업 효과를 입증하지 못했을 때의 복구 보류를 정의합니다.
아래 게시·검증·소유권 순서는 유지하며 FDAI 전체 설치 검증을 뜻하지 않습니다.
[배포 인수인계](../../runbooks/hub-lifecycle-deployment-handoff-ko.md)에서 단계별 담당자와
수동 작업·자동화 가능한 경계를 확인할 수 있습니다.

발행, 고정된 다이제스트를 통한 가져오기, 계획, 실행, 보고는 `fdai.application-release.v1`을
공유합니다. 제품, 앱 소스, 불변 구성요소 이미지와 HTTP 정보는 엔진의 분기 조건이 아니라
데이터입니다. [Release 계약](lifecycle-releases-and-channels-ko.md#애플리케이션-패키지-계약)이
필드 범위와 선택적 구성/데이터베이스 스키마 정보를 정의합니다. 데이터베이스 정보가 없으면
스키마 개정 0은 상태를 저장하지 않는 앱을 나타내며 마이그레이션이나 데이터베이스 초기화
권한을 주지 않습니다.

운영자가 고정한 Hub Settings와 설치 로컬 Agent 정책은 각각 `product`를 고정합니다. 등록 요청,
패키지나 Plan이 이 값을 선택할 수는 없습니다. 값이 없거나 다르면 앱 패키지를 차단합니다. 이 필드가
없는 기존 설치본은 기존 런타임 패키지 호환 경로만 유지합니다. 애플리케이션을 명시적으로 고정한
경우 기존 경로로 우회하지 않습니다. 기존 런타임 파서는 소스/오프라인 호환성을 위해 완전한
FDAI 서비스 구성을 계속 검증합니다.

등록된 기존 설치본을 위한 운영자 전용
`POST /v1/installations/{installation_id}/application-binding`에는 UUID, 현재 Settings
다이제스트, 사유와 확인문 `bind application <installation_id> <product> <settings_digest>`이
필요합니다. 설치본 행 잠금으로 실행 일정 변경과 계획 계산을 직렬화합니다. 열린 Plan,
이전 다이제스트와 다른 앱으로의 변경은 차단합니다. 같은 행위자의 동일 요청 재시도와
행위자가 명시된 감사 기록은 유지하며 소유권, 권한, 구성과 보고된 상태는 바꾸지 않습니다.
**Application** 탭은 열 때 값을 읽고 ID를 두 번 입력받으며 기계 값은 생성합니다.
결과가 불확실하면 자동 재전송하지 않고 새로고침해야 합니다. Agent 로컬 정책은 별도로
준비해야 합니다. [운영자 절차](../../runbooks/hub-lifecycle-operator-guide-ko.md)를 참조하세요.

**검토와 수정:** 하드코딩된 앱 이름만 바꿔서는 공통 엔진이 되지 않습니다. 이미지 목록만
받으면 다른 앱으로 바꿔치기할 수 있고 상태 관찰 방법도 빠집니다. 독립적인 앱 고정, 서명된
구성요소/상태 정보와 엄격한 JSON 검사로 정확한 서명, 버전/다이제스트 검사, 산출물 가용성,
회수, 실행 구간, 소유권, 사전 실행 검증, 롤백과 영구 재실행 방지 장치를 유지합니다.
앱 패키지는 기존 워크로드 프로필을 차단하며 소유권을 증명하거나 앱별 플래그, Entity 종류를 선택하지 않습니다.
임의의 Kubernetes 템플릿, 권한, 네임스페이스 생성, 새로운 소유권 근거와 데이터베이스
마이그레이션 실행은 이번 변경 범위 밖입니다.

릴리스 ID는 하나의 Release Hub 카탈로그 안에서 고유합니다. 이번 변경으로 어떤 앱에도
카탈로그를 사용할 수 있지만, 여러 제품의 버전 이름 공간을 도입하지는 않습니다. 로컬 합성
검증은 Azure 배포 근거나 프로덕션 자격 검증을 뜻하지 않습니다.

## 설치 Agent 구성 소스 소비 경로

기존 `fdai-lifecycle-agent poll-once` 진입점과 디렉터리 산출물 저장소는 원래 서명된
v2 전체 구성 컨테이너를 받습니다. 독립적인 설치 로컬 공개 키, X25519 비공개 입력,
활성 개정 및 Entity/이력 결합 정보는 Hub 전송과 분리합니다. Agent는 Plan, 정확한
Release/스키마, 패키지와 전체 이력을 검증한 뒤 복호화하고 각 Entity의 값을 기존
렌더러에 전달합니다. 선행 조건이 없으면 이 기능만 보류하며 기존 평면 산출물과 기본
사전 실행 동작은 유지합니다.
[구성 소유 문서](lifecycle-configuration-ko.md#설치-agent-소비-경로-설계와-비평)는
구현 전 비평과 개인정보 보호 경계를 기록합니다.

명시적인 읽기 전용 `reference-status` 명령은 기존 Kubernetes 전송 경로로 정확한
CSI/Pod/공급자 메타데이터를 검사하고 Entity, 출처 버전과 최신성을 명시합니다.
가장 강한 긍정 결과도 `reported-mounted`이며 비밀값의 사용 가능성을 검증한 결과가
아닙니다. Kubernetes Secret 데이터나 마운트된 파일은 읽지 않으며 출처 결합이 없으면
사용 불가 상태를 유지합니다. 로컬 입력은
[설치 가이드](../../runbooks/installation-agent-configuration-ko.md)를 참조하세요.

이는 구현된 소스와 로컬 합성 테스트 근거뿐입니다. 실제 등록, 산출물 전달, CSI 공급자
결합, Agent 배포, 운영 효과 증적 또는 운영 적격성을 주장하지 않습니다.
Hub 가져오기, 변경 승인, 활성화, 서명된 Plan 허용 심사와 로컬 실행 안전장치는
별도 결정으로 유지합니다.

## 기존 결합형 개발 검증 구성

선택적 구성 스키마 메타데이터가 있는 runtime v3 Release를 수락하면 기존 Hub 플래너는
Plan을 발행하기 전에 설치의 스키마 다이제스트를 해당 Release에서 수락한 스키마와
비교합니다. 다르면 그 후보를 차단합니다.
[구성 설계](lifecycle-configuration-ko.md#release-스키마-수락-설계와-검토)에서 주석과
버전 검사를 정의합니다. 이 선택적 기능이 없는 Release는 기존 동작을 유지하며 소스 및
오프라인 설치에 새 검사가 추가되지 않습니다. 독립 export pin, 매니페스트 서명, 만료,
회수, 로컬 효과 경계 검사는 계속 적용됩니다.

기존 업그레이드 플래너의 `plan_next` 소스 API는 서명된 전체 다중 Entity 구성 개정 하나를 임시
`ConfigurationRevisionCandidate`로 받을 수도 있습니다. 호출자는 독립적으로 연결한 고객 키와
설치 키, 봉인 키 분류, 수락한 전체 이력과 독립적으로 보관한 체인 끝을 제공합니다. 플래너는
정확한 카탈로그 Release 버전, 매니페스트 다이제스트와 스키마를 검증하며, 패키지가 설치에서
이미 관리 중인 Entity 집합과 불투명한 패키지 연결 값의 독립적인 일대일 매핑을 정확히 포함하는지
확인합니다. 기존 등록 식별자는 서명된 Plan에서도 바꾸지 않습니다. 각 Entity를 따로
해석하고, 하나라도 실패하면 후보 전체를 차단합니다. 서명된 Plan은 전체 패키지 다이제스트를
포함합니다. 패키지에 등장했다는 이유로 Entity를 관리 대상으로 바꾸지 않으며, 회수, 시간이나
영향 범위 검사도 우회하지 않습니다. 후보가 없으면 기존 계획 동작을 유지합니다. 후보가 있을 때
Release에 스키마 기능이 없으면 기존 구성으로 대체하지 않고 차단합니다.

이 API는 메모리 내 소스 소비 경로입니다. 원격 가져오기나 등록 경로로 노출하지 않고,
구성 체인 끝 증적을 기록하지 않으며, DB에 암호문만 저장한다고 주장하지 않습니다.
[구성 설계](lifecycle-configuration-ko.md#전체-다중-entity-개정-설계와-검토)가 새 형식,
호환성과 설계 검토를 정의합니다. 실제 키 등록, 같은 Release의 구성 변경
일정 영구 저장, Agent 전달과 복호화, CSI 참조 해석과 프로덕션 자격 검증은 남아 있습니다.

### 승인된 구성 키 소비

별도로 인증하는 구성 키 API는 이미 등록된 설치에 공개 Ed25519 구성 서명 키와 X25519
설치 암호화 키를 연결합니다. 기존 Ed25519 설치 신원은 요청 전체에 대한 증명을 제공하고,
인증된 다른 고객 운영자가 정확한 다이제스트를 승인합니다. 로컬 호출자 이름이나 패키지의
키로는 신뢰를 등록할 수 없습니다.
[구성 설계](lifecycle-configuration-ko.md#승인된-구성-키-설계와-검토)가 구현 전 검토,
역할 분리, 기한과 명시적 버전 체인을 정의합니다.

`HubStore.recompute_configuration`은 기존 설치 잠금 안에서 현재 승인된 공개 바인딩을
확인하고 해당 키만 실제 플래너와 검증기에 전달합니다. 기존 원격 카탈로그 재계산 API는
서버가 명시적으로 제공한 `target_routes(..., configuration_candidates=...)` 조합 경계를
통해 후보와 바인딩 버전을 소비할 수 있습니다. HTTP 본문에서 가져오지는 않습니다.
이 호환 경계에서는 Entity 매핑, 봉인 키 분류와 수락된 이력을 독립적인 조합 입력으로
유지합니다. 구성된 기본 경로는 `HubStore.recompute_persisted`를 사용합니다. 후보 주입 없이
영구 저장된 활성 개정, 독립 승인된 Entity 매핑, 분류와 원본 수락 이력을 확인합니다.
서버 시작은 패키지를 자동으로 가져오거나 활성화하지 않습니다.

구성 Plan은 같은 트랜잭션에서 정확한 승인 바인딩 버전과 요청 다이제스트를 영구 저장합니다.
만료, 교체나 회수 후에는 현재 Plan 조회를 보류합니다. 이전 공개 바인딩은 그대로
보존합니다. 원자적 가져오기 경로는 각 이전 패키지를 당시 수락한 정확한 키 버전과 증적으로
검증하며 교체 키를 쓰지 않습니다. 바인딩이 없거나 검증할 수 없어도 이 새 구성 기능만
보류하며 기존 등록과 계획은 호환성을 유지합니다. 명시적 Lifecycle Hub 스키마 개정 6은
개정 1과 2의 추가 전용 구성 갱신, 개정 4의 고객 로컬 채널과 개정 5의 빈 워크로드 상태를
보존합니다. 이전 실행 파일이 새 네이티브 소유권 근거를 해석하는 것도 차단합니다.
등록, 공개 키 바인딩과 기존 원시 구성은 그대로 유지하며 Release Hub는 개정 1을 유지합니다.

실제 인증된 소스 API는 설치가 증명한 Entity 범위 요청과 승인, 전체 서명 컨테이너 가져오기,
변경 요청 승인, 정확한 증적 활성화를 분리합니다. 수락한 체인 끝, 가져오기 기록과 감사는
pin 카탈로그/설치 소유자의 같은 트랜잭션에 기록합니다. 가져오기, 승인과 활성화는 서로 다르며
실행이나 승격 권한을 부여하지 않습니다.
[구성 설계](lifecycle-configuration-ko.md#원자적-가져오기와-구성-소비-설계와-검토)가 요청
형식, 제한, 이력 신뢰와 구현 전 검토를 정의합니다.

같은 카탈로그 트랜잭션에서 [고객 로컬 채널 관리](lifecycle-releases-and-channels-ko.md#고객-로컬-채널-관리-설계-및-검토)도 지원합니다. 기존 운영자 승인은 새로 검증한 `RELEASE` 집합의 범위를 `local-` 구성원으로 좁힐 수 있습니다. 정확한 로컬 리비전과 수락 핀/해시는 계획 감사에 남습니다. 설치 설정, 실행 승인 또는 공급업체 바이트를 바꾸지 않으며 서비스 제공에는 명시적인 현재 스키마 마이그레이션이 필요합니다.

새 가져오기 경로만 원본 암호문 컨테이너와 공개 메타데이터를 저장합니다. 기존 원시 구성은
바꾸지 않습니다. 로컬 HTTP/JWT와 격리된 PostgreSQL 테스트는 기본 소비, 독립 승인, 경쟁
분기 차단, 감사 롤백, 재시작/재시도와 키 교체 이력을 검증합니다. 실제 키 등록, 배포된
DB 마이그레이션, Agent 전송, 같은 Release의 구성 작업 예약이나 프로덕션 적격성을 뜻하지
않습니다.

기존 결합형 구성은 현재 state 소유자를 위해 유지하며, 기본 배포 단위가 아닙니다.
새 준비 작업은 아래의 제품별 독립 루트를 사용합니다.

벤더 Release Hub와 고객 Target Lifecycle Hub는 같은 테스트 구독의 별도 RG에 배치하며,
ACA Environment, VNet, PostgreSQL 서버와 DB, 관리 ID, Key Vault, 로그를 각각 분리합니다.
RG 분리는 관리 구획일 뿐 보안 격리의 증거가 아닙니다. VNet peering이나 벤더의 고객 측 접근
권한은 추가하지 않습니다. 승인된 브라우저 CIDR과 고객 NAT 주소로 HTTPS 접근을 제한하고,
비공개 DB와 Key Vault의 접근 경로는 분리합니다.

명시적으로 선택하는 원격 프로필은 Entra bearer 토큰의 발급자, 대상, 유효 시간과 운영자의
object ID, 클라이언트, scope를 직접 검증합니다. 서비스 요청은 정확한 고객 서비스 ID와
내보내기 읽기 전용 역할을 검증합니다. 프록시 헤더는 인증 근거가 아닙니다.
로컬 CLI의 loopback 기본값은 유지합니다. 버전이 지정된 secret reference로 독립적인 개발용
서명 키를 제공하고, PostgreSQL에는 Hub 자체의 관리 ID와 인증서를 검증하는 TLS만 사용합니다.
원격 서버를 시작하기 전에 명시적 migration을 완료해야 합니다. 키 교체나 호환되지 않는 기존
스키마는 별도로 검토한 migration이 필요합니다.

고객 운영자는 다운로드와 별개로 승인된 신뢰 경로에서 받은 revision과 정확한 digest를 먼저
승인한 뒤, 제한된 outbound import를 한 번 요청합니다. 다운로드 응답의 digest 자체는 승인이
아닙니다. 검증한 원본 바이트, digest, 키 식별 정보, 낮아지지 않는 revision 하한과 행위자 감사
기록을 영속 보관합니다. 기존 매니페스트 서명, 만료, 회수 계약과 플래너 제약을 유지하며,
회수 반영과 Plan 계산은 같은 신뢰 상태 행의 잠금으로 직렬화합니다.
UI는 이미 준비한 합성 설치본의 Plan을 계산합니다. 기존 검증 구성은 설치 Agent의
인증 연결을 설정하거나 Plan을 실행하지 않습니다.

준비 절차와 검증 명령은 [두 Hub 개발 경계 안내](../../../infra/hubs-development/README.md)를
따릅니다. 정적 IaC 검사와 로컬 컨테이너 검증만으로 Azure 네트워크/RBAC 격리, 실제 Entra
로그인, 레지스트리 아티팩트 존재, replica 교체 후 보존을 입증할 수는 없습니다.
이를 검증하려면 정확한 클라우드 preview와 실행 범위를 별도로 승인해야 합니다.
이 경로는 소스/오프라인 설치를 바꾸지 않으며, 자동 polling, 프로덕션 카탈로그 메타데이터와
신뢰 루트 설정, 클라우드 Agent 적용, 전체 FDAI 설치를 구현하지 않습니다.

## 실행 일정 준비 설계와 검토

인증된 고객 운영자는 이미 등록된 설치본의 일일 유지 관리 시간과 Plan 실행 시간을
준비할 수 있습니다. `GET /v1/installations/{installation_id}/execution-settings`는
일정 필드와 현재 전체 설정의 다이제스트만 반환합니다. `POST`에는 요청 UUID, 예상
다이제스트, 범위가 제한된 시간 설정, 사유 코드와 정확한 확인 문구
`update execution settings <installation_id> <settings_digest>`가 필요합니다.
운영자 신원은 요청 본문이 아니라 검증된 전송 인증 정보에서 가져옵니다.

유지 관리 시간은 현지 시각, IANA 표준 시간대, 1~1440 범위의 `duration_minutes`,
명시적인 중단 허용 여부로 구성합니다. 분 단위 소수 값으로 기존 초 단위 정밀도를
조회 결과에도 유지합니다. 최대 32개를 설정할 수 있으며, Plan 실행 시간은 1~1440분의
정수입니다. 알 수 없는 필드나 잘못된 값은 `422`, 8192바이트를 넘는 본문은 `413`을 반환합니다.

**검토와 수정:** 설치본 설정 전체를 바꾸면 배치 위치, 채널, 실행 세대까지 변경할 수
있습니다. 이 작업은 유지 관리 시간과 Plan 실행 시간만 바꿉니다. 기존 설치본 잠금을
사용하며, 열린 Plan이 있으면 전제를 몰래 바꾸지 않고 요청을 차단합니다. 같은 트랜잭션에서
설정을 갱신하고 작업자가 기록된 해시 연결 감사 기록을 추가합니다. 같은 운영자가 동일한
요청 UUID와 내용을 다시 보내면 설정을 또 바꾸지 않고 원래 적용한 다이제스트를 반환합니다.
같은 UUID를 다른 내용이나 다른 운영자가 사용하면 충돌로 처리합니다. 재요청 때 반환하는
다이제스트는 과거 작업을 가리키며, 이후에도 설정이 그대로라는 주장은 아닙니다.
설정이 같으면 설치본의 기록 시각을 갱신하지 않고 감사 기록에 `changed: false`를 남깁니다.
설정 리비전 충돌, 요청 ID 재사용 충돌, 열린 Plan은 `409`로 처리합니다.

이 준비 작업은 Entity 관리 전환, 소유권 증명 수락, 키 등록, 파일 가져오기, Plan 계산이나
적용 승인을 수행하지 않습니다. 설치본 Agent, 카탈로그 서비스 신원, 인증되지 않은 로컬
호출자의 이름으로 운영자 경로를 사용할 수 없습니다. 새 테이블이나 원격 DB 수정 스크립트도
필요하지 않습니다.

설치본의 **Execution schedule** 항목은 열었을 때만 이 정보를 조회합니다. 범위가 제한된
시간 입력, 서버에서 조회한 설정에 연결된 확인 문구, 브라우저가 생성하는 요청 UUID를
사용합니다. 읽기와 쓰기는 각각 10초로 제한합니다. 저장이 차단되거나 결과가 불확실하면
명시적으로 새로고침할 때까지 추가 변경을 막습니다. 쓰기를 자동 재시도하거나 Plan을
계산하고 적용하지 않습니다. 집중 소스 검사와 합성 UI 검증은 실제 배포 근거가 아닙니다.
정확한 소스의 활성화, 사람의 운영 확인, 근거에 기반한 나머지 워크로드 준비는 별도 단계입니다.

## 읽기 전용 입력 조회

**Available releases**는 `GET /v1/catalog/releases`로 이미 수락한 카탈로그를 조회합니다.
외부 가져오기 없이 고정값, 서명, 만료를 다시 검증합니다. 신뢰를 확인할 수 없으면
`503`을 반환하며, 검증한 빈 카탈로그와 구분합니다. **Configuration packages**는
`GET /v1/configurations`로 저장된 다이제스트, 개수, 시각, 현재 설치본 참조만 표시합니다.
값과 봉인된 식별자는 제외하고, 독립된 패키지 서명 출처를 기록하지 않았음을 명시합니다.
두 목록은 이미지 가용성, 배포 자격, 서명된 입력 준비 완료를 입증하지 않습니다.
Agent 신원은 이 운영자 목록을 읽을 수 없습니다.
초기 등록과 반복 배포 그림, 공개 입력의 출처, 현재 수동 절차와 운영 목표의 차이는
[운영자 가이드](../../runbooks/hub-lifecycle-operator-guide-ko.md)를 확인하세요.

## 명시적으로 선택하는 설치 Agent 통신

로컬 개발 구현은 설치본별로 명시적인 `auth.agent_principals` 연결을 받습니다.
호출자는 직접 검증한 Entra 토큰에 정확한 애플리케이션 object/client 쌍, `idtyp=app`,
`Agent.Access` 역할을 갖춰야 합니다. 해당 설치본의 Plan을 읽고 상태와 보고서를 제출할
수 있을 뿐입니다. 운영자, 카탈로그 ID, Agent ID는 구분합니다. Agent는 등록, 승인,
게시, 가져오기, 재계산을 할 수 없습니다. Release Hub는 Agent 연결을 받지 않으며,
연결 목록이 비어 있으면 기존 차단 동작을 유지합니다.

명시적으로 연결한 설치본에 한해, 인증된 운영자는 서명된 등록 요청을
`POST /v1/enrollments/{installation_id}/requests`로 제출할 수 있습니다.
기존 설치 키 증명, 요청 시각, 설치본 ID 일치 여부와 크기 검사를 그대로 적용합니다.
감사 기록의 `requested_by`에는 인증된 운영자를 남깁니다. 제출 결과는 승인 대기 요청일
뿐이며, 승인과 Entity 관리 설정은 별도입니다. 기존 Agent 등록 경로는 계속 차단하고,
연결하지 않은 설치본은 운영자 경로도 사용할 수 없습니다. 독립 Lifecycle Terraform
루트는 비어 있지 않은 Agent 연결을 실행 설정으로 전달합니다. 연결 목록이 비어 있으면
이전 이미지와의 호환성을 위해 실행 설정에서 해당 필드를 생략합니다.

운영자는 **Enrollment requests** 화면에서 연결된 설치본 ID를 입력하고 64 KiB 이하의
서명된 요청 JSON 파일을 선택할 수 있습니다. `signed_payload`와 `proof`만 전송하며,
개인 키는 업로드하지 않습니다. 제출 요청은 10초 안에 끝내고 자동으로 재시도하지 않습니다.
결과를 확인할 수 없으면 승인 대기 목록을 새로 고친 뒤 재시도하세요.
승인 대기 상태는 승인, 소유권 증명 또는 Plan 적용 권한을 뜻하지 않습니다.

Agent는 명시적으로 선택한 경우에만 AKS의 투영된 워크로드 ID로 지정된 Hub API 범위의
토큰을 얻습니다. 클러스터 내부 Kubernetes 인증은 별도로 읽으며 kubeconfig로 대체하지
않습니다. 횟수와 시간이 제한된 폴링은 오류, 입력 차단, 롤백 시 중단합니다. 서명된 입력은
별도로 승인한 digest에 고정하고, 오프라인 배치 전에 검증한 다음 Plan 수락 시 다시 검증합니다.
기존 fsync 기반 재전송 하한, 미전달 보고서, 롤백 저널은 현재 상태와 함께 Agent 네임스페이스의
영구 볼륨에 보관합니다. 워크로드 Role은 이 영역을 변경할 수 없습니다. 권한은 워크로드
네임스페이스의 Deployment, Service, Job 작업에만 한정합니다.
[Agent 준비 안내](../../../lifecycle/agent/README.md#remote-development-preparation)를 참조하세요.

이 선택 기능의 근거는 집중 로컬 테스트입니다. 실제 Entra 인증, 이미지, AKS, 볼륨 재연결,
워크로드 변경 효과를 입증하지 않습니다. 이 준비 작업은 기존 Hub의 이미지, revision,
카탈로그 연결, 네트워크 허용 목록을 변경하지 않습니다. 해당 변경에는 정확한 클라우드
계획과 별도 승인이 먼저 필요합니다.

## 제품별 독립 배포

Release Hub는 공급업체의 제품이고, Lifecycle Hub는 고객의 배포 관리 제품입니다.
각 제품은 자기 UI/API 묶음과 PostgreSQL을 루트 하나와 state 하나로 배포합니다.

| 제품 | 배포 루트 | 필수 상대 제품 입력 |
|------|-----------|---------------------|
| Release Hub | [infra/release-hub](../../../infra/release-hub/README.md) | 없음 |
| Lifecycle Hub | [infra/lifecycle-hub](../../../infra/lifecycle-hub/README.md) | 없음 |

개발과 프로덕션은 같은 코드에 비공개 입력과 별도 백엔드 state 경로를 사용합니다.
기본 로컬 백엔드는 영속 비공개 저장소의 절대 경로를 명시적으로 받아, Azure Storage 없이
기존 로컬 state를 보존합니다. 원격 백엔드는 후보 고정 전에 별도로 검토하는 표준 Terraform
재정의 설정으로 선택할 수 있으며, 실행 중 백엔드를 바꾸지는 않습니다.
공유 내부 모듈은 선택한 제품의 자원만 만듭니다. 다른 Hub의 state, ID, NAT 주소를 읽지 않습니다.
승인된 기존 레지스트리는 외부 입력입니다. FDAI 소스/오프라인 설치기, 본체 인프라 루트,
Agent 또는 클러스터 배포는 바꾸지 않습니다.

Entra 앱 등록이 0개여도 각 루트는 Graph나 디렉터리 state 없이 계획할 수 있고,
각 원격 앱은 자기 스키마 이행, 서버 기동, 상태/준비 확인과 UI 제공을 수행할 수 있습니다.
PostgreSQL/Key Vault 관리 ID, 인증서를 검증하는 TLS와 사람 DB 관리자는 유지합니다.
앱 소유의 제한된 SQL/Key Vault 초기화 명령은 임시 수동 Job에서 실행합니다.
Terraform 기본 도구로 자원을 선언하고 Azure CLI로 Job을 시작하고 관측합니다.
초기화 후 임시 권한은 영구 런타임 자원과 별도로 제거합니다.

로그인과 Lifecycle의 카탈로그 원본은 명시적으로 선택하는 연결이며 가짜 값을 넣지 않습니다.
로그인이 없으면 관리 API는 503으로 차단하고 UI는 기능을 사용할 수 없다고 표시합니다.
카탈로그가 없으면 원격 카탈로그 클라이언트를 만들지 않고 해당 기능만 사용할 수 없게 합니다.
나중에 원본을 연결할 때는 행위자를 기록하는 `bind-catalog`를 사용합니다.
이 명령은 가져오기나 고정값 승인을 하지 않으며 기존 키를 조용히 바꾸지 않습니다.
기존 인증 경로와 로컬 loopback 동작은 유지합니다.

[제품별 절차](../../../infra/modules/hub-service/README.md)는 소스/잠금 파일/기반 및 런타임 이미지
digest 고정, 수동 Job, 정리, state 백업 복사본 이관 검증을 설명합니다.
기존 state와 디렉터리/레지스트리 소유권은 자동으로 바꾸지 않습니다.
익명 관리 API 정책은 보류하며, 요청한 기능은 아직 충족하지 못했습니다.
관리 API는 계속 안전하게 차단합니다. 이 정책이 미정이어도 독립적인 스키마 이행, 기동,
UI 준비는 계속할 수 있으며, 별도 승인을 받으면 UI와 준비 상태 확인만을 위한 배포도 가능합니다.
그 배포가 입증하는 것은 프로세스, 스키마와 화면 제공이지 익명 관리 기능의 사용 가능 여부가 아닙니다.
웹 틀이나 기능 사용 불가 화면만으로 전체 기능이 완료되지는 않습니다.
SQLite/mock/브라우저 근거, PostgreSQL/이미지 검증, 실제 Azure 배포는 별도로 보고합니다.
로컬 인프라가 없어 실행하지 못한 검사는 통과로 세지 않습니다.
소스 전달, 이미지 게시와 Azure 변경에는 각각 별도의 명시적 승인이 필요합니다.

### 범위가 제한된 데이터베이스 복구 검사

승인된 비공개 관측 환경에서 앱 소유 명령
`python -m fdai_lifecycle_hub.database_inspection`으로 원본과 복원본을 별도로 관측하세요.
각 제품의 런타임 Managed Identity와 인증서를 검증하는 TLS를 재사용합니다.
연결 전에 URL 쿼리의 접속 대상 재정의를 차단한 뒤 스키마와 실제 권한을 확인합니다.
단일 repeatable-read 읽기 전용 트랜잭션에서 이행된 스키마와 실제 런타임 권한을 확인하고
항상 롤백합니다. 테이블별 행 수는 1,001행까지만 확인하고 최대 1,000행을 허용합니다.
기본 키 순서로 선택한 최대 32개 대표 행의 SHA-256 지문을 비교하며, 시간은 UTC로 표현합니다.

비공개 `0600` 증적은 기존 파일을 덮어쓰지 않으며 원시 행이나 연결 값 대신 행 수와 지문을
보관합니다. 임시 Job 밖에 증적을 보존하고, 승인된 비공개 경로로 원본 증적을 전달하세요.
명령 옵션과 관측 한계는
[제품별 절차](../../../infra/modules/hub-service/README.md#read-only-database-recovery-comparison)에서
다룹니다. 이 명령은 복원을 조정하거나 전체 데이터베이스 동등성을 입증하지 않습니다.
행 수가 같아도 표본 밖 변경은 놓칠 수 있습니다. 선택한 복원 시점에 가깝게 원본을 수집하고
그동안 쓰기를 중지하세요. 서버 신원, 비공개 DNS, Entra-only 인증과 관리자 연결, 임시 자원
부재는 별도의 권위 있는 관측으로 확인해야 합니다. 로컬 PostgreSQL 테스트는 Azure PITR이나
Managed Identity를 검증하지 않습니다.

## 핵심 개념

설계 전체는 네 가지 개념으로 이루어집니다. 이 개념들을 분리해 두어야 제품 하나가 포크 없이 모든
고객에게 쓰일 수 있습니다.

| 개념 | 정의 | 소유자 | 변경 방법 | 위치 |
|------|------|--------|-----------|------|
| 제품 | 모든 고객에게 동일한 서명된 Release로 제공되는 FDAI 자체 | 공급업체 | Release 파이프라인, 채널 승격, 회수 | Release 카탈로그 |
| 설치 | 고객 경계 하나 안에 있는 FDAI 배포 하나로, Apollo의 Environment에 해당합니다. 고객은 여러 설치를 가질 수 있습니다. | 고객 | 등록, 채널 구독, Entity 설정 | Hub의 `installation` 및 `entity` 테이블 |
| 구성 | 설치 하나에 대해 원하는 값인 Environment Config와 Entity 재정의 블록입니다. 권한은 절대 담지 않습니다. | 고객 | 고객 Git의 검토된 병합을 서명된 패키지로 전달 | 고객 Git, 이어서 Hub 구성 테이블 |
| 런타임 상태 | 설치가 실제로 실행하고 관측하는 것: 보고 상태, 증적, 정책과 권한 상태, 운영 데이터 | 설치 | 에이전트와 관리되는 권한 경로만 | 설치 저장소. Hub는 수명 주기 메타데이터만 봅니다. |

## 설계와 비판 검토

**초기 설계:** 중앙 컨트롤 플레인이 고객마다 원하는 상태 하나를 저장하고, 5계층 재정의 스택이
구성을 결정하며, 새로운 배포, 구성, 드리프트, 정책 에이전트가 롤아웃을 실행합니다.

**비판 검토:**

- Apollo는 환경별 목표 상태를 하나만 두지 않습니다. 제품은 release channel과 제약 조건을
  따르며 목표는 그로부터 도출됩니다
  ([Apollo overview](https://www.palantir.com/docs/apollo/core/overview)).
- 판테온은 고정되어 있습니다. 자신이 실행되는 런타임을 업그레이드하는 에이전트는 순환 의존성도
  만듭니다.
- 정확한 계획을 만드는 중앙 엔진에는 모든 고객의 Azure 자격 증명이 필요하며, 규제 고객은 이를
  금지합니다.
- 선형 재정의 스택은 구성으로 권한을 바꿀 수 있게 하며, ADR-0002가 이를 금지합니다.
- 오프라인 사이트는 중앙 서비스를 폴링할 수 없습니다.

**수정된 계약:** Hub는 조율만 합니다. 실제로 무엇이 바뀔 수 있는지는 서명된 산출물과 설치 쪽
에이전트가 결정합니다. 권한은 정책과 승격 레지스트리에 남고, 오프라인 사이트는 자체 Target Hub를
운영합니다.

### Hub 배치

| 배치 | 위치 | 카탈로그 원천 | 운영 주체 | 일반적인 고객 |
|------|------|---------------|-----------|---------------|
| 중앙 Hub cell | 고객과 합의한 리전의 공급업체 구독. 고객마다 자체 데이터베이스와 고객 관리 키를 가진 격리된 cell을 받습니다. | Release 카탈로그를 직접 사용 | 공급업체 | 연결되어 있고 경계 제한이 없는 고객 |
| 온라인 Target Hub | 고객 운영 리소스 그룹 | 허용 목록에 있는 아웃바운드 경로로 카탈로그에서 동기화 | 고객 | 규제를 받으며 연결된 고객 |
| 오프라인 Target Hub | 고객 운영 리소스 그룹 | 운영자가 가져오는 서명된 업그레이드 번들 | 고객 | 인터넷에 연결되지 않은 고객 |

Hub cell은 중앙 Hub의 고객별 격리 단위입니다. [하이퍼스케일 셀 아키텍처](../architecture/hyperscale-cell-architecture-ko.md)의
스트리밍 셀과는 관계가 없습니다.

### 신뢰 경계

- 공급업체 release 키는 Release, 카탈로그 메타데이터, 회수 공지, 업그레이드 번들에 서명합니다.
  최신성과 순서는 [카탈로그 무결성](lifecycle-releases-and-channels-ko.md#카탈로그-무결성)이
  정의합니다.
- 고객 구성 키는 구성 패키지에 서명합니다. 이 키는 고객의 Key Vault나 HSM에 남습니다.
- 각 설치는 자기 Key Vault에 내보낼 수 없는 설치 키를 보관합니다. 등록할 때 이 키의 보유를
  증명하고, 이후 봉인된 값을 풀고 증적에 서명하는 데 사용합니다.
- 각 Hub cell이나 Target Hub는 자체 Hub 키를 가집니다. Hub 키와 설치 키는 서명된 키 기록으로
  교체되며, 키를 폐기하면 그 키가 서명한 모든 Plan이 무효가 됩니다.
- 설치 에이전트는 서명된 Release, 구성 패키지, 소유권 증거, 로컬 강제 정책에서 최대 효과 경계를
  직접 도출합니다. Hub Plan은 그 경계를 좁힐 수만 있습니다.
- 경계를 넘는 것은 버전, 다이제스트, 대략적인 구성 요소 상태, 제약 조건 결과, 정리된 계획
  요약 같은 수명 주기 메타데이터뿐입니다. 이벤트 내용, 리소스 식별 정보, 온톨로지 내용, 감사
  내용, 비밀, 자격 증명, 평문 식별자는 설치 안에 남습니다.

## 수명 주기 루프

### 원하는 입력

Hub는 다음 입력에서 각 설치의 목표를 도출합니다.

- 채널 구독과 선택적인 버전 범위
- 현재 구성 개정: Environment Config와 Entity 재정의 블록
- 카탈로그 사실: Release, 채널 구성원, 회수, 제품 의존성, 스키마 범위
- 제약 조건과 최신 보고 상태

목표는 구독한 채널에서 버전 범위 안에 있고 모든 제약 조건을 통과하며 회수되지 않은 최신
Release입니다. 이 Release는 버전 범위가 가장 구체적으로 일치하는 재정의 블록과 함께 배포됩니다.

### Entity와 보고 상태

| Entity 종류 | 예 | 관리 여부 |
|-------------|-----|-----------|
| 워크로드 | Core, Operator API, Document Ingestion API, Document Processing Worker, isolated Executor, Console, CronJob, 수명 주기 에이전트 | 관리 |
| 플랫폼 | AKS 클러스터, PostgreSQL, Event Hubs 네임스페이스, Key Vault, 컨테이너 레지스트리, 스토리지, 네트워크 | 관리 |
| 비관리 | 고객 소유 API Management, 프라이빗 DNS 영역, ITSM 엔드포인트 | 관측만 함 |

보고 상태에는 Release 버전, 이미지 다이제스트, 구성 다이제스트, 대략적인 상태, 마지막 Plan
결과가 들어 있습니다. Core Entity는 에이전트마다 실행 중, 성능 저하, 중지 가운데 하나의 상태
구간과 범위가 정해진 consumer lag 구간 및 유휴 시간 구간을 추가합니다. 이벤트 내용과 이벤트별
시각은 설치 안에 남습니다. 플랫폼 Entity는 Terraform 상태 lineage, serial, 리소스 식별 정보의
다이제스트를 추가합니다. Apollo와 마찬가지로 설정과 보고 상태가 모두 있는 Entity는 관리
Entity이고, 보고 상태만 있는 Entity는 비관리 Entity입니다. 보고 상태는 추가 전용이며 이벤트
시각과 기록 시각을 유지합니다.

### Lifecycle Plan

Plan 유형은 설치, 업그레이드, 구성 변경, 회수 roll-off(회수된 Release에서 벗어나기), 드리프트
조정, 제거입니다. 제거에는 항상 운영자 확인이 필요합니다. 각 Plan은 대상 설치, Hub 키 epoch,
계산의 근거가 된 보고 상태 다이제스트, 설치별로 증가하는 순번, 펜싱 세대, 목표 Release, 구성
개정, Entity 집합, 제약 조건 결과, 범위를 좁히는 효과 경계, 만료 시각을 명시합니다. 에이전트는
순번, 세대, 원본 상태 다이제스트가 오래된 Plan을 거부하고 그 거부를 내구성 있게 기록합니다.

> **구현된 수락 경계:** 에이전트는 독립적으로 구성된 Hub 신뢰와 내구성 있는 로컬 순번 상태를
> 바탕으로 정규화된 Plan 서명 바이트를 검증합니다. apply 어댑터가 켜져 있어도 오래된 순번,
> 잘못된 대상, 폐기된 키와 지나치게 넓은 효과 경계는 클러스터 호출 전에 차단됩니다. 또한 자동
> 적용은 정확한 Plan 다이제스트, 펜싱 세대, Release 및 구성 다이제스트, 열린 구간에 결속된 로컬
> `LifecycleAuthorizationReceipt`를 요구하며, 같은 정확한 Plan 다이제스트에 대한 선행
> `infrastructure` 단계 완료 증적이 요구되지만 아직 없을 때는 워크로드 단계를 대기 상태로
> 보류합니다. 프로덕션 키 수명 주기, 다중 호스트 인프라 조정기 실행 및 실제 설치 검증은 별도로
> 유지됩니다.

Plan은 펜싱된 단계 순서로 실행됩니다. 인프라 에이전트가 인프라 단계를, 수명 주기 에이전트가
워크로드 단계를 소유합니다. 각 단계는 이전 단계의 증적이 기록된 뒤에만 시작합니다. 실패하면
Release가 허용하는 경우 완료된 단계를 역순으로 보상하고, 그렇지 않으면 설치를 운영자 판단까지
보류합니다.

1. 에이전트는 Hub를 폴링하고 Plan의 서명, 대상, 순번, 세대를 검증합니다.
2. 에이전트는 Release와 구성의 서명을 검증합니다. 공급업체가 서명한 회수가 롤백을 허용하지 않는
   한, 이미 적용한 최신 Release보다 오래된 Release를 거부합니다.
3. 인프라 에이전트는 봉인된 값을 로컬에서 복호화해 정확한 Terraform 계획을 만듭니다. 수명 주기
   에이전트는 워크로드 매니페스트를 만듭니다.
4. 에이전트는 정확한 변경을 Plan이 좁힌 로컬 도출 효과 경계와 비교합니다. 그 경계를 벗어난
   변경은 거부하고, 기존 Azure 리소스의 삭제나 교체는 같은 정확한 계획 다이제스트에 결속된
   운영자 확인이 있을 때까지 보류합니다.
5. 에이전트는 정확한 계획 다이제스트를 Plan, Release, 구성 개정, 열린 구간에 결속하는 로컬
   수명 주기 승인 증적을 기록합니다. 이 증적은 기존 정확한 계획의 claim, 적용, 검증 전용 복구
   단계에서 운영자의 명령 실행을 대신합니다. 에이전트는 다이제스트와 정리된 요약을 Hub에
   보고합니다.
6. 성공하려면 정상적인 워크로드, 두 번째 변경 없음 계획, 독립적인 재확인이 필요합니다. 증적은
   Foundation 스토리지에 추가되고 Hub는 결과를 기록합니다.

수명 주기 에이전트, 인프라 에이전트, Target Hub는 두 개의 슬롯으로 스스로 업그레이드합니다. 새
버전이 이전 버전 옆에서 시작해 상태 검사를 통과한 뒤 역할을 넘겨받습니다. 이전 슬롯은 롤백
대상으로 남습니다. `InfrastructureAgent`는 Plan 효과 경계를 강제하고 기존 Azure 리소스의 삭제나
교체를 정확한 Plan 다이제스트에 결속된 운영자 `DestructiveChangeConfirmation`이 있을 때까지
보류한 뒤 정확한 계획 조정기를 호출하며, `DualSlotUpgradeController`는 후보 슬롯을 쓰기 권한 없이
시작해 상태 검사가 실패하면 이전 슬롯으로 롤백하고 상태 및 인계 후 재확인 검사를 통과한 뒤에만
펜싱된 쓰기 권한을 이전합니다.

### 제약 조건

| 제약 조건 | 설정 주체 | 차단 대상 |
|-----------|-----------|-----------|
| 유지 관리 구간(무중단 또는 다운타임) | 고객. Release가 고정한 시간대 데이터베이스 버전의 IANA 시간대를 사용합니다. | 선언된 최대 소요 시간이 남은 구간에 들어가지 않는 Plan. 같은 종류의 구간이 겹치면 합치며, 신뢰할 수 있는 UTC 시계가 판단합니다. |
| 억제 구간 | 운영자, 또는 실패 후 자동 | 범위 안의 Plan. 실패로 생긴 억제는 실패한 Plan의 롤백을 막지 않습니다. |
| 버전 범위 | 고객 | 범위 밖의 Release |
| 제품 의존성과 스키마 범위 | Release 메타데이터 | 호환되지 않는 업그레이드와 롤백 |
| 산출물 가용성 | 설치 레지스트리 | 이미지가 경계 안에 없는 Plan |
| 재정의 적용 범위 | 고객 | 일치하는 재정의 블록이 없는 Release |
| 데이터 상주 | Environment Config | 허용 범위 밖에서 데이터를 처리하는 Release나 모델 바인딩 |
| 회수 | 공급업체 | 회수된 Release의 제안. 회수는 roll-off도 시작합니다. |
| 파괴적 변경 | 헌법 | 확인 전까지 기존 Azure 리소스의 삭제나 교체 |

> **구현된 계획 제약 경계:** `plan_next`는 Plan에 서명하기 전에 유지 관리 및 억제 구간, 버전 및
> 스키마 범위, 산출물 가용성, 설치 수준 및 각 관리 대상 Entity의 `EntitySettings` 재정의 적용 범위,
> 데이터 상주, Release 및 기능 회수를 평가합니다. 시점 제약(유지 관리 및 억제 구간)은 이전
> Release로 후퇴하지 않고 `Waiting` 상태로 대기하며, 시점 외 제약은 부적격 후보를 건너뛰거나
> `NoEligibleRelease`를 반환합니다. 물리적 단계 펜싱, 로컬 승인 증적 및 실제 설치 검증은 별도로
> 유지됩니다.

### 실패, 드리프트, 조정

- 실패한 Plan은 해당 Entity에 자동 억제 구간을 둡니다. 실패가 설정된 임계값을 넘으면 Apollo처럼
  설치 전체를 억제합니다. 스키마 범위가 허용하면 이전 Release로 롤백하는 Plan이 실행되고,
  그렇지 않으면 설치를 운영자 판단까지 보류합니다.
- 수명 주기 드리프트는 보고 상태와 원하는 입력의 차이입니다. Deployment를 수동으로 바꾸거나
  Terraform refresh에서 드리프트가 발견된 경우가 해당합니다. Hub는 다음 일치하는 구간에 조정
  Plan을 발행합니다.
- Hub는 보고 상태, Entity 설정, 구성 개정, 채널 구성원, 회수가 바뀔 때와 Plan이 정해진 임계
  시간보다 오래 차단될 때 Plan을 다시 계산합니다.

> **구현된 Deployment 드리프트 조정 경계:** 대기 중인 Plan이 없을 때 수명 주기 에이전트는 범위 내
> 실제 Deployment를 기록된 정상 렌더링과 비교하고, 스테이징된 `available_artifact_digests`를 보존한
> 채 드리프트가 발생한 Entity를 관측된 이미지 다이제스트와 함께 `degraded` 상태로 보고합니다.
> `plan_next`는 관리 대상 Entity가 비정상 상태이거나 실행 중인 Release 매니페스트 밖의 산출물
> 다이제스트를 보고하면 유지 관리 구간 밖에서는 `Waiting` 상태로 대기하고, 다음 일치하는 구간에서
> 현재 Release에 대한 서명된 `drift-reconciliation` Plan을 발급합니다. Terraform refresh 드리프트와
> 실제 AKS 검증은 별도로 유지됩니다.

### 명령과 재정의

Apollo에는 런타임 재정의 계층이 없습니다. 가장 가까운 개념은 억제 구간, 유지 관리 구간 재정의,
비상 해제(break-glass) 명령입니다. FDAI도 이 구분을 유지합니다.

| 명령 | 주체 | 효과 | 만료 |
|------|------|------|------|
| 억제 구간 | 수명 주기 운영자 | 범위 안의 새 Plan을 즉시 중지합니다 | 필수 |
| 권한을 낮추는 명령 | 설치 운영자 | ActionType 강등, 자율성 상한 하향, kill switch 작동을 즉시 적용합니다 | 필수. 운영자는 만료 전에 알림을 받고 연장할 수 있습니다. |
| 비상 해제 명령 | 새 인증을 마친 비상 해제 역할 | 스케일 아웃 같은 비상 구성 변경을 적용하거나, 유지 관리 구간, 억제 구간, 버전 범위를 우회합니다 | 필수. 만료되면 병합된 변경이 이를 채택하지 않은 한 Hub가 승인된 Git 개정으로 조정합니다. |

권한을 높이는 명령은 없습니다. 비상 해제 명령은 유지 관리 구간, 억제 구간, 버전 범위만 우회할
수 있습니다. 서명 검사, 로컬 효과 경계, 정확한 계획, 잠금, 멱등성, 감사 의도, 회수, 파괴적
변경 확인, 복구, 독립적인 재확인은 그대로 거칩니다. 설치 자체의 kill switch 경로는 기존 동작을
유지합니다.

> **구현된 명령 만료 및 비상 해제 경계:** `LifecycleCommand`와 `validate_lifecycle_command`는 모든
> 명령(`suppression-window`, `authority-lowering`, `break-glass`)에 명시적 만료 시각을 요구하며,
> 권한을 높이는 요청(`shadow`를 넘는 `target_mode`, `hil`을 넘는 `target_autonomy`, kill switch
> 해제, 또는 `maintenance-window`, `suppression-window`, `version-range` 밖의 우회)을 거부합니다.
> 비상 해제 명령이 활성 상태인 동안에는 시크릿 검사를 통과한 비상 재정의(`configuration-change`
> Plan)를 적용하고 선언된 구간·버전 범위 제약만 우회하되 회수, 스키마, 산출물, 데이터 상주 검사는
> 그대로 유지합니다. 만료 시점에는 병합된 변경이 비상 재정의를 채택하지 않은 경우 `plan_next`가
> 승인된 구성 개정으로 되돌리는 `drift-reconciliation` Plan을 발급합니다. 전용 Hub 명령 HTTP/UI
> 경로는 별도로 유지됩니다.

## 운영 루프와의 분리

- 수명 주기 루프는 소유함을 증명할 수 있는 리소스만 변경합니다. Foundation 리소스에는
  Terraform 상태 식별 정보와 일치하는 서명된 생성 증적이 필요합니다.
  [네이티브 최초 생성 경로](#애플리케이션-워크로드의-네이티브-최초-생성)는 새로 만든 워크로드
  객체만 별도로 다루며 상위 네임스페이스는 소유하지 않습니다. 태그 권한이 있는 누구나
  붙일 수 있으므로 `fdai:managed=true` 태그는 탐색 단서일 뿐입니다.
- 운영 루프는 소유가 증명된 FDAI 리소스를 대상으로 하는 작업을 제안하지 않으며, 위험 게이트는
  그런 대상을 차단합니다. Heimdall은 여전히 그 리소스의 드리프트를 참고 증거로 보고할 수 있습니다.
- 수명 주기 에이전트는 권한이 있는 이벤트를 게시하지 않습니다. Saga는 수명 주기 증적을 증거
  참조로만 인용할 수 있습니다.
- `ProvenFoundationOwnershipRegistry`는 검증된 서명 Foundation 생성 증적과 일치하는 Terraform 상태
  다이제스트가 있는 리소스만 수락하여 운영 루프 대상에 대해 `RiskGate`에 `deny` 신호를 전달하며,
  수동 태그만 붙은 고객 리소스(서명된 Foundation 증적이 없는 `fdai:managed=true`)는 FDAI 소유로
  채택하지 않습니다.

## 고객 격리와 데이터 상주

| 요구사항 | 설계가 충족하는 방법 | 확인 방법 |
|----------|----------------------|-----------|
| 데이터를 국내에 유지 | Target Hub와 설치를 Korea Central에 두고, Hub는 메타데이터만 저장합니다 | Azure Policy 허용 위치와 보고된 바인딩 범위 |
| 해외 엔드포인트 금지 | 허용 목록에 있는 카탈로그 동기화 또는 오프라인 번들 | 이그레스 방화벽 로그와 [네트워크 매트릭스](network-connectivity-matrix-ko.md) |
| 승인된 모델 엔드포인트만 사용 | Environment Config의 모델 바인딩 허용 목록과 상주 제약 조건 | 시작 시 바인딩 검증 |
| PTU 필수 | 용량 유형이 `ptu`인 모델 바인딩 | Settings의 모델 인벤토리 |
| 격리된 네트워크 | 프라이빗 엔드포인트를 쓰고, 에이전트는 경계 안의 Target Hub를 폴링합니다 | 네트워크 매트릭스 시나리오 |
| 데이터에 대한 중앙 접근 금지 | Target Hub를 경계 안에 둡니다. 중앙 cell도 운영 데이터는 보관하지 않고 봉인된 식별자만 보관합니다. | Hub 데이터 모델 검토와 감사 |

Azure 모델 배포 유형은 프롬프트를 처리하는 위치가 서로 다릅니다. Global 유형은 어느 리전이든
사용할 수 있고, Data Zone 유형은 아시아 태평양 같은 영역 안에 머무르며, Standard나 Regional
Provisioned 유형은 리소스가 속한 지역 안에 머무릅니다
([deployment types](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/deployment-types)).
따라서 PTU를 쓰면서 국내에서 처리하려면 Regional Provisioned가 필요하며, 이 유형은 모든 모델에
제공되지는 않습니다.

### Hub가 침해된 경우

침해된 Hub는 업그레이드를 지연하거나 Plan을 보류할 수 있습니다. 하지만 효과 경계를 넓히거나,
Release나 구성 패키지를 위조하거나, Plan을 다른 설치로 재전송하거나, 봉인된 값을 읽거나, Azure
자격 증명을 얻을 수는 없습니다. 에이전트는 공급업체가 서명한 회수 없이는 버전 롤백을 거부하며,
만료된 카탈로그 메타데이터는 [카탈로그 무결성](lifecycle-releases-and-channels-ko.md#카탈로그-무결성)에
설명한 대로 권한을 낮춥니다. 각 cell은 자체 키, 데이터베이스, 고객 관리 키를 가지므로 침해된
cell이 다른 고객의 cell에 영향을 줄 수 없습니다.

### 공급업체 지원

지원 담당자는 중앙 cell의 메타데이터만 봅니다. Target Hub의 기록은 고객이 정리된 지원 번들을
내보내지 않는 한 고객에게 남습니다. 설치에 접근하려면 고객이 자기 테넌트에서 부여하는 시간
제한 역할을 사용합니다. Hub는 어떤 접근도 부여하지 않습니다.

## 등록과 마이그레이션

1. 운영자는 다른 경로와 마찬가지로 자신의 로그인으로 Foundation을 만들거나 기존 설치에서
   시작합니다. 오프라인 사이트는 서명된 오프라인 패키지로 Target Hub와 첫 Release를 설치합니다.
2. 운영자는 서명된 Release에서 수명 주기 에이전트와 인프라 에이전트를 설치합니다.
3. 설치는 설치 키로 등록 요청에 서명해 키 보유를 증명하고, 고객 승인자는 별도 경로로 확인한 키
   ID를 지정해 등록을 수락합니다. 그때까지 Hub는 이 설치에 대해 아무것도 계획하지 않습니다.
   증명이 틀렸거나 요청 시각이 Hub 시계와 앞뒤로 5분 넘게 차이 나는 요청은 설치를 만들지 않으며,
   Hub는 그 사유를 감사에 남깁니다.
4. Entity는 비관리 상태로 시작합니다. 소유가 증명되고 운영자가 설정을 추가한 뒤에만 관리
   Entity가 됩니다. Foundation 소유는 서명된 생성 증적과 Terraform 상태 식별 정보가 함께
   있어야 증명됩니다. 네이티브 워크로드는 아래의 별도 최초 생성과 운영자 수락 경로를
   사용합니다. `fdai:managed=true` 태그만 있으면 Entity는 비관리 상태로 남고, Hub는 그
   사유를 기록합니다. 관리 Entity가 없는 설치는 Plan을 받지 않습니다.
5. 첫 Plan이 소스 빌드 이미지를 서명된 이미지로 바꾸거나, 명시적으로 비어 있는 워크로드
   자리에 서명된 이미지를 설치합니다.

### 빈 워크로드 상태

아직 설치하지 않은 Entity는 `release_id: null`, 빈 설치 아티팩트 다이제스트 목록,
`health: unknown`을 보고합니다. 이는 배포 버전을 만들어 내지 않고 명시적으로 부재를 나타냅니다.
미리 준비한 이미지 목록은 스냅샷의 `available_artifact_digests`에 별도로 보고합니다. 이 선택
필드를 생략하면 기존 목록 처리 방식을 유지하고, 빈 목록을 명시하면 사용할 수 없음을 뜻합니다.

설치하지 않은 관리 Entity가 있으면 플래너는 구독한 모든 Release를 검토합니다. 실제 카탈로그
버전인 `0.0.0`도 포함합니다. 소유권, 별도의 애플리케이션 연결, 일치하는 구성, 아티팩트 가용성,
서명, 작업 시간대, 로컬 영향 범위 조건은 그대로 적용합니다.
일반 첫 설치나 업그레이드 Plan은 이미 설치된 Entity의 버전을 낮추지 않습니다.
빈 자리를 관리하려면 `manage --initial-release <version>`으로 재정의 적용 범위를 검증합니다. 이 인자는 Plan을
고정하거나 후보 검사를 우회하지 않습니다.

**비판과 수정:** 상태를 모른다고 설치에 성공한 것은 아닙니다. 준비한 이미지는 실행 중인 이미지가
아니며, 현재 버전을 임의로 지정하면 유효한 첫 Release를 건너뛸 수 있습니다. 명시적인 null과
별도 목록으로 이를 구분합니다. 에이전트 사전 검사는 복원 대상이 기록되지 않은 기존 객체를
계속 차단합니다. 첫 적용이 실패하면 해당 시도에서 만든 객체만 제거하고 부재를 독립적으로
확인합니다. 이 상태 계약은 네임스페이스 소유권을 인수하거나 소유권 근거를 만들지 않습니다.
네이티브 소유권 확인과 초기 등록 경로는 별도 사전 조건으로 남습니다.

수명 주기 DB는 null Release ID나 별도 목록을 저장하기 전에 명시적 마이그레이션으로 최소
읽기 버전을 5로 높입니다. 기존 개정 4의 로컬 채널 기록, 기존 행과 스냅샷 다이제스트는 그대로
유지합니다. 이전 실행 파일은
부재를 잘못 해석하는 대신 새 DB 사용을 차단합니다. 서비스 시작은 DB를 자동 변경하지 않습니다.

현재는 Terraform 애플리케이션 단계가 워크로드를 만듭니다. Hub 경로는
[워크로드 렌더링 마이그레이션](#워크로드-렌더링-마이그레이션)에 정의한 대로 네임스페이스 범위의
워크로드 객체 생성을 수명 주기 에이전트로 옮깁니다. Azure 리소스, 클러스터 범위 객체, 권한을
부여하는 역할 바인딩은 Terraform에 남습니다.

## 애플리케이션 워크로드의 네이티브 최초 생성

기존 고객 네임스페이스는 계속 비관리 상태로 둡니다. 개발 설치는 별도로 승인된
네임스페이스 안에 선택기가 없는 내부 Service를 새로 만들어 워크로드 범위의 기준 객체로
소유할 수 있습니다. 이 소유권은 새 기준 객체와 이후 설치가 직접 만든 정확한 워크로드
객체에만 적용하며, 네임스페이스 소유권을 인수하지 않습니다. Foundation 소유 리소스에는
기존 Foundation과 Terraform 근거를 계속 요구합니다.

### 설계, 비판과 수정된 경계

**초기 제안:** 설치가 서명한 네임스페이스 선언을 소유권 근거로 수락합니다.

**비판:** 설치 키 보유는 신원을 증명할 뿐, 사람의 승인이나 실제 생성을 증명하지 않습니다.
레이블, 가져오기, 적용 성공이나 빈 네임스페이스도 소유권 근거가 아닙니다. 사전 검사와 변경
사이에 다른 주체가 만든 객체를 적용 작업이 인수할 수 있습니다. 이름만 사용하는 복구는
다른 소유자의 대체 객체를 삭제할 수 있습니다. 네임스페이스 이름만으로는 재생성을 구별하지
못합니다.

**수정된 개발 계약:**

1. 고객은 설치, 애플리케이션, Entity, 네임스페이스와 구성 요소 이름을 정확히 지정한
   독립적인 로컬 승인을 제공합니다. 승인자, 유효 기간과 전체 권한 개발 프로필을 명시합니다.
   Hub, 패키지, 등록 요청이나 Plan은 이를 제공할 수 없습니다. 고객이 적용을 명시적으로
   선택하지 않으면 초기 생성은 사전 실행만 합니다.
2. 에이전트는 기존 상태 잠금을 독점하고, 독립적인 로컬 애플리케이션 정책을 확인합니다.
   같은 잠금 안에서 현재 상태와 실행 이력을 다시 읽고 API 사전 실행을 확인합니다.
   생성 의도를 영구 기록한 뒤 기준 객체를 생성 전용 원자적 요청으로 만듭니다.
   기존 기준 객체는 충돌로 차단하며 인수하지 않습니다. 독립적인 조회로 생성 결과를 확인하고
   API가 부여한 UID를 보존합니다.
3. 에이전트는 설치, Entity, 애플리케이션 연결과 로컬 범위, 승인, 실제 생성 근거의
   다이제스트를 용도별 선언에 넣어 서명합니다. 네임스페이스 이름, 리소스 UID, 자격 증명과
   비공개 승인 값은 설치 안에 남습니다.
4. 인증된 고객 운영자가 요청 UUID, 현재 Settings 다이제스트, 사유와 명시적 확인으로
   정확한 선언을 별도로 수락합니다. Hub는 등록된 설치 서명과 애플리케이션 연결을 검증합니다.
   트랜잭션은 관리 중인 Entity, 설치된 상태, 진행 중인 Plan, 변경된 Settings와 충돌하는
   재시도를 차단하고 감사를 추가합니다. 에이전트 신원만으로는 Hub 소유권을 부여할 수 없습니다.
   수락 시 새 비관리 `native-workload-scope` Entity를 등록하거나 정확히 그 종류인 기존
   빈 Entity에 근거를 연결합니다. 네임스페이스 Entity의 종류는 바꾸지 않습니다. 이후
   에이전트가 실제 빈 상태를 보고해야 운영자가 초기 재정의 적용 범위를 지정해 관리할 수 있습니다.
5. 일반 서명 Plan 경로로 첫 설치를 수행합니다. 로컬 네이티브 실행은 작업마다 원래 기준
   객체의 UID를 확인합니다. 허용된 워크로드 객체를 원자적으로 생성하고, 후속 변경 전에
   실제 UID를 영구 기록합니다. 갱신에는 UID와 리소스 버전 사전 조건을, 삭제에는 UID 사전
   조건을 적용합니다. 기준 객체가 없거나 바뀌었거나 삭제 중이거나 외부 객체가 발견되면 인수하지 않고
   실행을 멈춥니다.
   Deployment와 Service의 선택 조건과 Pod 레이블은 Entity 및 실제 기준 객체 생성 신원에
   연결됩니다. 구성 요소 레이블만으로 외부 Pod나 소유자 없는 ReplicaSet을 선택하지 않습니다.
   상태를 다시 읽을 때도 선택 조건과 Pod 레이블을 확인합니다. 로컬에 삭제 작업을 기록한
   경우에도 삭제 중인 워크로드는 배포 완료로 판정하지 않습니다.
   UID 기반 어댑터는 API 탐색, 소유 객체 조회와 의도 기록을 마친 뒤 각 POST, PATCH, DELETE
   요청을 보내기 직전에 로컬 승인이 유효한지 다시 확인합니다. 보내지 않은 요청이 차단되면
   그 요청의 새 로컬 의도만 되돌립니다. 이전 요청의 결과가 불확실하다는 근거는 지우지 않습니다.
6. 복구는 보존한 UID 이력만 사용하며 이름만으로 삭제하지 않습니다. 생성 결과, 기록 성공이나
   신원이 불확실하면 성공으로 간주해 재시도하지 않고 검토를 요청합니다. 기존 서명 입력,
   제품 연결, 작업 시간대, 영향 범위, 사전 실행, 롤백, 재실행 방지와 독립적인 상태 확인은
   계속 필요합니다.
   공급자가 객체를 생성하지 않고 요청을 차단했다고 확정한 경우에만 미확정 생성 기록을
   해제해 재시도나 UID 기반 복구를 허용합니다. 시간 초과, 응답 유실과 서버 오류는
   생성 결과가 불확실한 상태를 유지합니다.
   생성 요청을 보내기 전에 로컬 실행 기한이나 승인 확인이 실패한 경우에도 미확정 생성
   기록을 해제합니다. 이 경우에는 API 요청 자체가 없었습니다.
   적용을 위한 매 조회에서는 Plan을 가져오거나 작업 기록을 복구하기 전에 같은 독점 상태
   잠금 안에서 실행 방식을 다시 확인합니다. 초기 생성 전에 준비된 기존 방식의 클라이언트는
   실행을 멈춥니다.

초기 범위는 애플리케이션 패키지의 Deployment와 내부 Service로 제한합니다. 네임스페이스,
RoleBinding, Azure 리소스, Secret 읽기, DB 마이그레이션 실행, 애플리케이션 전용 렌더러나
프로덕션 권한은 추가하지 않습니다. 명시적인 Hub 스키마 마이그레이션으로 최소 읽기 버전을
6으로 올린 뒤 네이티브 근거를 저장하며, 이전 실행 파일은 이를 다르게 해석하지 않습니다.
단계적으로 전환할 수 있도록 새 서버는 명시적인 마이그레이션 전에 버전 5로도 서비스할 수
있습니다. 서비스 시작과 준비 확인은 버전 5와 6, 또는 아래 절차로 명시적으로 준비한 이전
버전을 허용합니다. 네이티브 수락과 명시적인 스키마 검증은 계속 버전 6을 요구합니다.
버전 기록이 없거나 준비하지 않은 이전 버전이거나 향후 버전이면 차단합니다.
호환 이미지로 트래픽을 옮기고 이전 실행 파일의 처리가 끝난 뒤 최소 읽기
버전을 올립니다. 마이그레이션 전에는 이전 이미지로 돌아갈 수 있습니다. 이후에는 검증된
버전 6 호환 이미지로 복구하며 최소 읽기 버전을 낮추지 않습니다.
[구현 원장](../../roadmap-implementation/deployment/hub-managed-lifecycle.md)은 소스 검증,
게시, 활성화와 실제 설치 검증을 구분합니다.

### 최소 읽기 버전을 유지하면서 이전 Hub 준비

**설계와 검토:** 마이그레이션 전에 버전 5로 서비스할 수 있어도 버전 1-4 설치는 처리하지
못합니다. 최소 읽기 버전을 먼저 올리면 기존 서버가 멈춥니다. 새 서버에서 이전 버전
기록만 허용하는 것도 안전하지 않습니다. 필요한 열이 없을 수 있고 새 데이터를 기록하면
이전 이미지로 복구한 서버가 읽지 못할 수 있습니다.

**수정한 계약:** 명시적인 Lifecycle Hub `prepare` 명령이 잠금으로 보호한 트랜잭션 하나에서
기존의 추가형 마이그레이션을 적용합니다. 원래 최소 읽기 버전은 유지하고 스키마 버전
테이블에 `prepared_revision: 6`을 기록합니다. 없는 DB를 초기화하거나 애플리케이션
데이터를 바꾸거나 소유권을 수락하거나 최소 읽기 버전을 올리지 않습니다. 준비는 안전하게
반복할 수 있으며, 중단되면 구조 변경과 준비 기록을 함께 되돌립니다.

SQLite 쓰기는 실제 DB 쓰기 트랜잭션을 시작한 뒤 준비 기록을 확인하며, 기록을 마칠 때까지
트랜잭션을 유지합니다. 호출자가 이미 시작한 트랜잭션의 제어권은 그대로 유지합니다.
전환을 완료한 뒤에는 복구 점검에서 지원하는 두 버전 테이블 형식을 모두 검증하고
지문을 계산합니다. 원래 버전 열만 있는 형식과, null을 허용하는 정수형 준비 버전 열을
추가한 형식입니다. 알 수 없는 열이나 호환되지 않는 자료형은 계속 차단합니다.

각 단계는 기존 서비스 소유 마이그레이션 작업으로 실행합니다. 원격 DB의 DSN을 로컬에서
사용하지 않습니다.

1. `python -m fdai_lifecycle_hub.remote prepare`를 실행합니다. 기존 서버가 계속 준비
   상태이며 최소 읽기 버전이 바뀌지 않았는지 확인합니다.
2. 호환 이미지를 활성화합니다. 새 서버는 준비 기록이 있을 때만 버전 1-4를 허용합니다.
   준비하지 않은 이전 DB는 계속 차단합니다. 준비 중에는 새 Hub의 설정, 카탈로그,
   신뢰하는 호스트의 기록 작업을 차단합니다. HTTP는 `503 schema_migration_pending`을
   반환하며, 신뢰하는 호스트의 CLI는 마이그레이션 대기 오류를 명시하고 실패로 종료합니다.
   읽기 전용 조회와 상태 확인은 계속 제공합니다. 기존 실행 파일은 원래 최소 읽기 버전과
   데이터를 유지합니다. 이미지와 준비 상태를 독립적으로 확인하고 이전 실행 파일의
   처리를 끝냅니다.
3. `python -m fdai_lifecycle_hub.remote migrate`를 실행한 뒤 엄격한 `schema` 명령으로
   확인합니다. 구조 변경을 반복하지 않고 버전 6 전환을 완료합니다. 이후에만 네이티브
   수락과 다른 새 기록 작업을 허용합니다.

완료 전에는 버전 기록을 낮추지 않고 이전 이미지로 복구할 수 있습니다. 완료 후에는 검증된
버전 6 호환 이미지로 복구합니다. Release Hub, 아직 준비하지 않은 이전 DB에 대한 신뢰하는
호스트의 작업, 버전 기록이 없는 로컬 개발의 계약은 바꾸지 않습니다.

### 신뢰하는 Hub 호스트로 비공개 증명 전달

**설계와 검토:** 설치 내부의 비공개 증명 파일을 원격 운영자가 바로 읽을 수는 없습니다.
로그에 출력하거나, 설치 키를 복사하거나, `Agent.Access`를 운영자로 취급하거나,
브라우저 애플리케이션 대신 Azure CLI 토큰을 사용하면 기존 경계가 약해집니다.

**수정된 계약:** 등록된 에이전트는 기존 `SignedNativeScope`를
`/v1/installations/{installation_id}/native-proofs`에 POST할 수 있습니다.
이는 전달일 뿐 소유권 수락이 아닙니다. Hub는 정확한 에이전트 연결, 8 KiB의 엄격한 JSON
제한, 등록된 서명, 애플리케이션 연결과 완료된 스키마 6을 확인한 뒤 변경 불가능한 감사
기록을 추가합니다. Entity마다 제출된 주장은 하나이며 같은 내용의 재시도는 안전하지만
다른 주장은 충돌로 차단됩니다. Entity, 소유권, Settings, Plan, 보고 상태는 바뀌지 않습니다.
익명 호출자와 다른 설치는 제출할 수 없으며 에이전트는 증명 조회나 소유권 수락을 할 수 없습니다.

`fdai-lifecycle-agent submit-native-proof`는 기존 비공개 `--proof` 파일을
워크로드 신원으로 인증하는 HTTPS 경로로 전송합니다. 리소스 초기 생성, 키 읽기, Plan 수락이나
증명 출력은 하지 않습니다. 전달이 실패하면 비공개 파일을 유지하여 나중에 제한된 재시도를
할 수 있습니다. 신뢰하는 Hub CLI는 주장 다이제스트로 `--submitted-proof`를 선택하여
운영자가 별도로 수락할 수 있습니다. 파일 요청과 같은 UUID, Settings 다이제스트, 사유와
정확한 확인 문구가 필요합니다. 수락할 때는 현재 등록과 애플리케이션 상태를 기준으로
보관된 증명을 다시 검증합니다.
`--request-id`, `--settings-digest`, `--reason`, `--confirmation`, `--operator`를
제공합니다. 파일 요청과 제출된 증명 선택을 함께 사용할 수는 없습니다. 신뢰하는 호스트의
`bind-application <installation-id> <private-request-file> --operator <actor>` 명령은
API와 같은 엄격한 요청 형식, 영구 제품 연결, Settings 버전 비교 후 갱신과 감사 기록을 사용합니다.

`FDAI_HUB_REMOTE_CONFIG`가 원격 Target을 명시적으로 선택하면 신뢰하는 호스트의 CLI는
기존 TLS 검증 및 Managed Identity DB 연결을 사용합니다. Release Hub 설정이나 미완료
스키마는 로컬 저장소나 비밀번호로 대체하지 않고 차단합니다. 이 변수가 없으면 기존 로컬
DB 경로는 바뀌지 않습니다. 원격 모드의 `serve`는 처리 함수를 호출하기 전에 차단하며,
인증된 서버는 `fdai-hub-remote serve`로 실행합니다. 콘솔 접근은 독립적인 Azure 권한 경계로 유지되며 에이전트의
제출은 콘솔 접근이나 운영자 권한을 부여하지 않습니다. 새 역할, 공개 증명 조회 API, 서명 키,
DB 테이블이나 최소 읽기 버전 변경은 추가하지 않습니다.

### 로컬 준비와 수락

1. 설치를 애플리케이션에 별도로 연결합니다. 비공개 로컬 정책에 같은 `product`, 정확히
   하나의 Entity/구성 요소 매핑과 `native_scope_digest`를 제공합니다. 이 다이제스트는 Hub
   요청과 독립적으로 전체 `NativeScope`를 고정합니다. 이전 에이전트는 기존 적용 경로를
   조용히 선택하지 않고 새 정책 키를 차단합니다.
2. 별도의 `fdai.lifecycle-native-approval.v1` 파일을 제공합니다. 정확한 범위,
   `profile: full-authority-development`, `approved_by`, `approved_at`, `expires_at`을
   포함합니다. 승인 유효 기간은 최대 4시간입니다. 등록된 Ed25519 신원을 유지하며, 개인 키
   파일은 실행 사용자가 소유하고 권한이 `0600`이어야 합니다. 초기 생성은 키를 만들지 않습니다.
3. `fdai-lifecycle-agent bootstrap-slot`에 `--installation-id`, `--state-dir`,
   `--local-policy`, `--current-state`, `--native-approval`, `--installation-key`와
   `--kube-context` 또는 `--in-cluster` 중 하나를 전달합니다. 기본 동작은 기준 객체의
   사전 실행뿐입니다. 명시적인 `--apply`에는 비공개 `--proof-output`도 필요합니다.
   이 명령은 애플리케이션을 설치하지 않습니다.
4. 신뢰하는 로컬 Hub에서 `fdai-lifecycle-hub migrate`로 명시적으로 마이그레이션합니다.
   원격 배포는 별도의 명시적 마이그레이션 Job을 사용합니다. UUID, 현재 전체 Settings
   다이제스트, 서명된 증명, 사유와 정확한
   `required_confirmation`을 담은 `NativeOwnershipAcceptance` 요청을 준비합니다.
   인증된 운영자로 `POST /v1/installations/{installation_id}/native-ownership`에 제출하거나,
   신뢰하는 Hub 호스트에서 `fdai-lifecycle-hub accept-native-ownership <installation-id>
   <request-file> --operator <actor>`를 실행합니다. 인증하지 않은 루프백 HTTP 호출자와
   `Agent.Access`는 수락할 수 없습니다.
5. 수락과 에이전트의 빈 상태 보고 이후 `--initial-release`로 Entity를 관리합니다. 서명된
   입력을 준비하고 일반 Plan 경로를 사용합니다. 네이티브 적용에는 고정된 로컬 정책과
   영구 상태 외에도 `--native-approval`, `--installation-public-key`가 필요합니다.
   상태나 독립 입력이 없거나 기존 네이티브 상태에 정책 고정이 없으면 기존 경로로
   돌아가지 않고 적용을 멈춥니다.

Kubernetes 신원에는 승인된 Deployment와 내부 Service에 대한 네임스페이스 범위의
`get`, `create`, `patch`, `delete`가 필요합니다. 서버 사전 실행도 해당 쓰기 권한을
사용합니다. 초기 생성은 권한이나 역할 바인딩을 추가하지 않습니다. 갱신은 필드 관리자
소유권을 강제로 가져오거나 새 갱신 권한을 요구하지 않고 UID와 리소스 버전을 검사하는
JSON Patch를 사용합니다. 생성 응답을
잃으면 검토가 필요합니다. 재시작 후 증명 생성을 마칠 수 있는 경우는 API가 부여한 원래
기준 객체 UID를 이미 영구 기록했을 때뿐입니다. 네임스페이스 RBAC와 작업 전후 UID 확인은
네임스페이스 수명 전체를 원자적으로 잠그는 트랜잭션이 아닙니다. 기준 객체가 사라지거나
바뀐 경우 정상적인 성공으로 보고하지 않습니다.

## 워크로드 렌더링 마이그레이션

이 섹션은 Hub 관리형 설치가 워크로드 렌더링을 Terraform 애플리케이션 단계에서 수명 주기
에이전트로 옮기는 방법과 이를 되돌리는 방법을 정의합니다. 한 줄 소스 배포와 서명된 오프라인
패키지는 Terraform 애플리케이션 단계를 그대로 유지합니다.

### 현재 렌더링

로컬 개발용 `operator-service-v1` 범위는 이 목표 설계보다 좁습니다. 기존 서명된 Release의
다이제스트와 서명된 구성을 사용해 실제 Operator Deployment, 내부 Service, 읽기 전용 Core
이미지 스키마 확인 Job을 만듭니다. DB 마이그레이션은 미리 완료되어 있어야 하며, 모든 스키마
전환을 차단합니다. 기존 공통 스키마와 서비스별 마이그레이션 버전이 일치하기 전에는 워크로드를
전환하지 않습니다. Foundation 객체를 만들거나 기존 객체의 소유권을 인수하지 않습니다.
[에이전트 참고 문서](../../../lifecycle/agent/README.md#same-schema-operator-profile)에
사전 조건과 실패 복구 방법이 있습니다. 이는 스키마 확장 구현이나 실제 서비스 설치 근거가
아닙니다. 남은 검증은 [구현 원장](../../roadmap-implementation/deployment/hub-managed-lifecycle.md)에서
별도로 추적합니다.

배포 CLI는 기반 출력값, 이미지 다이제스트, 제품 프로필에서 `workloads` 맵과 `scheduled_jobs`
맵을 만듭니다. 그런 다음 정확한 계획의 claim, 적용, 검증 전용 복구 단계를 거쳐 Terraform 루트
하나(`infra/runtimes/aks/workloads`)를 적용합니다. 이 루트는 세 종류의 객체를 만듭니다.

- 각 워크로드와 예약 작업의 네임스페이스 범위 Kubernetes 객체
- 클러스터 범위 Kubernetes 객체와 FDAI 신원에 접근 범위를 부여하는 역할 바인딩
- Azure 리소스: 페더레이션 ID 자격 증명, API Management 브라우저 게이트웨이와 네트워크 보안 규칙

### 설계와 비판 검토

**초기 설계:** Terraform 워크로드 루트 전체를 수명 주기 에이전트 안에서 실행합니다.

**비판 검토:**

- 이 루트는 Azure 리소스를 쓰지만, ADR-0003 A11은 Azure 쓰기 신원을 실행 호스트에 둡니다.
- 이 루트는 네임스페이스와 클러스터 역할을 만듭니다. 수명 주기 에이전트는 FDAI 네임스페이스
  안에서만 Kubernetes 권한을 가집니다.
- API Management는 외부 LoadBalancer 서비스에서 백엔드 주소를 읽습니다. 에이전트가 이
  서비스를 소유하면 인프라 단계가 워크로드 단계에 의존하게 됩니다.
- 워크로드 값에는 이미지, 프로브, 보안 설정 같은 제품 내용과 클라이언트 ID, 엔드포인트 같은 설치
  식별자가 섞여 있습니다. Release는 식별자를 담을 수 없고, Hub는 식별자를 볼 수 없어야 합니다.
- `terraform state rm`으로 주소를 지우면 검토된 정확한 계획 밖에서 상태가 바뀝니다.

**수정된 계약:** 객체 종류에 따라 소유를 나눕니다. 수명 주기 에이전트는 따로 서명된 세 입력으로
네임스페이스 범위의 워크로드 객체만 렌더링합니다. Terraform은 `removed` 블록과 `import` 블록을
쓰는 정확한 계획으로만 이 객체를 넘기고 다시 가져옵니다.

### Hub 경로의 객체 소유

| 객체 | 범위 | 소유자 |
|------|------|--------|
| Deployment, HorizontalPodAutoscaler, PodDisruptionBudget, NetworkPolicy, 내부 Service, ServiceAccount, SecretProviderClass, CronJob, identity-bridge ConfigMap | FDAI 네임스페이스 | 수명 주기 에이전트 |
| Operator API와 Document Ingestion API의 외부 LoadBalancer Service | FDAI 네임스페이스 | 인프라 에이전트. API Management가 이 주소에 바인딩되기 때문입니다 |
| 실행기의 외부 스케일용 Role과 RoleBinding | FDAI 밖의 지정된 대상 네임스페이스 | 인프라 에이전트. 권한을 부여하기 때문입니다 |
| 네임스페이스, 인벤토리 조회용 ClusterRole과 ClusterRoleBinding | 클러스터 | 인프라 에이전트 |
| 페더레이션 ID 자격 증명, API와 작업을 포함한 API Management 브라우저 게이트웨이, 네트워크 보안 규칙 | Azure | 인프라 에이전트 |

수명 주기 에이전트는 역할 바인딩을 만들거나 바꾸지 않습니다. 따라서 워크로드 적용으로 어떤
신원의 접근 범위도 넓어지지 않습니다.

수명 주기 에이전트가 같은 필드를 두고 다른 쓰기 주체와 다투지 않도록 두 가지 규칙을 둡니다.

- **FDAI 네임스페이스 안에서는 실행기 효과를 쓰지 않습니다.** 기존 경로에서는 격리된 실행기가
  FDAI 네임스페이스의 Deployment를 패치하고 스케일하며 파드를 삭제할 수 있습니다. Hub 경로에서는
  인프라 에이전트가 이 역할을 바인딩하지 않습니다. 수명 주기 에이전트가 그 변경을 되돌리게 되고,
  [운영 루프와의 분리](#운영-루프와의-분리)에 따라 운영 루프는 FDAI 소유 리소스를 대상으로 삼으면
  안 되기 때문입니다. 그 결과 Hub 경로에서는 파드 재시작이나 Deployment 스케일 같은 Kubernetes
  ActionType을 FDAI 자신의 워크로드에 쓸 수 없습니다. 다른 네임스페이스의 실행기 스케일 대상은
  그대로 유지합니다.
- **레플리카 수는 오토스케일러가 소유합니다.** 워크로드에 HorizontalPodAutoscaler가 있으면,
  에이전트는 현재 Terraform 루트가 `ignore_changes`로 하듯이 적용하는 Deployment에서
  `spec.replicas`를 빼고 적용합니다. 레플리카 재정의 값은 대신 오토스케일러의 최솟값과 최댓값을
  정합니다.

### 렌더링 입력

수명 주기 에이전트는 세 입력으로 렌더링합니다. 입력마다 서명자와 공개 범위가 다릅니다.

| 입력 | 내용 | 서명 | Hub가 보는 것 |
|------|------|------|---------------|
| Release의 워크로드 템플릿 | 구성 요소별 이미지, 명령, 포트, 프로브, 보안 컨텍스트, 사이드카, 기본 크기, 값 출처가 지정된 환경 키 | 공급업체 Release 키 | 다이제스트 |
| Entity 재정의 값 | 템플릿 한도 안의 레플리카, CPU, 메모리 | 고객 구성 키 | 값 |
| 설치 바인딩 | 신원의 클라이언트 ID와 리소스 ID, 컨테이너 레지스트리 로그인 서버, Kafka와 PostgreSQL 엔드포인트, Event Hubs 토픽 이름, Key Vault 이름, 비밀 이름, 설치와 사용권 바인딩, 로컬에서 복호화한 봉인 식별자 | 설치 키 | 다이제스트만 |

설치 바인딩은 인프라 에이전트가 자기 단계를 마친 뒤 설치 안에서 작성합니다. 자기 Terraform
루트의 출력값과, [수명 주기 구성](lifecycle-configuration-ko.md#값-분류)에 정의된 대로 구성
패키지에서 복호화한 봉인 식별자를 합칩니다. 템플릿의 각 환경 항목은 값 출처를 리터럴, 구성 키,
바인딩 키 중 하나로
선언합니다. 렌더러는 알 수 없는 키와 다른 값 출처를 거부합니다. 그래서 템플릿은 엔드포인트를
담을 수 없고, Plan에는 바인딩 값이 필요하지 않습니다.

### 업그레이드 Plan의 단계

1. **인프라:** 인프라 에이전트가 Azure 리소스, 클러스터 범위 객체, 역할 바인딩, 외부 Service에
   대해 추가와 제자리 변경만 적용하고, 목표 Release의 모든 워크로드와 작업에 대한 페더레이션 ID
   자격 증명을 만듭니다. 그런 다음 설치 바인딩과 그 증적을 기록합니다.
2. **스키마 확장:** Release는 데이터베이스 마이그레이션을 Kubernetes Job 템플릿으로 제공하며,
   이 템플릿은 마이그레이션과 카탈로그 도구가 이미 들어 있는 Core 이미지를 사용합니다. Job은 현재
   관리 호스트의 마이그레이션 단계처럼 기존 마이그레이션, 선언된 순서에 따른 서비스 소유
   마이그레이션, 권위 카탈로그 반영을 실행합니다. 다만 Release가 확장으로 분류한 개정만 실행하고,
   스키마를 삭제하거나 이름을 바꾸는 개정은 거부합니다. 축소 개정은 [Lifecycle Release와
   채널](lifecycle-releases-and-channels-ko.md#스키마-호환성)이 요구하는 복원 체크포인트 뒤에 별도의
   펜싱된 Plan에서 실행합니다. 이전 개정은 이미 적용되어 있으므로, 분류는 설치의 등록 기준 시점
   이후에 추가된 개정에만 필요합니다. 기존 업그레이드 중 일부는 테이블을 삭제하므로, Hub 관리형
   업그레이드는 분류되지 않은 새 개정을 실행하지 않습니다. 기존 마이그레이션 잠금은 단계마다
   따로 쓰는 트랜잭션 잠금이고 카탈로그 반영에는 잠금이 없으므로, Job은 세 단계와 증적 기록 전체에
   걸쳐 설치 범위의 마이그레이션 리스 하나를 유지합니다. 수명 주기 에이전트는 어떤 워크로드도
   전환하기 전에 전용 마이그레이션 신원으로 FDAI 네임스페이스에서 이 Job을 실행합니다.
3. **워크로드:** 수명 주기 에이전트가 객체를 렌더링하고, 로컬에서 도출한 효과 경계와 비교한 뒤,
   자기 필드 관리자로 server-side apply를 사용해 적용합니다.
4. **검증:** 두 에이전트는 정상 워크로드, 변경 없는 두 번째 렌더링, 남은 Terraform 루트의 변경
   없는 계획, 독립적인 재조회를 요구합니다.
5. **인프라 정리:** 목표 Release에서 빠진 워크로드가 사라졌음을 재조회로 확인한 뒤, 인프라
   에이전트가 그 워크로드가 쓰던 외부 Service, API Management 경로, 역할 부여, 페더레이션 ID 자격
   증명을 제거합니다.

Release에 새로 추가된 워크로드는 1단계에서 페더레이션 ID 자격 증명을 받으므로, 3단계에서 파드가
생기기 전에 신원이 준비됩니다. 기존 경로에서는 관리 호스트가 애플리케이션 단계 직전에
마이그레이션을 직접 계속 실행합니다.

### 기존 설치의 소유 이전

등록된 설치는 네 단계로 워크로드 객체를 수명 주기 에이전트로 옮깁니다. 각 단계에는 로컬 수명 주기
승인 증적이 필요하며, 어떤 단계도 실행 중인 객체를 지우거나 다시 만들지 않습니다.

1단계 전에 두 개의 정확한 계획으로 소유 이전을 준비합니다.

- **Service 리소스 분리:** Terraform `removed` 블록은 인스턴스 키 없이 리소스 전체만 지정할 수
  있는데, 현재는 내부 Service와 외부 Service가 하나의 리소스 블록을 같이 씁니다. `moved` 블록을 쓰는
  리팩터링으로 이를 내부 Service 리소스와 외부 Service 리소스로 나눕니다. 이 변경은 모든 설치
  경로에서 변경 없는 계획으로 적용됩니다.
- **FDAI 네임스페이스에서 실행기 역할 제거:** Hub 경로에서는 별도 계획이 FDAI 네임스페이스의
  실행기 Kubernetes 효과용 Role과 RoleBinding을 삭제합니다. 권한을 낮추는 변경이며, 소유 이전 중
  허용되는 유일한 삭제입니다.

1. **관찰 비교:** 에이전트는 객체를 렌더링해 쓰기 없이 실행 중인 객체와 비교합니다. 서버 기본값과
   바인딩 순서에서만 오는 차이는 정규화합니다. 설정한 횟수만큼 연속으로 차이가 0이면 통과합니다.
2. **Terraform에서 해제:** 인프라 에이전트가 Release에 들어 있는 Hub용 워크로드 루트 변형의
   정확한 계획을 적용합니다. `removed` 블록은 해당 리소스 블록이 설정에 없어야 하므로, 이 변형은
   에이전트 소유 리소스 블록을 각각 `destroy = false`인 `removed` 블록으로 바꿉니다. 이 블록은
   Terraform 1.7 이상에서 지원되며, 고정된 도구 체인은 1.9.8입니다. 계획에는 삭제와 수정이 없어야
   합니다.
3. **인수:** 에이전트는 `fdai-lifecycle-agent` 필드 관리자로 같은 렌더링 결과를 server-side
   apply로 적용합니다. Terraform 필드 관리자가 소유한 필드에서만 충돌을 강제로 넘겨받고, 다른
   충돌이 있으면 멈춥니다. 객체를 하나씩 인수하면서 객체 UID, 리소스 버전, 렌더링 다이제스트를 담은
   객체별 증적을 기록하므로, 중단된 인수는 마지막 증적부터 이어집니다. 각 객체는 Release ID와 렌더링
   다이제스트를 주석으로 기록합니다.
4. **검증:** 두 번째 렌더링에 변경이 없고, 워크로드가 정상이며, 남은 Terraform 루트의 계획에
   변경이 없어야 합니다.

2단계 이후에는 설치가 로컬 Hub 소유 표시를 기록합니다. 전체 워크로드 루트를 계획하려는 배포 CLI의
모든 진입점은 실행을 거부하거나 Hub용 변형을 사용합니다. 일반 애플리케이션 단계, 서비스별
업데이트, 과거 상태 조정이 모두 포함됩니다. 그래서 Terraform과 에이전트가 같은 객체를 함께 쓰지
않습니다.

**되돌리기:** 먼저 에이전트가 인수한 객체의 조정을 멈추고, 조정 리스를 놓고, 해제를 기록합니다.
그런 다음 인프라 에이전트가 같은 주소에 대해 `import` 블록이 있는 정확한 계획을 적용하고, 이어지는
계획에 변경이 없으면 Terraform 상태가 실행 중인 객체와 일치함이 증명됩니다. 2단계나 3단계에서
실패해도 이미 인수한 객체의 필드 소유와 주석만 바뀝니다. 실행 중인 객체를 지우거나 다시 만들지
않으므로, 되돌리기에 재생성이 필요하지 않습니다.

### 렌더링 동등성

단일 렌더러가 생기기 전까지는 Terraform 루트와 수명 주기 에이전트가 하나의 워크로드 템플릿
계약을 구현합니다. 집중 테스트가 같은 입력 조합을 두 렌더러에 넣고 Terraform 계획 값과 에이전트
출력을 비교합니다. 입력 조합은 제품 프로필, 추가 기능, identity bridge, 실행기 스케일 대상을
포함합니다. 비교에는 Kubernetes 서버 기본값을 제거하고 비밀 공급자 바인딩을 정규화하는 배포 CLI의
기존 규칙을 재사용합니다. 보호된 CronJob 템플릿 다이제스트와, 인프라 에이전트가 만든 외부
Service의 셀렉터가 에이전트가 렌더링한 파드 레이블과 일치하는지도 확인합니다. 차이가 하나라도
있으면 테스트가 실패합니다.

Hub 경로에서 카탈로그 검토와 초기 인벤토리를 실행하는 일회성 Job 실행은 보호된 CronJob 템플릿
다이제스트를 Terraform 입력이 아니라 에이전트의 렌더링 증적에서 도출합니다.

### 이전 미해결 질문에 대한 결정

Hub 관리형 수명 주기 담당자가 2026-10-07에 다음과 같이 결정했습니다.

- **마이그레이션 신원:** 스키마 확장 Job은 어떤 워크로드와도 공유하지 않는 전용 마이그레이션
  ServiceAccount와 관리 ID로 실행합니다. MVP에서는 이 신원이 현재 관리 호스트의 마이그레이션
  단계가 쓰는 것과 같은 Key Vault 데이터베이스 비밀을 읽습니다. 마이그레이션이 서비스 역할을 만들고
  데이터를 채우기 때문에 이 비밀에는 서버 관리자 로그인이 들어 있습니다. 이후 변경에서 객체 소유를
  관리자에서 전용 마이그레이션 데이터베이스 역할로 옮긴 뒤, 마이그레이션에 필요한 권한만 가진 그
  역할로 바꿉니다.
- **단일 렌더러:** MVP가 검증될 때까지 Terraform 루트와 에이전트 렌더러를 렌더링 동등성 검사와
  함께 모두 유지합니다. 그 뒤에는 Terraform 워크로드 루트가 에이전트가 렌더링한 매니페스트를
  적용하므로 모든 설치 경로가 하나의 렌더러를 쓰고, 동등성 검사는 필요 없어집니다.

### 미해결 질문

- 현재 관리 호스트가 애플리케이션 단계 뒤에 실행하는 배포 후 단계(Trial 활성화, 초기 인벤토리,
  카탈로그 검토)를 어떤 구성 요소가 실행할지
- 실행 호스트가 선택 사항인 매일 자동 종료(`runner_auto_shutdown_time`)를 쓸 때 인프라 에이전트를
  어떻게 계속 실행할지
- 설치가 `postgres-aks` 데이터베이스 배치를 선택했을 때 클러스터 안 PostgreSQL 네임스페이스를 어느
  에이전트가 소유할지

| 구간 | 주간 다운타임 구간과 야간 무중단 구간 | 매일 구간 | 합의한 대로 |
| 모델 | 승인된 엔드포인트의 Regional Provisioned PTU | Standard 종량제 | API Management를 통해 Azure에서 도달할 수 있는 자체 호스팅 모델 |
| 거버넌스 | 정책이 모든 상태 변경을 승인까지 보류 | 운영자가 승격한 작업과 상시 권한을 쓰는 단독 운영자 프로덕션 프로필 | 실행별 승인 |

Customer C의 온프레미스 런타임과 로컬 모델에는 별도 승인과 ADR이 필요합니다.

## Hub 데이터 모델

| 테이블 | 키 | 용도 | 시간 필드 | 변경 방식 |
|--------|-----|------|-----------|-----------|
| `installation` | `installation_id` | 등록 상태와 설치 키, Hub 배치, 채널, 버전 범위, 구간 | `requested_at`, `enrolled_at`, `recorded_at` | 개정 관리 |
| `entity` | `installation_id`, `entity_id` | 종류, 소유권 근거, 설정 개정. 설정이 있는 Entity가 관리 Entity | `effective_from`, `recorded_at` | 개정 관리 |
| `entity_reported_state` | `installation_id`, `entity_id`, `observed_at` | 버전, 다이제스트, 상태, 에이전트 하위 상태 | `observed_at`, `recorded_at` | 추가 전용 |
| `lifecycle_plan` | `plan_id` | 유형, 목표 Release, 구성 개정, 효과 경계, 만료 | `created_at`, `issued_at`, `expires_at` | 상태 변경은 `lifecycle_plan_event`에 기록 |
| `plan_evaluation` | `evaluation_id` | 재계산 한 번의 결과, 대상 릴리스, 발급한 Plan(있는 경우) | `evaluated_at` | 추가 전용 |
| `plan_constraint_result` | `evaluation_id`, 후보 릴리스, `constraint` | 결과와 사유 | `evaluated_at` | 추가 전용 |
| `plan_execution_report` | `plan_id`, `attempt` | 정확한 계획 다이제스트, 정리된 요약, 결과 | `reported_at` | 추가 전용 |
| `lifecycle_command` | `command_id` | 범위와 실행자가 있는 억제, 권한 하향, 비상 해제 명령 | `starts_at`, `expires_at`, `recorded_at` | 철회 가능 |
| `hub_audit` | `sequence` | 모든 Hub 변경의 해시 체인 기록 | `recorded_at` | 추가 전용 |

대기하거나 적격 릴리스가 없는 재계산은 Plan을 발급하지 않으므로, 제약 결과는 Plan이 아니라 재계산에
속합니다.

Release 테이블은 [Lifecycle Release와 채널](lifecycle-releases-and-channels-ko.md)이, 구성 테이블은
[수명 주기 구성](lifecycle-configuration-ko.md)이 소유합니다.

## 현재 한계

- 현재 동작하는 것은 Lifecycle Hub의 등록, Plan 계산, 저장, 에이전트 API뿐이며 loopback에서 관찰
  모드(shadow mode)로 실행됩니다([Lifecycle Hub](../../../lifecycle/hub/README.md)). 이 문서의 나머지
  내용은 설계만 있습니다.
- Terraform 밖의 전체 워크로드 렌더링은 [워크로드 렌더링 마이그레이션](#워크로드-렌더링-마이그레이션)에
  설계되어 있습니다. 같은 스키마를 사용하는 개발용 Operator 범위만으로는 전체 렌더러,
  렌더링 동등성 검사, 소유권 인수가 구현되었다고 볼 수 없습니다.
- Lifecycle I0에서는 적용이 실패해도 별도의 롤백 Plan을 만들지 않습니다. 에이전트가 실패한 Plan
  안에서 이전 이미지를 복원하고 `rolled-back`을 보고합니다. 그러면 Hub는 그 Plan의 각 Entity에
  24시간짜리 실패 억제 구간을 두며, 운영자는 이를 더 일찍 해제할 수 있습니다. 설치 전체에 대한
  실패 임계값은 구현되지 않았습니다.
- [자체 업그레이드 실패 분석](hub-managed-lifecycle-self-upgrade-ko.md)은 슬롯/실행 제한 세대,
  데이터 호환성과 복구 의무를 정의합니다. 제어기와 운영 훈련은 아직 구현되지 않았습니다.
- [사용권 연속성](hub-managed-lifecycle-entitlement-ko.md)은 설치 내부의 사용권 권한과 전달만 하는
  Hub를 선택합니다. 전달/인계는 아직 구현되지 않았으며 업그레이드는 Trial을 갱신하지 않습니다.
- 오프라인 설치는 운영자가 다음 번들을 가져올 때만 회수를 받습니다.
- Hub 경로는 AKS만 지원하며 온프레미스 런타임은 범위 밖입니다.
