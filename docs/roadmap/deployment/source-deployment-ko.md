# 단일 명령 소스 배포

FDAI 저장소를 clone한 누구나 `az login` 뒤 명령줄 한 줄로 모든 FDAI 리소스를 자신의 Azure
구독에 배포할 수 있습니다. 이 문서는 그 명령, 명령이 만들 수 있는 산출물과 만들 수 없는 산출물, 그리고
30일 Trial과 전체 사용권 중 무엇을 선택하는지를 정의합니다.
[헌법 제1조](../architecture/fdai-constitution-ko.md#제1조-목적과-범위)의 첫 번째 설치
방식을 이 문서가 소유합니다.

> **상태:** 이 문서는 목표 계약입니다. 이제 소스 실행은 서명된 키트 없이 검증된 Foundation
> 인계에서 공유 AKS 애플리케이션 단계로 이어집니다. 고정된 소스 스냅샷을 managed host로
> 전송하고, 배포 레지스트리로 서비스 이미지를 빌드하며, 커밋된 lock 파일 기준으로 공개
> 레지스트리에서 Terraform 공급자를 해석합니다. 또한 checkout의 마이그레이션과 카탈로그를
> 실행하고, 동일한 상태 확인, 인벤토리, 두 번째 무변경 계획 확인을 유지합니다.
> [구현 원장](../../roadmap-implementation/deployment/source-deployment.md)이 현재 상태와
> 순서가 정해진 남은 작업을 기록합니다.
>
> **범위:** 런타임과 프로비저닝 토폴로지, Trial과 토큰의 의미, 서명된 오프라인 패키지는
> [관련 문서](#관련-문서)에 나열한 소유 문서가 계속 맡습니다.

## 한눈에 보는 설계

| 관심사 | 결정 |
|--------|------|
| 배포할 수 있는 사람 | clone, 대화형 `az login`, 대상 구독에서 리소스와 역할 할당을 만들 권한을 가진 누구나 |
| 진입점 | 한 줄 명령 `git clone https://github.com/dotnetpower/fdai.git && fdai/scripts/deployment/azure/fdai-up.sh --region <region>` 또는 `fdaictl provision azure --source <checkout> --region <region>`. 둘 다 하나의 조정기를 실행 |
| 산출물 출처 | 깨끗하게 커밋된 checkout 하나. 서비스 이미지는 그 checkout에서 배포 자체의 레지스트리로 빌드 |
| 만드는 릴리스 산출물 | 없음. 서명된 키트, 번들, 제어 패키지, wheelhouse, 어플라이언스, 호스트 이미지, SBOM, provenance, attestation, 게시된 릴리스를 만들지 않음 |
| 필요한 키 | 없음. 서명 키는 설치 입력이 아님 |
| 무결성 서명 키 없음 | 설치 생성 시각에 고정된 영속 30일 Trial 하나 |
| `secrets/integrity-signing-key.pem` | 그 설치에 바인딩되고 만료가 없는 전체 카탈로그 설치 사용권 |
| Trial 이후 | 변경 작업은 차단되고 관찰은 계속되며, 모든 Console 화면에 영구 만료 워터마크가 표시됨 |
| 승인 | 명령 실행이 그 명령이 보여 주는 각 계획을 승인. 기존 리소스 삭제나 교체에는 입력 확인 한 번이 필요 |
| 해체 | 소스 해체는 보존된 소스 의도, 준비, Foundation 인계 근거로 증명된 리소스 그룹만 입력 확인 한 번과 부재 재조회 뒤 제거 |
| 성공 | 서비스 상태와 두 번째 무변경 계획을 확인한 뒤에만 `deployment_ready=true` |

## 설계와 비판

**초기 설계:** `secrets/` 아래의 어떤 비공개 키든 전체 사용권의 증거로 보고, 그렇지 않으면 관찰
전용으로 배포하며, 배포 전에 checkout에서 서명된 키트를 계속 빌드합니다.

**비판:**

- 파일 이름이나 임의의 키는 증거가 아닙니다. 비어 있거나 일치하지 않는 파일도 존재 검사를
  통과하며, 오프라인 패키지 서명 키는 사용 권한이 아니라 산출물을 인증합니다.
- 배포된 런타임은 비공개 키를 결코 읽어서는 안 됩니다.
- 관찰 전용은 Trial이 아닙니다. 새 사용자는 변경 기능을 평가할 수 없습니다.
- 변경 작업을 뒤에서 막기만 하는 Trial은 눈에 띄지 않으며, 설정, 삭제된 기록, 재배포로
  숨기거나 초기화할 수 있는 만료는 평가 경계가 아닙니다.
- 키 보유자 자신의 설치에 30일 토큰을 쓰면 키 보유자가 다시 배포하지 않는 한 기능이 줄어들며,
  이름만 다를 뿐 Trial과 같습니다.
- 소스에서 배포하려고 키트를 빌드하고 서명하면 아무도 따로 검증하지 않는 산출물이 생기고, 새
  사용자에게는 없는 서명 키가 필요해집니다.

**수정된 계약:** 추적 대상 무결성 공개 키와 일치함이 증명된 업스트림 무결성 서명 키만 전체
모드를 선택하며, 작업 스테이션이 그 키를 서명된 설치 사용권으로 바꿉니다. 소유자가 2026-10-01에
이 키를 선택했으므로 이제 하나의 키가 프레임워크 무결성과 라이선싱을 함께 보호하며, 도메인
분리된 문서 덕분에 한 용도로 만든 서명은 다른 용도로 검증되지 않습니다. 그 키가 없으면
배포는 설치 생성 시각에 고정된 영속 Trial 하나를 초기화하고, Trial이 끝나면 어떤 설정으로도
숨길 수 없는 영구 만료 워터마크를 모든 Console 화면에 표시합니다. 소스 경로는 이미지를 배포
안으로 직접 빌드하고 서명된 릴리스 산출물을 만들지 않습니다. 키가 있지만 사용할 수 없으면
조용히 Trial을 선택하지 않고 첫 Azure 영향 전에 실행을 멈춥니다.

소스 배포가 `read-only-console` 또는 `enterprise-identity-governance`를 선택하면 Foundation 준비
전에 테넌트 로컬 Entra 표시 이름도 확인합니다. FDAI는 정확한 표시 이름으로 확인되는 테넌트
로컬 공유 세트 하나에 바인딩됩니다. `fdai-*` 애플리케이션 또는 `aw-*` 그룹 이름이 중복되면
소스 실행은 Azure에 어떤 영향도 주기 전에 고정된 모호성 이유로 멈춥니다. 명령은 추측하거나,
설치 범위 이름을 만들거나, 검토되지 않은 바인딩 파일을 받지 않습니다.

**애플리케이션 계속 진행 수정:** 첫 구현 선택지는 완료된 소스 Foundation을 서명된 키트 채택
경로로 보내는 것이었습니다. 그러면 기존 애플리케이션 코드를 보존할 수 있지만, 키트 아카이브,
공급자 미러, 런타임 release 매니페스트, 지원 wheelhouse, Console 아카이브가 필요합니다. 이
입력들은 소스 경로가 피하려는 release 산출물을 다시 들여옵니다. 대신 소스 경로는 standalone
애플리케이션 조정기를 재사용하고 산출물 입력 연결 지점만 바꿉니다.

- managed host는 검증된 소스 전송 아카이브를 받고 그 소스 스냅샷에서 배포 CLI를 설치합니다.
- Terraform 루트와 마이그레이션 지원은 스냅샷에서 오며, 공급자는 커밋된 `.terraform.lock.hcl`
  파일 기준으로 공개 레지스트리에서 직접 해석됩니다. 미리 만든 wheelhouse가 없으므로 워크스테이션은
  런타임 패키지의 커밋된 `uv.lock` 의존성 집합을 해시가 포함된 요구 사항 파일 하나로 내보내고, 호스트는
  그 다이제스트를 다시 확인한 뒤 해시가 고정된 바이너리 패키지로만 설치하고, 의존성 해석 없이
  스냅샷의 워크스페이스 패키지를 더한 다음 영수증을 기록합니다.
- 호스트는 키트에 고정된 `kubectl`과 `kubelogin` 릴리스를 내려받아 커밋된 다이제스트가 일치할
  때만 보관합니다.
- 서비스 이미지 참조는 substrate 적용으로 배포 레지스트리가 만들어진 뒤 소스 이미지 단계
  증적에서 옵니다.
- Console 아카이브는 Console 추가 기능을 선택한 경우에만 로컬 checkout에서 빌드됩니다.
- `--evidence-verifier-input`은 검토된 독립 운영 근거 검증기 바인딩을 같은 애플리케이션
  계속 진행 경로로 전달할 수 있습니다. 생략하면 소스 배포 값은 그대로 유지되고 검증기는 꺼져
  있습니다.
- 모든 증적은 `operator-selected-source`와 `release_signature_verified=false`를 기록합니다.

서명된 키트 채택은 오프라인 패키지로 계속 진행하겠다고 명시한 복구 Foundation에만 남습니다.

**보호된 해체 수정:** 처음에는 현재 작업 트리에서 Terraform destroy를 재사용할 수 있었습니다.
그러나 소스 배포에서는 보존된 상태가 부분적이거나 복구됐거나 실패한 실행 뒤 없을 수 있으므로
범위가 너무 넓습니다. 대신 소스 경로는 보존된 소스 의도, 소스 준비 증적, Genesis 표식,
검증된 Foundation 상태 인계만으로 해체 검토를 만듭니다. 이 검토는 그 근거에서 나온
애플리케이션 및 운영 리소스 그룹만 이름으로 지정하고, 대상 바인딩과 소스 실행 바인딩에
결속하며, 입력 확인 한 번을 요구하고, 그 그룹만 삭제한 뒤 부재를 다시 조회합니다. 리소스
이름, 다이제스트, 대상, 소스, 인계 필드 중 하나라도 증명할 수 없으면 삭제 호출 전에 해체를
거부합니다. 일부 삭제만 끝나면 부분 실패 증적을 반환하고 운영자 검토를 위해 라이브 해체
근거를 열린 상태로 유지합니다.

## 명령 실행

```bash
git clone https://github.com/dotnetpower/fdai.git && fdai/scripts/deployment/azure/fdai-up.sh --region koreacentral
```

`fdai-up.sh`가 자신의 checkout을 찾으므로 이 한 줄은 어느 디렉터리에서든 동작합니다. 먼저
`az login`으로 로그인하세요. Azure CLI 세션이 없으면 명령이 대화형 로그인을 직접 시작합니다.
`fdai-up.sh`는 checkout의 잠긴 환경을 준비하고 나머지 옵션과 함께
`fdaictl provision azure --source <checkout>`을 호출합니다. 두 진입점은 같은 조정기를 실행하고
같은 결과를 냅니다. 명령을 다시 실행하면 같은 설치를 재개하거나 업그레이드합니다.

작업 스테이션에는 Bash, `git`, Azure CLI, `uv`가 필요합니다. Console 추가 기능을 선택하면 커밋된
lockfile로 Console을 빌드할 Node.js와 npm도 필요합니다. 컨테이너 엔진, GitHub 계정, 저장소
비밀, 워크플로, 등록된 runner는 필요하지 않습니다.

## 사용권 선택

조정기는 Azure에 영향을 주기 전에 작업 스테이션에서 사용권 모드를 한 번 선택합니다.

| 작업 스테이션 상태 | 배포가 받는 것 | 30일 이후 |
|--------------------|----------------|-----------|
| `secrets/integrity-signing-key.pem` 없음 | 설치 생성 시각에 고정된 Trial 기록 하나 | 새 변경 작업은 차단되고 만료 워터마크가 나타나며, 관찰, 진단, 감사, 내보내기는 계속됨 |
| 사용 가능한 무결성 서명 키 | 전체 카탈로그 설치 사용권 | 변화 없음. 사용권에 만료가 없음 |
| 무결성 키가 있지만 사용할 수 없음 | 없음. Azure 영향 전에 실행이 멈춤 | 해당 없음 |

사용 가능한 키는 checkout의 무시된 `secrets/` 디렉터리에 있는 고정 파일
`secrets/integrity-signing-key.pem`이며, 커밋할 때 프레임워크 표면에 다시 서명하는 바로 그
파일입니다. 이 파일은 현재 UID 소유의 mode-`0600` 일반 파일이어야 하며, 그 Ed25519 공개 키가
추적 대상 `security/integrity/upstream-signing-key.pub`와 일치해야 합니다.
`scripts/deployment/release/check-signing-key.py --scan secrets`를 실행하면 키 자료를 출력하지
않고 각 키가 충족하는 역할을 보고합니다. 오프라인 패키지 서명 키는 전체 모드를 선택하지 않습니다.

- **키 보관:** 비공개 키는 작업 스테이션을 떠나지 않습니다. 이미지, Terraform 입력이나 상태,
  명령줄 값, 로그, Key Vault에 들어가지 않습니다. 서명된 사용권만 다이제스트에서 파생한 비밀
  이름으로 Key Vault 파일 입력을 통해 이동합니다.
- **바인딩:** 사용권과 Trial 기록은 소스 리비전이나 이미지 다이제스트가 아니라 설치와 배포
  다이제스트에 바인딩됩니다. 업그레이드와 재시작은 전체 사용권을 무효화하지 않고 Trial을 갱신하지도
  않으며, 잃어버린 Trial 기록은 원래 활성화 시각으로 돌아옵니다.
- **공유 키:** 같은 키가 프레임워크 표면 매니페스트와 라이선싱 문서에 서명합니다. 키가 침해되면
  둘 다 영향을 받으며, 키를 교체한 뒤에는 키 보유자가 배포를 다시 실행해 사용권을 다시
  발급합니다.
- **모드 변경:** 이후 사용 가능한 키로 실행하면 재설치 없이 Trial을 전체 사용권으로 바꿉니다. 이후
  키 없이 실행해도 설치된 사용권은 유지되며, 생략은 사용권을 철회하지 않습니다.
- **권한:** 사용권은 기능의 `available` 축만 움직입니다.
  [기능 라이선싱](../fork-and-sequencing/capability-licensing-ko.md#이-설계를-안전하게-만드는-규칙)이
  요구하듯 승격, RBAC, 위험, 사람 승인, 실행기 신원, 효과 검증은 독립적으로 유지됩니다.

## Trial이 끝난 뒤

Trial이 끝나면 Core는 재시작 없이 다음 결정부터 새 변경 작업을 차단하고, 관찰, 진단, 감사,
내보내기는 계속합니다. 그때부터 모든 Console 화면은 정품 인증되지 않은 데스크톱 운영 체제처럼
오른쪽 아래 모서리에 영구 워터마크를 표시하며, 모든 Operator API 응답도 같은 상태를 전달합니다.
설정, 데이터 변경, 재배포로는 숨길 수 없고 전체 사용권만 워터마크를 없앱니다. 정확한 계약은
[기능 라이선싱](../fork-and-sequencing/capability-licensing-ko.md#trial-만료-워터마크)이 소유합니다.

## 명령이 빌드하는 것

| 입력 | 소스 경로 동작 |
|------|----------------|
| 서비스 이미지 | 정확한 커밋의 `git archive`를 배포 자체 레지스트리의 빌드 서비스가 빌드하고, `sha-<commit>` 태그를 붙여 다이제스트로 배포 |
| 의존 이미지 | 고정된 다이제스트로 배포 레지스트리에 가져옴 |
| Console | Console 추가 기능을 선택한 경우에만 checkout에서 빌드하고 게시 |
| Terraform | `PATH`의 `terraform`이 커밋된 바이너리 다이제스트와 일치할 때만 사용하고, 그렇지 않으면 고정된 `linux_amd64` 릴리스를 한 번 내려받아 `infra/genesis-runner-image/toolchain.json`의 아카이브 다이제스트와 바이너리 다이제스트가 모두 일치할 때만 보관 |
| 런타임 지원 환경 | 워크스테이션에서 내보낸 커밋된 `uv.lock` 의존성 집합을 managed host에 해시 고정 바이너리 패키지로 설치하고 스냅샷의 워크스페이스 패키지를 추가 |
| Kubernetes 클라이언트 도구 | 키트에 고정된 `kubectl`과 `kubelogin` 릴리스를 managed host에서 내려받아 커밋된 다이제스트가 일치할 때만 보관 |
| Terraform 공급자 | 커밋된 lock 파일 기준으로 공개 Terraform 레지스트리에서 해석 |
| 데이터베이스 | checkout의 마이그레이션과 권위 있는 카탈로그를 적용한 뒤 Trial 초기화 |
| 출처 기록 | 비공개 실행 증적에 `operator-selected-source`로 기록하며 서명된 릴리스로 기록하지 않음 |

소스 경로는 서명된 키트, 배포 번들, 번들 서명, 배포 제어 패키지, 서명된 wheelhouse, 런타임
릴리스 매니페스트, 어플라이언스, runner나 호스트 이미지, SBOM, provenance나 attestation 문서,
TUF 메타데이터, 게시된 릴리스나 이미지를 결코 만들지 않습니다. 보호 브랜치, CI 결과, 공개 GHCR
패키지, 유지 관리자도 요구하지 않습니다. FDAI가 서명하는 설치 산출물은
[연결 끊긴 배포](disconnected-deployment-ko.md)의 서명된 오프라인 패키지뿐입니다. 이미지 단계의
클레임, 다시 읽기, 복구 규칙은 [설치형 배포 CLI](installable-deployment-cli-ko.md#소스-이미지-단계)가
소유합니다.

## 단계 순서

1. 활성 `az login` 세션에서 사람 대상을 읽고 구독을 확인합니다.
2. 깨끗하게 커밋된 checkout 하나를 받아들이고 그 스냅샷을 고정합니다.
3. 작업 스테이션에서 사용권 모드를 선택합니다.
4. 읽기 전용 공급자, 정책, 할당량, SKU 사전 점검을 실행합니다.
5. 선택한 런타임과 프로비저닝 프로파일로 플랫폼 계획을 세우고 적용합니다.
6. 서비스 이미지를 빌드하고 의존 이미지를 가져온 뒤 모든 다이제스트를 다시 읽습니다.
7. 마이그레이션과 카탈로그를 실행하고 Trial 기록이 없을 때 설치의 고정된 활성화 시각으로
   초기화합니다.
8. 전체 모드에서는 설치 사용권을 발급하고 Key Vault를 통해 저장합니다.
9. 서비스를 다이제스트로 계획하고 적용하며, Console을 선택했으면 게시합니다.
10. 상태를 확인하고 초기 인벤토리를 실행한 뒤 두 번째 무변경 계획을 요구합니다.
11. `deployment_ready`, 사용권 모드, Trial 종료일을 비밀 값 없이 보고합니다.

독립적인 읽기와 빌드는 동시에 실행할 수 있습니다. 승인, 적용, 마이그레이션, 사용권 기록,
활성화는 직렬로 유지됩니다. 모든 적용은
[설치형 배포 CLI](installable-deployment-cli-ko.md#승인-및-복구)의 영향 전 claim 기록,
검증 전용 복구, 모호한 적용 반복 금지 규칙을 그대로 지킵니다.

## 정직한 한계

- **변조는 드러나지만 막지는 못함:** Trial 검사와 워터마크의 판정 및 렌더링은 서명된 프레임워크
  표면에 속하므로, 이를 바꾸려면 서명된 코드를 수정해야 하고 업스트림이 서명한 매니페스트로
  검증하면 그 수정이 드러납니다. 워터마크를 마운트하는 Console 셸은 일반 Console 코드이며,
  소스와 런타임을 통제하는 운영자가 수정된 코드를 실행하는 것을 막을 방법은 없습니다.
  Trial은 평가 경계이지 복제 방지 장치가 아닙니다.
- **재설치 탐지 없음:** 설치를 해체하고 새로 배포하면 새 Trial이 시작됩니다. FDAI는 전역 활성화
  서비스를 운영하지 않습니다.
- **빌더 가용성:** 원격 이미지 빌드에는 대상 구독의 레지스트리 빌드 서비스가 필요합니다. 그
  서비스를 쓸 수 없으면 다른 이미지 출처로 대체하지 않고 서비스 적용 전에 고정된 안내와 함께
  멈춥니다.
- **운영자가 선택한 소스:** 소스 설치는 운영자가 어떤 커밋을 선택했는지를 증명할 뿐, 게시자가 그
  커밋을 릴리스했다는 사실을 증명하지 않습니다.
