# 구독 초기 프로비저닝

이 문서는 신규 또는 일부만 구성된 Azure 구독에 FDAI를 배포해 준비 완료 상태로 만드는 전체
수명 주기를 정의합니다. 기존 Terraform, 보호된 실행기, 데이터베이스, 카탈로그, 모델,
인벤토리 경로를 하나의 재개 가능한 `fdaictl` 작업으로 구성하되, 정확한 계획 승인과 비공개
네트워크 경계를 약화하지 않습니다.

> **범위:** 현재 구현 대상은 Azure입니다. 운영자는 VPN으로 접속할 수 있지만, 모든 배포
> 데이터 플레인 작업은 Azure 내부의 승인된 호스트에서 실행합니다. 노트북은 제어 표면이며
> 비공개 엔드포인트를 우회하지 않습니다.
>
> **안전:** "하나의 작업"은 일시 중지, 재개, 진행률 보고가 가능한 하나의 영속 실행을 의미합니다. 검토하지 않은 단일 변경을 의미하지 않습니다. 새 비공개 백엔드가 필요하면
> 기반 계층을 먼저 승인하고, 해당 백엔드에서 생성한 정확한 애플리케이션 계획을 다시
> 승인합니다.
>
> **구현 원장:** 전달 상태와 관찰 가능한 남은 작업은 [구독 초기 프로비저닝 구현 원장](../../roadmap-implementation/deployment/subscription-genesis-provisioning.md)에서
> 추적합니다.
> 단계 간 보안, 완전성, 복구, 비용, 진행률 게이트는
> [구독 초기 구성 보증](subscription-genesis-assurance-ko.md)에서 정의합니다.

## 한눈에 보는 설계

`fdaictl`은 조정과 표시를 담당합니다. Terraform은 인프라 진실 원본으로 유지하고, 서비스
이행 도구는 스키마 변경을 소유하며, 저장소 카탈로그는 온톨로지와 규칙을 소유하고,
인벤토리 단일 작성기는 관측된 리소스 인스턴스를 소유합니다.

```text
inspect -> reconcile current state -> foundation plan/apply -> attest runner
        -> application plan/apply -> migrate -> materialize catalogs and defaults
        -> deploy and verify models -> scan and promote inventory -> readiness receipt
```

모든 필수 단계에 독립적인 사후 조건 근거가 있어야 실행을 `ready`로 종료합니다. Azure 생성
응답, Terraform 적용 완료, 이행 프로세스 종료, 모델 배포 상태, 인벤토리 스트림 완료 중 하나만
확인해서는 준비 완료로 판단하지 않습니다.

## 현재 미비점

저장소에는 대부분의 하위 메커니즘이 있지만, 완전한 구독 온보딩 제품으로 구성되어 있지
않습니다.

| 영역 | 현재 근거 | 이 설계가 해소하는 미비점 |
|------|-----------|---------------------------|
| 운영자 진입점 | `fdaictl`은 bootstrap 조정과 보호된 애플리케이션 계획, 정확한 적용, 상태, 검증 전용 재개를 제공합니다. | 승인된 기반 계층 적용, 원격 상태 이전, 완전한 준비 완료 증적이 남아 있습니다. |
| 초기 구성 진행률 | `genesis-up.sh`는 안전하게 중단하는 호환성 안내 스크립트이며, CLI와 Console은 단계 완료와 준비 상태를 구분하는 제한된 상태 스냅샷을 공유합니다. | 정본 Azure 생성기와 영속 Blob-to-Operator 복제가 없습니다. |
| 데이터베이스 초기 구성 | 통합 및 서비스 소유 이행과 안전하게 차단하는 데이터베이스 및 의미 체계 재확인 계약이 있습니다. | 런타임 시작 전 표식 생성과 런타임 주체 근거가 완전한 준비 완료 증적으로 통합되지 않았습니다. |
| 온톨로지와 규칙 | 카탈로그가 저장소에서 버전 관리되고 변경 불가능한 Operator 변환 결과로 구체화될 수 있습니다. | 카탈로그 변환 결과 생성이 Operator API 경로에 조건부로 연결되며 구독 준비도 필수 게이트가 아닙니다. |
| 모델 배포 | 실제 해석기, 기능 평가, Terraform 모듈, 키 없는 역할이 있습니다. | 요청 용량에 명시적 최솟값, 사용률 여유, 워크로드 프로필, 종단 간 처리량 승인 게이트가 없습니다. |
| 최초 리소스 스캔 | 지속 인벤토리 Job은 완전한 세대만 승격하며 Console은 예상 스캔 수치와 검증된 완료를 구분합니다. | 보호된 실행이 영속 공급자 진행률을 아직 게시하지 않으며 전체 구독 증적을 보존하지 않았습니다. |

인벤토리 CLI는 정제된 수집 상태 조립을 전용 순수 도우미에 위임한 뒤 기존 상태 저장소
어댑터를 통해 결과를 영속화합니다. 모든 인벤토리 원본을 사용할 수 없으면 일회성 예약 실행은
계속 실패하므로 초기 구성 조정기가 실패를 관측할 수 있습니다. 로컬 장기 실행 프로필은 같은
실패를 명시적으로 기록하고 구성된 루프 간격 후에만 다시 시도합니다. 두 모드 모두 출처 권한이나
준비 상태 의미를 바꾸지 않습니다.

## 목표 운영자 경험

상위 경로는 정본 명령 그룹을 사용하고 영속 실행 식별자를 추가합니다.

```bash
fdaictl provision inspect --profile .fdai/environments/dev.json
fdaictl provision init --profile .fdai/environments/dev.json
fdaictl onboard guided --profile .fdai/environments/dev.json \
  --source-commit <git-sha> --run-id <run-id> \
  --journal .fdai/runs/<run-id>.jsonl \
  --repository <owner>/<repository> --output json
fdaictl deploy status --profile .fdai/environments/dev.json \
  --repository <owner>/<repository> \
  --request-id <request-id> --commit-sha <git-sha> --output json
fdaictl onboard guided --profile .fdai/environments/dev.json \
  --source-commit <git-sha> --run-id <run-id> \
  --journal .fdai/runs/<run-id>.jsonl \
  --repository <owner>/<repository> --plan-id <plan-id> \
  --plan-digest <plan-digest> --plan-expires-at <expires-at> \
  --approve-application --output json
fdaictl onboard status --journal .fdai/runs/<run-id>.jsonl --output json
```

- `provision inspect`와 `provision init`은 Azure를 변경하지 않습니다.
- `onboard guided`는 하위 `deploy plan`과 `deploy apply`를 구성합니다. `deploy status`는
  요청에 연결된 작업 흐름 상태와 `expires_at`을 포함한 정제된 계획 메타데이터를 반환합니다.
  애플리케이션 적용에는 `--plan-expires-at`(`deploy status` 계획 메타데이터에서 획득)과
  `--approve-application`이 필요합니다.
- `status`는 정제된 변환 결과를 읽습니다. Terraform 상태, 비밀 값, DSN, 토큰, 모델 요청
  내용, 공급자 페이로드를 내려받지 않습니다.

정확한 dev 계획에서 비공개 리소스 운영 Function 게이트웨이를 유지하거나 프로비저닝해야 할
때는 `--deploy-dev-operations-gateway`를 사용합니다. 이 선택은 plan, apply, status가 공유하는
컨텍스트 다이제스트에 봉인되며 기존 cutover, executor-effect, OHL 보호를 계속 적용받습니다.
범위가 제한된 게이트웨이 대상 집합에는 주소가 이동된 measurement runner 작업 두 개가 모두
포함되므로 Terraform이 종속 리소스를 계획하기 전에 상태 주소 마이그레이션을 완료할 수 있습니다.

```bash
fdaictl deploy plan \
  --profile .fdai/environments/dev.json \
  --repository <owner>/<repository> \
  --commit-sha <git-sha> \
  --run-id <run-id> \
  --deploy-dev-operations-gateway \
  --output json
```
- `resume-verification`은 Terraform 적용을 다시 실행하지 않습니다. 적용 점유가 없는 단계는
  다시 시작할 수 있고, 증적이 없는 적용 점유는 검증만 재개하며, 실패한 점유는 새 계획과
  승인이 필요합니다. 실패한 사후 조건을 건너뛰거나 변경된 맥락을 승인할 수 없습니다.
- 사람용 출력은 확인을 위해 구독과 테넌트 이름을 표시하지만 식별자는 가립니다. 안정적인
  JSON은 자동화에 필요한 다이제스트와 불투명 참조를 전달합니다.

### Console 전환

Console이 준비되기 전에는 `fdaictl`과 보호된 실행기만 프로비저닝 상태를 표시합니다. 따라서
기반 계층, 데이터베이스, 의미 체계, 모델 단계가 실패해 브라우저 화면을 시작할 수 없는
경우에도 CLI에서 상태를 확인할 수 있습니다.

애플리케이션 단계는 최초 인벤토리 단계보다 먼저 인증된 Console을 시작합니다. Operator
변환 결과와 Console 상태 검사가 통과하면 운영자는 `/provisioning`을 열 수 있습니다.

- 이 페이지는 기존 `provision.*` 스트림과 `/provisioning` 경로를 확장합니다. 별도의 초기
  구성 경로를 만들거나 Terraform 출력을 직접 읽지 않습니다.
- 단방향 가져오기 작업이 비공개 Blob 원장의 정제되고 순서가 보존된 이벤트를 Operator
  변환 결과로 복제합니다. Console과 Operator API에는 Blob 액세스, Terraform 상태, 공급자
  페이로드 또는 배포 비밀을 제공하지 않습니다.
- 이전 단계는 영속 재생으로 표시합니다. 페이지가 열린 후 최초 인벤토리와 최종 시스템
  검증은 실시간으로 이어서 표시할 수 있습니다.
- 실행 진행률, 검사점 진행률, 데이터베이스 준비도, 의미 체계 준비도, 모델 준비도,
  인벤토리 진행률을 각각 구분합니다. 일반 `done` 이벤트, Terraform 완료 또는 예상 리소스
  수만으로 `ready`를 만들 수 없습니다.
- 독립적인 사후 조건 관찰자가 활성 세대와 커버리지 매니페스트를 검증할 때까지 인벤토리
  합계를 예상값으로 표시합니다. 최종 준비 완료 증적이 있어야 100%에 도달합니다.
- 승인 대기와 차단 사유는 읽기 전용입니다. 브라우저 실행 경로를 추가하지 않고 실행 참조와
  정확한 다음 `fdaictl` 작업을 표시합니다.
- 완료 후에도 이 경로에서 정제된 실행 기록을 볼 수 있으며 관련 데이터베이스, 온톨로지,
  모델, 인벤토리, 감사 근거 화면으로 이동할 수 있습니다.

## 목표 상태 프로필

`fdaictl provision init`은 모드 `0700` 디렉터리에 모드 `0600` 프로필을 씁니다. 스키마는 발견된
비밀이 아니라 의도를 기록합니다.

| 필드 그룹 | 필수 의도 |
|-----------|-----------|
| 대상 | 클라우드, 테넌트 참조, 구독 참조, 환경, 애플리케이션 지역, 선택적 모델 지역 |
| 연결 | 기존 Azure 호스트 또는 관리형 VM, 전송 방식, VPN 기대 사항, 비공개 DNS 및 관리 플레인 경로 |
| 도입 | 생성 전용, 명시적 도입 허용 목록, 허용된 Terraform import 주소, 충돌 정책 |
| 서비스 | Core, Operator API, Console, 수집, 격리된 실행기, dev 운영 게이트웨이, 모니터링, 예약 Job 선택 |
| 데이터베이스 | 가용성 및 보존 프로필, 확장 집합, 백업 정책, 이행 제한 시간 |
| 모델 | 워크로드 프로필, 기능 정책, 최소 용량, 목표 용량, 할당량 예비분, 허용 지역 및 SKU |
| 인벤토리 | 구독 또는 관리 그룹 범위, 원본 순서, 리소스 형식 범위, 페이지 및 요청 예산 |
| 안전 | shadow 전용 기본값, 승인 정책과 정족수, 계획 만료, 취소, 비용 상한, 전체 및 무진행 제한 시간 |

프로필에는 암호, 액세스 토큰, 클라이언트 비밀, 웹후크 값, 개인 키, 연결 문자열, Terraform
상태 또는 고객 데이터를 저장하지 않습니다.

이미 배포된 격리된 실행기를 유지하는 계획에서는 `--runtime-image-revision`으로 검증된 런타임
이미지 소스 커밋을 고정합니다. 값은 ACR과 GHCR 모두에 존재하는 소문자 40자 git SHA입니다.
배포 맥락 다이제스트에 봉인되어 plan, apply, status 전반에서 일관된 선택을 공유합니다. 실행기의
ancestor, 이미지, 인증 검사는 그대로 유지됩니다.

## 생성 전 현재 상태 조정

프로비저닝은 빈 구독과 운영자가 일부 구성한 기존 상태를 모두 지원합니다. 점검은 의도한 각
객체를 다음과 같이 분류합니다.

| 분류 | 동작 |
|------|------|
| `managed` | 객체가 예상 Terraform 상태에 있고 소유권 태그와 일치합니다. |
| `adoptable` | 객체가 형식, 범위, 변경 불가능한 설정, 소유권 근거, 명시적 프로필 허용 목록과 정확히 일치합니다. 계획은 정확한 import를 제안합니다. |
| `external_dependency` | FDAI가 객체를 참조하지만 수명 주기를 소유하지 않습니다. |
| `conflict` | 이름 또는 주소가 있지만 충분한 소유권 또는 호환성 근거가 없습니다. 계획을 중지합니다. |
| `missing` | 객체 생성을 제안할 수 있습니다. |

이름 유사성은 도입 근거가 아닙니다. Import는 봉인된 계획에 포함되고 승인이 필요하며,
관련 없는 삭제가 0인 계획으로 사후 확인합니다. 기존 외부 엔드포인트나 빌려 쓰는 모델
계정은 자동으로 재사용하지 않고 충돌 또는 외부 의존성으로 보고합니다.

### 버전이 지정된 프로비저닝 매니페스트

계획은 선택한 프로필, 정확한 원본 리비전, Terraform 계획에서 서명된
`SubscriptionProvisioningManifest` 하나를 컴파일합니다. 이 매니페스트는
[최소 리소스 인벤토리](deploy-and-onboard-ko.md#azure-리소스-인벤토리-최소-세트)의 모든
필수 및 선택된 조건부 Azure 리소스, 공급자 등록, 역할 할당, 외부 선행 조건, 데이터베이스
아티팩트, 의미 아티팩트, 모델 배포, 런타임 서비스, 인벤토리 범위를 열거합니다. 각 항목은
소유자, 목표 상태, Terraform 주소 또는 외부 근거, 사후 조건, 롤백 등급을 선언합니다.

준비 완료에는 모든 매니페스트 항목의 종결 처리 결과가 필요합니다. 선택 사항은 프로필에서
명시적으로 비활성화된 항목이며 묵시적으로 생략한 항목이 아닙니다. 누락된 공급자 등록은 점검
경고가 아니라 계획된 변경과 사후 조건입니다.

## 영속 실행 및 승인 모델

빈 구독 기반 계층에는 명시적인 부트스트랩 경계가 있습니다.

1. CLI는 모드 `0700` 임시 기반 디렉터리와 모드 `0600` 로컬 Terraform 상태 캐시를 만듭니다.
   Azure 실행 호스트가 아직 없으므로 로그인한 운영자가 봉인된 기반 계획을 로컬에서
   실행합니다. 이 단계는 Azure 컨트롤 플레인 작업만 수행하고 비공개 데이터 서비스에 쓰지
   않습니다.
2. 기반 생성에는 운영 및 빈 애플리케이션 리소스 그룹, 상태 계정, 네트워크, 안정적인 배포
   신원, 실행기가 포함됩니다. 모든 생성 리소스는 실행 다이제스트를 전달합니다.
3. 검증된 실행기가 비공개 상태 컨테이너를 만들고 정확한 로컬 Terraform 상태를 원격
   백엔드로 이행한 뒤 변경 0 계획을 증명합니다. 원격
   상태를 정본으로 전환하기 전에 계보, 일련 번호, 주소 집합, 리소스 ID, 관리 개수를
   비교합니다.
4. 로컬 상태는 복구 캐시이며 승인 또는 준비도 권위가 아닙니다. 원격 재구성과 사후 읽기가
   성공할 때까지 유지한 뒤 안전하게 제거합니다. 그 전에 충돌이 발생하면 이름 일치가 아니라
   봉인된 기반 계획과 Azure Activity Log 관측으로 재개합니다.
5. 실행기는 Microsoft Entra 인증으로 해시 체인, 순번, 변경 불가능한 증적을 비공개 Blob에
   씁니다. 항목은 인증된 행위자, 보존 기간, 이전 항목 다이제스트를 포함하며, 구성된 변경
   불가능 보존 또는 서명 앵커로 삭제를 탐지할 수 있습니다.
6. PostgreSQL 준비 후 Operator API와 Console용 읽기 전용 변환 결과를 복제합니다. 비공개
   Blob 원장이 부트스트랩 권위로 유지됩니다.

각 변경 지점은 대상 테넌트와 구독, 원본 커밋, 프로필 다이제스트, Terraform 루트, 백엔드
신원, 계획 다이제스트, 만료, 승인자, 실행기 신원, 예상 사후 조건을 연결합니다. 입력이
바뀌면 해당 지점은 무효가 됩니다. 비공개 Blob이 존재하기 전에는 외부 보호 환경 기록과
봉인된 계획 다이제스트가 승인 권위이며, Azure Activity Log가 변경 행위자를 독립적으로
식별합니다.

새 비공개 구독에는 일반적으로 두 개의 승인 확인 지점이 필요합니다. 각 지점에는 현재 책임자
한 명 이상의 승인이 필요하고 영향이 큰 계획에는 구성된 정족수를 적용합니다.

1. **기반 승인:** 비공개 상태 계정, 운영 네트워크, 배포 신원, 실행기입니다.
2. **애플리케이션 승인:** 검증된 실행기가 새 백엔드에 대해 생성한 정확한 계획입니다.

기존의 정상 기반 계층이 있으면 첫 승인을 생략합니다. `--approve-all` 또는 침묵 기반 승인
모드는 지원하지 않습니다.

## 프로비저닝 단계 계약

각 단계는 의존성 순서로 실행하고 다음 단계 시작 전에 종결 증적을 영속화합니다.

| # | 단계 | 필수 사후 조건 |
|---|------|----------------|
| 0 | 컨텍스트 점검 | 로그인 사용자, 대상 일치, 역할 할당 가능 권한, 공급자 등록 상태, 정책 차단 요인, 할당량, 네트워크 경로, 도구 체인을 변경 없이 보고합니다. |
| 1 | 현재 상태 조정 | 의도한 모든 객체를 분류하고, 충돌을 차단하며, 제안된 import를 명시합니다. |
| 2 | 기반 계획 및 적용 | 리소스 그룹, 비공개 백엔드, 운영 네트워크, 안정적인 배포 신원, 실행 호스트가 존재하고 원격 상태 재구성, 유효 역할, 공급자 등록, 비공개 저장소 접근을 다시 읽어 확인합니다. |
| 3 | 실행 호스트 검증 | 정확한 원본 리비전, 번들 다이제스트, Azure 컨텍스트, 실행기 principal, 도구 버전, DNS, 비공개 엔드포인트 연결이 계획과 일치합니다. |
| 4 | 데이터 기반 계획 및 적용 | 애플리케이션 네트워크, Key Vault, PostgreSQL, Event Hubs, 레지스트리, 신원, 이행 Job이 관련 없는 삭제 없이 수렴합니다. 런타임 소비자는 닫힌 상태입니다. |
| 5 | 데이터베이스 초기 구성 | 레거시 기준선과 모든 서비스 이행이 선언된 head에 도달하고 확장, 역할, 권한, 명령 제한 시간, 롤백 참조를 검증합니다. |
| 6 | 의미 기본값 구체화 | 정확한 온톨로지 릴리스, 규칙, 워크플로, ResourceType, 설정 기본값, shadow 전용 승격 상태를 원본 다이제스트와 함께 쓰거나 변환합니다. |
| 7 | 모델 해석 및 배포 | 지역, 패밀리, 버전, 게시자, SKU, 엔드포인트, 역할, 용량이 승인된 모델 계획과 사후 읽기 결과를 충족합니다. |
| 8 | 런타임 서비스 배포 | 다이제스트로 고정된 리비전은 데이터베이스와 의미 준비도 표시가 있을 때만 시작합니다. 상태 및 보호된 처리 준비도 검사를 통과합니다. |
| 9 | 최초 인벤토리 실행 | 완전한 공급자 세대를 계수, 수집, 검증, 변환, 원자적 승격하고 독립적으로 다시 읽습니다. |
| 10 | 시스템 준비도 검증 | 카나리, 이벤트 흐름, 데이터베이스 읽기, 카탈로그 다이제스트, 모델 점검, 인벤토리 최신성, 감사 종결, Console 읽기 변환 결과를 검증합니다. |

실패하면 의존 단계를 중지합니다. 완료된 재시도 안전 단계는 근거가 만료되거나 입력이
변경되지 않는 한 반복하지 않습니다.

## 데이터베이스 및 의미 초기 구성

데이터베이스 단계는 버전이 지정된 부트스트랩 매니페스트를 사용해 "이행 성공"과 "제품 준비
완료"를 구분합니다.

- **스키마 소유권:** 레거시 Alembic 기준선을 실행한 다음 선언된 의존성 순서로 각 서비스
  소유 브랜치를 실행합니다. 각 head와 도입 증적을 기록합니다.
- **확장과 역할:** 필수 PostgreSQL 확장, 분리된 이행 및 런타임 역할, 최소 권한, 명령 제한
  시간, 런타임 DDL 권한 부재를 검증합니다.
- **온톨로지:** 저장소에서 읽은 정확한 온톨로지 릴리스를 영속화하고 인스턴스 쓰기를
  허용하기 전에 다이제스트를 검증합니다. 이행은 호환성 시드만 제공합니다.
- **규칙과 워크플로:** 코드로 관리하는 카탈로그를 정본으로 유지합니다. 초기 기준선은 정확한
  원본 리비전의 서명된 번들에 포함된 스키마 유효 범용 온톨로지, 규칙, 워크플로,
  ResourceType, 제품 기본값 전체입니다. 부트스트랩 매니페스트는 모든 ID, 버전, 다이제스트,
  의존성, 사후 읽기 검사를 열거합니다. 변경 불가능한 읽기 변환 결과를 구체화하고 복사된
  데이터베이스 행을 두 번째 규칙 원본으로 만들지 않습니다.
- **기본값:** 버전이 지정된 제품 기본값과 배포 소유 범위 연결만 씁니다. 모든 작업은 shadow
  모드로 유지하며 어떤 기본값도 실행 권한을 부여하지 않습니다.
- **사후 읽기:** 이행 principal이 아니라 런타임 신원으로 질의하고 개수, 릴리스
  다이제스트, 스키마 head, 역할 기능을 매니페스트와 비교합니다.

데이터 기반 적용 중에는 런타임 소비자를 닫아 둡니다. 데이터베이스와 의미 준비도 표시가
커밋된 후에만 서비스를 활성화해 새 Container App 리비전이 자체 스키마와 경쟁하지 않도록
합니다.

## 모델 용량 및 검증

"충분한 TPM"은 고정된 큰 숫자가 아니라 측정된 배포 속성입니다. 초기 구성은 비어 있지 않은
핵심 집합 `t1.embedding`, `t1.judge`, `t2.reasoner.primary`와 혼합 모델 모드에서
`t2.reasoner.secondary`를 요구합니다. `hil-only`는 모델 준비도를 충족하지 않습니다. 모델
계획은 기능별로 다음 입력을 사용합니다.

- 최소 사용 가능 TPM 또는 프로비저닝된 처리량 단위
- 목표 최대 요청, 입력 토큰, 출력 토큰, 동시 호출 수
- 목표 사용률 상한, 기본 계획 상한 70%
- 구독 할당량 예비분, 기본 20%
- 정상, 신규 사례, 불일치 시에만 호출과 같은 호출 등급
- 허용된 게시자, 패밀리, 안정 버전, SKU, 지역, 데이터 상주 제약

최소 용량은 버전이 지정된 워크로드 묶음에서 계산하며 근거 없는 운영자 추측값을 받지
않습니다.

`minimum_tpm = ceil(peak_requests_per_minute * max_tokens_per_request / utilization_ceiling)`

값은 공급자 SKU 단위로 올림합니다. 프로필은 검증 시간, 동시성, 요청 속도, 성공 비율,
최대 제한 비율, 최대 p95 지연도 고정합니다.

해석기는 필수 기능 커버리지, 예비분을 제외한 SKU별 가용 할당량, 정책 호환성, 비공개
네트워크 지원, 선언된 지역 선호를 기준으로 지역 순위를 결정론적으로 계산합니다. 승인된
프로필이 허용하면 애플리케이션과 모델 지역을 다르게 선택할 수 있습니다.

필수 기능이 최소 용량에 미달하면 계획을 차단합니다. 최소와 목표 사이의 용량은 성능 저하를
명시적으로 수락해야 합니다. 선택적 기능은 계획에 기능 영향을 표시한 경우에만 사람 승인
전용으로 전환할 수 있습니다. 프로비저닝은 사용 가능하다는 이유만으로 보이는 할당량을 모두
소비하지 않습니다.

적용 후 실행기는 다음을 수행합니다.

1. 계정, 배포, 모델 버전, SKU, 용량, 비공개 접근, 역할 연결을 다시 읽습니다.
2. 런타임 엔드포인트가 새로 관리되는 계정에 속하는지 확인합니다.
3. 모든 필수 기능에 대해 범위가 제한된 키 없는 추론 점검을 수행합니다.
4. 승인된 비용과 토큰 예산 이내에서 고정된 워크로드 묶음을 실행하고 선언된 성공률, 제한,
   처리량, p95 지연 기준을 요구합니다.
5. 프롬프트나 출력을 저장하지 않고 관측된 제한, 지연, 달성 처리량을 기록합니다.

사후 읽기와 점검이 성공해야 모델 준비도를 종결합니다.

## 실행 전체 진행률

계획이 매니페스트를 봉인한 뒤 모든 표면은 정확한
`checkpoints_completed / checkpoints_total`, `stages_completed / stages_total`, 현재 단계와
시도, 건너뛴 선택 단계, 승인 대기, 차단 이유, 마지막 진행 시각, 제한 시간을 표시합니다.
전체 진행률은 봉인된 계획에 기록된 고정 단계 가중치를 사용합니다. 재연결로 후퇴하지 않고
재시도로 전체 수량이 늘어나지 않습니다. 승인 대기는 활동 중인 것처럼 보이지 않고
`waiting`으로 표시합니다. 종결 준비도 증적이 있어야 전체 진행률이 100%가 됩니다.

## 최초 인벤토리 진행률

최초 스캔은 명시적인 온보딩 단계입니다. 다음 예약 cron을 기다리지 않습니다. 진행률은 CLI,
워크플로 요약, Operator API, Console이 공유하는 하나의 영속 스키마를 사용합니다.

| 필드 | 의미 |
|------|------|
| `run_id`, `attempt_id`, `sequence` | 재생 및 재연결 식별자 |
| `stage`, `state`, `reason_code` | 계수, 수집, 단계화, 보강, 검증, 승격, 확인, 완료 또는 실패 |
| `scopes_completed`, `scopes_total` | 정확한 구성 범위 진행률 |
| `provider_types_completed`, `provider_types_total` | 정확한 공급자 형식 샤드 진행률 |
| `resources_observed`, `resources_expected` | 현재 개수와 스캔 전 공급자 개수 스냅샷 |
| `pages_completed`, `pages_expected` | 범위가 제한된 페이지 작업 추정값이며 연속 토큰이 작업을 추가하면 단조롭게 수정됩니다. |
| `links_observed`, `unmapped_objects`, `coverage_gaps` | 완전성 판단에 유용한 맥락 |
| `started_at`, `last_progress_at`, `deadline_at` | 경과 시간과 정체 상태 |
| `fraction`, `fraction_basis` | 단조로운 전체 진행률과 계산에 사용한 카운터 |

수집 중 리소스가 바뀔 수 있으므로 스캔 전 개수는 추정값으로 표시합니다. 최종 경계, 공급자
커버리지 조정, 원자적 그래프 승격, 활성 세대 독립 확인을 모두 마친 후에만 `fraction=1`을
내보냅니다. 개수가 바뀌면 원래 추정값보다 많은 관측 리소스를 표시할 수 있지만 진행률을
100%보다 크게 주장하지 않습니다.

초기 구성은 리소스 형식 필터 없이 정확한 대상 구독 루트를 항상 스캔합니다. 좁은 범위는 이후
운영자 요청 새로 고침에만 사용할 수 있으며 온보딩을 충족하지 않습니다. 리소스 형식 하위 집합
승격은 전역 활성 스냅샷 또는 온톨로지 projection을 변경하기 전에
차단되므로 좁은 범위의 새로 고침이 요청 집합 밖의 신원을 삭제할 수 없습니다.
구체화된 미매핑 형식을 포함한 공급자 원본 객체 커버리지는 완전하고 잘리지 않아야 합니다. 분류된 관계
미비점은 객체 인벤토리를 종결할 수 있지만 관계 커버리지를 제한하고 그래프 의존 자율성을
낮춥니다. 검증된 보강에서 추가된 관계 누락은 같은 승격 메타데이터에 남으며 인계 중 사라질 수
없습니다. 부분 원본 커버리지, 분류되지 않은 누락, 잘못된 검증 메타데이터, 누락된 최종
경계는 준비 완료를 차단합니다.
변환 출처 메타데이터에는 정제된 음이 아닌 커버리지 개수만 포함할 수 있습니다. 잘못된 개수는
준비 완료 근거가 되지 않고 변환 레코드를 차단합니다.

완전한 승격 후 인벤토리 단일 작성기는 검증된 `resource.operational_state` 변경을 Core 소유
PostgreSQL 전이 원장에 추가할 수 있습니다. 이 쓰기는 보존된 `StateFactMetadata`의 권한,
시각, 최신성, 완전성, 충돌, 근거 필드를 사용합니다. 스냅샷 비교는 `initial_state_only` 또는
`snapshot_interval_only`로 기록하며 Genesis 준비 완료를 충족하거나 지속 관측을 주장하지
않습니다. 상태 전이 저장은 토폴로지 이력이 진행되기 전에 완료되어야 하므로 재시도에서 상태
전이가 조용히 유실되지 않습니다.

Inventory Job이 시작되기 전에 Core 서비스 migration head에 정규화된 inventory 관측 원장이
포함되어야 합니다. Job은 온톨로지 변환 결과를 만들기 전에 승격된 전체 snapshot을 이 원장에
이중 기록하고, 그래프 commit이 성공한 후에만 온톨로지 watermark를 전진시킵니다. 원장 지연이나
확인되지 않은 tombstone이 있으면 inventory 원본 완전성은 false로 유지되므로 Genesis 준비
상태가 온톨로지에 반영되지 않은 sparse 이벤트를 숨길 수 없습니다. 이 선행 조건은 후속 수명
인스턴스, correction partition, 보존 또는 archive 작업을 완료하지 않습니다.

Core migration은 이제 정규화 원장 다음에 이러한 수명 주기 레코드를 추가합니다. Inventory
promotion은 관측을 정확한 수명 인스턴스와 논리적인 시간 및 범위 partition에 결속하고, 변환
결과는 replay 근거를 사용해 지연 correction을 종료합니다. 배포에서 제공한 보존 policy는 schema
검증 후에만 안전한 `retain` 기본값을 대체합니다. Archive writer, 검증된 principal 범위 reader,
database purge gate 및 고정 shadow schedule은 전용 Job binding을 준비했으며, 해당 Job과 보호된
증적이 생길 때까지 Genesis는 archive 수명 주기를 incomplete로 보고합니다.
CI는 database integration 검사 전에 service 소유 migration chain 전체를 적용하고 해당 검사가
그 migration 적용 database를 사용하게 하여 Genesis runtime 순서와 일치시킵니다.

각 배치가 영속 진행 신호를 갱신합니다. 무진행 제한 시간을 넘기면 시도를 실패로 처리하고
이전 완전한 그래프를 유지하며 재개 가능한 커서 또는 범위가 제한된 재시작 결정을 남깁니다.
Console은 `관측 / 예상`, 형식 및 범위 개수, 현재 단계, 경과 시간, 마지막 진행 시각을
표시합니다. 안정적인 최근 속도가 있을 때만 예상 완료 시간을 표시합니다.

## 실패, 롤백, 재개

- 기반 계층 실패는 명시적인 부분 기반 증적과 생성된 정리 계획을 남깁니다.
- 애플리케이션 실패는 정확한 Terraform 계획과 상태 잠금 근거를 유지합니다. 재개 전에 대상과
  드리프트를 다시 확인합니다.
- 중복, 모호함, 실패 상태의 Terraform 적용 점유는 자동으로 다시 실행하지 않습니다. 적용하지
  않은 단계는 다시 계획하고, 적용된 단계는 정확한 기존 점유에서 검증만 재개하며, 실패한
  점유는 운영자 검토와 새로 승인된 계획이 필요합니다.
- 이행 실패는 런타임 활성화를 막습니다. 복구는 이행별 롤백 또는 백업/복원 계약을 따르며
  임의로 downgrade하지 않습니다.
- 카탈로그 실패 시 스키마가 최신이어도 의미 준비도를 false로 유지합니다.
- 모델 실패 시 결정론적 계층은 사용할 수 있지만 필수 기능이 없으면 배포 준비 완료로 표시할
  수 없습니다.
- 인벤토리 실패는 마지막 완전한 세대를 유지하고 온보딩 미완료를 보고합니다.
- 정리 실패는 성공 형태의 경고가 아니라 운영자 검토가 필요한 종결 미완료 상태입니다.

## 구현 계획

구현은 다음 의존성 순서 작업 패키지를 따릅니다.

1. **P0 - 계약 고정:** CLI 패키지 골격, 정본 명령 체계, 프로필 및 프로비저닝 매니페스트
   스키마, 실행 및 이벤트 스키마, 단계 상태 머신, 오류 코드, 정제 계약, 의미 기준선
   생성기, 기준 JSON 픽스처를 추가합니다.
2. **P1 - 읽기 전용 계획:** `inspect`, 현재 상태 분류, 공급자 및 할당량 사전 점검, 결정론적
   목표 상태 컴파일, 정제된 사람용 및 JSON 보고서를 구현합니다.
3. **P2 - 기반 조정:** `infra/bootstrap/`을 봉인된 계획, 명시적 도입, 실행기 검증, 영속
   비공개 Blob 이벤트, 상태, 재개 기능으로 감쌉니다.
4. **P3 - 애플리케이션 수렴:** 보호된 플랫폼 워크플로를 하위 단계로 구성하고, 데이터 기반과
   런타임 활성화를 분리하며, 정확한 계획 승인과 증적을 연결합니다.
5. **P4 - 데이터베이스 및 의미 준비도:** 버전이 지정된 부트스트랩 매니페스트, 순서가 있는
   이행 게이트, 제품 기본값 구체화 도구, 온톨로지 및 카탈로그 사후 읽기, 런타임 역할 검사를
   추가합니다.
6. **P5 - 모델 용량:** 기능 정책에 최소, 목표, 사용률, 예비분, 워크로드 입력을 추가하고,
   결정론적 지역 선택, 용량 사후 읽기, 범위가 제한된 키 없는 점검을 구현합니다.
7. **P6 - 인벤토리 진행률:** 계수 계획, 영속 진행 이벤트, 최초 스캔 시작, 활성 세대 검증,
   CLI 표시, Operator 변환 결과, Console 표시를 추가합니다.
8. **P7 - 종단 간 보증:** 빈 구독, 일부 구성, 중단, 할당량 부족, 정책 차단, 제한, 재실행
   시나리오를 검사하고 하나의 통제된 신규 구독 증적을 보존합니다.

P0 이후 P4, P5, P6을 병렬로 진행할 수 있습니다. P7은 이 계약들이 P3 상태 머신을 통해
통합된 후에 시작합니다.

## 설계 비판 및 개정

첫 초안은 단일 승인, 최초 실행기와 전체 리소스 매니페스트 생략, 애플리케이션
데이터베이스를 이용한 진행률 저장, 요청 TPM만으로 충분성 판단, 인벤토리 단일 백분율 표시를
가정했습니다. 이 선택은 신규 비공개 구독에서 실패합니다.

- 아직 존재하지 않는 백엔드에 대해 정확한 애플리케이션 계획을 봉인할 수 없습니다.
- 실행기가 자신을 만들 수 없고 로컬 부트스트랩 상태가 조용히 원격 진실이 될 수 없습니다.
- 열거 가능한 매니페스트 없이는 "모든 리소스"와 "모든 기본값"을 검증할 수 없습니다.
- PostgreSQL이 만들어지기 전 이벤트의 권위를 PostgreSQL에 둘 수 없습니다.
- 요청 용량은 할당량, 여유, 엔드포인트 소유권, 사용 가능한 처리량을 증명하지 않습니다.
- 스캔 중 리소스 개수가 바뀔 수 있으므로 설명 없는 정확한 백분율은 거짓 정밀도입니다.
- 스키마와 카탈로그 준비 전에 런타임 서비스를 적용하면 시작 경쟁 상태가 생깁니다.
- 이름 일치만으로 자동 도입하면 관련 없는 리소스의 소유권을 가져올 수 있습니다.

따라서 개정 설계는 검증된 원격 상태 재구성을 포함하는 범위가 제한된 로컬 기반 실행기, 기반
생성이 필요할 때 두 번의 승인 지점, 버전이 지정된 리소스 및 의미 매니페스트, 정본 명령
소유권, 적용 점유에 안전한 재개, 해시 체인 비공개 Blob 원장, 측정된 용량 게이트, 실행 전체
및 인벤토리 카운터, 전체 구독 객체 커버리지, 지연된 런타임 활성화, 명시적 도입 근거를
사용합니다.

## 신규 구독 승인 기준

- [ ] 신규 구독의 읽기 전용 점검이 정확한 대상, 누락 권한, 공급자 등록, 정책 차단 요인,
  네트워크 경로, 모델 할당량을 변경 없이 보고합니다.
- [ ] 검토된 실행이 노트북 데이터 경로, 장기 클라우드 자격 증명, 공개 데이터 서비스,
  관련 없는 Terraform 삭제 없이 비공개 기반 및 애플리케이션 스택을 프로비저닝합니다.
- [ ] 공급자 등록과 역할 할당을 포함한 모든 필수 및 선택된 매니페스트 항목이 선언된 사후
  조건에 도달하며 선택 항목을 묵시적으로 생략하지 않습니다.
- [ ] 각 단계 후 실행을 중단하고 `resume`을 호출하면 안전하게 계속하거나 안정적인 이유로
  중지하며, 완료된 효과를 중복 실행하지 않습니다.
- [ ] 두 번째 전체 실행은 계획되지 않은 인프라 또는 데이터 변경이 없다고 보고합니다.
- [ ] 모든 데이터베이스 이행 head, 런타임 역할, 필수 확장, 온톨로지 릴리스 다이제스트,
  카탈로그 변환 결과 다이제스트, 제품 기본값, shadow 전용 모드를 독립적으로 다시 읽어
  검증합니다.
- [ ] 비어 있지 않은 필수 모델 기준선이 워크로드에서 계산한 최소 용량을 충족하고 배포
  소유이며, 키 없는 비공개 접근을 사용하고, 정량적 추론 및 부하 기준을 통과하며, 목표
  미달을 보고합니다.
- [ ] 실행 전체 UI가 완료 및 전체 단계와 확인 지점, 현재 시도, 승인 대기, 차단 요인, 마지막
  진행, 제한 시간을 지속적으로 표시합니다.
- [ ] 최초 인벤토리 UI가 완료 및 전체 범위, 공급자 형식, 리소스, 페이지를 지속적으로
  표시하고 활성 세대 검증 후에만 100%에 도달합니다.
- [ ] 인벤토리가 초기 형식 필터 없이 전체 대상 구독을 포함하고, 매핑되지 않은 공급자 신원을
  구체화하며, 관계 제한과 객체 미완성을 구분하고, 구체화, 검토된 사용 불가, 미분류 관계 후보
  수를 기록하며, 주입한 부분 실패에서 이전 완전한 그래프를 유지합니다.
- [ ] 실행을 `ready`로 전환하기 전에 런타임 상태, 카나리, 이벤트 흐름, 감사 종결, Console
  변환 결과를 검증합니다.
- [ ] 로그, 아티팩트, 로컬 원장, 요약, 증적에 비밀, DSN, 토큰, 프롬프트, 공급자 페이로드,
  소스 제어에 적합하지 않은 테넌트별 값을 포함하지 않습니다.
