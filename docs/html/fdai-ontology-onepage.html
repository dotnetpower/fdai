01 / DECLARATIONS

객체와 관계는 먼저 계약으로 정의합니다

객체의 구조를 정의하는 ObjectType과 실제 대상을 나타내는 인스턴스는 다릅니다. Resource는 리소스의 공통 구조를 정의하며, 개별 VM·스토리지·DB는 이 정의를 따르는 객체입니다.

실제 객체 선언: Resource

Resource.yaml 발췌 / 설명·선택 속성·출처 필드 생략
schema_version: "1.0.0"
name: Resource
version: "1.1.0"
key: id
query_terms: [resource, resources, 리소스]
properties:
  id:
    type: string
    required: true
  type:
    type: string
    required: true
  name:
    type: string
    required: false
  location:
    type: string
    required: false

id는 인벤토리 어댑터가 부여한 안정적인 식별자입니다. type은 카탈로그에 정의된 세부 리소스 타입입니다. 이름이나 임베딩 유사도만으로 타입을 확정하지 않습니다.

실제 관계 선언: depends_on

depends_on.yaml 발췌 / 설명·출처 필드 생략
schema_version: "1.0.0"
name: depends_on
version: "1.1.0"
from_type: Resource
to_type: Resource
cardinality: many_to_many
forward_role: depends_on
reverse_role: required_by
semantic_traits: [dependency]
타입 제한
관계 양쪽의 객체는 모두 Resource여야 합니다. 아무 타입의 객체나 연결할 수 있는 관계가 아닙니다.
저장 방향
의존하는 쪽 → 의존 대상. API → DB라면 API가 DB에 의존합니다.
역방향 탐색
DB에 의존하는 대상을 찾을 수 있습니다. 그렇다고 DB가 API에 의존한다는 반대 방향의 사실을 새로 만들지는 않습니다.
관계의 의미
의존관계는 영향이 전파될 수 있는 경로를 나타냅니다. 그 관계만으로 해당 장애의 원인을 입증하지는 못합니다.
객체·관계 정의의 버전도 고정합니다

객체·관계 선언을 카탈로그에서 검증하고, 특정 온톨로지 릴리스에 연결합니다. 저장된 객체·관계의 타입 버전이 해당 릴리스와 일치하지 않으면, 현재 계약에 맞는 사실로 해석하지 않습니다.

02 / INSTANCES & PROVENANCE

관측 정보를 객체로, 검증된 참조를 관계로 바꿉니다

LLM이 연결 관계를 자유롭게 그리는 방식이 아닙니다. 실제 관측 정보와 검토된 매핑을 사용하며, 그래프에 반영하지 못한 정보는 제외 이유를 기록합니다. 여기서 수집 세대는 같은 수집 작업에서 얻은 인벤토리 정보를 구분하는 단위입니다.

  1. 어댑터가 리소스를 관측

    Azure 인벤토리 등 공급자별 응답을 공통 ResourceRecord와 관계 후보로 정규화합니다. Core는 공급자 SDK 응답을 직접 해석하지 않습니다.

  2. 관계 후보를 별도로 검증

    동일한 수집 세대가 완전한지, 그 세대에서 관계 양쪽의 식별자가 모두 관측되었는지 확인합니다. 매핑·타입·방향·중복·충돌을 검사하고, 불완전한 수집 세대의 관계 후보는 검증된 관계로 인정하지 않습니다.

  3. 검증 결과를 읽기 모델에 반영

    투영기는 관측 정보를 읽기 모델로 변환하는 구성요소로, 객체와 등록된 관계를 반영합니다. 관계의 끝점이 누락되었거나 관계 종류를 알 수 없어 제외한 경우에는 그 이유를 기록합니다. 해당 하위 그래프는 쓰기를 담당하는 단일 주체만 갱신합니다.

  4. 시간 정보와 근거를 함께 보존

    현재 그래프와 과거 토폴로지(리소스 간 연결 구조)는 용도를 구분합니다. 유효 시점·이벤트 시점·기록 시점과 함께 수집 세대·최신성·완전성 정보를 보존합니다.

설명용 가상 예시 / 저장 레코드의 전체 스키마는 아님
객체
  object_type: Resource
  id: r-demo-api
  properties.name: demo-api

객체
  object_type: Resource
  id: r-demo-db
  properties.name: demo-db

관계
  from_id: r-demo-api
  link_type: depends_on
  to_id: r-demo-db

함께 확인할 메타데이터
  정확한 릴리스와 수집 세대
  관측 출처와 시간
  관계 검증 상태
  누락·충돌·불완전성

문서에서 추출한 주장과 실제 관측 사실은 구분합니다

문서에서 추출한 "API가 DB를 사용한다"는 주장은 출처가 있는 변경 제안입니다. 현재 연결된 처리 경로는 활성 그래프에 적용하지 않는 검토용 패키지를 만듭니다. 이 경로가 있다는 사실만으로, 승인된 변경안을 활성 그래프에 반영하는 통합 경로까지 완료되었다고 볼 수는 없습니다. 원문·문서 버전·식별자, 출처가 해당 내용을 확정할 권한이 있는지, 다른 정보와 충돌하는지를 검토하더라도, 그 문장만으로 현재 공급자 상태를 관측했다고 간주하지 않습니다.

PostgreSQL 구현은 객체·관계를 ontology_resource와 ontology_link에 저장합니다. 논리적인 그래프 모델과 물리적인 저장 엔진은 분리되어 있습니다.

관계 검증 객체·관계의 읽기 모델 반영 PostgreSQL 저장소 문서에서 추출한 변경 제안

03 / QUESTION → VERIFIED RESOURCE READ

자연어 질문을 타입과 조건이 명시된 조회로 바꿉니다

"의미를 이해하는 것"과 "벡터 유사도가 높은 객체를 찾는 것"은 다릅니다. 리소스 목록·집계·상태를 묻는 질문에 모두 유사도 상위 결과만으로 답하지는 않습니다.

예: "한국중부에 있는 스토리지 리소스를 보여줘."

  1. 인증된 사용자 역할과 조회 목적에 따라 기능 명세 구성

    QueryManifest에는 특정 온톨로지 릴리스의 정의를 기준으로, 해당 사용자가 조회할 수 있는 ObjectType·속성·LinkType·FunctionType을 담습니다. 질문의 문장이 접근 권한을 넓히지는 않습니다.

  2. 질문의 목표와 제약을 구조화

    목표는 목록 조회, 대상은 Resource, 제약은 위치와 리소스 타입입니다. 질문의 표현을 카탈로그에서 검토된 개념·속성·값에 연결합니다. 대상이 모호하면 추가 확인을 거치거나 처리를 보류합니다.

  3. 등록된 조회 기능으로 계획 작성

    객체 선택·필터·관계 탐색과 필요한 함수 호출, 출력 사이의 의존관계를 타입이 명시된 계획으로 표현합니다. 전체 목록을 요구하는 질문과 일부 후보를 찾는 질문은 결과가 충족해야 할 조건이 다릅니다.

  4. 질의 계획을 검증한 뒤 현재 그래프 조회

    검증기는 알 수 없는 선언·숨겨진 속성·미등록 기능·잘못된 인자를 차단합니다. 실행할 때도 릴리스·기능 명세·역할·목적을 확인하고, ObjectSet 조회에 권한 필터와 범위 제한을 적용합니다.

  5. 조회된 사실과 한계를 함께 응답

    식별자·속성·근거를 반환하고, 정보의 최신성·완전성과 조회 결과의 일부 생략 여부를 명시합니다. 그래프의 정보가 불충분하면 허용된 범위 안에서 실시간 조회로 보완하거나 응답을 보류합니다.

04 / SEMANTIC CANDIDATE RETRIEVAL

시멘틱 검색은 어떻게 객체 후보를 찾을까요?

객체를 검색 문서로 표현하고, 후보 순위를 계산한 뒤 현재 그래프에서 다시 확인하는 구조입니다. 검색 점수는 후보 순위를 정하는 데 사용하며, 현재 사실인지는 그래프에서 다시 확인합니다.

현재 표준 런타임에서는 유사도 순위 검색이 비활성화되어 있습니다

build_ontology_index_runtime()은 검색기를 semantic_search_available=False로 구성합니다. 정확한 식별자 조회는 유지하지만, 임의의 자연어 질문에 대한 벡터 순위 검색은 기본 답변 경로에서 활성화되어 있지 않습니다. 타입 기반 후보 선택도 별도로 검증해야 합니다. shadow 비교는 실제 답변에 적용하지 않고 비교하는 경로이며, 이를 연결하더라도 실제 답변의 후보 선택 기능이 활성화되는 것은 아닙니다.

A. 질의를 처리하기 전에 검색 세대를 미리 준비

검색 세대는 함께 검증하고 사용하는 검색 문서와 임베딩·버전 정보를 묶은 단위입니다. 원본 세대는 검색 문서가 참조하는 원본 데이터의 버전을 구분합니다. 인벤토리의 수집 세대와 검색 세대는 역할이 다릅니다.

  1. 검색 문서 구성

    권한 범위 안의 선언과 런타임 객체를 검색용 문서로 만듭니다. 객체 문서에는 id·object_type·properties와 검토된 query_terms가 들어가며, 관련 타입 선언을 참조합니다.

  2. 임베딩과 원본 버전 연결

    검색 세대마다 임베딩 공간·모델 버전·차원, 기능 명세, 사용자 범위, 원본 객체의 해시를 함께 기록합니다. 문서가 변경되면 이전 문서에서 생성한 벡터를 최신 문서의 벡터로 재사용하지 않습니다.

  3. 검증된 스냅샷만 사용하도록 준비

    후보 검색기는 스냅샷·원본 세대·기능 명세가 Heimdall의 독립 검증 결과와 정확히 일치하는지 확인합니다. 질문을 받을 때 전체 말뭉치를 다시 읽거나 즉석에서 새 인덱스를 만들지 않습니다.

B. 활성화된 경로에 따라 후보 검색

정확한 객체 식별자가 주어지면 질의 임베딩을 생성하지 않고 일치하는 문서를 찾습니다. 별도로 허용된 혼합 검색에서는 질의 벡터와 객체 벡터의 코사인 유사도, 키워드 일치, 정확한 식별자 일치에 정책별 가중치를 적용해 점수를 합산합니다. 점수가 같으면 문서 식별자로 정렬해 순서를 일정하게 유지합니다.

rank_documents()의 실제 점수 구조
score =
    exact_weight    * exact
  + lexical_weight  * lexical
  + semantic_weight * semantic

lexical:
  질의 토큰 중 문서와 겹친 토큰의 비율

semantic:
  질의·문서 벡터의 cosine similarity
  → 0..1 범위로 제한

결과:
  최소 점수 통과 → 점수 내림차순
  동점은 문서 식별자로 결정적 정렬
실제 구성 코드 발췌 / 일부 인자 생략
reader = OntologyInstanceCandidateReader(
    snapshots=snapshots,
    vectors=vectors,
    ranking_policy=CatalogRankingPolicy(),
    semantic_search_available=False,
    typed_selection_shadow=(
        typed_selection_shadow is not None
    ),
)

C. 후보를 사실로 사용하기 전에 다시 검증

검색 문서의 내용을 그대로 답변하지 않습니다. 후보의 타입과 식별자로 SecuredObjectSetQueryGateway를 다시 호출해, 현재 권한으로 조회할 수 있는 객체를 읽습니다.

권한
역할·목적·사용자 범위가 동일한지 확인합니다.
존재·내용
객체가 삭제되거나 변경되었는지 확인하며, 오래된 인덱스 내용을 그대로 신뢰하지 않습니다.
원본 세대
현재 원본 세대가 스냅샷·릴리스와 일치하는지 확인합니다.
완전성
재조회한 정보가 불완전하거나 결과 일부가 생략되었다면, 빠짐없이 조회한 후보 결과처럼 반환하지 않습니다.
검색 결과가 0건이라고 리소스가 없는 것은 아닙니다

상위 후보를 찾는 검색만으로는 전체 인벤토리에 해당 리소스가 없다고 단정할 수 없습니다. 후보 함수 query.ontology_instance_candidates는 계약상 최대 20개를 반환하며, 실행 권한은 부여하지 않습니다. "전체가 몇 개인가?"라는 질문에는 전체 범위를 빠짐없이 확인할 수 있는 별도 조회로 답해야 합니다.

현재 비활성화 설정 검색 문서·세대 생성 혼합 순위 계산 식별자·혼합·조건 기반 경로 현재 그래프 재검증

05 / CAUSAL HYPOTHESES & VERIFICATION

인과관계는 검색 결과만으로 판단하지 않고, 가설을 세워 검증합니다

문서 유사도로 관련 사례를 찾을 수는 있지만, 이번 장애의 원인을 입증할 수는 없습니다. 실제 분석에서는 토폴로지·시간·작동 메커니즘·반박 근거와 독립적으로 관측한 결과를 함께 검토합니다.

  1. 장애의 기준 시점과 관련 그래프 고정

    영향받은 리소스·서비스와 관련 관계·변경·관측 정보를 범위가 제한된 하위 그래프로 묶습니다. 현재 상태를 과거 상태로 간주하거나 서로 다른 시점의 관계를 이어 붙이지 않습니다. 과거 토폴로지가 없으면 그 한계를 표시합니다.

  2. 분석 단계별로 원인 후보 구성

    T0는 규칙이 지목한 원인을 사용합니다. T1은 증상에 앞선 변경과 증상 사이의 시간적 연결을 재구성하거나, 현재 상황에도 적용되는 과거 사례를 재사용합니다. T2는 그래도 남은 모호함에 대해 제공된 그래프와 근거를 바탕으로 가설을 제안합니다.

  3. 영향의 방향과 작동 메커니즘 검토

    같은 리소스에서 발생한 변경인지, 검증된 의존 경로를 따라 영향을 줄 수 있는지, 증상이 예상 메커니즘과 일치하는지 확인합니다. T1 체인 분석기는 제공된 의존 그래프가 있으면 무관한 리소스의 연결을 배제합니다. 의존 그래프 없이 계산한 상관관계를 검증된 토폴로지에 근거한 분석으로 해석해서는 안 됩니다.

  4. 지지·반박 근거와 경쟁 가설을 함께 관리

    가설마다 근거 참조와 관측 결과를 남깁니다. 한 가설을 지지하는 관측이 다른 가설을 자동으로 반박하지는 않습니다. 확인되지 않은 경쟁 가설이나 관측 정보가 없는 부분은 미해결로 남깁니다.

  5. 다음 관측을 선택하고 정해진 한도 안에서 조사

    적응형 선택기는 미리 검증된 읽기 전용 관측 후보 중 두 가설을 가장 잘 구별할 수 있는 관측을 고릅니다. 평가 결과가 같으면 비교 가능한 비용과 내용 식별자를 기준으로 선택합니다. 이 선택만으로 질의나 조치가 승인되는 것은 아닙니다.

  6. 독립적으로 관측한 실제 결과로 가설 평가 종료

    예상 효과와 실제 관측 결과를 비교합니다. 정확한 대상·시간·실행 증적·승인·독립 관측 조건이 충족되어야 인과관계를 강하게 확인하고 가설 평가를 종료할 수 있습니다. 실제 런타임은 평가 결과를 "안전하지 않음", "반박됨", "불충분함", "확인됨"으로 구분합니다.

시계열 분석으로 어디까지 판단할 수 있나요?

시간차를 둔 상관관계를 계산하고 반대 방향의 상관관계와 비교합니다. 여러 후보와 시간차를 탐색한 데 따른 영향을 반영해 유의확률을 보정합니다. 선행 시간차가 0이거나 역방향의 상관관계가 더 약하지 않으면 선행성을 인정하지 않습니다.

이 분석기가 직접 부여하는 등급은 association 또는 predictive_precedence입니다. 높은 상관계수만으로 interventional 등급을 부여하지 않습니다.

CausalEvidenceAssessment.confidence의 실제 구조
weakest = min(
    temporal_precedence,
    topological_reachability,
    mechanism_fit,
    intervention_consistency,
)

confidence = (
    weakest * evidence_completeness
    / sqrt(ambiguity)
)

가장 낮게 평가된 요소, 근거의 완전성, 경쟁 후보 수를 반영하는 점수입니다. 통계적으로 보정된 "원인일 확률"을 뜻하지는 않으며, 모든 RCA 모듈이 같은 점수를 사용하는 것도 아닙니다.

가설 평가를 "확인됨"으로 종료하기 위한 조건

텔레메트리의 완전성, 정해진 관측 구간 준수, 관측자의 독립성, 예상한 효과 방향과의 일치, 개입 승인 여부를 확인합니다. 실행 증적의 검증 여부와 정확한 원인·효과 대상의 일치 여부를 확인하고, 금지된 효과가 발생하지 않았는지도 확인합니다. 성공 응답 한 건이나 "롤백했더니 좋아 보인다"는 설명으로 이 조건들을 대체할 수는 없습니다.

연관

association

함께 나타난 현상을 기록합니다. 원인의 방향이나 개입 효과는 입증하지 못한 상태입니다.

예측적 선행

predictive_precedence

시간차·방향성·통계 조건을 충족한 상태입니다. 실험으로 인과관계를 확인했다는 뜻은 아닙니다.

준실험

quasi_experimental

비교·대조 등 준실험에서 얻은 근거를 나타내는 등급입니다. 시계열 상관관계만으로 부여하지 않습니다.

개입 근거

interventional

검증된 개입과 독립적인 효과 관측이 필요합니다. 이 등급만으로 실행 권한이 부여되지는 않습니다.

장애 하위 그래프 T1 원인 체인 시계열·역방향·다중 검정 가설·점수·등급 독립 관측에 따른 가설 평가 종료 적응형 관측·인과 계약

06 / END-TO-END WALKTHROUGH

질문 하나를 끝까지 따라가 봅니다

아래는 설계와 모듈별 역할을 설명하기 위해 구성한 가상 시나리오입니다. 실제 FDAI 실행 로그나 고객 장애 사례, 실환경 테스트 결과가 아닙니다.

"demo-api 오류가 늘었는데, 최근 배포 때문인지 DB 문제인지 지난 30분을 조사해 줘."

1. 대상 확정

현재 권한 범위에서 demo-api의 정확한 Resource.id를 찾습니다. 이름이 같은 리소스가 있으면 범위를 좁힙니다. 이름이 비슷한 상위 후보를 그대로 실행 대상으로 삼지 않습니다.

2. 시간·관계 고정

질문의 시간 구간과 기준 시점을 정하고, 그 시점의 API → DB 의존관계를 확인합니다. 과거 관계를 복원할 근거가 없으면 현재 관계로 과거 관계를 입증하지 않습니다.

3. 근거 수집

관련 변경·배포와 API·DB의 관측 정보를 조회합니다. 과거 RCA는 참고할 사례일 뿐이며, 이번 대상·실패 메커니즘·토폴로지에도 적용되는지 다시 확인합니다.

4. 경쟁 가설 비교

H1: API 배포로 인한 회귀. H2: DB 지연. H3: 공통 의존성 문제. 각 가설을 지지하거나 반박하는 근거와 아직 확인하지 못한 사항을 구분해 기록합니다.

5. 가설을 구별하는 데 필요한 다음 관측

가설을 구별할 수 있는 읽기 전용 관측 후보를 평가합니다. 예를 들어 요청 구간과 DB 지연의 시간적 관계를 확인합니다. 실제 질의에는 등록된 기능을 사용해야 하며, 별도 검증도 통과해야 합니다.

6. 근거 수준에 맞는 답변

"DB 지연이 먼저 발생했지만, 배포가 원인인지에 대해서는 추가 확인이 필요합니다"처럼 지지 근거와 미해결 항목을 함께 설명합니다. 승인된 개입과 그 결과를 독립적으로 관측한 근거를 확보하기 전에는 원인을 확정하지 않습니다. 원인 확인과 조치 승인은 별개이며, 조치는 필요한 승인과 안전 조건을 충족한 뒤에만 실행합니다.

이 예시에서 그래프가 하는 일

정확한 대상과 영향 경로를 연결하고, 어느 시점의 어떤 근거로 답했는지 재현할 수 있게 합니다. 원인처럼 들리는 설명을 사실로 인정하는 역할은 하지 않습니다.

07 / IMPLEMENTATION & VALIDATION BOUNDARIES

확인한 구현과 추가 검증이 필요한 범위를 구분합니다

코드가 구현되어 있는지, 표준 구성에서 기능이 활성화되어 있는지, 특정 배포 환경에서 동작이 검증되었는지는 각각 구분해서 확인해야 합니다.

코드·설계에서 확인한 기반

  • 버전으로 관리하는 객체·관계 선언과 PostgreSQL 객체·관계 저장소
  • 실제 인벤토리를 읽기 모델의 객체로 변환하고, 관측 정보를 바탕으로 관계를 검증하는 기능
  • 사용자 역할·목적별 기능 명세, 타입이 명시된 계획, 검증된 그래프 조회
  • 객체 검색 문서와 벡터 세대 구성, 혼합 순위 계산, 현재 그래프 재검증 구현
  • 원인 가설·시간적 연결·반박 근거를 관리하고, 독립적으로 관측한 결과로 가설 평가를 종료하는 인과 모델

이 페이지가 주장하지 않는 것

  • 승인된 문서 제안이 활성 그래프에 자동으로 반영된다는 주장
  • 표준 답변 경로에서 리소스의 벡터 유사도 검색이 활성화되어 있다는 주장
