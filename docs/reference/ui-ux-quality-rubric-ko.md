# UI/UX 품질 평가 루브릭

이 루브릭은 FDAI Console과 정적 시안을 일관된 기준으로 검토하기 위한 도구입니다. 관찰 가능한
평가 지표 50개, 공통 점수 기준, 근거 요건을 정의해 시각적 완성도가 조작, 접근성, 정보 품질의
결함을 가리지 않도록 합니다.

> 점수는 명시한 검토 범위에 대한 결과이며 제품 전체의 평가가 아닙니다. 100점이라도 WCAG 인증,
> 사용자 만족도 증명, 게시, 배포, 실행 권한을 뜻하지 않습니다.
> 헌법, 제품 계약, 공통 디자인 토큰이 계속 우선합니다.

## 평가 범위

10개 영역마다 지표가 5개씩 있습니다. 지표의 가중치는 동일하며, 중요한 조건은 가산점이 아니라
필수 통과 기준으로 관리합니다. 버전 `1.0.0`은 초기 검토 기준이며 과학적으로 보정된 사용성
측정 도구는 아닙니다.

| 영역 | ID | 평가 초점 |
|------|----|-----------|
| 목적과 정보 구조 | UX-01 to UX-05 | 사용자가 이해하고 수행해야 할 일 |
| 배치와 시각적 위계 | UX-06 to UX-10 | 정보 묶음, 밀도, 첫 화면의 우선순위 |
| 타이포그래피와 언어 | UX-11 to UX-15 | 읽기 쉽고 일관된 문구와 값 |
| 색상과 절제된 표현 | UX-16 to UX-20 | 대비, 의미, 차분한 화면 |
| 컴포넌트 일관성 | UX-21 to UX-25 | 재사용 가능한 조작 요소, 목록, 겹침 화면 |
| 조작과 복구 | UX-26 to UX-30 | 실제로 작동하는 흐름, 피드백, 안전한 조치 |
| 데이터와 시각화 | UX-31 to UX-35 | 정확한 해석과 근거 |
| 접근 가능한 조작 | UX-36 to UX-40 | 키보드, 의미 구조, 대체 정보, 조작 영역 |
| 반응형과 적응형 동작 | UX-41 to UX-45 | 재배치, 확대, 극단적인 내용, 사용자 환경 |
| 검증과 전달 절차 | UX-46 to UX-50 | 상태별 검증, 성능, 구현 일치, 회귀 방지 |

## 수정 전에 범위 선택

1. 정확한 경로나 컴포넌트, 시안 또는 실제 구현 환경, 사용자 작업, 데이터 모드, 지원 언어,
   브라우저, 화면 크기, 탐색 패널 상태, 필요한 상호작용 상태를 기록합니다.
2. 공통 지표 12개부터 시작합니다. `UX-01`, `UX-02`, `UX-06`, `UX-08`, `UX-11`, `UX-16`,
   `UX-26`, `UX-36`, `UX-37`, `UX-41`, `UX-46`, `UX-50`입니다. 관련된 필수 통과 지표와
   변경 영향을 받는 지표를 모두 추가합니다. 새 경로나 전체 재설계는 보통 50개를 모두 선택합니다.
3. 선택하지 않은 ID와 이번 작업 범위에서 제외한 이유를 기록합니다. 공통 토큰이나 화면 틀을
   바꾸면 영향받는 대표 화면까지 범위를 넓히되, 자동으로 제품 전체를 검증하지는 않습니다.
4. 선택한 지표의 기능이 범위 안에 실제로 없을 때만 `N/A`를 사용합니다. 입력이 없는 화면의
   양식 검증이 예입니다. 채점 전에 이유를 기록합니다.
5. 기능이 있지만 검증하지 않았다면 `N/A`가 아니라 `U`입니다. 인프라, 인증, 필요한 사람의
   확인이 없으면 근거가 부족한 상태입니다. 실패한 뒤 평가 범위를 줄이지 않습니다.

대시보드는 첫 화면에 담을 정보와 기준 데스크톱 크기, 탐색 패널 상태를 먼저 정합니다. 모든 상세
페이지, 모바일 화면, 글자를 확대한 화면에 스크롤 금지를 적용하지 않습니다. 가독성과 부가 정보에
접근할 수 있는 경로를 유지합니다.

## 채점과 판정

### 점수 기준

| 점수 | 의미 |
|------|------|
| 0 | 필요한 기능이 없거나, 작동하지 않거나, 오해를 유발하거나, 접근할 수 없음 |
| 1 | 중대한 결함이 명시한 작업을 방해함 |
| 2 | 사용할 수 있지만 의미 있는 불일치나 불편이 남아 있음 |
| 3 | 기본 완성도는 확보했으며 작고 구체적인 개선점이 남아 있음 |
| 4 | 명시한 범위 전체에서 기준을 충족하고 근거가 있으며 알려진 결함이 없음 |
| U | 적용 대상이지만 채점에 필요한 근거가 없음 |
| N/A | 선택한 지표이지만 실제로 적용되지 않으며 이유를 기록함 |

점수는 정수입니다. 스크린샷만으로 요청 성공, 키보드 동작, 스크린리더 출력을 증명할 수는 없습니다.
자동 검사에서 발견된 문제가 없다고 시각적 평가와 상호작용 지표까지 채점하지 않습니다.
3점에는 남은 개선점을, 4점에는 "좋아 보임"이 아니라 실제 근거를 기록합니다.

선택한 지표에서 `N/A`를 뺀 개수를 `A`, 0~4점으로 채점한 개수를 `E`라고 합니다.

```text
coverage_percent = 100 * E / A
score = 100 * sum(ratings) / (4 * A), only when A > 0 and E == A
```

`A == 0`이면 통과 점수가 아니라 `not-applicable`로 기록합니다. `E < A`이면 검증 비율과 부족한
근거만 보고하고 최종 점수는 비워 둡니다. 선택하지 않은 항목은 두 계산의 분모에 들어가지 않습니다.
영역별 적용 항목 수와 평균도 함께 보고하며, 범위가 다른 총점을 같은 작업의 평가처럼 비교하지 않습니다.

### 필수 통과 기준과 수락 조건

아래 표의 `G`는 필수 통과 지표입니다. 적용되는 모든 `G` 지표가 4점이어야 합니다. 그 밖의 적용
지표도 각각 3점 이상이어야 하며, 검증 비율 100%와 반올림 전 총점 90점 이상을 충족해야 해당
범위의 검토를 통과할 수 있습니다.

| 모든 필수 기준과 항목별 하한을 충족한 뒤의 총점 | 해석 |
|-----------------------------------------------|------|
| 95~100점 | 평가 범위 안에서 높은 완성도 확보 |
| 90점 이상 95점 미만 | 작은 개선점을 명시한 상태로 검토 준비 완료 |
| 90점 미만 | 해당 작업을 완료로 보기 전에 개선 필요 |

적용 대상이 있는 검토의 결과는 `passed`, `failed`, `needs-human`, `needs-infrastructure`로 기록합니다.
총점이 높아도 확인된 필수 기준 실패는 실패입니다. 필요한 근거가 없으면 `passed`로 기록할 수
없습니다. 모든 차단 사유를 적고, 다음 단계를 막고 있는 사유에 맞는 결과를 선택합니다.
이는 로컬 UI 검토 결과이지 배포 허가가 아닙니다.

**계산 예시이며 현재 대시보드를 평가한 결과는 아닙니다.**

- 적용 지표 40개에서 148점을 얻으면 92.5점입니다. 필수 지표 하나가 3점이면 여전히 통과할 수 없습니다.
- 적용 지표 40개 중 38개만 채점했다면 검증 비율이 95%인 것이며, 최종 품질 점수는 없습니다.
- 50개가 모두 4점이면 기록된 경로, 상태, 근거 범위에서만 100점입니다.

## 평가 지표 50개

근거 코드: `M` = DOM, 위치와 크기, 시간, 계산된 스타일 측정, `V` = 판단 이유를 기록한 시각적 비교,
`I` = 실제 키보드, 포인터, 사용자 작업 수행, `T` = 집중 테스트 또는 계약 확인,
`H` = 필요한 경우 사람이 수행한 사용성 또는 보조 기술 확인입니다.
실제로 사용한 방법을 기록합니다. 아래에 방법이 적혀 있다고 해당 검증을 수행한 것은 아닙니다.

## UI 작업에 적용하는 절차

1. **수정 전:** 범위와 지표를 선택하고 적용 여부를 기록합니다. 기준 화면을 남기고, 다음 변경으로
   확인할 가장 중요한 결함을 명시합니다.
2. **구현 중:** 반응형 조정 전에 데스크톱 구조와 동작을 완성합니다. 기본 상태뿐 아니라 변경한
   펼침, 겹침 화면, 오류, 권한 상태도 평가합니다.
3. **완료 전:** 필요한 최소 검사를 실행하고 실제 화면을 본 다음 선택한 지표를 채점합니다.
   필수 기준, 3점 미만 항목, 남은 사용자 불편의 중요도 순서로 수정합니다.
4. **결과 보고:** 범위, 검증 비율, 점수 또는 미채점 사유, 필수 기준, 남은 개선점, 근거를 적습니다.
   시안 구현, 실제 환경 검증, 게시 완료를 구분합니다.

50개 지표를 새로운 테스트 명령 50개로 취급하지 않습니다. 기존 계약 테스트, 브라우저 측정,
잘 선택한 시나리오 하나가 여러 지표의 근거가 될 수 있습니다. 반대로 스크린샷 하나가 모든
시각적 평가나 숨은 상태까지 자동으로 증명하지는 않습니다.

채점이 실제 Azure나 모델 호출, 자격 증명 내보내기, 더 넓은 검증 범위를 허가하지는 않습니다.
기존 로컬 근거를 먼저 사용하며, 인증을 약화하거나 실패한 검사를 숨기는 대신 차단 사유를
보고합니다.

### 평가 기록 양식

상세 기록은 비공개 세션 자료나 기존의 Git 추적 제외 시각 검토 폴더에 보관합니다.
소스 저장소에는 민감한 정보를 제거한 요약만 넣습니다.

```yaml
rubric_version: "1.0.0"
surface: "<exact route or component>"
venue: "static-mock"
task: "<observable user goal>"
source_inputs: "<revision or task-owned diff and relevant configuration>"
conditions: "<browser, viewport, navigation state, language, theme, data mode>"
states: ["default", "expanded"]
selected_ids: ["UX-03", "UX-46"]
selection_note: "Illustrative excerpt; a real review includes the core set and relevant gates."
not_selected: "<IDs and scope reasons>"
na: []
ratings:
  - id: "UX-03"
    state: "U"
    score: null
    evidence: []
    finding: "Expanded state has not been inspected."
    next_step: "<check, owner, and expected result>"
summary:
  applicable: null
  evaluated: null
  coverage_percent: null
  score: null
  gates: "not-yet-verified"
  disposition: "needs-human"
  limitations: []
```

채점한 항목에는 0~4의 정수와 실제 근거를 기록합니다. `U`이면 점수를 비워 두고 부족한 검증을
명시합니다. `N/A`에는 이유가 필요합니다. 실제 기록에서는 선택한 모든 ID의 처리 결과를 설명해야
합니다. 이 양식은 의도적으로 미완성 상태이며 완료된 평가가 아닙니다.

## 점수를 유리하게 바꾸지 않고 기준 보정

서로 다른 UI 작업 세 개에서 검토자별 점수를 비교합니다. 같은 스크린샷과 조작을 기준으로
2점 이상 차이 나는 항목을 논의하고, 단순 평균으로 차이를 없애지 않습니다.
판단 비중이 큰 항목은 비교 대상과 구체적인 채점 이유를 기록합니다.

ID는 유지합니다. 지표의 의미, 필수 기준, 점수 척도, 통과선을 바꾸면 버전도 변경합니다.
점수를 높이려고 가중치나 제외 항목을 조용히 바꾸지 않습니다. 범위가 달라지면 이전 결과를 남기고
수정된 기록을 시작합니다. 수치상 하한을 통과했더라도 검토자는 개선을 요청할 수 있습니다.
