01

신호가 흩어져 있습니다

리소스 상태, 변경 기록, 비용과 운영 목표를 여러 도구에서 따로 확인해야 합니다.

03

사람만 늘려 대응하기 어렵습니다

운영 규모와 속도가 커질수록 수동 분석과 인력 추가만으로 대응을 지속하기 어렵습니다.

FDAI는 신호, 운영 기준, 담당 체계와 실행 결과를 하나의 제어 루프로 연결합니다.

Decision Tiers

가장 단순하고 검증된 판단 방법부터 사용합니다

T0
규칙과 정책반복 가능한 운영 조건을 동일하게 판단합니다.
목표 70-80%
T1
검증된 사례 재사용비슷한 과거 상황과 효과가 확인된 대응을 찾습니다.
목표 15-20%
T2
근거 기반 추론새로운 상황에서 여러 근거와 검증 결과를 종합합니다.
목표 5-10%
결정론 우선

규칙으로 해결할 수 있는 업무를 매번 새롭게 해석하지 않습니다.

새로운 판단은 검증을 거쳐 재사용 가능한 운영 지식으로 발전합니다.

표시된 비율은 측정된 성과가 아니라 검증할 목표 범위입니다.

FDAI

Authority Classes

작업의 성격에 따라 책임 수준을 구분합니다

A0관찰과 설명현재 상태를 조회하고 설명하거나 결과를 시뮬레이션합니다.
A1범위가 명확한 일상 작업되돌릴 수 있고 하나의 리소스에 한정된 작업입니다.
A2검증된 운영 절차측정과 사전 합의를 거쳐 적용 범위가 정해진 워크플로입니다.
A3-H사람과 함께 결정중요한 작업은 실행할 때마다 독립적인 승인을 받습니다.
A3-E사전에 합의한 긴급 대응정해진 시간과 범위 안에서 사용하는 비상 대응 목표입니다.
A4운영 범위 밖의 작업정책이나 책임 범위에 포함되지 않아 적용하지 않습니다.

A3-E는 목표 설계이며 현재 실행 가능한 운영 경로는 계획 단계입니다.

Agent Collaboration

에이전트는 정해진 이벤트를 통해 협업합니다

직접 제어하지 않습니다에이전트는 서로 직접 호출하지 않고 형식이 정해진 이벤트를 발행하고 구독합니다.
결과마다 작성 책임자가 있습니다판단, 승인, 실행과 감사 기록은 각각 정해진 에이전트만 작성합니다.
역할을 분리합니다판단한 에이전트가 실행하지 않고, 승인한 사람도 실행 ID를 사용하지 않습니다.

Typed Event Flow

관찰>판단>승인>실행>감사

정보는 필요한 여러 역할에 전달될 수 있지만, 권위 있는 결과를 작성하는 주체는 하나입니다.

Execution Assurance

모든 자동 작업은 실행 전 확인과
실행 후 검증을 함께 갖습니다

01중지 조건어떤 상황에서 작업을 멈출지 정의합니다.
02복구 방법이전 상태로 돌아갈 방법을 준비합니다.
03영향 범위작업이 영향을 줄 수 있는 범위를 계산합니다.
04사전 확인What-if 또는 시뮬레이션 결과를 확인합니다.
05대상 잠금같은 대상의 작업 순서를 일관되게 유지합니다.
06중복 방지재시도해도 같은 변경이 두 번 적용되지 않습니다.
07감사 이력실행 전 의도와 실행 후 결과를 연결해 기록합니다.
API 응답만으로 성공을 판단하지 않습니다. 별도의 관찰을 통해 기대한 효과를 확인합니다.

Ownership Handover

업무가 에이전트로 이동해도
사람의 책임은 이어집니다

수행자에서 책임 담당자로

기존 담당자는 반복 작업을 직접 수행하는 대신 운영 기준을 관리하고, 중요한 판단을 검토하며, 필요한 경우 에스컬레이션을 받습니다.

담당 체계는 누가 책임지고 연락받는지를 정합니다. 실행 권한은 별도의 역할과 정책에서 결정합니다.

주 담당자가장 먼저 판단 요청을 받습니다.
>
백업 담당자주 담당자를 대신할 수 있습니다.
>
에스컬레이션업무 영역의 추가 판단을 담당합니다.
모든 에이전트에는 책임 담당자 또는 명시적으로 합의된 자율 운영 범위가 필요합니다. FDAI 자체에도 유지관리자를 지정합니다.
